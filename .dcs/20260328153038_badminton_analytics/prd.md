## 1. エグゼクティブサマリー

### 概要

badkichi は、バドミントンの試合動画（YouTube またはローカルファイル）を再生しながら、ラリー中のショットタイミングとポイント結果を手動入力し、バドミントンのダブルスルールに基づくルールエンジンによって戦術分析を自動算出するWebアプリケーションである。

### 背景と目的

バドミントンのダブルスでは「得点者が次のサーブ権を持つ」というルールがあり、サーバー/レシーバーの立ち位置も得点の偶奇で決定される。この規則性を活用すれば、最小限の手動入力（ポイント結果のみ）から各ラリーのサーバー・レシーバーを自動特定でき、「誰がサーバーの時に得点率が高いか」といった戦術的に有用な統計を算出できる。

現状、アマチュアのバドミントンプレーヤーにはこのような分析ツールが存在せず、試合の振り返りは主観的な記憶に頼っている。badkichi によりデータに基づくペアの組み合わせ最適化や戦術改善を可能にする。

### MVPのターゲットユーザー

- **Group（グループ）単位での利用**（人数制限なし）
- 1ユーザーは複数のグループに所属可能
- グループ内ではデータを共有（誰が入力しても全員から見える）
- MVPでは対戦相手の情報は管理しない（自グループの分析に集中）
- 注: 「Group」は組織としての所属単位（例: ○○バドミントンクラブ）。試合内の対戦サイド「チームA / チームB」とは別概念。

### マルチテナント設計

- **共有DB + Row Level Security (RLS) パターン**
- 全データに `group_id` を持たせ、PostgreSQL の RLS で「自分が所属するグループのデータのみ」アクセス可能とする
- 複雑なロール管理は MVP では行わない（グループメンバーは全員フラットに read/write 可能）

### 期待される成果

- 個人またはペアが試合動画を見返しながら、最小限の操作でラリーデータを蓄積できる
- サービス/レシーブ時の得点率を選手別に可視化し、ペア編成や戦術の改善に活用できる
- 蓄積されたデータ（動画+タイミング情報）を将来のAI自動検出の教師データとして活用できる

## 3. 機能要件

### 3.1 MVP 範囲

#### F-01: 試合・選手管理

**概要**: ダブルスの試合を作成し、選手情報と初期設定を管理する。

**詳細**:
- 選手の登録（名前、利き手）
- ダブルスの試合を作成（チームA: 2名、チームB: 2名の計4人を選択）
- MVPでは対戦相手の詳細情報は管理しない（名前のみ）
- 最初の立ち位置（左右）を各選手に設定
- 動画ソースの登録（YouTube URL またはローカルファイル）
- 各セットの目標ポイントを設定可能（デフォルト: 1,2ゲーム目=21点、3ゲーム目=15点）

**受け入れ基準**:
- [ ] 選手を名前・利き手で登録・一覧表示できる
- [ ] 4人の選手を選択してダブルスの試合を作成できる
- [ ] 各選手の初期立ち位置（左右）を設定できる
- [ ] YouTube URL またはローカルファイルパスを試合に紐付けて登録できる
- [ ] セットごとの目標ポイントを変更できる

#### F-02: 動画再生 + データ入力

**概要**: 動画を再生しながら、ショットタイミングとポイント結果を記録するメイン画面。

**詳細**:
- YouTube IFrame API によるYouTube動画の再生
- HTML5 Video API によるローカル動画の再生
- 再生コントロール: 一時停止、シーク、速度変更
- 「打った」ボタンでショットタイミングを記録（動画内の現在時間を自動取得）
- ラリー終了時に「チームAの得点」「チームBの得点」ボタンでポイント結果を記録
- 「レット」ボタンでラリーやり直しを記録（得点に影響しない）
- 得点者不明時のスキップ機能（後から確定可能）
- スコアの手動修正機能（動画視聴中にリアルタイムで修正。全試合終了後の一括修正ではない）
- ダブルスの左右入れ替わりの記録機能（実際のポジションを追跡し、「変わった」ことを記録する。遡及的な修正ではなく、間違った状態を正として進め、戻った時点で「戻った」を入力する）
- 現在のスコア、サーバー/レシーバー情報をリアルタイム表示

**受け入れ基準**:
- [ ] YouTube動画URLを入力して動画を再生できる
- [ ] ローカル動画ファイルを選択して再生できる
- [ ] 動画の一時停止・再開・シーク・速度変更ができる
- [ ] 「打った」ボタンで現在の動画時間がショットとして記録される
- [ ] ラリー終了時にどちらのチームが得点したかを記録できる
- [ ] 「レット」ボタンでラリーをやり直しとして記録できる
- [ ] 得点者を一旦スキップし、後から確定できる
- [ ] スコアを手動で修正できる
- [ ] 左右の立ち位置が変わったことを記録できる（間違った状態を現状として受け入れ、戻った時点で「戻った」を入力する方式）
- [ ] 動画再生中のデータ入力にラグがない（UXを損なわない）

#### F-03: ルールエンジン（バドミントンダブルスルール）

**概要**: バドミントンのダブルスルールに基づき、最小限の入力から各ラリーのサーバー/レシーバーを自動推論する。

**詳細**:
- 得点者が次のサーブ権を持つ
- サーバーの立ち位置はチームの得点で決定（偶数=右コート、奇数=左コート）
- 最初の立ち位置 + 得点経過から、各ラリーのサーバー・レシーバーを自動特定
- **インクリメンタル計算**: ラリー入力のたびに次のサーバー/レシーバーを即座に算出する（バッチ再計算ではない）
- スコア修正時は、修正箇所以降のラリーのサーバー/レシーバーを再計算
- レットはラリー番号を振るがスコアに影響しない
- **左右入れ替わり対応**: PositionOverride が入力された場合、実際の立ち位置（ルール上の位置ではなく）を現状として採用し、以降のサーバー/レシーバー推論に反映する

**受け入れ基準**:
- [ ] 初期立ち位置と得点経過から、各ラリーのサーバーが正しく特定される
- [ ] 得点者のチームの得点が偶数の場合、サーバーは右コート側に配置される
- [ ] 得点者のチームの得点が奇数の場合、サーバーは左コート側に配置される
- [ ] ラリー入力のたびに、次のサーバー/レシーバーが100ms以内に表示される
- [ ] スコアを手動修正した場合、以降のラリーのサーバー/レシーバーが再計算される
- [ ] レットを追加/削除した場合、以降のラリーのサーバー/レシーバーが再計算される
- [ ] レットのラリーはスコアに影響しない
- [ ] 左右入れ替わりが記録された場合、実際のポジションに基づいて推論が継続される

#### F-04: 統計ダッシュボード

**概要**: 蓄積されたラリーデータから戦術分析を算出・可視化する。

**詳細**:
- **最重要**: サービス時 vs レシーブ時の得点率（選手別）
- **次に重要**: ラリー本数（ショット数）と得点率の関係
- ラリー一覧表示（ラリー番号、サーバー、レシーバー、スコア、ショット数、結果）
- ラリー一覧からワンクリックで該当ラリーの動画再生位置にジャンプ

**受け入れ基準**:
- [ ] 選手別のサービス時/レシーブ時得点率がチャートで表示される
- [ ] ラリーのショット数と得点率の関係がチャートで表示される
- [ ] ラリー一覧がテーブルで表示される
- [ ] ラリー一覧の項目をクリックすると、動画が該当位置にジャンプして再生される

### 3.3 AI 自動化ロードマップ

AI による自動化は以下の優先順位で段階的に導入する。MVP で蓄積されたデータを教師データとして活用する。

| 優先度 | 検出内容 | 技術的実現可能性 | 備考 |
|--------|---------|-----------------|------|
| 1 | サーブ位置の検出（誰が・左右どちらから） | 高 | これだけで得点者・スコアが逆算可能 |
| 2 | ラリー終了の検出（シャトルの動き停止） | 中〜高 | シャトル追跡ベース |
| 3 | 打ったタイミングの検出 | 中〜高 | MVPデータを教師データとして学習。GRU + TrackNetV2（既存OSS参考） |
| 4 | どちらのチームが打ったかの自動判定 | 中 | GRU + シャトル追跡（既存OSSを活用） |
| 5 | ダブルスの2人のうち誰が打ったかの判定 | 中 | ポーズ推定 + シャトル追跡の組み合わせ |
| 6 | ショット種別の自動分類 | 低〜中 | 教師データ不足。外部データセット活用が必要 |
| 7 | AI による左右間違い自動検出 | 中 | ルール推論 vs 実際の位置の不一致を検出 |
| 8 | レットの自動推定 | 中 | 同じ人が同じ位置から連続サーブ |

**AI学習基盤**:
- MVPで蓄積されるショットタイミング+動画の紐付けデータが教師データとなる
- AI学習フェーズでサーバー側動画保管を導入（YouTube URLだけでなく、動画ファイル自体をクラウドに保存）
- 入力データと動画の紐付けを保持することで、AI学習パイプラインへの入力とする

**ラリー終了パターン**（AI検出時の考慮事項）:
- シャトルが地面に触れる（IN/OUTの判定は動画からは困難）
- ネットにかかる（最後に打った側の失点）
- 人に当たる（検出困難）

### 5.2 データモデル

```
Group（グループ・組織）
+-- id: UUID
+-- name: string
+-- created_at: timestamp
注: 組織としての所属単位（例: ○○バドミントンクラブ）。試合内の「チームA/B」とは別概念。

GroupMember（グループ所属ユーザー）
+-- id: UUID
+-- group_id: FK -> Group
+-- user_id: FK -> auth.users（Supabase Auth）
+-- joined_at: timestamp
注: 1ユーザーは複数グループに所属可能。MVPではロール管理なし。

Player（選手）
+-- id: UUID
+-- group_id: FK -> Group
+-- name: string
+-- handedness: 'right' | 'left' | 'unknown'（利き手）
+-- created_at: timestamp
+-- (将来: 性別、年齢、歴、レベル等の属性)

Match（試合）
+-- id: UUID
+-- group_id: FK -> Group
+-- team_a_player1_id: FK -> Player
+-- team_a_player2_id: FK -> Player
+-- team_b_player1_id: FK -> Player
+-- team_b_player2_id: FK -> Player
+-- video_source_type: 'youtube' | 'local'
+-- video_source_url: string
+-- set_target_points: number[] (例: [21, 21, 15])
+-- created_at: timestamp
+-- updated_at: timestamp

SetPlayerPosition（セット開始時の選手立ち位置）
+-- id: UUID
+-- set_id: FK -> Set
+-- player_id: FK -> Player
+-- team: 'A' | 'B'
+-- position: 'left' | 'right'
注: ダブルスでは1セットあたり4行。シングルス/トリプルス対応時は行数が変わる。

Set（セット）
+-- id: UUID
+-- match_id: FK -> Match
+-- set_number: number (1, 2, 3)
+-- target_points: number (21 or 15)
+-- score_team_a: number
+-- score_team_b: number
+-- winner: 'A' | 'B' | null
+-- created_at: timestamp

Rally（ラリー）
+-- id: UUID
+-- set_id: FK -> Set
+-- rally_number: number（セット内の連番）
+-- server_player_id: FK -> Player（ルールエンジンが自動推論）
+-- receiver_player_id: FK -> Player（ルールエンジンが自動推論）
+-- video_start_timestamp: number（動画内の開始時間、秒）
+-- point_winner: 'A' | 'B' | null（nullはレットまたは未確定）
+-- is_let: boolean
+-- is_point_confirmed: boolean（得点者が確定しているか）
+-- score_team_a_after: number（このラリー後のスコア）
+-- score_team_b_after: number
+-- created_at: timestamp

Shot（ショット）
+-- id: UUID
+-- rally_id: FK -> Rally
+-- shot_number: number（ラリー内の連番）
+-- video_timestamp: number（動画内の時間、秒）
+-- input_source: 'manual' | 'ai'（将来の拡張用）
+-- (将来: player_id, shot_type)

PositionOverride（左右入れ替わりミスの記録）
+-- id: UUID
+-- rally_id: FK -> Rally（このラリーから状態が変わる）
+-- team: 'A' | 'B'（どちらのチームで起きたか）
+-- override_type: 'swapped' | 'restored'（入れ替わった / 元に戻った）
+-- created_at: timestamp
注: 通常のラリーでの左右入れ替わり（同じサーバー連続得点、サーブ権移動）はルールエンジンが
    自動計算するため記録不要。Override は人為的ミス（本来立つべき位置と違う場所に立った）
    だけを記録する。ダブルスではペアの2人が必ず一緒にズレるためチーム単位のイベントで表現する。
    トリプルス対応時は player_id を追加するか別テーブルを検討する。
```

### 5.3 API設計（概念レベル）

Supabase Client SDK を使用してデータベースに直接アクセスする。カスタムAPIは最小限とする。

#### Player
- `GET /players` -- 選手一覧
- `POST /players` -- 選手登録
- `PATCH /players/:id` -- 選手情報更新

#### Match
- `GET /matches` -- 試合一覧
- `POST /matches` -- 試合作成（選手・動画ソース・初期立ち位置を含む）
- `GET /matches/:id` -- 試合詳細（セット・ラリー・ショットを含む）
- `PATCH /matches/:id` -- 試合情報更新

#### Set
- `POST /matches/:id/sets` -- セット作成
- `PATCH /sets/:id` -- セット情報更新

#### Rally
- `POST /sets/:id/rallies` -- ラリー作成（ポイント結果を含む）
- `PATCH /rallies/:id` -- ラリー情報更新（ポイント修正、レット設定等）
- `DELETE /rallies/:id` -- ラリー削除

#### Shot
- `POST /rallies/:id/shots` -- ショット記録
- `DELETE /shots/:id` -- ショット削除

#### Statistics（クライアントサイドで算出、またはSupabase RPC）
- `GET /matches/:id/statistics` -- 試合統計（サービス/レシーブ得点率等）

**注**: ルールエンジンはクライアントサイド（TypeScript）で実装し、サーバー/レシーバーの推論・スコア再計算を行う。結果はデータベースに保存する。

## 7. テスト戦略

| テスト種別 | 対象 | ツール | 優先度 |
|-----------|------|--------|--------|
| ユニットテスト | ルールエンジン（サーブ権、立ち位置、再計算） | Vitest | 最高 |
| ユニットテスト | 統計算出ロジック（得点率、ラリー分析） | Vitest | 高 |
| コンポーネントテスト | データ入力画面の各UIコンポーネント | Vitest + Vue Test Utils | 中 |
| E2Eテスト | 試合作成 -> データ入力 -> 統計確認の一連フロー | Playwright | 中 |
| 手動テスト | 動画再生とデータ入力のリアルタイム連携 | -- | 高 |
| 手動テスト | YouTube API の動作確認（各種ブラウザ） | -- | 中 |

**ルールエンジンのテストケース（重点項目）**:
- 通常の得点経過でサーバー/レシーバーが正しく特定されること
- ラリー入力のたびにインクリメンタルに次のサーバー/レシーバーが算出されること
- スコア修正時に以降の全ラリーが正しく再計算されること
- レットの追加/削除時にスコアが正しく維持されること
- 得点の偶奇によるサーバー立ち位置（左右）が正しいこと
- セットの切り替わり時の処理が正しいこと
- デュース時の処理が正しいこと
- 左右入れ替わり（PositionOverride）が記録された場合、実際のポジションに基づいて推論が継続されること
- 「戻った」が記録された場合、ルール通りのポジションに復帰すること

## 8. リスクと対策

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|---------|------|
| 動画再生とデータ入力のリアルタイム連携が遅延する | 高 | 中 | YouTube IFrame API / HTML5 Video API の事前検証。入力は非同期でバッファリング |
| ルールエンジンのバグにより統計結果が不正確になる | 高 | 中 | ユニットテストを網羅的に作成。実際のバドミントンの試合データで検証 |
| YouTube API の制約（再生位置取得の精度、利用制限） | 中 | 中 | 事前にAPIの精度を検証。ローカル動画をフォールバックとして常に用意 |
| 開発者がWeb開発未経験のため学習コストが高い | 中 | 高 | Claude Code + tsumiki による仕様駆動開発で補完。Nuxt/Vue のチュートリアルを事前学習 |
| AI学習用データの品質（撮影条件のばらつき） | 低（MVP時点） | 高 | 将来のAI導入時に撮影ガイドラインを策定。MVPでは影響なし |
| Supabase の無料枠制限 | 低 | 低 | チーム内利用の小規模データのため当面問題なし。必要に応じてプランアップグレード |

| 依存先 | 用途 | リスク |
