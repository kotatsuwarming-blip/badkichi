# ユーザーストーリーから要件定義の単位を導く規約 (story-splitting)

**作成日**: 2026-11-24 / **状態**: 試行中 (数周回して外れた基準は直す。数値はすべて暫定)
**出典**: Humanizing Work の分割パターン (Richard Lawrence)、SPIDR (Mike Cohn)、Example Mapping (Matt Wynne)、INVEST (Bill Wake)、DDD の境界づけられたコンテキスト。作者方針 (2026-11-24): ユーザーストーリーは人が修正・確認する。AI も提案してよいが、人も提案する。ストーリーから要件定義を必要に応じて小さく分割する工程をループで回す。

## 0. 文書の階層と持ち主

| 層 | 置き場所 | 中身 | 持ち主 |
|---|---|---|---|
| 親 (機能群) | `docs/spec/<親>/` | `user-stories.md` (ストーリー)、`requirements.md` (概要・方針・単位の分割と境界の契約・人が判断すること)、`note.md` (履歴) | **ストーリーは人**。AI は PR で提案する。方針と分割は AI が案を出し人が拒否権 |
| 子 (単位) | `docs/spec/<単位>/` | `requirements.md` (EARS、🔵🟡🔴)、`acceptance-criteria.md`、`note.md`、`user-stories.md` (親のストーリーへの**対応表**だけ) | AI が書き、人が PR で確認 |
| タスク | GitHub Issues `loop:task` | 1 PR で閉じられる大きさ | `/refill-queue` が子から導く。人は閉じる・prio を変える |

- 小さい機能は親を作らず、従来どおり 1 単位 (`docs/spec/<name>/` にストーリーも持つ)。親を作るのは §2 の信号が出たとき。
- 親はタスクの単位にならない。タスクは必ず子 (または親を持たない単位) から導く。
- 例: 親 `video-upload-analysis` → 子 `video-upload`、`video-analysis-job` (2026-11-24)。

## 1. 分割には 2 つの軸がある

| 軸 | 何を割るか | 守るもの | 基準 |
|---|---|---|---|
| 縦 | ストーリー → 小さいストーリー | 利用者に見える価値 | §3 (Lawrence の 9 パターン) |
| 横 | ストーリー群 → 要件定義の単位 | 一緒に変わるものの凝集 | §2 (4 問) |

縦の手法で横を割ると「部品やタスクになった断片」ができる (Lawrence の警告)。横の手法で縦を割ると、どの単位も利用者に価値を出せない。先に §2 で単位の境界を決め、単位の中で大きすぎるストーリーを §3 で縦に割る。

## 2. 横: 要件定義を単位に割る基準

### 2-1. 割るべきかの信号 (Example Mapping 流)

親または単位の `requirements.md` に次のどれかが出たら、分割を**提案**する (人が拒否できる)。

| 信号 | しきい値 (暫定) | 意味 |
|---|---|---|
| 条件付き要件 (REQ-1xx) の本数 | 8 本超 | ルール (青カード) が多すぎる。単位が大きい |
| 🟡🔴 の本数 | 5 本超 | 不明点 (赤カード) が多い。分割ではなく spike か人への問い (inbox) |
| 1 本のストーリーがまたぐ単位の数 | 3 単位以上 | ストーリーが粗い。§3 の Workflow Steps で縦に割る候補 |
| 依存単位の欄に並ぶ外部依存の種類 | 2 種類以上 (Storage、GPU 基盤、決済、外部 API) | 変わる速さが違うものが同居 |

### 2-2. どこで割るかの 4 問

隣り合う要件の塊 X と Y について、次の 4 問のうち **2 つ以上で「別」** なら別単位にする。

1. **データの持ち主が別か** (テーブル・状態機械が別。例: `match_videos` と `analysis_jobs`)
2. **外部依存の種類が別か** (Storage / GPU 基盤 / 決済 / 外部 API / なし)
3. **変わる速さが別か** (モデルの版ごとに変わる vs 同意の文言のように年単位)
4. **片方だけでテストが閉じるか** (もう片方は契約のモックで済む)

### 2-3. 割った後の検査

- 単位間の**契約を明示**する (親の `requirements.md` に「境界の契約」として 1 本ずつ書く: 誰が何を渡すか、形式、参照する REQ)。
- 契約が **3 本を超えたら** 結合が強い。割り方を戻すか、境界を動かす。
- 各単位が INVEST の I (他の単位の実装を待たずに PR を閉じられる、契約のモックで)・T (受け入れ基準が書ける) を満たす。
- 一方の単位に 8 割の要件が残る分割は分割になっていない (Lawrence の「大きさが揃ったか」)。

## 3. 縦: ストーリーを小さくする順序 (Lawrence の 9 パターン)

単位の中のストーリーが 1 周 (1 PR) で閉じられないとき、上から順に試す。合うものが見つかったら止める。

| # | パターン | 一言 | badkichi の例 |
|---|---|---|---|
| 1 | Workflow Steps | 多段の流れを、まず端から端までの単純な 1 本にし、中間の段を後で足す | 動画を上げる → 解析 → 確認、のうち「手元の候補ファイルを手動登録して確認」を先に |
| 2 | Operations (CRUD) | 「管理する」を作成・編集・削除に割る | 候補の追加・削除・訂正 |
| 3 | Business Rule Variations | ルールの変種ごとに割る | 得点者の導出で「レット」を後回し |
| 4 | Variations in Data | データの変種ごとに割る | mp4 だけ先、mov / webm は後 |
| 5 | Data Entry Methods | 単純な UI を先、凝った UI は後 | 4 隅をタップ → 線の延長で画面外も |
| 6 | Major Effort | 最初の 1 件に労力が集まるなら、どれを先にするかは後で決める | 下書き JSON の 1 項目 (打刻) だけ取り込む |
| 7 | Simple / Complex | 最も単純な版を 1 本にし、複雑さは別の本に | 1 試合 1 動画が先、複数試合入りは後 |
| 8 | Defer Performance | 動くことと速いことを分ける | 解析時間 2 時間以内は後 |
| 9 | Break Out a Spike | 時間を区切った調査。**最後の手段** | GPU 基盤の選定 |

分割の良し悪しは 2 点で見る: **捨てられる断片ができたか** (優先度を下げられる本が出たら良い分割)、**大きさが揃ったか** (8 を 2+2+2+2 にする方が 5+3 より良い)。

## 4. ループでの回し方

```
人がストーリーを書く・直す (親 user-stories.md)  ─┐
AI がストーリーを提案する (PR)                     ─┤ 人がマージ (持ち主は人)
                                                   ▼
/refill-queue 手順 1b: 親のストーリーが変わったら §2 で単位の分割案を出し、
                      子の要件定義を kind:docs のタスクとして起票 (分割案は Issue 本文)
                                                   ▼
/next-task: 子の requirements.md / acceptance-criteria.md / note.md / user-stories.md (対応表) を書き PR
                                                   ▼
人が PR をマージ → /refill-queue 手順 1 が子から実装タスクを導く
```

- `/refill-queue` は分割を**提案**するだけ。分割案の Issue を閉じるのは人 (拒否権)。
- `/next-task` は与えられた子の要件定義を書く。親のストーリーを書き換えない (提案は inbox に `finding:` で出す)。
- 単位の中で §2-1 の信号が再び出たら、同じ手順で孫を作らず、まず §3 で縦に割る (階層は 2 段まで)。
