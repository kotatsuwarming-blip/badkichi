# ユーザビリティテスト #01 — 実施計画

> 方針は [ADR-015](../../decisions/015-validation-approach.md) を参照。本ファイルは「計画」、
> 結果は [results.md](./results.md) に残す。

## 1. 目的 (検証したい問い)

**2 つの層を順に観察する**:

1. **理解の層 (Phase 0)**: 入口の説明を見て、**これが何のアプリか・誰向けか・何ができそうかが伝わるか**
2. **操作の層 (Phase 1)**: 目的を理解した上で、**コアループを自力で完走できるか**

- コアループ = **試合を記録する → ダッシュボードで分析する (得点率・選手別・動画ジャンプ)**
- 「使いこなせない」という作者の感触を、**説明が分かりにくいのか / 操作で詰まるのか**へ切り分ける
- 得られたデータ (伝わらなかった点・詰まった点) を **説明文と UI 修正の優先順位の入力**にする (推測で直さない)

非目的 (今回やらないこと):
- 機能の要望ヒアリング・アンケート (= 意見聴取。③フェーズで行う)
- 「面白いか / 欲しいか」の評価 (= 需要検証。今回は行動だけ見る)

## 2. 前提作業: 入口の説明 (LP) — 実装済み (Phase 0 の検証対象)

「そもそも何のアプリか分からない」問題に対し、**公開ランディングページ (`app/pages/index.vue`) を実装済み**。
ただし作って終わりにせず、**その説明文が伝わるかを Phase 0 で検証する**(分かりにくさもテスト対象)。

現在の確定コピー (`i18n/locales/ja.json` の `landing.*` / Phase 0 はこの文言そのものを検証する):

- **ブランド**: 「バドきち」
- **見出し**: 「バドミントンの試合を記録して、強みと課題を“数字”で分析」
- **サブ見出し**: 「試合を記録するだけで、得点に効く要素を分析。気になった場面は映像でそのまま振り返れます。」
- **CTA**: 「Google で始める」(→ `/login`)
- **価値3点**: 直感的に記録 / 得点率を多角的に分析 / 映像とセットで振り返り

注意: 説明は「機能の羅列」ではなく **「誰が何を得られるか」**。Phase 0 で伝わらなければ
**この文言の修正が発見**になる(推測で直さず、観察データで直す)。

## 3. 対象ユーザー (被験者像)

- **チームメイト = バドミントン経験者かつ本アプリ初見**
- ドメイン (バド用語・試合の流れ) は理解しているので、**純粋に「説明の伝わりやすさ」と「UI の分かりにくさ」だけが露出する**理想条件
- 人数: **3 人**を目安 (Nielsen: 5 人で約 85% の問題発見。まず 1 人から始めてよい)
- 各セッション 20〜30 分

## 4. 進め方 (プロトコル)

- 環境: **本番 (Vercel) の実機**。被験者自身のスマホ / PC で触ってもらう (実利用条件に近づける)
- 手法: **シンクアラウド (think-aloud)**。「今何を考えているか・何を探しているかを声に出して」と依頼する
- 観察者 (作者) の鉄則:
  - **絶対に助けない・誘導しない**。「次どうすれば?」と聞かれても「どうすればいいと思いますか?」と返す
  - 操作を**先回りして説明しない**。被験者が自力で見つけるか・詰まるかを見る
  - 詰まっても**最大 2〜3 分は待つ**。完全に手が止まったら次へ
- 記録: **二段構え**で取る
  - **生キャプチャ**: 画面録画 + think-aloud 音声 (一番忠実)。これがあれば当日は**書くより見る**ことに集中する
  - **分析シート**: 録画を見返して `results.md` の各タスク表 (詰まった箇所/発話/所要/観察者所感) を埋める。これが「発見」になる
  - Tips: 当日は**詰まった瞬間の時刻だけ手元メモ** → 後で録画の頭出しが速い (全部見返さずに済む)

## 5. Phase 0 — 理解度テスト (説明が伝わるか)

タスクを渡す**前**に、**LP (§2 のコピー込み) だけを見せ、何も補足せず**こう聞く。
汎用質問 + 確定コピーの語を狙い撃ちする質問の 2 段で取る:

汎用 (まず自由に言わせる):
- 「これ、**何のアプリ**だと思いますか?」
- 「**誰向け**で、**何ができそう**?」
- 「**最初に何をする**と思いますか?」

コピー狙い撃ち (実際の文言が伝わるか / 推測修正を避けるための直接検証):
- 「見出しの **“強みと課題を数字で分析”** とは、具体的に何が分かりそう?」
- 「**“得点に効く要素を分析”** と書いてあるけど、何を指していると思う?」(→ サービス/レシーブ・立ち位置・ラリー長 等に届くか)
- 「**“Google で始める”** のボタンを押すと、何が起きると思う?」(→ いきなり登録/課金されそう等の不安・誤解を取る)

> 変種: **5 秒だけ見せて隠し**、何が伝わったか/記憶に残ったかを聞く (5 秒テスト)。

記録すること:
- 説明が伝わったか (**自分の言葉で**「何のアプリか・誰向けか」を言えたか)
- コピーの語の誤解 (「数字で分析」「得点に効く要素」が伝わらない / 別物だと思った)
- CTA への不安・誤解 (押すのをためらう等)
- 分かりにくかった語・表現

ここで伝わらなければ **「説明文の修正」が発見**になる。
**コンティンジェンシー**: 全く伝わらず Phase 1 に進めない場合でも、口頭でシナリオを補って
Phase 1 の操作データは取る (セッションを無駄にしない)。例: 「チームのコーチが試合を記録して
選手ごとの得点率を分析する、と思って使ってみてください」。

## 6. Phase 1 — タスクテスト (T1〜T5)

Phase 0 を経て被験者は説明を読んだ状態。そのまま自然にタスクへ。各タスクは**ゴールだけ伝え、
手順は言わない**。完了/失敗と詰まりを観察する。
(説明文が文脈を担えていれば、ここでも口頭の補足なしで進めるはず。それ自体も観察対象。)

実フロー: `LP → /login (Google のみ) → /onboarding (グループ未所属は強制) → グループ作成 (/groups/new) → 選手登録 → 試合作成 → 記録 → 統計`。
タスクはこの順に対応させている。

| # | タスク (被験者への指示文) | 観察したいコアループ要素 |
|---|---|---|
| T1 | 「このアプリを始めて、ログインしてください」 | LP の CTA → **Google ログイン** (本番は Google 限定) |
| T2 | 「あなたのチームを作って、選手を何人か登録してください」 | onboarding → **グループ作成** (/groups/new) → 選手登録。招待 URL 方式 (コード手入力なし) の理解も観察 |
| T3a | 「この試合を記録してください (**1 ゲーム分**のラリーを記録して保存)」 | 試合作成 → ラリー記録 → 保存 (**コアの中心**) |
| T3b | 「試合の途中で○○側の**左右が入れ替わりました**。それを記録してください。そのあと**元に戻った**ことも記録してください」 | **Position Override** `[A入替]`/`[B入替]` を自力で見つけ、swapped→restored を操作できるか |
| T4 | 「○○選手の得点率を調べてください」 | stats ダッシュボード / ドリルダウン (チーム→選手) の読み取り |
| T5 | 「気になった場面の動画を見返してください」 | 統計からの動画ジャンプ |

> **T3a が最重要** (詰まるとコアループ不成立)。所要時間を必ず記録する。
> **T3b (Position Override) は UX リスクの検証対象** — NFR-203 / [[project_override_ux]] で「ラリー開始ボタンと
> 操作が競合する懸念があり、プロトタイプ検証が必要」と明示フラグ済み。今回がその検証の場。
> 指示では**ボタン名を言わない** (「入れ替わった事実」だけ伝え、被験者が `[A入替]`/`[B入替]` を見つけられるか観察する)。
> 素材に入れ替わりが無い被験者 (峻さん想定) は §事前準備のコンティンジェンシーで口頭シナリオを与える。

## 6.5 Phase 1.5 — 振り返り (debrief / 全タスク完了後)

**タスク中は絶対に意見を聞かない** (行動観察が濁る)。全タスクが終わってから、使い勝手の意見をまとめて取る。
ここは「事実」ではなく「意見」だが、**直前の観察を補強する仮説の入力**として使う (UI 修正の優先度は
あくまで複数人の行動の一致で決める。意見はその裏付け)。

- 「一番**迷った/分かりにくかった**のはどこ?」
- 「もし変えるなら**どこがどうなってたら**楽だった?」
- (T3b について) 「**左右入れ替わり**の操作、ボタンはすぐ分かった? 記録中に押すのは大変じゃなかった?」

## 6.6 需要メモ (任意 — あすか・峻さんのみ / セッション最後 / 別バケツ)

現役プレイヤーの貴重な機会なので、**全部終わった最後に少しだけ**需要シグナルを聞く。ただし厳格に隔離する:

- **順序厳守**: 行動観察 (T1〜T5) → 振り返り (6.5) → **最後に**需要の雑談。タスク中・振り返り中には需要質問を混ぜない
- **別バケツ**: 結果は `results.md` の「需要メモ」へ。**n=2 の意見**と明記し、③フェーズ backlog の入力にする
- **UI 修正の優先度には混ぜない** (ADR-015 §3。②の発見と③の需要は分けて扱う)
- 例: 「これ、自分のチームの練習で使い続けたいと思う?」「今お金払ってでも欲しい場面ある?」「無くて困ってる機能ある?」
- 川島さんは素材提供者で立場が違うため対象外 (聞いてもよいが需要シグナルとしては弱い)

## 7. 観察・記録項目 (タスクごと)

- **完了したか**: 自力完了 / ヒント後完了 / 失敗 (スキップ)
- **詰まった箇所**: どの画面・どのボタンを探していたか / 誤って押したもの
- **発話**: 「え、どこ?」「これでいいのかな」等、迷い・誤解を示す言葉
- **所要時間**: 特に T1 (ログイン)・T3a (記録)
- **観察者所感**: 原因の仮説 (ラベルが不明瞭 / 導線が隠れている 等)
- **T3b 専用**: `[A入替]`/`[B入替]` を**ヒントなしで見つけられたか** / swapped→restored の 2 ステップを正しく操作できたか /
  **ラリー進行 (記録中) と操作が競合しなかったか** (NFR-203 の検証ポイント)

## 8. 成功基準

- **理解度 (Phase 0)**: **3 人中 2 人以上**が、説明を見て「何のアプリか・誰向けか」を**自分の言葉で正しく**言える
- **タスク成功率 (Phase 1)**: 主要タスク (特に T1・T3a) を **3 人中 2 人以上が自力完了**できれば「公開ライン到達」
- **Position Override (T3b)**: 3 人中 2 人以上が `[A入替]`/`[B入替]` を**自力で見つけて操作**できる。
  見つけられない / ラリー記録と競合して混乱が起きるなら、NFR-203 の懸念が顕在化 = **High 優先の修正対象**
- **詰まりの集中**: 説明・タスクのどちらでも、複数の被験者が**同じ箇所**で詰まったら、それが修正の最優先
- 1 人でしか起きない詰まりは優先度を下げる (個人差の可能性)

## 9. アウトプット

- [results.md](./results.md) に**セッションごとの記録**(Phase 0 / Phase 1)と**発見した問題リスト (優先度付き)**をまとめる
- 優先度 High の問題 (説明文 / UI) → 修正タスクとして起票
- 修正したら、**修正後に再テスト (usability-test-02)** で改善を確認する
