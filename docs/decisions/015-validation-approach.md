# ADR-015: MVP 公開前後の検証アプローチ方針

## ステータス
Accepted (2026-06-11)

## 背景

[[project_monetization_strategy]] (ADR-013) で「公開 SaaS・freemium」、
[[project_hosting_vercel]] (ADR-014) で本番ホスティング (Vercel) を確定し、
MVP の実装と本番デプロイ・Google ログインまで疎通した。

ここから先は **「作る」フェーズから「使われるか検証する」フェーズ**に移る。
本 ADR は、その**検証の進め方の方針**を定める。具体的な実施記録 (タスク・観察結果) は
`docs/research/` 配下に別途残す (本 ADR は方針、research は実施ログ、と役割を分ける)。

### 解決したい問題

作者 (利用者本人) は dev 環境で 2 試合分を記録し、統計ダッシュボードが機能することを
確認済み (ドッグフーディング完了)。一方で **「初見の人は今の UI では機能を使いこなせない」**
という強い感触がある。ここで陥りやすいのが、**自分の推測で UI を作り込んでしまう**ことで、
これは未検証の機能追加と同じ「時間の投機」になる。

検証の道具を目的別に正しく使い分け、UI 修正や機能追加の入力を
**推測ではなく観察・データから取る**ための方針が必要になった。

## 決定

### 1. 検証フェーズを 4 段階で順番に進める (飛ばさない)

| 段階 | 検証したい仮説 | 主な道具 | 状態 |
|---|---|---|---|
| ① ドッグフーディング | 自分が本気で使い続けられるか / コアループが壊れないか | 作者の自己利用 | ✅ 完了 (2 試合記録 + ダッシュボード確認) |
| ② ユーザビリティテスト | 初見が説明なしでコアループを完走できるか | **他者の行動観察** | ⏳ 次にやる (usability-test-01) |
| ③ クローズドβ | 他チームも使い続けたいと思うか | 配布 + リテンション計測 + アンケート | 未着手 |
| ④ 需要・収益検証 | 一般ユーザーが登録・利用・課金するか | 公開 + analytics + 課金導線 | 未着手 |

ニッチな team 向けプロダクトの需要は「1 チームが練習に組み込んで使い続けるか」に出る。
バズや登録者数のような虚栄の指標 (vanity metric) ではなく、**アクティベーションと
リテンション**を需要シグナルの中心に置く。

### 2. 「ドッグフーディングの終了条件」は機能の充実度ではなくブロッカーの不在

コアループ = **試合を記録する → ダッシュボードで分析する (得点率・選手別・動画ジャンプ)**。

このループを作者が完走でき、かつ以下のブロッカーが無ければ「公開ライン」とみなす:

- 1 試合まるごと記録できる (録画 → ラリー記録 → 保存まで途中で落ちない)
- 統計の数字が信頼できる (手計算と合う)
- **データが消えない / 壊れない** (最優先・譲れない)
- ログイン不能等の詰みが無い
- 初見が説明なしで「記録開始」まで辿り着ける (← ②で検証する項目)

このチェックリストに無い「あったら良い機能」は**ゼロ個でも公開できる**。
作者の追加機能リストはすべて **「リリース後 backlog」に退避**し、
②③④で得た**実需要で優先順位を付け直す**。

### 3. 道具の使い分け — 行動観察 と 意見聴取 を混同しない

| 検証したいこと | 正しい道具 | 取れるもの | 入力先 |
|---|---|---|---|
| 初見が使いこなせるか | ユーザビリティテスト (行動観察) | **事実** (何で詰まるか) | UI 修正の優先順位 |
| 何を欲しがるか・払うか | アンケート / ヒアリング (意見聴取) | **意見** (何を思ったか) | 機能 backlog の優先順位 |
| 戻ってくるか | analytics (利用計測) | **行動ログ** (リテンション) | 需要シグナル / 続行判断 |

原則: **「ユーザーは何が欲しいかを正しく言えないが、何で詰まるかは見れば分かる」**。
今の UI 問題には**まず行動観察 (②) を当て、その観察データを根拠に UI を修正する**。
アンケートは③以降の需要・機能優先度フェーズで効かせる。

### 4. 「初見が使えない」問題はドッグフーディングでは検出できない

作者は自分の UI の分かりにくさを **知識で無意識に補完する** (知識の呪い / curse of
knowledge)。ゆえに初見の使いこなしは構造的に自己検証できず、**他者の行動観察 (②) が必須**。
UI 修正に着手する前に、必ず②を経由する。

### 5. ドキュメント構成

- **方針** → 本 ADR (`docs/decisions/015-validation-approach.md`)
- **実施記録** → `docs/research/{調査名}/`
  - `plan.md` … 目的・対象・タスクシナリオ・観察項目・成功基準
  - `results.md` … セッションごとの記録・発見した問題・優先度・対応方針

発見した問題は `results.md` に蓄積し、対応するものは backlog / tasks へ流す。

## 理由

### なぜ段階を飛ばさないか

作者が持つ追加機能リストは **全項目が推測で優先順位付けされている** (実ユーザーデータ ゼロ)。
作り込んでから公開すると「誰も使わない機能に時間を溶かす」が確定するリスクがある。
早く②③に進めるほど、backlog が**推測順から実需要順に並び替わる**。

### なぜ行動観察を意見聴取より先にやるか

「初見が使えない」は UI の問題 = 行動の問題であり、アンケート (意見) では正確に取れない。
被験者は「分かりにくかった」と言えても「どの瞬間にどう詰まったか」を再現できないことが多い。
観察なら詰まりの瞬間が直接見える。

### データエンジニアのアナロジー

- **ドッグフーディング** = 自分で書いたパイプラインを自分で流す。ロジックの正しさは見えるが、
  **「他人がこのスキーマを初見で使えるか」は分からない** (作者バイアス)。
- **ユーザビリティテスト** = 他のエンジニアにドキュメントなしでテーブルを触らせ、どこで
  詰まるかを観察する。**スキーマの分かりにくさは利用者の手元でしか露見しない**。
- **アンケート/需要検証** = 「このデータマートに需要があるか」をクエリログ (利用計測) で測る。
  自己申告ではなく**実利用ログが最強のシグナル**。

## 影響

### 次のアクション

1. `docs/research/usability-test-01/` でユーザビリティテストを実施 (対象: チームメイト = バド経験者)。
2. 発見した詰まりを優先度付けし、UI 修正タスクへ。
3. 並行して、③以降に必要な利用計測 (analytics) の導入方針を別途検討
   (ファネル: 登録 → 初回試合記録 → 統計閲覧 → 再訪)。

### まだやらないこと

- analytics ツールの選定・導入 (③クローズドβの前までに決める)
- アンケート設計 (③フェーズで行う。②は行動観察に集中する)
- 課金導線・Pro 機能の検証 (④。ADR-013 のマトリクスに従う)

## 採用しなかった選択肢

| 案 | 却下理由 |
|---|---|
| A. 感触に基づき先に UI を作り込む | 作者バイアスで推測ベースの修正になる。②の観察データを入力にする方が外さない |
| B. 追加機能を実装してから公開する | 未検証機能への投機。実需要が分かる前に時間を溶かすリスク |
| C. ②を飛ばしていきなりアンケート | 意見聴取では UI の詰まり (行動の問題) を正確に取れない |
| D. ②を飛ばして一般公開 | 初見が詰まる UI のまま公開すると、需要シグナルが「UI が悪いだけ」で濁る |
