# ADR-013: 収益化・プラットフォーム方針

## ステータス
Accepted (2026-06-05)

## 背景

MVP は「特定チーム内で使うバドミントン分析アプリ」として設計・実装が進んでいるが、
事業としての方向性について以下の意向が確認された:

1. **最終的には不特定多数に広く公開したい** (公開 SaaS 化)
2. **最初は仲間内数人に公開**して使ってもらう (スモールスタート)
3. **小さくても事業として売上を立てたい** (広告は初期から許容)
4. **PC / スマホ どちらからも使える**ようにしたい

これらは MVP のスコープ外だが、収益モデル・プラットフォーム選択・課金手数料が
相互に依存するため、早期に方針を確定し、各機能の設計時に「有料ゲートの裏かどうか」を
意識できる状態にしておく。本 ADR は実装計画ではなく**方針の確定**であり、
課金・広告の実装自体は MVP 完成後に着手する。

## 決定

### 1. プラットフォーム: レスポンシブ Web → (必要なら) PWA

- 配信は **ブラウザ Web を主軸**とし、レスポンシブ対応で PC / スマホ両対応を満たす
- 将来必要に応じて **PWA** (`@vite-pwa/nuxt` 等) を追加してアプリ風 UX を提供する
- **ネイティブアプリストア配信は当面採らない** (App Store / Google Play の手数料 15〜30%、
  およびアプリ内デジタル課金のストア決済強制を回避するため)
- 現行の Nuxt + Supabase 構成のまま公開 SaaS にスケール可能 (作り直し不要)

### 2. 収益モデル: freemium (サブスク主軸・広告は補助)

- **サブスク (月額) を主たる売上源**とする。決済は **Stripe** (手数料 約 3.6%/件、
  Supabase 連携の定番パターン) を想定
- **広告は補助**。AdSense は審査制かつ少人数規模では収益がほぼ立たないため、
  **無料プランの収益＋有料への誘導装置**として、ユーザー規模が出てから導入する
- 「事業として売上を立てる」目的に対しては、小規模でも確実に計上できるサブスクを優先する

### 3. プランは Free / Trial / Pro の **3 つ** (Trial は独立列)

「Free ⊂ Trial ⊂ Pro」の直線的サブセットにはせず、**Trial を独立した第 3 のプラン**として扱う。
理由は §理由 を参照。

### 4. 権限は「機能 × プラン」のマトリクスで判定する

各機能について Free / Trial / Pro の 3 列の値を**個別に**決められる構造とする。
新機能を追加するたびに 3 列の値を 1 行埋めるだけで権限設計が完結する。

#### エンタイトルメント・マトリクス (たたき台)

| 機能 | Free | Trial (初月) | Pro |
|---|---|---|---|
| 試合 / 動画の分析数 | **累計 N 本まで** | 無制限 | 無制限 |
| 基本ダッシュボード | ○ | ○ | ○ |
| 詳細ダッシュボード | × | ○ | ○ |
| 広告 | あり | なし | なし |
| AI 自動記録 / サポート (将来) | × | △ 回数制限付き | ○ |
| 切り抜き機能 (将来) | × | **× (または数本まで)** | ○ |

- **動画分析数の制限は「累計」**(月次リセットなし)。上限到達後は課金しないと増やせない
  = 転換圧力が強く、データ的にも総数カウントのみで月跨ぎ集計が不要
- **Trial で開放しない / 絞る機能**: 切り抜き・AI 生成のような
  「成果物が残る」「使うたびに従量コストが発生する」もの (§理由 の分類ルール)

### 5. プラン判定ロジック (概念)

1. **プラン判定**: ユーザー (グループ) が今どの列か → `'free' | 'trial' | 'pro'`
   - Trial = 登録から 30 日以内 かつ 未課金
2. **権限判定**: `can(機能, プラン)` がマトリクスを引くだけ

```ts
// イメージ (実装は MVP 後)
const ENTITLEMENTS = {
  detailedDashboard: { free: false, trial: true,    pro: true },
  clipExport:        { free: false, trial: false,   pro: true },  // ← trial でも除外
  aiAutoRecord:      { free: false, trial: 'limited', pro: true },
}
```

### 6. AI 入力補助の方針 (将来機能・MVP 後)

AI による入力補助を Pro の中核価値と位置づける。**全自動ではなく「AI が下書き → 人が確認・訂正」**
の補助として設計する (素人動画では全自動を約束できないため。§理由 参照)。

#### 6-1. 狙う出力信号

| 出力信号 | 中心技術 | 検出原理 | 位置づけ |
|---|---|---|---|
| ショットを打った瞬間 | シャトル軌道 (TrackNet) ＋姿勢 | 軌道の急反転点＝打点。腕振りピークで裏取り | MVP 相当情報 |
| サーブの瞬間 | 上記＋ラリー境界 | 静止/不在 → 動き出しの最初の打点＝サーブ | MVP 相当情報 |
| 選手の立ち位置 | 人物検出/姿勢＋コート射影 | 足元をコート座標へ変換 | MVP 相当情報 |
| 誰が打ったか | 上の統合＋ID 追跡 | 打点の最寄り選手。ラリー通して ID 保持 | **MVP 超え** |

4 信号は「シャトル軌道 + 姿勢 + コート射影」の 1 スタックから導出する。

#### 6-2. 動画の扱い: 「勝手に保存」は不採用。クライアント側 or ハイブリッド

- **YouTube 動画のサーバー側ダウンロード/保存は不採用** (ToS 違反 + 著作権)。
- **ローカル動画を本人非明示で裏送りするのも不採用** (プライバシー / 肖像 / ストア審査 / 信頼)。
- 採用するアーキテクチャ:
  - **クライアント側 (ブラウザ内) で AI 推論** … 動画は端末から出ない。ToS/プライバシー/コスト回避。
    WebGPU でブラウザ内推論は実用段階。
  - **ハイブリッド (本命)** … クライアントで**数値特徴量だけ抽出** (シャトル座標・骨格キーポイント・
    コート座標) し、**動画ではなく数値時系列だけ**を送る。著作権・プライバシー・コストをまとめて回避。
- 既存の方式 A (動画はローカル再選択・非保存, [[project_video_playback_spec]]) と一貫する。

#### 6-3. 起点となるオープンモデル

| 役割 | 資産 | ライセンス | 備考 |
|---|---|---|---|
| シャトル追跡 | TrackNetV3 | **MIT (商用 OK)** | 学習済み ckpt 付き。まず狙う起点 |
| 姿勢推定 | MediaPipe Pose / YOLOv8-pose | 商用 OK | ブラウザ内で動作 |
| ショット種別分類 | BST (CVPR 2025) | **要確認** | skeleton ベース |
| 学習データ | ShuttleSet (18 ショット種別) | **要確認** | 自前 fine-tune の起点 |

**商用前にライセンス精査が必須** (推論コードが OSS でも、重み/データが研究用途限定の場合がある)。

#### 6-4. 学習データ戦略: 特徴量主・動画はオプトイン寄付・訂正フライホイール

- **下流タスク (ラリー区切り・ショット分類等) は特徴量だけで学習可能** (ShuttleSet/BST が証拠)。
- ただし特徴量保存は**不可逆**: 上流モデル (シャトル追跡/姿勢) の改善や未保存特徴の後出しは不可
  (medallion の bronze を捨てる判断に相当)。よって特徴量は**ケチらず広く・抽出モデルのバージョン
  付きで**保存する。
- **人の訂正履歴 = 最大の資産**。「AI 下書き → 人が確認・訂正」の訂正そのものが正解ラベルになる
  学習フライホイールを、最初から保存設計に入れる。
- **上流モデルを素人映像に強くする fine-tune にだけ生動画が要る** → 全ユーザーは特徴量のみ、
  改善協力に**明示同意したユーザーから対価/特典付きで生クリップをオプトイン寄付**してもらう
  (or 処理後即削除の transient 保持)。

#### 6-5. 素人動画対策: 撮影ガイド + プライミング

素人動画 (低画質・人の横切り・複数試合・手ブレ) への対策は 2 系統:

- **(A) 撮影ガイド (撮る前)**: 三脚固定 / コート全体が入り寄りすぎない高さ・角度 / 明るさ。
  信号そのものを底上げ。**シャトルの解像度問題はここでしか直せない (精度の天井)**。
- **(B) プライミング注釈 (処理時の一回きり)**: 難問を制約に変換。

| ユーザー操作 | 潰す失敗 | 解禁 |
|---|---|---|
| コート 4 隅をドラッグ (射影校正 + ROI) | 横切り・複数試合・コート外誤検出 | 立ち位置のコート座標化 |
| 選手 4 人をタップ/枠指定 | 観客/通行人の誤認・ID 取り違え | **「誰が打ったか」**・選手追跡 |
| 試合区間を指定 | 1 動画に複数試合 | 試合ごとの分離 |
| AI 下書きを確認・訂正 | 取りこぼし全般 | 訂正 = 教師ラベル (6-4 フライホイール) |

プライミングは「冒頭の数クリックで失敗クラスを丸ごと 1 つ消す」交換比率重視の設計。
特に**コート 4 隅 + 選手 4 人マークは、横切り/複数試合/誤検出を潰しつつ「誰が打ったか」(MVP 超え)
まで解禁**する一石二鳥。

## 理由

### 1. プラットフォームを Web に寄せると課金手数料が最小化される

3 つの検討事項を繋ぐ最重要ポイント。配信形態が課金手数料を直接決める:

- **Web 課金 (Stripe)**: 手数料 約 3.6%/件
- **アプリ内課金 (App Store / Google Play)**: 手数料 15〜30%、かつアプリ内デジタル課金は
  原則ストア決済を強制されるため Stripe を自由に使えない

→ Web / PWA に寄せることで、サブスクを低手数料で回せる。ストア配信は手数料・審査・
申請運用のコストに見合う段階 (相当な規模) まで保留する。

### 2. 現行構成のまま公開 SaaS にスケールできる

`groups` / `group_members` / RLS によるマルチテナント基盤 ([[project_single_group_per_user]],
[[project_players_vs_auth_users]]) が既にあるため、「数人 → 不特定多数」の拡張で
データ分離の作り直しは発生しない。公開化で追加するのは**コードの作り直しではなく周辺機能**
(課金・広告・サインアップ開放・プライバシーポリシー / 特商法表記・運用) に限られる。

### 3. 広告より少額サブスクの方が「売上を立てる」に確実

「小さくても売上を」という目的に対し:

- AdSense は審査制で、コンテンツ量・アクセスが乏しい少人数会員制アプリは承認が下りにくい。
  通っても数人 PV では月数円〜数十円のオーダー
- サブスクは友人 1 人が少額でも払えば明確な売上として計上でき、審査リスクもなく金額も読める

→ 広告を否定せず、AdSense が機能する規模になってから補助として足す順序が効率的。

### 4. 動画数制限は「コスト」ではなく「純粋な値付けレバー」

動画はサーバー保存せずローカル再選択方式 (方式 A, [[project_video_playback_spec]]) のため、
動画数が増えてもこちら側のストレージコストは増えない。よって動画数制限は**コスト抑制ではなく
純粋に金額を取るための線引き**であり、制限値は自由に設計できる。

帰結として、**仲間内ローンチ時は制限を緩く (または無制限に) し、公開時に締める**のが定石。
初期ユーザーは「広めてくれる人」であり、いきなりきつい上限で離脱させない。
実装は「**今は制限をかけず、累計数をカウントできる状態だけ作っておき、後でスイッチを入れる**」。

### 5. Trial を独立列にする理由 (機能の 2 分類)

機能は trial 開放時の挙動で 2 タイプに分かれる:

- **消える価値型**: trial 終了で効果も消える (詳細ダッシュボードの閲覧・分析など)。
  trial で開放しても害がなく、むしろ「これは良い」と思わせ課金につながる
- **残る / コスト型**: trial 中に作ったものが**後に残る** (切り抜き動画の量産)、または
  **使うたびに従量コストが発生する** (AI 生成)。trial で開放すると
  「1 ヶ月で資産だけ作って離脱」される

分類ルール:

> **trial で開放してよい = 価値が trial 終了で消えるもの**
> **trial でも絞る = 成果物が残る / 従量コストがかかるもの**

切り抜き機能はまさに後者であり、trial であっても除外 (または少数キャップ) が必要。
この「trial だけ × にする」という変則を表現するには、Trial を Pro のサブセットにせず
独立列にする必要がある。

### データエンジニアのアナロジー

- **エンタイトルメント・マトリクス = 権限テーブル (GRANT 行列)**: 主体 (プラン) × オブジェクト
  (機能) の二次元で権限を引く。`can(feature, plan)` は `has_privilege()` に相当
- **累計動画数制限 = 行数上限のソフトクォータ**: パーティション (月) ごとではなくテーブル全体の
  `COUNT(*)` に対する上限。閾値判定だけで月次ロールアップ不要
- **Trial = 期限付きの一時 GRANT (一部 REVOKE 付き)**: 30 日で失効する権限付与だが、
  従量 / 永続成果系の権限は最初から付与しない

## 影響

### MVP 中に意識しておくこと (後付けを楽にする仕込み)

実装は MVP 後で十分。ただし設計時に以下を意識しておくと後付けコストが下がる:

1. **試合 / 動画の累計数をカウントできる状態**にしておく (制限値は後決め。既存 `matches` の
   件数で足り、月次集計は不要)
2. **ダッシュボードを「基本 / 詳細」でグルーピングできる**ようにし、どの分析が「詳細 (=有料)」
   かを作りながら意識する
3. 各機能を作るとき、**その機能の Free / Trial / Pro 3 列の値を一言メモ**しておく。
   特に切り抜き・AI のような「残る / コスト型」は trial 除外 / 制限候補として明記する

### まだやらないこと

- Stripe・広告・trial の実装本体 (先行すると MVP が遅れるだけ)
- AdSense 申請 (機能する規模に達してから)
- PWA / ストア配信

### 公開 SaaS 化の際に追加で必要になるもの (記録のみ)

- プライバシーポリシー / 特定商取引法に基づく表記 (課金時は法的に必須)
- サインアップの開放 (現状 dev は signup OFF, [[project_auth_provider_policy]])
- 決済 (Stripe) と課金状態の DB 同期 (Webhook)

## 採用しなかった選択肢

| 案 | 却下理由 |
|---|---|
| A. ネイティブアプリ (Capacitor / フルネイティブ) で配信 | ストア手数料 15〜30% とアプリ内課金のストア決済強制でサブスク収益を圧迫。審査・申請の運用コストも大。Web/PWA で PC/スマホ両対応は満たせる |
| B. 広告を主たる収益源にする | 少人数会員制では AdSense 審査が通りにくく、通っても収益がほぼ立たない。「売上を立てる」目的にはサブスクが確実 |
| C. Trial = Pro 全機能の完全開放 | 切り抜き等「成果物が残る / 従量コスト型」機能を 1 ヶ月で量産・濫用される。Trial を独立列にして個別除外できる必要がある |
| D. 動画数制限を「月 N 本」にする | 月次リセットで無料のまま粘られやすく転換圧力が弱い。月跨ぎ集計も必要。累計制限の方が目的に合い実装も簡単 |
| E. freemium をやめ最初から有料のみ | 仲間内ローンチで「広めてくれる初期ユーザー」を獲得できず、公開 SaaS への成長導線を断つ |
| F. AI 用に動画をバックグラウンドで自社クラウドへ保存 | YouTube は ToS 違反 + 著作権。ローカル動画の本人非明示の裏送りはプライバシー/肖像/ストア審査/信頼の地雷。クライアント側 or ハイブリッド (数値特徴量のみ) で代替可能 |
| G. 学習データとして生動画を主ストレージにする | コスト/法務/プライバシー負担大。下流タスクは特徴量だけで学習でき (ShuttleSet/BST)、生動画は上流 fine-tune 用にオプトイン寄付で少量集めれば足りる |
| H. AI を全自動記録として提供 | 素人動画 (低画質/横切り/遮蔽) で精度を保証できず信頼を損なう。「AI 下書き → 人が確認・訂正」の補助に留める (訂正が教師ラベルにもなる) |
