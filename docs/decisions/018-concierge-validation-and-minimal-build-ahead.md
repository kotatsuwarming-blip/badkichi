# ADR-018: 検証戦略の改訂 — テスター限定代行入力と最小実装先行

## ステータス
Accepted (2026-07-19)

## 背景

[[project_validation_rollout]] (ADR-016) は第1ゲートを「自前で試合記録 → 統計閲覧を完走」と
定義した。しかしこのファネルは、実は2つの別々の仮説を1つに混ぜている:

- **仮説A: 統計に価値があるか** (アウトプットへの需要)
- **仮説B: 入力コストを払ってくれるか** (インプットへの耐性)

このままではゲート不通過のとき「統計に興味がない」のか「記録が面倒だっただけ」なのかを
区別できず、次の投資先 (統計の強化 / 入力 UX の磨き込み / AI・代行の前倒し) を誤る。

川島氏インタビューで「**統計をまず見られることが一番の価値。初見の人は動画情報を送れば
こちらで入力を済ませ、統計が見られる状態にしてはどうか**」という意見を得た。
これは仮説Aだけを純粋に検証できる装置 (コンシェルジュ MVP / Wizard of Oz) である。

さらに2つの制約が確認された:

1. 現在の統計はサーブ/レシーブ得点率とラリー長×得点率のみで、**この2枚でカテゴリ需要を
   測ると偽陰性のリスクが高い** (刺さらなかったのが「統計」なのか「この2枚」なのか不明)。
   ショットレベル統計 ([[project_ai_ladder]] ADR-017) を検証の試料に含めたい。
2. 統計は**自分 (たち) の試合についてだから刺さる**。作者チームのデータや架空データの
   デモでは仮説Aの検証にならない。テスター本人の試合で見せる必要がある。

本 ADR は、検証の装置 (テスター限定代行)・実装の先行範囲 (ゲートの読み替え)・
ゲート定義の更新を確定する。

## 決定

### 1. 仮説を2トラックに分離して検証する

| トラック | 検証する仮説 | 手段 |
|---|---|---|
| **代行トラック** | A: 統計に価値があるか | テスター限定の代行入力 (§2)。本人の試合の統計を見せ、反応と自発的リピートを観察 |
| **セルフトラック** | B: 入力コストを払うか | 従来どおりの usability-test (別テスター)。記録 → 統計の完走を観察 |

- **同一テスターで A → B を続けて検証しない** (機能を知った状態では B の発見可能性テストが
  汚染される)。ただし代行テスターに事後で「自分でも記録してみるか」を振るのは補助シグナル
  として有効: **価値を知った上での No は入力コストへの最強の否定シグナル** (動機が最大化
  されていたのに払わなかった)。
- ゲート定義を次のように更新する (ADR-016 の2段ゲート構造・「自前で = 介助なし」原則は維持):

| トラック | 第1ゲート (アクティベーション) | 第2ゲート (リテンション) |
|---|---|---|
| セルフ記録 | 自前で記録 → 統計閲覧を完走 (現行どおり) | 催促なしに別日に再度記録 (現行どおり) |
| **代行** | 動画+試合情報を送る → 統計を閲覧 | **催促なしに2本目の動画を自発的に送ってくる** |

- 第2ゲート (課金・本丸投資の解禁) は**いずれかのトラックのリテンションで成立**とする。
  「他人に依頼する手間を払ってでも2本目を見たい」はセルフ再記録と同等以上の需要シグナル。

### 2. 仮説Aの装置: テスター限定代行入力 (全員向けオンボーディングではない)

代行はスケール装置ではなく**研究装置**である。全ユーザーの初戦を代行するのは
作者の時間で回らないため採らない (選択肢 C)。

**枠 (研究予算)**:

- テスター**上限5人・初回1試合まで** (Nielsen の5ユーザー・ロジックは ADR-016 と同じ)
- 1試合あたりの作者作業 ≒ ライブ記録 40〜60分 + 注釈 → **1.5〜2時間/人、5人で計8〜12時間**
- SLA 感覚: 受領から3日以内に返す。詰まったらそれ自体が需要シグナル

**受け入れ条件 (往復のやり取りを最小化)**:

- **YouTube 限定公開 URL 必須** (ローカルファイルの受け渡しは不採用: 方式 A の思想に反し、
  作者端末に他人の動画を置くことになる)
- 出場4選手の名前 (+利き手)・カメラ手前チーム・セット数と目標点を事前にもらう。
  この項目リストが将来の「依頼フォーム」の仕様になる

**作業の段階制 (コスト制御)**:

1. まずライブ記録 + クイックパス (決着注釈) + 既存データ由来の統計で返す
2. 食いついたテスターにだけ**1セット分のフル注釈**を追加し、ショットレベル統計を見せる
   (統計の説得力には1セットで足りることが多い。全セットは反応を見てから)

**観察項目 (定性)**:

- どのチャートに反応したか / スクショをチームに共有したか
- 「〇〇は見られないのか」という追加要望 → **要望リスト = 将来ダッシュボードのロードマップ**
- 催促なしの2本目送付 (= 代行トラックの第2ゲート)
- 事後の「自分で記録してみるか」への反応 (仮説Bの補助シグナル)

**テスター選別の副次効果**: 参加条件が「自分の試合動画を持っている」なので、
募集自体がターゲット顧客 (試合を撮影する習慣のある層) の選別を兼ねる。

### 3. 最小実装先行 — ゲートの読み替え

ADR-016 の「機能追加への投資は第2ゲート後」は「**需要不明の機能に開発時間を溶かさない**」
ことを守るルールだった。AI 支援開発により実装コストの大半を作者の時間から切り離せる現在、
希少資源は開発時間ではなく**作者の運用時間・少ない伝手テスターの注意・製品の複雑性**に移る。
そこでゲートを次のように読み替える:

> 旧: 第2ゲートまで機能を実装しない
> **新: 検証に必要な最小範囲のみ実装する。本丸投資 (課金 / AI 推論 / PWA / ストア配信 /
> 代行の製品化) は引き続き第2ゲート後**

先行実装するスコープ (検証の試料として必要な最小範囲):

1. **ADR-017 Stage 0**: スキーマ拡張 + アノテーションスタジオ (まず作者が使えれば十分な粗さ)
2. **ショットレベル統計 2〜3枚** (配球ヒートマップ・決定打/エラー傾向)。どれが刺さるかは
   不明なまま作るが、「**捨てる前提の安い探針を複数**」と割り切る (反応を見て磨くのも
   捨てるのも安い)
3. デモ機能・依頼フォーム・進捗管理画面などは**作らない** (§採用しなかった選択肢 D, G)

**作者チームのデータの役割**: テスターに見せるデモではなく (刺さらないため不採用)、
(a) テスターの試合を預かる前にスタジオ・統計画面をデバッグする**社内 QA**、
(b) **教師ラベルの初期蓄積** (入力者が一人 = ラベル一貫性が高く学習データとして理想的)。

### 4. 代行の将来位置づけ

- 検証終了後、代行は**有料メニュー候補**として残す (ADR-013 の分類で従量コスト型 =
  Trial でも絞る側)。初回1試合無料はフックとして機能する
- AI 階段 (ADR-017) の各 Stage は代行の原価を直接下げる: 代行は「人力で動く AI」であり、
  **サービス業 → ソフトウェア化の利益構造** (AI の進捗と共に粗利が改善する) を持つ
- 依頼が実際に複数件続いてから製品化 (依頼フォーム・ステータス管理) を検討する

### 5. 計測・プライバシー

- PostHog の作者除外は user_id 基準 (ADR-016) のため、**作者が他人のグループで代行作業を
  しても計測は汚れない**。代行ユーザーの `stats_viewed` / 2本目送付は少人数につき
  手動把握で足りる (専用イベントは製品化時に検討)
- 代行はグループへの**招待コード参加** (既存機能) で行う。依頼時に「運営が入力のため
  グループに参加する」ことを明示し、作業後に退出するか残るかを事前に合意する
- プライバシーポリシーに代行入力 (運営によるデータ入力・動画閲覧) の記載を追加する
  (feat/legal-pages の延長)

## 理由

### なぜ仮説を分離するか

「統計は刺さるが誰も自分では入力しない」と分かれば答えは AI・代行の強化であり、
「統計自体に興味がない」なら入力 UX を磨いても無意味。混ぜたままでは
ゲート不通過の原因が特定できず、次の一手を誤る。分離は実験計画の交絡除去である。

### なぜ代行を全員向けにしないか

1試合1.5〜2時間の人力作業は標準オンボーディングとして回らない。
一方、検証に必要なのはスケールではなく数人分の定性シグナルなので、
上限5人の研究予算 (計8〜12時間) なら現実的に払える。

### なぜデモではなく本人の試合か

このプロダクトの統計は「自分 (たち) のプレーについての事実」だから刺さる。
他人の試合や架空データでは価値の実感が薄く、仮説Aを測ったことにならない。
匿名化した作者チームのデータでも同じ問題が残る (ユーザー確認 2026-07-13)。

### なぜ最小実装先行がゲート違反でないか

ゲートが守っていたのは資源であってルールの字面ではない。実装コストの構造が変わった以上、
守るべき資源 (運用時間・テスターの注意・複雑性) に合わせて線を引き直すのが目的整合的。
また現在の2統計だけでは検証の試料が薄く偽陰性を生むため、**検証自体がモノ (ショットレベル
統計) を要求する**。手作りレポート (スプレッドシート注釈 + 手動チャート) での代替は
作者負荷が過大で、機能として実装する方が安い構造になっている (選択肢 B)。

### データエンジニアのアナロジー

- **代行 = 手動バックフィル**: パイプライン (AI) を作る前に、人手で同じ出力を作って
  下流 (統計の需要) を先に検証する。バックフィル作業自体がパイプライン仕様の草案になる
- **仮説A/Bの分離 = 交絡の除去**: 1つのメトリクスに2つの要因が乗った実験を分割する
- **探針統計 = アドホッククエリ**: まず使い捨てクエリで反応を見て、当たったものだけ
  ダッシュボード化 (製品コード化) する
- **テスター選別 = サンプリングバイアスの活用**: 「動画を持っている人」という参加条件が
  そのまま ICP (ideal customer profile) のフィルタとして働く

## 影響

### 次のアクション

1. ADR-017 §9 (実装時期) を本 ADR に合わせて改訂 (同時に実施)
2. `docs/spec/shot-annotation/` 要件定義 → スキーマ拡張 + スタジオ + ショットレベル統計の実装
3. 作者チームの試合でドッグフーディング (QA + ラベル蓄積)
4. プライバシーポリシーへ代行入力の記載追加
5. テスターのリクルート (伝手で「試合動画を持っている人」3〜5人)

### まだやらないこと

- 課金 (Stripe)・AI 推論 (Stage 1 以降)・PWA・ストア配信 (第2ゲート後、変更なし)
- 代行の製品化 (依頼フォーム・ステータス管理・通知) — 依頼が複数件続いてから
- デモ統計機能 (サンプルグループ・LP 埋め込み)
- 定量リテンション閾値の設計 (ADR-016 のまま)

## 採用しなかった選択肢

| 案 | 却下理由 |
|---|---|
| A. 現行2統計のみで需要テスト | 「統計」でなく「この2枚」の不発を需要なしと誤読する偽陰性リスク |
| B. 手作りレポート (スプレッドシート注釈 + 手動チャート) で統計候補をテスト | 作者負荷が過大。AI 支援開発では機能として実装する方が安い構造 |
| C. 全ユーザーの初戦を代行する標準オンボーディング | 1試合1.5〜2時間の人力は回らない。代行は研究装置・将来の有料メニューに限定 |
| D. デモ統計 (作者チームの実データ / 匿名化 / 架空データ) | 統計は本人の試合だから刺さる。他人・架空のデータでは仮説Aを測れない。架空は説得力も欠く |
| E. 同一テスターで仮説A→Bを連続検証 | 機能を知った状態では入力 UX テストが汚染される。B は別テスターで実施 |
| F. ゲート字面の厳守 (実装を第2ゲート後まで凍結) | 検証の試料 (ショットレベル統計) がモノを要求する。守るべき資源の再定義で目的整合を取る |
| G. 依頼フォーム等の代行製品化を先行 | 依頼ゼロ件の段階で作るのは投機。口頭 + 既存機能 (招待コード) で運用検証が先 |
