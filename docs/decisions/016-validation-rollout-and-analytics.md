# ADR-016: 少人数フェーズの検証ロールアウトと計測基盤 (PostHog)

## ステータス
Accepted (2026-07-01)

## 背景

[[project_validation_phase]] (ADR-015) で検証を4段階
(①ドッグフーディング → ②ユーザビリティテスト → ③クローズドβ → ④需要・収益検証)
に定め、②の実施準備 (公開LP・ブランド・usability-test-01 テンプレ) まで整えた。
ADR-015 は「analytics ツールの選定・導入は③クローズドβの前までに決める」を宿題として残していた。

本 ADR はその宿題に答えつつ、**現実の制約 (伝手が少ない) に合わせて③④のロールアウト設計を簡略化**し、
**合格ライン (ゲート) と計測基盤を確定**する。

### 解決したい問題

1. **③クローズドβ と ④一般公開を"別々の客層"として分ける実益が薄い**。
   ニッチなチーム向けプロダクトは signup を開けても知らない人が自動流入するわけではなく、
   初期ユーザーは結局あなたの伝手から入る。両者の客層は事実上同じ。
2. 一方で計測は入れたい。理由は (a) **未知のユーザーが現れたか**を捉えたい、
   (b) **伝手の人が実際にどんな操作をしているか**を知りたい (推測でなく事実で UI を直すため)。
3. 「継続利用者がいるか」という需要シグナルを、**何をもって合格とするか (ゲート)** が未定義だった。

## 決定

### 1. ③④を統合し「一本道ロールアウト」にする (分けるのは客層でなく作る順番)

```
② → 伝手に配る一括ロールアウト → 🚦第1ゲート → 🚦第2ゲート → 課金・機能
```

- 「一般公開」は**新規需要を連れてくるイベントではなく、単に signup を開放し課金を載せた"状態"**と捉える。
- ③と④を客層で分けるのはやめ、**伝手＋たまたま来た未知ユーザーを同じ一本道**で扱う。
- ただし**「作る順番」は崩さない**: 課金・機能追加への投資は後述の第2ゲート通過後に限る。
  これは客層の分離ではなく投資判断の分離であり、伝手が少なくても意味が消えない。

### 2. 合格ラインは2段ゲート (アクティベーション → リテンション)

| ゲート | 定義 | 何を証明するか | 何を解禁するか |
|---|---|---|---|
| **第1: アクティベーション** | 誰かが**自前で** (作者が横で手伝わず) 一度、**試合記録 → 統計閲覧**まで完走した | UI・コアループが他人に通用する (②の卒業) | ロールアウト継続・UI 修正の打ち切り判断 |
| **第2: リテンション** | 催促なしに**別日に再度**試合を記録した | 需要がある (「使えた」でなく「また使いたい」) | **課金導線・機能追加への投資** |

- 第1は「使えたか」、第2は「欲しがってるか」。混同すると
  「使えるUIを作っただけ」で需要ありと誤判定するため、**明確に2段に分ける**。
- 両ゲート共通の必須条件は **「自前で = 作者が介助しない」**。少人数なので誰が自発かは把握でき、
  セッションリプレイでも裏取りできる。

#### リテンションの期間は固定窓を設けない

第2ゲートの「別日に再訪」に **Dn / N日コホートのような固定閾値は設けない**。
チームごとに練習頻度が異なり、n が小さくコホート閾値は統計的に無意味なため、
**「催促なしに自発的にもう一度やったか」という質的な有無**で判定する
(厳密な定量リテンション計測は④で n が増えてから)。

### 3. 計測ツールは PostHog 単体で確定

ファネル・リテンション・**セッションリプレイ (実際の操作の録画再生)**・流入
(リファラ / UTM / ランディングページ / 地域) を **1つのツールで**賄う。
HogQL で SQL 風に自分でクエリできる点もデータエンジニアの運用に合う。

- Nuxt へは **CSR プラグインで `posthog-js`** を差す ([[project_video_playback_spec]] 系の
  CSR 境界方針 ADR-010 に整合)。
- **作者自身の user_id / ドッグフーディンググループは計測から除外**する
  (少人数だと自分の操作でデータが濁るため)。
- GA4 は不採用ではなく**保留**。④で n が増え流入解析の粒度が必要になったら補助として足す。

### 4. 最小 instrument イベント

合格ライン (§2) の計測に必要な最小セットだけをまず仕込む:

| イベント | 意味 | 用途 |
|---|---|---|
| `match_recorded` | 試合の記録を保存した | 第1ゲート・第2ゲート両方の中心 |
| `stats_viewed` | 統計ダッシュボードを開いた | 第1ゲート (記録→統計のファネル) |
| `identify` (user/group) | 誰の操作か紐付け | 自発性判定・作者除外・リテンション集計 |

- **`match_recorded` → `stats_viewed` のファネル**が第1ゲートの計測。
- **同一 user の別日 `match_recorded`** の有無が第2ゲートの計測。

### 5. プライバシー対応 (セッションリプレイの前提)

セッションリプレイは個人の操作画面を録画するため、**プライバシーポリシーに analytics /
リプレイ利用を明記**する (現在 `feat/legal-pages` で整備中の法務ページに追記)。
選手名などの表示情報が画面に映るため、PostHog のマスキング設定を確認し、
必要な入力・要素はマスクする。

## 理由

### なぜ③④を統合するか

③④の分離は ADR-015 では「UI が荒い状態で公開すると需要シグナルが濁る」ことを避ける目的だった。
だがその本質は**客層の分離ではなく作る順番 (リテンションを見てから課金・機能に投資する)**。
伝手が少ないと客層としての③④は実質同一集団になるため、**客層の分離は畳み、投資順のゲートだけ残す**
のが制約に合う。

### なぜ2段ゲートにするか

「一度使えた (アクティベーション)」と「また使いたい (リテンション)」は別物。
前者は UI の合格、後者は需要の合格。1つのゲートにまとめると、
「他人が使えるUIを作った」時点で需要ありと誤認し、需要ゼロのまま課金・機能に時間を溶かすリスクがある。
ADR-015 の「虚栄の指標でなくアクティベーション＆リテンション」を、投資判断に直結する形へ具体化したもの。

### なぜ PostHog か

ユーザの目的 (b)「実際にどんな操作をしているか」は集計値では取れず、**セッションリプレイ**が要る。
かつ合格ラインは本質的に**ファネル (記録→統計) とリテンション (再訪コホート)** であり、
PostHog はこの3つ (リプレイ・ファネル・リテンション) と流入計測を1ツールで持ち、
HogQL で直接クエリできる。Clarity+Vercel はリプレイは強いがファネル/リテンションを作れず
**第2ゲートを測れない**。GA4 はリプレイが無く、イベント設計が煩雑で n が小さいと閾値抑制で濁る。

### なぜリテンション期間を固定しないか

固定窓 (例: 7日リテンション) はコホートに十分な n がある前提の道具。
本フェーズは n が数人で、練習頻度もチームで異なる。固定窓を切ると
「週1練習のチームが D7 に来なかった＝離脱」のような誤判定を生む。
**自発的再訪の有無**という粗いが正しいシグナルで足り、定量化は④に回す。

### データエンジニアのアナロジー

- **ファネル** = イベントテーブルを step ごとに条件カウントし、脱落率を段で見る `SELECT`。
- **リテンション** = 登録週でコホートを切り、以降週のアクティブ数を数える `GROUP BY` 三角表。
- **セッションリプレイ** = 集計 (メトリクス) では落ちる「実際のクエリ実行ログ / 操作トレース」を
  そのまま再生するもの。**スキーマの分かりにくさは利用者の手元でしか露見しない** (ADR-015) を
  直接観察する道具。
- **作者除外** = 自分のテスト実行を本番メトリクスから除く (dogfooding トラフィックのフィルタ)。

## 影響

### 次のアクション

1. `posthog-js` を CSR プラグインで導入し、`match_recorded` / `stats_viewed` / `identify` を instrument。
   作者 user_id / DF グループを除外。
2. プライバシーポリシー (`feat/legal-pages`) に analytics・セッションリプレイ利用を追記、マスキング確認。
3. ②usability-test-01 は並行して進める (analytics は②には不要)。
4. 公開前ブロッカーのモバイルUI再設計 (特に match-recording) を別途対応。

### まだやらないこと

- GA4 導入 (④で n が増え流入解析が必要になったら)。
- 課金 (Stripe) 実装 (第2ゲート通過後。ADR-013 のマトリクスに従う)。
- 定量リテンション (Dn コホート) の閾値設計 (④)。
- 重いイベント設計 (最小3イベントで始め、必要に応じて足す)。

## 採用しなかった選択肢

| 案 | 却下理由 |
|---|---|
| A. ③クローズドβと④一般公開を客層で分け続ける | 伝手が少なく初期客層が実質同一。分離の実益が薄く、投資順のゲートだけ残せば足りる |
| B. 計測せず自前 SQL (Supabase 直クエリ) のみ | 「実際の操作」はリプレイでしか取れず、未知ユーザーの流入元切り分けも弱い。ユーザ目的 (a)(b) を満たせない |
| C. Clarity + Vercel Analytics | リプレイ・流入は取れるがファネル/リテンションを作れず、**第2ゲート (需要判定) を測れない** |
| D. GA4 を主軸 | セッションリプレイ無し。イベント設計が煩雑で、n が小さいと閾値抑制でデータが濁る。本フェーズの目的に不向き |
| E. 1つのゲート (アクティベーションのみ) で課金・機能へ進む | 「使えた」を「欲しがってる」と誤認し、需要ゼロで投機するリスク |
| F. リテンションを固定窓 (D7 等) で判定 | n が小さく練習頻度もチーム依存。固定窓は誤判定を生む。自発再訪の有無で足りる |
| G. 課金を先に実装しておく | リテンション未検証で Stripe を作るのは典型的な投機。第2ゲート後に限る |
