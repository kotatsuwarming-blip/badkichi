## ヒアリング目的

rule-engine の要件定義書をもとに、アーキテクチャ・ファイル配置・関数設計などの技術設計上の不明点を明確化するためのヒアリングを実施しました。

## 質問と回答

### Q1: rule-engine のファイル配置はどこが良い？

**質問日時**: 2026-04-10
**カテゴリ**: アーキテクチャ
**背景**: Nuxt 3 ではファイルの配置場所によって auto-import の挙動が変わる。rule-engine はフレームワーク非依存だが、使うのは Nuxt アプリの中。

**初回回答**: 「全然分かりません。もう少し各選択肢を詳しく知りたい」
**補足回答**: 「そもそもそれぞれの機能がどのように呼び出されるのか、依存関係や技術スタックやアーキテクチャの全体像が分からないため、判断できません」
**最終回答**（全体アーキテクチャ説明後）: 拡張性の確認を経て `app/utils/rule-engine/` で確定

**対応**: badkichi 全体のレイヤードアーキテクチャ（Presentation → Use Case → Domain → Infrastructure）を図示して説明。rule-engine が Domain Layer に位置し、外側の変更（認証方式・課金・広告）に影響されないことを確認。

**信頼性への影響**:
- ディレクトリ構造が 🔵 で確定
- アーキテクチャパターン（レイヤードアーキテクチャ）が 🔵 で確定

---

### Q2: 計算単位はセット単位で良い？

**質問日時**: 2026-04-10
**カテゴリ**: データモデル
**背景**: rule-engine の関数が受け取るデータの粒度を決める必要がある。

**初回回答**: 「あまり意味がわかりません」
**対応**: 試合 = セットの集まり、セット = ラリーの集まり、という構造を説明。セット単位のメリット（関数が小さい、録画中はセット単位でデータが増える）を説明。
**最終回答**: セット単位で良い

**信頼性への影響**:
- 関数シグネチャのスコープが 🔵 で確定
- `computeRallyStates` 等が1セット分のデータを受け取る設計が確定

---

### Q3: composable の具体的なイメージは？ バックエンドサーバーは今後必要？

**質問日時**: 2026-04-10
**カテゴリ**: アーキテクチャ
**背景**: ユーザーが Web 開発初学者のため、composable（状態管理）の役割と、BaaS（Supabase）でバックエンドサーバーなしの構成が将来拡張に耐えるか確認。

**回答**: 「今後、Googleアカウント連携や広告入れたりとか課金システム入れたりしたい。それに耐えれますか？」

**対応**: 
- composable の具体的なコード例（TypeScript + Python 対比）を提示
- Googleアカウント連携 → Supabase Auth の設定変更のみ
- 広告 → Presentation Layer の変更のみ
- 課金 → Supabase Edge Functions + 外部サービス連携
- いずれも rule-engine（Domain Layer）には影響なしと説明

**信頼性への影響**:
- レイヤードアーキテクチャの採用が 🔵 で確定
- 拡張性の担保が確認できた

## ヒアリング結果サマリー

### 確認できた事項
- ファイル配置: `app/utils/rule-engine/`
- 計算単位: セット単位
- アーキテクチャ: レイヤードアーキテクチャ（Domain Layer として配置）
- 拡張性: Google認証・広告・課金に対応可能（rule-engine は影響なし）

### 設計方針の決定事項
- composable が Use Case Layer としてオーケストレーションを担当
- Vue の `computed` で rule-engine の純関数を自動再計算
- Supabase への保存は composable 側の責務

### 残課題
- composable の詳細設計は match-recording の設計フェーズで実施
- テストファイルの配置パターン（`__tests__/` vs 別ディレクトリ）は実装時に決定
