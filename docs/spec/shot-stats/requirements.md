# shot-stats 要件定義書

**作成日**: 2026-08-03
**作業規模**: フル機能開発
**位置づけ**: ADR-018 §3 先行実装スコープの後半（ショットレベル統計）。テスター限定代行（仮説A = 統計需要の検証）の試料。
**依存単位**: shot-annotation（注釈データの供給源, PR #50）, stats-dashboard（表示画面・集計 RPC/View の前例・グローバルフィルタ）, rule-engine（denormalize 済み導出値）, video-playback（動画ジャンプ）

## 概要

アノテーションスタジオ（`/annotate`）で付与されたショット注釈（球種・打者・打点・フォア/バック）とラリー決着注釈（end_reason・落下点）を消費し、既存 stats 画面（試合単位 / Group 横断）に**ショットレベル統計の探針 5 枚**を追加する。あわせて、注釈を必要とせずライブ記録データのみで算出できる**ラリー展開統計 3 枚**（局面別得点率・展開スピード・セット推移）を追加する。

本単位は stats-dashboard と同じく**読み取り専用**であり、スキーマ変更・録画系テーブルへの書き込みを一切行わない。集計は読み取り専用 RPC / View（additive migration）で行う。

**ADR-018 からの意図的な逸脱**: ADR-018 は探針を「2〜3枚・捨てる前提」としていたが、ヒアリング（2026-08-03）で**探針 5 枚に枠を拡大し、全て同列で実装する**ことを決定した。「捨てる前提の安い試料」という位置づけ自体は維持する。🔵 *ヒアリング2026-08-03（5枚同列で枠を拡大）*

## スコープ

### 含む

**探針（注釈依存・5 枚）** — ヒアリング2026-08-03 で選定:

- **A: 決着分析** — 得点/失点の内訳（エース/相手ミス/自ミス/被エース）+ 決定打球種ランキング + 決着落下点の 3×3 ゾーン表示。クイックパス注釈のみで成立（最速で埋まる探針）
- **C: サーブ種別分析** — serve 3 種 × 当該ラリーの得点率
- **D: 球種構成比・成果** — 選手別の球種構成比 + 球種ごとの決定打率⇄ミス率
- **F: 配球ヒートマップ** — 打点（hit_x/y）の 3×3 コート図ヒートマップ + 選手・球種フィルタ
- **G: フォア/バック分析** — 球種別 F/B 比率 + F/B 別の成果

**ラリー展開統計（注釈不要・ライブ記録のみ・3 枚）** — ヒアリング2026-08-03 で追加:

- **J: 局面別得点率** — セットを序盤/中盤/終盤に分割し、接戦局面を強調した選手/ペア別得点率
- **K: 展開スピード分析** — ラリーのテンポ（連続値）を得点ラリー/失点ラリーで分布比較。measure は「ラリー平均テンポ」⇄「終盤テンポ」の切替トグル
- **L: セット推移チャート** — 得点差の階段折れ線（スコアワーム）+ 連取/連失ハイライト + ラリータップで動画ジャンプ

**共通**:

- 既存 stats 画面（試合単位 `/groups/[id]/matches/[matchId]/stats` / Group 横断 `/groups/[id]/stats`）への追加タブ/セクションとして表示
- フィルタ軸: 選手（打者）/ 球種 / セット / hand（既存グローバルフィルタ＝期間・試合・選手/ペアはそのまま併用）
- 注釈率バッジ + 全チャートへの母数併記（n / N）
- 読み取り専用の集計 RPC / View（additive migration）

### 含まない

- 探針 H（3打目パターン）・ラリー間時間分析 → 見送り（ヒアリング2026-08-03。note.md に将来候補として記録）
- ミラーの切替トグル（絶対座標表示）→ 選手視点固定のみ（ヒアリング2026-08-03）
- 注釈率による試合の絞り込みフィルタ → v1 はバッジ + 母数併記のみ
- 基本/詳細のグルーピング・課金ゲート → 今は全機能基本扱い。ADR-019 の課金設計時にまとめて検討（ヒアリング2026-07-26）
- 精密なテンポ分析（annotated_timestamp_ms ベース）→ K は押下時刻ベースの近似で先行し、精密版は注釈時刻が揃う将来フェーズ（PRD §3.2 との整合は下記 REQ-107 参照）
- 注釈の入力・修正（shot-annotation の責務）、スキーマ変更、録画系テーブルへの書き込み

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: ADR・確定スキーマ・既存実装・ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: 上記から妥当な推測による要件
- 🔴 **赤信号**: 出典のない推測による要件

### 通常要件

**表示場所・共通**

- REQ-001: システムは、ショットレベル統計とラリー展開統計を、既存の試合単位 stats 画面および Group 横断 stats 画面への**追加タブ/セクション**として表示しなければならない 🔵 *ヒアリング2026-07-26（既存 stats 画面に追加タブ/セクション）*
- REQ-002: システムは、全チャートに母数（注釈済み n / 対象全体 N）を併記しなければならない 🔵 *note.md §3-6 + stats-dashboard NFR-201 + ヒアリング2026-08-03*
- REQ-003: システムは、試合・チャートヘッダーに注釈率バッジ（例: 種別 72%）を表示しなければならない 🔵 *ヒアリング2026-08-03（バッジ + 母数併記）*
- REQ-004: システムは、ショットレベル統計のフィルタ軸として選手（打者 `hit_player_id`）・球種（`shot_type`）・セット・hand を提供しなければならない。期間・試合・選手/ペアの既存グローバルフィルタ（stats-dashboard REQ-013）はそのまま併用できること 🔵 *ヒアリング2026-08-03（フィルタ4軸）*

**探針 A: 決着分析**

- REQ-005: システムは、選手/ペア別に得点・失点の内訳を積み上げ表示しなければならない。内訳は end_reason と決定打から導出し、得点側 =「エースで獲得 / 相手ミスで獲得」、失点側 =「被エース / 自ミス」に分類する。※実装済みスキーマでは end_reason は 6 値（`in`/`out` は `floor` に統合済み）であり、エース = body または floor×最終打者が勝者、ミス = net/not_over/service_fault または floor×最終打者が敗者、として導出する（`deriveInOut` と同一規則） 🔵 *note.md §4-② + ヒアリング2026-08-03（A 採用）+ 実装調査2026-08-03（floor 統合）*
- REQ-006: システムは、決定打の球種ランキング（得点に繋がった決定打の shot_type 上位）を表示しなければならない 🔵 *note.md §4-②（決定打 shot_type）+ ヒアリング2026-08-03*
- REQ-007: システムは、決着落下点（`land_x/land_y`）を 3×3 ゾーンのコート図で得点/失点別に表示しなければならない 🔵 *ヒアリング2026-07-26（3×3）+ note.md §4-②*

**探針 C: サーブ種別分析**

- REQ-008: システムは、サーバー別・サーブ種別（serve_short / serve_long / serve_drive = 1打目の shot_type）ごとに、当該ラリーの得点率を棒グラフで表示しなければならない。サービスポジション（右/左）での絞り込みは既存 REQ-014（stats-dashboard）と同形式とする 🔵 *note.md §4-④ + ヒアリング2026-08-03（C 採用）*

**探針 D: 球種構成比・成果**

- REQ-009: システムは、選手別の球種構成比（shot_type の割合。実装済みスキーマは 18 種 + `unknown` の 19 値。2026-08-05 に lob → lob_high/lob_low、clear → clear_high/clear_driven へ分割済み）を表示しなければならない。分析対象の打者は Group 内の任意の選手（対戦相手側の選手を含む）を選択できること 🔵 *note.md §4-③ + ヒアリング2026-08-03（D 採用・相手のショットも分析したい）*
- REQ-010: システムは、球種ごとの成果として **ミス率**（その球種のミス決着数 ÷ その球種の総打数）と **決定率**（決定打数 ÷ 総打数）を表示し、あわせて**球種の使用割合（構成比）と球種別得点率（その球種を打ったラリーの得点率）の関係**を対比できる表示を提供しなければならない（対比の見せ方＝散布図/並列棒等は kairo-design で確定） 🔵 *ヒアリング2026-08-03（分母・指標をユーザ指定で確定）*

**探針 F: 配球ヒートマップ**

- REQ-011: システムは、打点（`hit_x/hit_y`）を 3×3 ゾーンのコート図ヒートマップで表示し、選手・球種で絞り込めなければならない 🔵 *note.md §4-① + ヒアリング2026-07-26（3×3）+ 2026-08-03（F 採用）*

**探針 G: フォア/バック分析**

- REQ-012: システムは、球種別のフォア/バック比率と、F/B 別の成果（決定打率・ミス率）を表示しなければならない 🔵 *ヒアリング2026-08-03（G 採用）+ hand 列（ADR-017）*

**ラリー展開統計 J: 局面別得点率**

- REQ-013: システムは、セット内の局面（序盤/中盤/終盤）別の選手/ペア得点率を表示し、接戦局面（終盤かつ僅差）を強調表示しなければならない 🔵 *ヒアリング2026-08-03（J 採用。クラッチ力と序盤/中盤/終盤を1枚に統合）*
- REQ-014: 局面の区分は、リード側の得点で序盤（0〜7）/ 中盤（8〜14）/ 終盤（15〜）の 3 分割とし、接戦は「終盤かつ 2 点差以内」（20-20 以降の延長を含む）とする 🔵 *ヒアリング2026-08-03（3分割で確定）*

**ラリー展開統計 K: 展開スピード分析**

- REQ-015: システムは、ラリーのテンポを**連続値**として算出し、得点ラリーと失点ラリーの分布を重ねて比較表示しなければならない（ビン分けの棒グラフにはしない） 🔵 *ヒアリング2026-08-03（3段階に分けなくてよく連続値でいい）*
- REQ-016: テンポの measure は「**ラリー平均テンポ**（= (ショット数 − 1) ÷ ラリー時間）」と「**終盤テンポ**（= ラリー最後の 3 打が作る 2 つの間隔の平均（秒）。決まる直前の展開の速さ）」の 2 種とし、切替トグルで選べなければならない 🔵 *ヒアリング2026-08-03（両方・切替トグル。「ラリーが終わる直前の展開の速さ」はユーザ発案。間隔定義は 2026-08-03 確定）*

**ラリー展開統計 L: セット推移チャート**

- REQ-017: システムは、試合単位画面でセットごとに、ラリー順 × 得点差の階段折れ線（取ったら +1 / 取られたら −1）を表示しなければならない。視点（どちらを上にするか）は選択中の選手/ペアのチームに自動で合わせる 🔵 *ヒアリング2026-08-03（L 採用。説明済みの仕様を承認）*
- REQ-018: システムは、3 連続以上の連取/連失区間を色帯でハイライトし、最大連取/最大連失を注記し、11 点インターバル位置に目印を表示しなければならない 🔵 *ヒアリング2026-08-03（L 詳細説明を承認）*
- REQ-019: システムは、L 上のラリーをタップした際、その時点のスコアを表示し、該当ラリーの動画へジャンプできなければならない（既存のラリー一覧 → 動画ジャンプ REQ-007/011（stats-dashboard）と同じ仕組み。ラリー一覧テーブルとも連動選択） 🔵 *ヒアリング2026-08-03（L 詳細説明を承認）+ stats-dashboard REQ-007/REQ-011*

### 条件付き要件

- REQ-101: 得点率・内訳を算出する場合、システムはレット（`is_let=true`）および未確定ラリー（`point_winner IS NULL` または `is_point_confirmed=false`）を母数・分子の双方から除外しなければならない。**レットラリーは注釈が付かないだけで行は存在するため、`is_let=false` フィルタを必ず掛ける** 🔵 *note.md §3-2 + stats-dashboard REQ-101*
- REQ-102: `hand` が null のショットは「未判定」として扱い、フォアと解釈してはならない。G の F/B 集計では母数から除外し、除外数を母数併記に反映する 🔵 *note.md §3-3 + shot-annotation REQ-104*
- REQ-103: out の細分（side/back/both）を集計する場合、システムは `land_x/land_y` から導出し、座標が null のときのみ `out_direction` を用いなければならない。導出規則は `app/utils/annotation/court-coords.ts` の `deriveOutDirection` と同一とする 🔵 *note.md §3-4*
- REQ-104: 決定打を特定する場合、システムは `app/utils/annotation/derive.ts` の `decisiveShotIndex` と同一規則（body: 最終ショット、net/not_over: その 1 つ前、floor: 最終打者が勝者なら最終・敗者ならその 1 つ前、service_fault/unknown: なし。最終打者が未注釈の floor は決定打なし）を用いなければならない 🔵 *note.md §3-5 + 実装調査2026-08-03（実シグネチャ準拠）*
- REQ-105: 座標（打点・落下点）を選手視点で表示する場合、システムは保存された絶対座標を集計側でミラーしなければならない（打者/対象がチーム B なら x→1−x, y→1−y）。**選手視点固定**とし、絶対座標表示への切替は提供しない 🔵 *note.md §3-1 + ヒアリング2026-08-03（選手視点固定）*
- REQ-106: K のテンポ算出は、**ラリー内の全ショットに打点時刻があるラリーのみ**を対象としなければならない（1 本でも時刻欠損があれば対象外。部分欠損ラリーは得点率との関連表示のノイズになるため）。加えてショット 2 本以上（終盤テンポは 3 本以上）を要し、対象外ラリー数を母数併記に反映すること 🔵 *ヒアリング2026-08-03（全ショット時刻ありの条件はユーザ指定）*
- REQ-107: K の時刻は記録時のボタン押下時刻（`video_timestamp_ms`）ベースの**近似値**であることを UI 上に明示しなければならない。PRD §3.2 はテンポ分析を将来フェーズとしているが、近似版を先行実装する（精密版は `annotated_timestamp_ms` が揃う将来フェーズ） 🔵 *ヒアリング2026-08-03（K 採用）。PRD からの逸脱として明記*
- REQ-108: 決定打の shot_type が未注釈（null）の場合、システムは決定打球種ランキング・球種別成果では「未注釈」として区別し、内訳（REQ-005）には含めなければならない 🔵 *ヒアリング2026-08-03（この規則で確定）*

### 状態要件

- REQ-201: 集計対象が 0 件（注釈ゼロ・全件除外等）の状態の場合、システムは空状態（「データなし」「未注釈」等）を表示し、チャートをエラーにしてはならない 🔵 *stats-dashboard REQ-103/REQ-201 踏襲*
- REQ-202: 母数 0 の選手・区分の得点率は「-」等の未算出表示としなければならない 🔵 *stats-dashboard REQ-202 踏襲*
- REQ-203: 記録途中のセットの場合、L は記録済みラリーまでの推移を描画しなければならない 🔵 *ヒアリング2026-08-03（L 詳細説明を承認）*

### オプション要件

- REQ-301: システムは、本機能群を将来「基本 / 詳細」にグルーピングし課金ゲート（ADR-013/019）を掛けられる構造としてよい（**今は全機能を基本扱いとし、グルーピングもゲートも設けない**） 🔵 *ヒアリング2026-07-26（今は全部基本扱い）+ stats-dashboard REQ-301*
- REQ-302: ゾーン粒度（3×3）は集計側のパラメータとして変更可能な実装としてよい（保存は座標のままのため後から変更できる） 🔵 *ヒアリング2026-07-26（保存は座標のまま・後から変更可を前提に 3×3 を選択）*

### 制約要件

- REQ-401: システムは読み取り専用であり、録画系・注釈系テーブルへの INSERT / UPDATE / DELETE を行ってはならない 🔵 *stats-dashboard REQ-401 + note.md §2（読み取りのみ）*
- REQ-402: システムは既存テーブルのスキーマ変更を行ってはならず、集計は**読み取り専用 RPC / View の追加（additive migration）**で実現しなければならない。RPC / View は `STABLE`・RLS 維持（`security_invoker` / `is_member_of()`）とし、適用は CI 経由 `db:push` とする 🔵 *note.md §2 + stats-dashboard REQ-402/REQ-408*
- REQ-403: システムは RLS に従い、他 Group のデータを集計してはならない 🔵 *stats-dashboard REQ-403*
- REQ-404: システムは CSR 限定で動作し、Supabase クライアント経由でデータを取得しなければならない 🔵 *ADR-010 + stats-dashboard REQ-404*
- REQ-405: システムはチャート描画に vue-echarts を用いなければならない 🔵 *PRD §6 + stats-dashboard REQ-406*
- REQ-406: 集計 SQL 内で out 細分・決定打を再実装する場合、`deriveOutDirection` / `decisiveShotIndex` との規則一致を integration テストで検証しなければならない 🔵 *note.md §3-4/§3-5（同一規則にする）+ ADR-012 テスト戦略*
- REQ-407: クライアント側の派生計算・整形ロジックは composable / util として分離し単体テスト可能にし、RPC / View は integration テスト（CI 専用）で検証しなければならない 🔵 *stats-dashboard REQ-407 踏襲*

## 非機能要件

### パフォーマンス

- NFR-001: 統計チャートの初期表示は 3 秒以内でなければならない 🔵 *PRD §性能要件 + stats-dashboard NFR-001*
- NFR-002: 集計は読み取り専用 RPC / View（Postgres 側）で算出し、クライアントは取得・整形・可視化に専念する 🔵 *stats-dashboard NFR-002 踏襲*
