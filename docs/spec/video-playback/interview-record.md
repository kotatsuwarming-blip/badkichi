### Q2: ローカル動画のページ再読み込み後の復元方式

**質問日時**: 2026-06-01
**カテゴリ**: 未定義部分詳細化（UX 波及・重要決定）
**背景**: ブラウザのセキュリティ制約により、ローカルファイルのオブジェクト URL はセッションを跨いで永続化できない。`matches.video_source_url` に保存できるのはファイル名/パス文字列のみで、再読み込み後に自動再アクセスは不可能（YouTube は URL だけで復元可能）。記録途中で離脱・再開する US-01 のフローに直結するため確認が必要だった。

**初回提示の誤り**: 当初 Claude は選択肢として「再選択 / YouTube 推奨 / IndexedDB バイト保存」を提示したが、ユーザーから「動画再生中にブラウザ更新したら再指定が必要という理解で合っているか。そのような挙動のアプリは見たことがない」と指摘を受けた。これを受けて Claude は以下を訂正・補足した:
- 事実として素朴な `<input type=file>` 実装では再選択が必要（ブラウザのローカルファイルセキュリティ制約が原因）。
- 更新後も復元できるアプリは、(1) そもそも URL 再生（YouTube/クラウド）、(2) File System Access API でハンドルを IndexedDB 永続化（Chromium 限定）、(3) ファイル実体を IndexedDB/OPFS にコピー（GB 級二重保存で重い）のいずれかを使っている。
- 比較表を提示し、A（再選択・最小）/ B（File System Access API・Chromium 優先 + フォールバック）/ YouTube 一本化検討、の 3 案で再質問した。

**回答**: **方式 A（再選択・最小）** を採用。

**信頼性への影響**: REQ-103・REQ-301・NFR-101 が 🔵（ユーザ決定）として確定。

### 黄信号潰しの設計決定（Claude 主導で 🔵 化、2026-06-01）

Q3/Q4 以外の 🟡 は、要件レベルの契約を明文化する設計決定として 🔵 に確定した:

| 要件 | 確定内容 |
|---|---|
| REQ-007 | duration(ms) + 統一再生状態（unstarted/buffering/playing/paused/ended）を取得。UI 必須要件 |
| REQ-104 / EDGE-101 | シーク範囲外は [0, duration] にクランプ（負値→0、超過→duration） |
| REQ-201 / EDGE-102 | 未ロード時の契約: 現在時刻取得は `null`、シークは no-op。NaN/負値を返さない |
| NFR-002 | 操作の即時反映は NFR-001 に紐付く確定 UX 要件 |
| EDGE-002 | 無効 YouTube URL は再生前に検証してエラー提示 |
| EDGE-004 | バッファ停滞は REQ-007 の `buffering` 状態で提示、他操作を阻害しない |

**結果**: spec 内の機能/非機能/Edge 要件の 🟡 はゼロに。受け入れ基準は 🔵 100%。

## ヒアリング結果サマリー

### 確認できた事項
- ローカル動画の更新後復元は方式 A（再選択）。長時間記録は YouTube 推奨誘導。
- video-playback の責務は「単一ソースの連続再生制御 + ms 単位の現在時刻取得 / シーク」に限定。
- 録画断絶・データ記録は match-recording の責務（スコープ外）。

### 追加/変更要件
- REQ-103（再選択促し）、REQ-301（YouTube 推奨誘導）、NFR-101（ローカル参照のセキュリティ制約）を追加。

### 残課題
- composable の具体的なインターフェース（メソッド名・戻り値・コンポーネント分離）は kairo-design で確定（ADR-007 準拠）。
- YouTube IFrame API の秒 → ms 変換の丸め仕様は設計で詳細化。

### 信頼性レベル分布

**ヒアリング前（PRD/設計のみ）**: 🔵 多数 / 🟡 数件 / 🔴 ローカル復元方式が未確定（実質 🟡〜🔴）

**ヒアリング後（黄信号潰し完了 2026-06-01）**: 機能/非機能/Edge 要件の 🟡 はゼロ。受け入れ基準は 🔵 100%。残る判断は kairo-design に委ねる実装詳細（下記 残課題）のみで、要件レベルの曖昧さはない。
