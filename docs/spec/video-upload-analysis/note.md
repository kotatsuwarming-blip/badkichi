## 1. 改訂の履歴

- **2026-11-01 (ユーザー決定)**: サーブ候補の生成を運営者の手元だけでなく利用者自身が使えるようにする。動画をアプリにアップロードし、サーバーで解析する。再生は YouTube に任せ、ローカルに動画を置かせない。候補の時刻と YouTube のずれは長さの比較と最初の候補での手合わせで扱う (serve-start-assist REQ-113)。
- **2026-11-23 (VUA-0、ADR-020 との整合)**: 同意の 4 点 (アップロード・解析・削除・学習利用、学習利用は既定オフ)。原本は解析後削除が既定、学習利用はオプトイン保管。ジョブの出力にショット層の下書き JSON を追加し、ai-draft-loop の取り込み経路 (#102) と共有。Storage 直接再生 (旧 REQ-204 / serve-start-assist REQ-304) は不採用。billing 依存は課金保留に合わせて条件付き (#122)。旧キューの VID-0〜4 と BL-031 は本機能群に統合 (#100 / #101 / #103〜#106 は削除候補)。
- **2026-11-24 (作者指摘 3 点)**:
  1. 入力が完了するまで原本を消したくない。持ち続けると費用。テスト用のデータは消えてはいけない。→ 「解析後に削除」を **保持の理由 (hold)** に置き換え (方針 3、video-upload note §3)。
  2. 要件が大きすぎる。アップロードして解析に使える状態にするまでと、解析とを別の機能単位に。→ **video-upload** と **video-analysis-job** に分割。
  3. 分割するとユーザーストーリーが書きづらい。大粒度の要件定義があって、そこから単位の要件定義を起こす形に。→ 本書を **大粒度 (機能群) の要件定義** に改め、ストーリーと方針と単位の分割を持たせた。子の単位が EARS と受け入れ基準を持つ。

## 2. ADR-013 との関係

- ADR-013 §6-2 は「本人に明示せず動画を裏送り」と「YouTube のサーバー側取得」を不採用とし、ブラウザ内推論かハイブリッド (特徴量だけ送る) を本命にしていた。本機能群は **明示的な同意つきのアップロード** で、不採用の 2 点には抵触しない。ブラウザ内推論からの転換は ADR-020 §6 / §7 で決定済み。理由: 検出は Python (姿勢 + TrackNet + 分類器) で、ブラウザ内に移植すると開発と検証をやり直すことになり、処理も実時間の 13 倍 (M2) で端末では現実的でない。
- ADR-013 §4「動画数制限はコストではなく値付けレバー」は、Storage と GPU の実費が発生するため前提が変わる。動画分析数の上限 (billing) が実費の回収にも効くようになる。

## 3. 親子の要件定義という書き方

- 親 (本書): 概要、ストーリー、方針、単位の分割と境界の契約、人の判断。EARS の要件は持たない。
- 子 (`docs/spec/<unit>/`): `requirements.md` (EARS)、`acceptance-criteria.md`、`note.md`、`user-stories.md` は親のストーリーへの対応表。
- `/refill-queue` はタスクを **子の単位** から導く (1 PR で閉じられる大きさ)。親はタスクの単位にならない。
- この書き方を tsumiki の規約 (docs/rule) に書くかは人の判断 (inbox に起票)。

## 4. 進め方の注意

- 最初の利用者は運営者自身 (戸塚・南区の動画で通す)。顧客に開くのは精度の確認運用を決めてから。
- 実装の順: video-upload (台帳と保持の列、`ready` まで) → video-analysis-job (台帳 + 手動登録 → ワーカー基盤)。削除の定期ジョブとプロキシは費用が見えてから。
- プライバシーポリシー (BL-004) と利用規約 (BL-005) に、動画のサーバー保管・削除 (入力完了後)・解析・学習利用 (オプトイン) の記載を足す。
