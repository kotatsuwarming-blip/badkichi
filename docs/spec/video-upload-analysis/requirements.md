# video-upload-analysis 要件定義書

**作成日**: 2026-11-01 / **改訂**: 2026-11-23 (ADR-020 との整合。改訂箇所は「改訂 2026-11-23」と記す)
**作業規模**: 新規単位。動画のアップロード (Storage)、解析ジョブの台帳と進捗、サーバー側の解析ワーカー (本体リポジトリ外の Python をジョブとして実行)、候補ファイルの受け渡し
**依存単位**: data-foundation (`matches`、新規テーブル `analysis_jobs`)、match-management (試合画面からのアップロード導線)、serve-start-assist (候補ファイルの消費側)、billing (動画分析数の計測)、video-tap-annotation / プライミング (コート 4 隅の校正を解析に渡す)
**上位の決定**: ADR-020 §6 (改訂 2026-11-23) で確定。**再生は YouTube だけ、動画は解析用のアップロードのみ、原本は解析後に削除が既定、学習利用はオプトインの保管**。ADR-013 §6-2 が不採用とした「本人に明示せず動画を裏送り」には抵触しない (明示的な同意つき)。旧キューの VID-0〜4 と BL-031 (動画原本の ADR) は本単位に統合され不要

## 概要

利用者が試合の動画ファイル (YouTube に上げたものと同じファイル) をアプリにアップロードし、サーバーの解析ジョブが **サーブ候補ファイル** (サーブの時刻・サーバーのスロット・ラリー終了の参考値) を作って、記録モード (serve-start-assist) に渡す。再生は従来どおり YouTube に任せ、利用者の手元に動画ファイルを置き続ける必要をなくす。

いまは候補の生成を運営者の Mac で行っている (`~/dev/badkichi-ai/`、HANDOFF §9-10〜9-12)。それでは運営者しか使えず、代行枠 (月 8 時間) の制約から抜けられない。利用者自身が動画を上げて候補を受け取れるようにするのが本単位の目的で、顧客自身による確認と訂正 (BL-044) の前提になる。

**設計の中心は 5 点**:

1. **アップロードは明示的な同意つき。** 「この動画をサーバーで解析する」ことに同意して初めて送る。解析が終わったら原本は既定で削除する (保管はオプトイン)。
2. **解析はジョブ。** 台帳 (`analysis_jobs`) に状態・進捗・結果を持ち、画面はそれを表示するだけ。ワーカーは本体とは別のプロセス (GPU を使う Python) で、本体はワーカーの中身を知らない。
3. **出力は小さな候補ファイルだけ。** 動画はワーカーの外に出さず、選手名も含めない (スロットとチームのみ)。
4. **解析にはコートの校正が要る。** 現在の検出はコート座標 (ホモグラフィ) に依存するので、コート 4 隅の座標を解析の入力にする。校正は video-tap-annotation (BL-021) の仕組みを使い、無ければアップロード時に 1 枚の静止画で入力させる。
5. **ジョブの出力はサーブ候補だけでなくショット層の下書きにも広げられる契約にする** (改訂 2026-11-23)。同じ動画・同じ校正から、ラリー確認 (serve-start-assist) 用のサーブ候補ファイルと、ai-draft-loop 用の下書き JSON (打刻・打者・球種・打点) を同じジョブの出力として返せる。ワーカーの中身 (`~/dev/badkichi-ai`) が育っても本体の契約は変えない。

背景の数字 (検証の実測、`~/dev/badkichi-ai/STATUS.md` §D / HANDOFF §9-11):

| 項目 | 値 |
|---|---|
| 検出の処理速度 (Apple M2) | 姿勢検出 ≈ 実時間と同程度、TrackNet ≈ 実時間の 13 倍 |
| 動画の大きさ | 1280×720 30 fps で 10 分あたり 100〜300 MB (端末の設定による)。1 試合 45 分で 0.5〜1.5 GB |
| 候補ファイルの大きさ | 数十 KB (JSON) |
| 精度 (戸塚 1 試合で学習・検証) | サーブ開始 20/23、サーバーのスロット 91/100。別会場・別画角は未検証 |

## スコープ

### 含む
- 試合に対する動画ファイルのアップロード (再開可能、進捗表示、同意の取得)
- 解析ジョブの台帳 (`analysis_jobs`) と状態遷移 (待機 → 実行中 → 完了 / 失敗)、進捗と推定残り時間の表示
- 解析ワーカーの起動契約 (入力: 動画の取得先、コート 4 隅、試合区間、fps。出力: 候補ファイル、ログ、処理時間) と結果の保存
- 原本の保管期間と削除 (既定: 解析成功後に削除。失敗時は診断のため 7 日)
- 候補ファイルの保存と serve-start-assist への受け渡し。ショット層の下書き JSON の保存と ai-draft-loop の取り込み経路への受け渡し (改訂 2026-11-23)
- 動画分析数の計測 (billing の「動画分析数」に加算。課金は保留中 (ADR-020 §8) なので、計測だけ行い上限の強制は billing の実装後)
- コート 4 隅の校正の受け取り (既存の校正があれば再利用、無ければ入力)

### 含まない
- 解析アルゴリズムそのもの (`~/dev/badkichi-ai/` の検証コード。ワーカーへの移植は本単位の実装タスクだが、精度の改良は別)
- ショット層の下書きの**中身** (検出アルゴリズム)。契約上は同じジョブの出力に含められる (REQ-006) が、出す・出さないはワーカー側の版で決まる
- アップロードした動画の再生。**不採用** (作者決定 2026-11-23: 再生は YouTube だけ。旧 serve-start-assist REQ-304 も不採用)
- 訂正を使った再学習 (ADR-020 §4 L1。学習提供に同意した動画と、人の確定 (human_resolutions) が対象。`~/dev/badkichi-ai` 側)
- YouTube からの動画取得 (ADR-013 §6-2 で不採用)
- メール等の外部通知 (アプリ内の表示のみ)

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: 既存の設計文書・ADR・検証の実測に基づく確実な要件
- 🟡 **黄信号**: 既存実装・検証結果・一般的な運用から妥当な推測による要件 (kairo-design で確定)
- 🔴 **赤信号**: 出典のない推測による要件

### 通常要件

- REQ-001: システムは、試合 (`matches`) に対して動画ファイルを 1 本アップロードできなければならない。試合の動画ソース (`video_source_type` / `video_source_url`) はそのまま YouTube を使い、アップロードは解析専用とする 🔵 *ユーザー決定 2026-11-01 (再生は YouTube、解析用にアップロード)*
- REQ-002 (改訂 2026-11-23): システムは、アップロードの開始前に次の 4 点を示して同意を取得し、同意の日時と内容を記録しなければならない。(1) 動画をサーバーに**アップロード**すること、(2) サーバーで**解析**すること、(3) 解析後に原本を**削除**すること (既定。失敗時は 7 日)、(4) **学習利用**への提供は別のオプトイン (REQ-301) であり、同意しなければ原本は学習に使われないこと。(4) は既定でオフとする 🔵 *ADR-020 §6 (同意の 4 点) + ADR-013 §6-2 + BL-004*
- REQ-003: システムは、アップロードを中断から再開できる方式 (再開可能アップロード) で行い、進捗 (割合と転送量) を表示しなければならない 🔵 *1 試合 0.5〜1.5 GB。通常の 1 回送信では失敗しやすい*
- REQ-004: システムは、アップロード完了後に解析ジョブを 1 件作成し、台帳 (`analysis_jobs`: 試合、状態、進捗、開始/終了時刻、エラー、処理時間、出力の参照) に記録しなければならない 🔵 *ジョブ方式の採用 (本書「設計の中心」2)*
- REQ-005: システムは、ジョブの状態 (待機 / 実行中 / 完了 / 失敗) と進捗 (処理済みの動画時間 / 全体) を試合画面で表示し、完了時に serve-start-assist へ進む導線を出さなければならない 🔵 *serve-start-assist REQ-201 (ジョブ未完了時の案内)*
- REQ-006 (改訂 2026-11-23): システムは、解析ワーカーに対して「動画の取得先 (期限付き署名 URL)、コート 4 隅の画像座標、試合区間 (開始・終了秒、任意)、動画の fps と向き、要求する出力の種類」を入力として渡し、出力として「サーブ候補ファイル (JSON、serve-start-assist note.md §5 の形式)」と、ワーカーの版が対応していれば「ショット層の下書き JSON (ai-draft-loop REQ-304 の契約。batch_id、ai_model_version、predictions[])」、および処理時間・ログを受け取らなければならない。出力の種類ごとに契約のバージョンを持つ 🔵 *検出パイプラインの入力 (HANDOFF §9-3 ホモグラフィ、§9-10 クリップ) + ADR-020 §4 L1 (推論は 1 コマンド、出力は下書き JSON)*
- REQ-007 (改訂 2026-11-23): システムは、サーブ候補ファイルを試合に紐づけて保存し serve-start-assist が読める形で提供し、ショット層の下書き JSON が出力に含まれる場合は ai-draft-loop の取り込み経路 (REQ-006〜008、Issue #102) に渡さなければならない。下書き JSON の取り込みは、ラリー確認で確定したラリーに対してだけ現在の値に反映される (ADR-020 §1 の原則。反映の規則は ai-draft-loop 側) 🔵 *serve-start-assist REQ-001 + ai-draft-loop REQ-006〜008*
- REQ-008: システムは、解析ジョブの完了を「動画分析数」として 1 本記録しなければならない (失敗は記録しない)。billing への加算と上限の強制は billing の実装後 (課金は保留中、ADR-020 §8) 🔵 *billing 要件 (動画分析数は累計 N 本まで) + ADR-020 §8*
- REQ-009: システムは、解析に必要なコート 4 隅の座標を、当該試合に既存の校正 (video-tap-annotation のコート校正) があればそれを使い、無ければアップロード時に動画の静止画 1 枚の上で 4 隅をタップさせて取得しなければならない 🔵 *検出がホモグラフィに依存 (コート内判定・静止・スロット特徴)。校正の仕組みは ADR-017 Stage 1 / BL-021*
- REQ-010: システムは、解析ワーカーが動画を処理する際に 1280 幅・30 fps 相当に正規化し (大きい動画は縮小、60 fps は間引き)、縦向きの動画は向きの情報に従って回転してから処理しなければならない 🔵 *検証は 1280×720 30 fps で行った (STATUS)。南区は縦向きで transpose が要った (HANDOFF §3)*

### 条件付き要件

- REQ-101: アップロードが中断された場合 (ネットワーク断、タブを閉じた)、システムは同じファイルを選び直すことで続きから再開できなければならない 🔵 *REQ-003*
- REQ-102: 解析ジョブが失敗した場合、システムは失敗の種類 (動画が読めない / 校正が無い / 処理の内部エラー / 時間切れ) を表示し、同じ動画で再実行できなければならない。再実行は新しいジョブとして記録し、原本の再アップロードを求めてはならない (保管期間内) 🔵 *原本は失敗時 7 日保管 (REQ-402)*
- REQ-103: 解析ジョブが成功した場合、システムは原本を既定で削除しなければならない。利用者が学習提供に同意 (REQ-301) している場合に限り保管し、保管期間 (既定 30 日。学習に取り込んだ後は数値特徴量と人の確定だけを残し原本は削除) の後に削除する 🔵 *ADR-020 §6 (削除が既定、学習利用はオプトイン保管) + BL-004*
- REQ-104: 同じ試合に対して解析ジョブが待機中または実行中の場合、システムは新しいアップロードとジョブの作成を受け付けてはならない 🔵 *二重実行の防止*
- REQ-105: 候補ファイルが既にある試合で解析を再実行した場合、システムは serve-start-assist の規則 (記録前なら置き換え、記録後は確認のうえ判断を捨てて置き換え) に従わなければならない 🔵 *serve-start-assist REQ-112*
- REQ-106: 1 本の動画に複数の試合が入っている場合、システムは試合区間 (開始・終了秒) の指定を受け付け、ワーカーはその区間だけを解析し、候補の時刻は動画の先頭からの秒数のまま出さなければならない 🔵 *ADR-013 §6-5 (試合区間の指定) + 候補時刻の定義 (serve-start-assist REQ-113)*
- REQ-107: 解析ワーカーが候補を 1 件も出せなかった場合 (コート内に選手を検出できない等)、システムはジョブを「完了 (候補 0 件)」として記録し、撮影条件 (カメラの位置・高さ) の確認を促さなければならない 🔵 *検出はコート後方 120 cm の三脚で検証。横からの床置きでは成立しない (STATUS §D、BL-008)*
- REQ-108: 利用者が原本の削除を要求した場合、システムは保管期間内でも直ちに削除し、削除の日時を記録しなければならない 🔵 *BL-004*
- REQ-109: ジョブの実行時間が上限 (既定: 動画の長さの 5 倍、最大 6 時間) を超えた場合、システムはジョブを失敗 (時間切れ) として終了し、ワーカーを停止しなければならない 🟡 *GPU での処理速度は未実測。上限は暫定*

### 状態要件

- REQ-201: billing が導入された後、動画分析数が契約の上限に達している Group では、システムはアップロードを受け付けず、上限とプランの案内を表示しなければならない。billing 導入前は上限を設けない (運営者がアップロードを行う期間) 🔵 *billing (累計 N 本) + ADR-020 §8 (課金は保留)*
- REQ-202: 試合に校正 (コート 4 隅) が無い状態では、システムはアップロードを完了させても解析ジョブを開始せず、校正の入力を求めなければならない 🔵 *REQ-009*
- REQ-203: ジョブが実行中の状態では、システムは進捗を定期的に更新して表示し、画面を離れても再表示で状態が分かるようにしなければならない 🔵 *REQ-005*
- ~~REQ-204: 原本が削除済みの状態では Storage 再生を提示しない~~ → 不要 (Storage 再生自体を不採用。改訂 2026-11-23)

### オプション要件

- REQ-301 (改訂 2026-11-23): システムは、利用者が「学習への提供」に別途同意 (REQ-002 の (4)、既定オフ) した動画を、学習用に保管してよい。同意の有無は試合に紐づけて保存し、ai-draft-loop の学習用書き出し (REQ-022) が同意のない試合を除外できるようにする。同意は解析の同意とは別の明示的な操作とし、後から取り消せる (取り消し時は原本を削除) 🔵 *ADR-020 §6 (学習利用はオプトイン) + ADR-013 §6-4*
- REQ-302: システムは、解析ジョブの完了をアプリ内の通知として表示してよい (メール等は対象外) 🟡
- REQ-303: システムは、運営者が手元で作った候補ファイルを手動で登録する経路 (ジョブを経由しない) を提供してよい (検証・障害時用) 🔵 *serve-start-assist REQ-001*
- REQ-304: システムは、ジョブごとの処理時間・GPU 時間・推定費用を運営者向けに記録してよい (利用者には表示しない) 🟡 *費用の見積に使う (note.md §3)*

### 制約要件

- REQ-401: システムは、動画の原本をアプリの Storage の非公開バケットに置き、取得は期限付きの署名 URL に限り、RLS で Group の構成員以外から参照できないようにしなければならない 🔵 *data-foundation の RLS 方針 + ADR-013 §6-2*
- REQ-402: システムは、原本を解析成功後に削除 (既定)、失敗時は 7 日後に削除、保管を選んだ場合は保管期間後に削除し、削除の記録 (日時・理由) を残さなければならない 🔵 *BL-004 (保管と削除の明記)*
- REQ-403: システムは、解析ワーカーが動画・候補以外のデータ (選手名、他の試合、他の Group) にアクセスできないようにし、ワーカーの出力に選手名・個人を特定する情報を含めてはならない 🔵 *serve-start-assist REQ-406 + 最小権限*
- REQ-404: システムは、解析ワーカーを本体 (Nuxt / Vercel) とは別の実行環境 (GPU を使えるジョブ実行基盤) で動かし、本体は台帳と Storage を介してのみワーカーと連携しなければならない 🔵 *Vercel の関数は長時間・GPU の処理に向かない (ADR-014) + 検出は Python (ultralytics / TrackNetV3)*
- REQ-405: システムは、解析に使うモデルと重みのライセンスを商用利用可能なものに限らなければならない (TrackNetV3: MIT、YOLO11: AGPL-3.0 のため商用はライセンス購入か代替モデルの検討が要る) 🔵 *BL-030 (ライセンス確認) + ultralytics のライセンス*
- REQ-406: システムは、YouTube から動画を取得してはならない 🔵 *ADR-013 §6-2*
- REQ-407: システムは、アップロードできるファイルを動画 (mp4 / mov / webm) に限り、1 本の上限 (既定 4 GB) と長さの上限 (既定 3 時間) を設けなければならない 🟡 *1 試合 45 分で 0.5〜1.5 GB。上限は Storage のプランと費用で決める*
- REQ-408: システムは、画面の全文言を i18n locales (ja/en) 経由で表示しなければならない 🔵 *他単位と同じ*

## 非機能要件

### パフォーマンス

- NFR-001: 解析ジョブは、45 分の試合 1 本を 2 時間以内に完了しなければならない (待機時間を除く) 🟡 *M2 で TrackNet が実時間の 13 倍。GPU で実時間の 1〜2 倍を見込むが未実測*
- NFR-002: アップロードは利用者の回線速度に依存するが、システム側の処理 (署名 URL の発行、再開) で 1 秒以上待たせてはならない 🟡
- NFR-003: 進捗の表示は 30 秒以内の遅れで更新されなければならない 🟡

### セキュリティ

- NFR-101: 動画の原本・候補ファイル・ジョブの台帳は、他 Group から取得・作成・更新・削除のいずれもできてはならない 🔵 *RLS*
- NFR-102: 署名 URL の有効期限はワーカーの処理時間に必要な範囲 (既定 12 時間) に限り、URL をログに残してはならない 🟡
- NFR-103: ワーカーの認証情報 (service role 等) をクライアントに含めてはならず、ワーカーの起動はサーバー側からのみ行わなければならない 🔵 *他単位の NFR-102 踏襲*

### ユーザビリティ

- NFR-201: アップロード画面は、同意・ファイル選択・校正 (必要な場合)・試合区間 (任意) を 1 つの流れで済ませ、選んだファイルの長さと大きさ、推定の解析時間を表示しなければならない 🟡
- NFR-202: 失敗の表示は「何が起きたか」と「利用者ができること」(撮り直し、校正のやり直し、再実行、運営への連絡) を文言で示さなければならない 🟡

### 運用・保守性

- NFR-301: ワーカーの入出力の契約 (REQ-006) はバージョン番号を持ち、本体とワーカーを独立して更新できなければならない 🟡
- NFR-302: ジョブの台帳は、運営者が全 Group のジョブの状態・失敗率・処理時間を一覧できなければならない (運営画面または SQL) 🟡
- NFR-303: 原本の削除は定期ジョブで行い、削除漏れを検知できなければならない 🟡

## Edgeケース

### 入力検証

- EDGE-001: 動画以外のファイル、または上限 (大きさ・長さ) を超えるファイル → アップロード前に拒否し、理由を表示する 🔵 *REQ-407*
- EDGE-002: 同じ試合に 2 回目のアップロード (前のジョブが完了済み) → 前の原本が残っていれば削除してから受け付け、ジョブを新規に作る (候補の置き換えは REQ-105) 🔵
- EDGE-003: 校正の 4 隅が画面外 (手前の 2 隅が映らない、戸塚と同じ) → 4 隅のうち映らない点は「画面外」として扱い、映っている線の延長で校正できる方式を校正側 (BL-021) に求める 🟡 *HANDOFF §9-3 (手前 2 隅は画面外)*

### 解析の条件

- EDGE-101: カメラが横から・床置きの動画 (南区) → コートの校正はできても検出が成立しない。候補 0 件またはごく少数になる。REQ-107 の案内で撮影ガイド (BL-008) に誘導する 🔵 *STATUS §D*
- EDGE-102: 途中でカメラが動いた動画 (戸塚 2395 秒付近) → 校正がずれ、以降の候補の精度が落ちる。検出できないので、serve-start-assist 側の抜け検知で表面化させる 🔵 *HANDOFF §9 (2395 秒でカメラが動く)*
- EDGE-103: 別会場・別画角の動画 → スロット分類器は戸塚 1 試合で学習したもので、精度は未検証。候補ファイルの信頼度は出るが保証しない。初回は運営者が結果を確認する運用にする 🟡
- EDGE-104: 60 fps・1080p 以上の動画 → 30 fps・1280 幅に正規化して処理 (REQ-010)。候補の時刻は元の動画の秒数で返す 🔵
- EDGE-105: 1 本の動画に複数の試合、区間の指定なし → 全体を解析し、候補は全部出す。記録側でセットごとに扱う 🔵 *REQ-106*
- EDGE-106: 動画の音声が無い・壊れている → 検出は映像のみを使うので影響しない 🔵 *音は不採用 (STATUS 行 6)*

### 状態・運用

- EDGE-201: ワーカーが異常終了して台帳が「実行中」のまま残る → REQ-109 の時間切れで失敗に落とす。運営者が手で失敗にできる (NFR-302) 🟡
- EDGE-202: 保管期間中に Group が解約・削除された → 原本と候補ファイルを削除する 🟡
- EDGE-203: 動画分析数の上限にちょうど達するジョブが失敗した → 加算しない (REQ-008) ので再実行できる 🔵

## 受け入れ基準

### 機能テスト

- [ ] 同意なしにアップロードできない。同意の日時が記録される (REQ-002)
- [ ] 1 GB の動画を中断・再開してアップロードでき、進捗が表示される (REQ-003 / REQ-101)
- [ ] アップロード完了でジョブが作られ、状態と進捗が試合画面に出る (REQ-004 / REQ-005)
- [ ] ワーカーが候補ファイルを返し、serve-start-assist で読める (REQ-006 / REQ-007)
- [ ] 成功後に原本が削除され、失敗時は 7 日残り、学習提供に同意した場合だけ保管期間残る (REQ-103 / REQ-402 / REQ-301)
- [ ] 同意画面に 4 点 (アップロード・解析・削除・学習利用) が示され、学習利用は既定オフ (REQ-002)
- [ ] ワーカーがショット層の下書き JSON を返した場合、ai-draft-loop の取り込み経路に渡る (REQ-006 / REQ-007)
- [ ] 校正が無いとジョブが始まらず、校正を入れると始まる (REQ-009 / REQ-202)
- [ ] 上限到達の Group はアップロードできない (REQ-201)
- [ ] 他 Group から原本・候補・台帳にアクセスできない (NFR-101)

### 非機能テスト

- [ ] 45 分の試合の解析が 2 時間以内に終わる (NFR-001)
- [ ] 時間切れでジョブが失敗に落ち、ワーカーが止まる (REQ-109)
