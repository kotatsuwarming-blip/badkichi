# rally-first-recording 要件定義書

**作成日**: 2026-11-01
**作業規模**: 既存 2 単位（match-recording / shot-annotation）への拡張 + additive migration 1 本 + video-playback の再生速度追加
**依存単位**: data-foundation（`sets` / `rallies` への additive migration）, match-recording + rule-engine（段 1）, shot-annotation（段 2・既存パスの調整）, video-playback（0.25 倍速）
**バックログ**: BL-027

## 概要

試合の入力を「ショットを 1 打ずつ 3 回訪ねる」方式から、**ラリー単位で軽く記録し、打刻と打点を 1 回のパスで同時に入れる**方式に変える。

1. **ラリー記録モード（段 1）**: record 画面で、ラリーの開始と終了、得点者、左右入替・コートチェンジだけを 1.5〜2 倍速で記録する。ショットは押さない。
2. **打点パス（流し）（段 2）**: アノテーションスタジオで、段 1 の区間だけを低速で 1 回流し、打球の瞬間にコート図をタップする。タップの時刻が打刻、位置が打点になる。ループ再生はしない。
3. **種別パス（段 3）**: 既存の種別パスで種別と打者（個人）を入れる。変更しない。

現状は 42 分の試合で 186〜204 分（動画の 4.4〜4.8 倍）。新方式で記録 + 打点を 46〜73 分（現状 88〜106 分）に縮め、全体で 15〜60 分短縮する見込み（[analysis.md §3-1](../../research/input-automation/analysis.md)）。

既存の記録方式（ショット単位）と既存データは一切変えない。方式はセット単位で選び、既定は従来どおりとする。

## スコープ

### 含む
- `sets.recording_mode`（`shot` / `rally`）と `rallies.video_end_timestamp_ms` の additive migration
- セット設定での記録方式の選択（既定 `shot`）
- ラリー記録モードの操作（ラリー開始 / 得点 A・B / レット / スキップ / 取り消し / 左右入替 / コートチェンジ）と rule-engine 連携
- アノテーションスタジオの新モード「打点パス（流し）」（区間再生・コート図タップ・ショット行の作成・打者プレフィル・取り消し・やり直し）
- 再生速度 0.25 の追加と、押している間だけ低速にする操作
- クイックパスのループ基準をショット無しラリーでも成立させる調整
- 進捗表示でショット 0 件のラリーを「打点パス（流し）未着手」として扱うこと
- 既存のショット単位記録・既存の打点パス・種別パス・統計の挙動を変えないこと

### 含まない
- 動画直接タップと 4 隅校正（BL-021）
- 作業時間の自動計測（BL-020）
- 種別パスのループ窓の変更
- 統計 SQL の変更（ショット 0 件のラリーの扱いは kairo-design で確認し、必要なら別単位）
- AI による下書き（BL-033 以降）
- 既存セットの記録方式の変更（セット作成時に決め、以後は変えない）

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: 根拠資料（analysis.md / 既存要件 / ADR / 実測）・ユーザー発言を参考にした確実な要件
- 🟡 **黄信号**: 根拠資料・既存実装から妥当な推測による要件（note.md の論点表に対応、ユーザー確認待ち）
- 🔴 **赤信号**: 出典のない推測による要件

### 通常要件

- REQ-001: システムは、セットの記録方式として `shot`（ショット単位、従来）/ `rally`（ラリー単位）を保持しなければならない（`sets.recording_mode`、既定 `shot`） 🔵 *analysis.md §3-1 A「ラリー単位の軽い記録モードを別に作る」+ ADR-017 §3*
- REQ-002: システムは、セット設定フォームで記録方式を選択させ、既定をショット単位としなければならない 🟡 *論点 1・6（セット単位で選ぶ）*
- REQ-003: システムは、ラリー記録モードで「ラリー開始」操作を提供し、押下時の再生位置（ms）を `rallies.video_start_timestamp_ms` に保存しなければならない 🔵 *analysis.md §3-1 パス 1 + 既存列の流用*
- REQ-004: システムは、ラリー記録モードで得点 A / 得点 B / レット / スキップの操作を提供し、押下時の再生位置（ms）を `rallies.video_end_timestamp_ms` に保存したうえで、match-recording REQ-006 / REQ-007 と同じ手順でラリーを確定（rule-engine `applyRally` → denormalize 保存）しなければならない 🟡 *論点 2（得点操作 = 終了時刻。1 ラリー 2 操作）*
- REQ-005: システムは、ラリー記録モードで記録したラリーを**ショット 0 件のまま正常なデータ**として保存し、以降の画面（注釈・統計・履歴）で読めなければならない 🔵 *段 2 で後からショットを作る前提*
- REQ-006: システムは、アノテーションスタジオに「打点パス（流し）」モードを追加し、対象ラリーの区間 [`video_start_timestamp_ms` − 前余白, `video_end_timestamp_ms` + 後余白] を選択中の再生速度で**1 回だけ連続再生**しなければならない（ループしない） 🔵 *analysis.md §3-1 パス 2 + ユーザー発言 2026-11-01「ループ再生ではなく流して記録」*
- REQ-007: システムは、打点パス（流し）の再生中にコート図がタップ / クリックされたとき、その時点の再生位置を `video_timestamp_ms`、タップ座標を正規化座標（shot-annotation REQ-014、ライン外は範囲外値）で `hit_x` / `hit_y` とする `shots` 行を 1 件作成し、`shot_number` をラリー内の連番としなければならない（`input_source = 'manual'`、`annotation_source = 'human'`） 🔵 *analysis.md §3-1 パス 2「タップの時刻が打刻、位置が打点」*
- REQ-008: システムは、打点パス（流し）で作成したショットの打者（`hit_player_id`）を shot-annotation REQ-012 と同じ規則でプレフィルしなければならない（1 打目 = `server_player_id`、2 打目 = `receiver_player_id`、3 打目以降はチームのみ確定し個人は未定 = `NULL`。シングルスは候補 1 人なので個人まで確定） 🔵 *ユーザー発言 2026-11-01「ショット種類と誰が打ったかは次に記録」+ REQ-012*
- REQ-009: システムは、区間の終端で再生を自動停止し、そのラリーで作成したショット数を表示したうえで、次の対象ラリーへ進む操作を提供しなければならない 🔵 *shot-annotation REQ-008（ラリー境界での自動一時停止）の踏襲*
- REQ-010: システムは、打点パス（流し）の再生速度として少なくとも 0.25 / 0.5 / 0.75 倍を提供し、既定を 0.5 倍としなければならない 🔵 *analysis.md §3-1「0.5 倍速では速い打ち合いに追いつけない → 0.25 倍速への切り替えが要る」*
- REQ-011: システムは、種別パスを変更せず、打点パス（流し）で作成したショット行をそのまま巡回対象としなければならない（1 打目サーブ自動確定・打者二択・挿入削除は既存どおり） 🔵 *段 3 = 既存の種別パス*
- REQ-012: システムは、注釈の進捗で、記録方式 `rally` のセットのショット 0 件のラリーを「打点パス（流し）未着手」として数え、次の未着手ラリーから再開できなければならない 🔵 *shot-annotation REQ-013（進捗は注釈列の null 有無から導出）*

### 条件付き要件

- REQ-101: 記録方式が `rally` の場合、システムは record 画面に「打った」ボタンを表示せず、「ラリー開始」ボタンを表示しなければならない。スコア表示・コート図・ラリー履歴・左右入替・コートチェンジ・取り消しは従来モードと同じものを表示する 🟡 *論点 1*
- REQ-102: ラリー開始が押されていない状態で得点 / レット / スキップが押された場合、システムは開始時刻を `NULL` のままラリーを確定しなければならない（押し忘れでも記録を止めない。区間の前端は段 2 で前のラリーの終了時刻 or 手動シークで補う） 🟡 *match-recording REQ-103（記録を止めない方針）からの推測*
- REQ-103: ラリー開始が連続して押された場合、システムは後の押下で開始時刻を**上書き**しなければならない（押し直し） 🟡 *妥当な推測*
- REQ-104: ラリー記録モードで取り消し（↩ / Backspace）が押された場合、システムは直近の操作を 1 つ戻さなければならない。戻す対象はラリー開始（開始時刻の消去）・得点 / レット / スキップ（ラリー行の削除と rule-engine 状態の復元）・左右入替・コートチェンジで、ショット 0 件を理由にラリー行を自動削除する従来の規則（match-recording REQ-110）は適用しない 🔵 *REQ-005 + match-recording REQ-110*
- REQ-105: 記録方式が `shot` の場合、システムは従来の操作・保存・取り消しを一切変えてはならない（`video_end_timestamp_ms` は `NULL` のまま） 🔵 *ADR-017 §3 + 既存データの保全*
- REQ-106: 打点パス（流し）で Backspace が押された場合、システムは直前のタップで作成したショット行を削除し、再生は止めずに続けなければならない 🔵 *shot-annotation REQ-108（Backspace = 直前 1 段）*
- REQ-107: 打点パス（流し）で「やり直し」が選ばれた場合、システムはそのラリーのショットを全件削除し、区間を先頭から再生し直さなければならない 🔵 *shot-annotation EDGE-003（ラリー単位でやり直し可能）*
- REQ-108: 打点パス（流し）で指定キーが押されている間、システムは再生速度を 0.25 倍に落とし、離したら直前の速度に戻さなければならない 🟡 *論点 4 + analysis.md §3-1「キーを押している間だけ 0.25 倍速」*
- REQ-109: 対象ラリーに `video_end_timestamp_ms` が無い（`shot` モードのラリー、または REQ-102 の押し忘れで `video_start_timestamp_ms` も無い）場合、システムは区間を自動では決めず、ユーザーの手動シークと「ここから流す」「ここで止める」操作で区間を与えられなければならない 🟡 *欠損への備え。妥当な推測*
- REQ-110: クイックパスで対象ラリーにショットが無い場合、システムは決着ループの基準を `video_end_timestamp_ms`（無ければ `video_start_timestamp_ms`）とし、基準の**前側を長く**取った窓でループしなければならない（決着イベントは得点操作より前に起きるため） 🔵 *shot-annotation REQ-004 / REQ-101 の非対称窓の考え方*
- REQ-111: 打点パス（流し）で既にショットがあるラリー（段 2 済み、または `shot` モードのラリー）を開いた場合、システムは既存のショットをタイムライン上に表示し、追加タップは末尾に追記、やり直しは REQ-107 としなければならない 🟡 *妥当な推測*
- REQ-112: 記録方式が `rally` でセットのラリー全件が段 2 未着手の場合、システムは打点パス（流し）をそのセットの既定モードとして提案しなければならない（従来の打点パスは選べるが、ショット 0 件のラリーでは対象が無い旨を表示） 🟡 *妥当な推測*

### 状態要件

- REQ-201: 動画がロード未完了 / バッファ中の状態では、システムはラリー開始・得点・タップの時刻依存操作を無効化しなければならない 🔵 *match-recording REQ-202 / shot-annotation REQ-202 踏襲*
- REQ-202: セットが決着済みの状態では、システムはラリー記録モードでもラリー追加を不可としなければならない 🔵 *match-recording REQ-203*
- REQ-203: 打点パス（流し）の再生中にユーザーが一時停止した状態では、システムはタップを受け付け（停止位置の時刻で記録）、再開で区間の続きを流さなければならない 🟡 *狙いやすさのため妥当な推測*

### オプション要件

- REQ-301: システムは、ラリー記録モードで得点操作とは別の「ラリー終了」操作を提供してもよい（終了時刻を先に押し、得点者を後で押す 3 操作の形） 🟡 *論点 2 の代替*
- REQ-302: システムは、打点パス（流し）のタップ面を、BL-021 導入後に動画オーバーレイへ差し替えられるよう、タップ → 正規化座標の変換を 1 箇所の util に閉じてもよい（本単位ではコート図のみ） 🔵 *video-tap-annotation note.md §2-3（既存座標系と互換）*
- REQ-303: システムは、区間の前余白・後余白を設定で変えられるようにしてもよい（既定値は kairo-design で決める。目安: 前 1.0 秒 / 後 1.5 秒） 🟡 *得点操作の反応遅れ（analysis.md §2: 0.2〜0.5 秒 × 再生倍率）を吸収するため*

### 制約要件

- REQ-401: システムは migration を additive（列追加・CHECK 追加）のみとし、CI 経由（db:push）で適用しなければならない 🔵 *data-foundation / match-recording / shot-annotation の前例*
- REQ-402: システムは従来モードのコアループ（「打った」→ 100ms 以内に記録、`ShotButton` / `useRecordingSession` の shot 系経路）を変更してはならず、ラリー記録モードは別コンポーネントで実装し、状態管理・rule-engine 連携は既存 composable を流用しなければならない 🔵 *ADR-017 §3「ライブ記録 UI は聖域」+ analysis.md §3-1 注意点*
- REQ-403: システムは rule-engine を純ロジックとして利用し、ラリー記録モードでも `applyRally` / `applyOverride` を無変更で使わなければならない 🔵 *match-recording REQ-403 + singles-support の流用方針*
- REQ-404: システムは page / component から supabase クライアント・動画 API を直叩きせず、composable 経由で操作しなければならない 🔵 *ADR-007*
- REQ-405: システムは全文言を i18n locales（ja / en）経由で表示しなければならない 🔵 *既存単位踏襲*
- REQ-406: システムは統計の集計 SQL を変更してはならない。ショット 0 件のラリーが混在する試合で、ショットに依存する指標（ラリー長・ショット統計）が段 2 完了まで欠けることは許容する 🔵 *スコープ外 + ADR-002（stats-dashboard の責務）*
- REQ-407: システムは `PlaybackRate` に 0.25 を追加するにあたり、video-playback にドメイン概念を持ち込んではならない（速度の選択肢を増やすだけ） 🔵 *video-playback REQ-405*
- REQ-408: システムは既存の `shot` モードのセット・ラリー・ショット・注釈データを変換・更新してはならない 🔵 *既存データの保全*

## 非機能要件

### パフォーマンス

- NFR-001: ラリー開始・得点操作の押下から再生位置の取得・ローカル状態への反映は 100ms 以内でなければならない（2 倍速再生中に押すため、遅延は 2 倍で動画時刻に乗る） 🔵 *match-recording NFR-001 + 2 倍速の前提*
- NFR-002: 打点パス（流し）のタップから `video_timestamp_ms` の確定までは同期的（タップイベント内で再生位置を読む）でなければならず、保存は楽観書き込みとする 🔵 *shot-annotation NFR-002*
- NFR-003: 0.25 / 0.5 倍速再生中のタップで、取得した再生位置と実際の表示フレームの差が 1 フレーム（33ms @30fps）以内でなければならない（ローカル動画）。YouTube は IFrame API の精度に従う 🟡 *analysis.md §3-1「タップ時刻 − 打刻時刻: 中央値 −0.03 秒」を保つため*

### セキュリティ

- NFR-101: RLS により他 Group の試合の記録・注釈データは取得・追加・更新・削除不可でなければならない 🔵
- NFR-102: publishable key のみを使用し、service_role キーをクライアントに含めてはならない 🔵

### ユーザビリティ

- NFR-201: ラリー記録モードの操作（ラリー開始 / 得点 A / 得点 B / レット / スキップ / 取り消し）はすべてキーボードのみで行え、2 倍速再生中に見ずに押せる配置でなければならない 🔵 *match-recording NFR-201*
- NFR-202: 打点パス（流し）のコート図タップは、タブレットの指タップを想定した大きさ（既存 `CourtDiagramInput` の NFR-202 トーン: ±50cm の精度で足りる）でなければならない 🔵 *shot-annotation NFR-202 + analysis.md §3-1「タブレットの指のタップのほうが向く」*
- NFR-203: 打点パス（流し）の画面は、動画・コート図・現在ラリーの情報（ラリー番号 / サーバー / 残り区間 / タップ数）・速度表示を同時に見せ、再生中に視線を動画から外さずに操作できる配置でなければならない 🟡 *analysis.md §2「視線の往復」の指摘から*

### 計測

- NFR-301: 受け入れでは、同じ 1 ゲーム（11 分、37 ラリー、224 ショット相当）をストップウォッチで測り、段 1 + 段 2 の合計が従来の打刻 + 打点（12 + 20 分 = 32 分）を下回ることを確認する。自動計測（BL-020）は本単位に含めない 🟡 *論点 7 + analysis.md §1 の 8 月実測*

### 保守性

- NFR-401: 全文言は locales/ja.json・en.json に定義し、キー構造一致 CI チェックの対象とする 🔵
- NFR-402: 単体テストは、区間計算（前後余白・欠損時）、タップ → ショット行の生成（連番・プレフィル）、クイックパスのアンカー選択、ラリー記録モードの取り消し規則、記録方式ごとの分岐を高優先とし、見た目テストは書かない 🔵 *ADR-012*
- NFR-403: composable は操作別に分割し、ラリー記録モードは `useRecordingSession` の拡張（または薄い wrapper）、打点パス（流し）は `useFlowPositionPass`（仮）として既存 6 分割に 1 つ足す形とする。粒度は kairo-design で決める 🟡 *shot-annotation NFR-402 の踏襲*

## Edgeケース

### エラー処理

- EDGE-001: ラリー開始を押さずに得点を押す → 開始時刻 `NULL` で確定。段 2 では REQ-109 の手動区間指定、または直前ラリーの終了時刻を前端の既定値として提案する 🟡 *REQ-102*
- EDGE-002: 打点パス（流し）でタップが区間外（余白内）に入る → そのまま記録する（余白はこのためにある）。区間の終端停止後のタップは受け付けない 🟡
- EDGE-003: 打点パス（流し）の保存（INSERT）が失敗 → ローカルの連番は維持し、`useToast()` で通知。次のタップは失敗分を飛ばさず再試行の対象にする 🔵 *cross-cutting/error-handling.md*
- EDGE-004: 2 人が同じラリーを同時に段 2 → last-write-wins。連番の衝突は `shots` の UNIQUE（rally_id, shot_number）で後者が失敗し、通知する 🔵 *shot-annotation EDGE-001 + 既存制約*
- EDGE-005: ローカル動画でページ再読込 → 同一ファイルの再選択を促す（既存方式 A）。記録済みの時刻・区間は保持される 🔵 *match-recording REQ-108*

### 境界値

- EDGE-101: `video_start_timestamp_ms` − 前余白 が負 → 0 に clamp 🔵 *shot-annotation EDGE-004 と同型*
- EDGE-102: `video_end_timestamp_ms` < `video_start_timestamp_ms`（開始を押し直さずに巻き戻して得点した等） → 区間を [end − 前余白, end + 後余白] に縮退し、警告を表示する 🟡
- EDGE-103: 区間が極端に長い（例: 60 秒超、終了の押し忘れで次のラリーまで流れた） → そのまま流すが、警告を表示し、REQ-109 の手動区間指定を案内する 🟡
- EDGE-104: タップ 0 回で区間が終わる → ショット 0 件のまま次へ進める（未着手扱いが続く）。「このラリーにショット無し」を確定する操作は設けない 🟡
- EDGE-105: 1 打目のタップ位置がサーバー側の半面に無い → 記録は拒否せず、ソフト警告のみ（サーバーのプレフィルは変えない） 🟡 *shot-annotation EDGE-002 と同型のソフト警告*
- EDGE-106: レットラリー（`is_let = true`）→ 段 2 の巡回対象と進捗の分母から除外 🔵 *shot-annotation REQ-106*
- EDGE-107: シングルスのセットでラリー記録モード → 打者プレフィルは候補 1 人で個人まで確定。左右入替ボタンは非表示（singles-support REQ-106） 🔵

### 互換性

- EDGE-201: migration 適用後に既存セットを読む → `recording_mode = 'shot'`、`video_end_timestamp_ms = NULL`。record / annotate / stats の挙動は変わらない 🔵 *REQ-105 / REQ-408*
- EDGE-202: `rally` モードのセットを統計で開く → 得点率・決まり方は正しく、ラリー長・ショット統計は段 2 未完了分が欠ける。ラリー長 0 のラリーの扱い（除外 / 0 と数える）は kairo-design で既存 SQL を確認して決め、必要なら別単位にする 🟡 *REQ-406*

### 機能テスト

- [ ] セット設定で記録方式を選べ、既定がショット単位である
- [ ] ラリー記録モードで「ラリー開始 → 得点」の 2 操作でラリーが確定し、開始・終了時刻が保存される
- [ ] ショット 0 件のラリーが保存され、注釈・履歴で読める
- [ ] 打点パス（流し）で区間が 1 回だけ流れ、タップごとにショット行（時刻・座標・連番・打者プレフィル）ができる
- [ ] 0.25 倍速と押下中低速が効く
- [ ] Backspace で直前のタップが消え、やり直しでラリーのショットが全消去される
- [ ] 種別パスが段 2 のショットをそのまま巡回する
- [ ] クイックパスがショット無しラリーでも終了時刻を基準にループする
- [ ] ショット単位の既存セットの挙動・データが変わらない（回帰）

### 非機能テスト

- [ ] 1 ゲームのストップウォッチ計測で段 1 + 段 2 が従来の打刻 + 打点を下回る（NFR-301）
- [ ] 全文言 i18n、キー構造一致 CI 通過
- [ ] 単体テスト（区間計算・タップ → ショット生成・アンカー選択・取り消し規則）が green
