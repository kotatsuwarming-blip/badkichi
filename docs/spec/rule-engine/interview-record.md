# rule-engine ヒアリング記録

**作成日**: 2026-04-10
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

PRD（F-03: ルールエンジン）と ADR-002 の rule-engine 責務定義を確認し、実装に必要な詳細仕様を明確化するためのヒアリングを実施しました。

## 質問と回答

### Q1: 新しいセット開始時、最初にサーブを打つチームはどう決まる？

**質問日時**: 2026-04-10
**カテゴリ**: 未定義部分詳細化
**背景**: PRD にはセット内のサーブ権ルールは記載されているが、セット間の遷移ルールが未定義。rule-engine がセットをまたぐ計算をする際に必要。

**回答**: 前セットの勝者がサーブ権を持つ。

**信頼性への影響**:
- REQ-009 を 🔵 で追加

---

### Q2: デュース時のスコア上限は？

**質問日時**: 2026-04-10
**カテゴリ**: 未定義部分詳細化
**背景**: PRD にデュース処理のルールが未記載。BWF 公式ルールでは 30 点キャップだが、草バドミントンではローカルルールも多い。

**回答**: 上限は 30 だが、デュースなしルールも存在する。選べるのがよい。また、得点も 21 や 15 などのバリエーションがある。

**信頼性への影響**:
- REQ-101, REQ-102, REQ-103 を 🔵 で追加
- rule-engine の設定パラメータとして `deuce_rule` と `target_points` を定義

---

### Q3: PositionOverride の `restored`（「戻った」）の意味論は？

**質問日時**: 2026-04-10
**カテゴリ**: 未定義部分詳細化
**背景**: PRD には「戻った時点で『戻った』を入力する」とあるが、「何に戻るのか」（ルール計算上の位置 vs オーバーライド前の状態）が不明確。

**回答**: 人間の入力はひとつ前のラリーから入れ替わったことをボタンで教えるだけで、正しい位置であるかどうかは気にしない。極論そのラリー開始時の位置が分かればよい。

**追加回答（2026-04-10 追加ヒアリング）**: ユーザーはAかBのどちらか、または両方がひとつ前のラリーから見て入れ替わったことを入力する。得点入力後にルールエンジンが次のサーバー/レシーバーの位置を表示し、それが違っていたら入れ替わりを入力して表示が変わる。swapped と restored がセットである必要はない。トグル（毎回反転）で十分。

**信頼性への影響**:
- REQ-104, REQ-105 の仕様が明確化。`swapped` / `restored` の区別は不要、トグル方式に変更
- REQ-105 の信頼性が 🟡 → 🔵 に向上

---

### Q4: rule-engine はセット・試合の勝敗判定も責務に含めるか？

**質問日時**: 2026-04-10
**カテゴリ**: 既存設計確認
**背景**: ADR-002 では rule-engine の責務に「スコア状態」はあるが「勝敗判定」は明示されていない。

**回答**: 含める。

**信頼性への影響**:
- REQ-007, REQ-008 を 🔵 で追加

---

### Q5: rule-engine の API 形式はどちらが良い？（純関数 vs クラスベース）

**質問日時**: 2026-04-10
**カテゴリ**: 既存設計確認
**背景**: ADR-002 では API 形式が未定義。テスト容易性と開発者の理解しやすさの観点で確認が必要。

**回答**:（比較表を提示した結果）純関数を選択。

**補足**: ユーザーは当初「選択肢ごとのメリデメを比較しないと判断できない」と回答。dbt モデルとの類似性、テスト容易性、Vue Composition API との相性を比較表で提示し、純関数を選択。

**信頼性への影響**:
- REQ-004 を 🔵 で追加

---

### Q6: 得点者未確定（スキップ）のラリーがある時、rule-engine はどうする？

**質問日時**: 2026-04-10
**カテゴリ**: 未定義部分詳細化
**背景**: PRD の US-05 に「得点者が判断できない場合に一旦スキップし、次のサーブを見てから記録したい」とあるが、rule-engine にとって得点者未確定のラリーが計算を阻害する。

**回答**: 得点者未入力のラリーはなしにしたい。どちらかが得点かレットは入力しないといけない。動画を一旦停めてどちらの得点だったかを入力してもらえばよい。

**信頼性への影響**:
- REQ-403 を 🔵 で追加（全ラリーは必ず得点者 or レットが確定）
- PRD の US-05（スキップ機能）は match-recording の責務として再検討が必要

---

### Q7: 誤入力の修正方法について、rule-engine がサポートすべき操作は？

**質問日時**: 2026-04-10
**カテゴリ**: 追加要件
**背景**: ユーザーが「打ったボタンや得点を間違えて入力することがあるので、その時どうするかも考えたい」と発言。

**回答**: 得点者変更は必要だが、以降のラリーの再計算というような機能はいらない。次のラリーの開始のサーブを打つ側が得点していることが動画から分かるため。レットと得点の相互変更に近い。

**信頼性への影響**:
- rule-engine は純関数なので、修正されたデータを渡せば自然に正しい結果が返る。特別な「再計算」APIは不要
- match-recording 側の責務として、ラリーの得点者変更・レット⇔得点切り替えのUIを提供する

---

## ヒアリング結果サマリー

### 確認できた事項
- 新セット開始時のサーバーは前セットの勝者
- デュースルールはパラメータ化（cap30 / no_deuce）
- 目標ポイントもパラメータ化（21, 15 等）
- 勝敗判定は rule-engine の責務
- API形式は純関数
- 得点者未確定のラリーは存在しない（rule-engine の前提条件）
- PositionOverride は相対的な変化（前ラリーからの差分）
- 誤入力修正は純関数の性質で自然に対応

### 追加/変更要件
- REQ-007, REQ-008（勝敗判定）を追加
- REQ-101, REQ-102, REQ-103（デュースルールのバリエーション）を追加
- REQ-403（全ラリー確定済みの前提条件）を追加
- PRD US-05 のスキップ機能は rule-engine 側では不要（match-recording で「動画を止めて入力を促す」方式に変更）

### 残課題
- PositionOverride の `swapped` / `restored` の連続・交互発生時の厳密な挙動（EDGE-002 として記載済み）
- 3セットマッチ以外のフォーマット（5セットマッチ等）をサポートするか（MVP では 3 セットのみと想定）
