## REQ-001: サーバー / レシーバー推論 🔵

**信頼性**: 🔵 *PRD F-03 + テストケース重点項目*

### Given（前提条件）
- セット開始時の 4 人の立ち位置（SetPlayerPosition[]）が設定されている
- ラリー結果の配列（Rally[]）が渡される
- 全ラリーの得点者またはレットが確定している

### When（実行条件）
- `computeRallyStates(config, initialPositions, rallies, overrides)` を呼び出す

### Then（期待結果）
- 各ラリーのサーバー（player_id）が返される
- 各ラリーのレシーバー（player_id）が返される
- サーバーの立ち位置（左 / 右）が返される

### テストケース

#### 正常系

- [ ] **TC-001-01**: 基本的な得点経過 🔵
  - **入力**: 初期位置（A1:右, A2:左, B1:右, B2:左）、チームAが最初のサーブ権、ラリー #1 でチームA得点
  - **期待結果**: ラリー #1 のサーバーは A1（右コート）。ラリー #2 のサーバーは A1 or A2（チームAの得点が 1=奇数なので左コート側の A2 がサーバー…ではなく、A1 が左に移動してサーブ）
  - **信頼性**: 🔵 *PRD F-03 のルール定義*
  - **備考**: 「得点したチームのサーバーが左右入れ替わる」がバドミントンの正確なルール。得点偶奇でサーバーの左右が決まる。

- [ ] **TC-001-02**: サーブ権の移動 🔵
  - **入力**: チームA がサーブ → チームB が得点
  - **期待結果**: 次のラリーのサーブ権はチームB
  - **信頼性**: 🔵 *PRD F-03「得点者が次のサーブ権を持つ」*

- [ ] **TC-001-03**: 連続得点時のサーバー維持 🔵
  - **入力**: チームAがサーブ → チームA得点（3連続）
  - **期待結果**: 3 ラリー連続でチームAがサーブ権を持つ。サーバーは毎回左右が入れ替わる
  - **信頼性**: 🔵 *バドミントン公式ルール + PRD*

- [ ] **TC-001-04**: 長いラリー経過（20ラリー以上） 🟡
  - **入力**: 20 ラリー分のランダムな得点パターン
  - **期待結果**: 全ラリーのサーバー / レシーバーが正しく算出される
  - **信頼性**: 🟡 *PRD テストケース「通常の得点経過でサーバー/レシーバーが正しく特定されること」から推測*

- [ ] **TC-001-05**: セット開始直後（ラリー配列が空） 🔵
  - **入力**: ラリー配列が空、初期位置（A1:右, A2:左）、チームAがサーブ権
  - **期待結果**: サーバーは A1（右コート、得点 0=偶数）
  - **信頼性**: 🔵 *REQ-001「ラリー配列が空の場合は初期立ち位置とサーブ権に基づく最初のサーバーを返す」*

#### 異常系

- [ ] **TC-001-E01**: 空のラリー配列 🟡
  - **入力**: ラリー配列が空（セット開始直後）
  - **期待結果**: 初期位置に基づく最初のサーバーが返される（EDGE-001）
  - **信頼性**: 🟡 *エッジケースとして推測*

## REQ-006: レット処理 🔵

**信頼性**: 🔵 *PRD F-03「レットはラリー番号を振るがスコアに影響しない」*

### Given（前提条件）
- ラリー配列にレット（`is_let: true`）が含まれている

### When（実行条件）
- スコアおよびサーバーを計算する

### Then（期待結果）
- レットのラリーはスコアに加算されない
- レット後のサーバーはレット前と同じ

### テストケース

#### 正常系

- [ ] **TC-006-01**: レット1回 🔵
  - **入力**: ラリー #1 チームA得点（1-0）→ ラリー #2 レット → ラリー #3
  - **期待結果**: ラリー #3 のスコアは 1-0。サーバーはラリー #2 と同じ
  - **信頼性**: 🔵 *PRD F-03*

- [ ] **TC-006-02**: レット連続 🟡
  - **入力**: レットが3回連続
  - **期待結果**: スコアは変化せず、サーバーも変わらない（EDGE-103）
  - **信頼性**: 🟡 *ルールからの推測*

- [ ] **TC-006-03**: レットと得点の交互 🔵
  - **入力**: 得点 → レット → 得点 → レット → 得点
  - **期待結果**: スコアは得点分のみ加算。レットのラリーはスキップされてサーバー計算
  - **信頼性**: 🔵 *PRD F-03 のレット定義から*

  - **信頼性**: 🔵 *BWF ルール*

  - **入力**: scoreA=22, scoreB=21, target=21, enableDeuce=true, cap=30

  - **信頼性**: 🔵 *BWF ルール*

  - **入力**: scoreA=24, scoreB=22, target=21, enableDeuce=true, cap=30

## REQ-104/105: PositionOverride（トグル方式） 🔵

**信頼性**: 🔵 *PRD F-03 + ユーザヒアリング 2026-04-10*

### Given（前提条件）
- PositionOverride の配列が渡される
- 各オーバーライドには rally_id と team が含まれる（override_type は不要）
- 得点入力後に rule-engine が位置を計算し、実際と違う場合にユーザーがオーバーライドを入力する

### When（実行条件）
- サーバー / レシーバーの立ち位置を計算する

### Then（期待結果）
- オーバーライドが記録されたラリーで、当該チームの左右が直前の表示状態からトグル（反転）される
- 以降のラリーはトグル後の状態を基準に推論が継続される

### テストケース

#### 正常系

- [ ] **TC-104-01**: 1回のトグルで反転 🔵
  - **入力**: ラリー #5 で チームA にオーバーライド
  - **期待結果**: ラリー #5 以降、チームAのペアの左右がルール計算から反転した状態で推論
  - **信頼性**: 🔵 *PRD F-03「実際の立ち位置を現状として採用」+ ユーザヒアリング*

- [ ] **TC-104-02**: 2回のトグルで元に戻る 🔵
  - **入力**: ラリー #5 でオーバーライド、ラリー #10 でオーバーライド
  - **期待結果**: ラリー #5-9 は反転状態、ラリー #10 以降は元の状態
  - **信頼性**: 🔵 *ユーザヒアリング「swapとrestoreがセットの必要は無い」→ トグル方式*

- [ ] **TC-104-03**: 両チーム同時オーバーライド 🔵
  - **入力**: ラリー #5 で チームA にオーバーライド、同ラリーで チームB にもオーバーライド
  - **期待結果**: 両チームとも独立して反転状態
  - **信頼性**: 🔵 *ユーザヒアリング「AかBのどちらか、または両方が入れ替わったことを入力」*

#### 境界値

- [ ] **TC-104-B01**: 3回連続トグル（奇数回 = 反転状態） 🔵
  - **入力**: ラリー #3, #7, #12 でチームAにオーバーライド
  - **期待結果**: #3-6 反転、#7-11 元に戻る、#12以降 再び反転
  - **信頼性**: 🔵 *トグル方式の論理的帰結*
