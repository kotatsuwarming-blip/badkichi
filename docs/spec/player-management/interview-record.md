# player-management ヒアリング記録

**作成日**: 2026-06-01
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

data-foundation で確定済みの `players` テーブル・RLS・制約を出発点に、UI 層として未確定の
製品判断（重複名の扱い・削除時の振る舞い）を明確化するためヒアリングを実施した。

## 事前に確定できた事項（コード調査のみで解決、質問不要）

| 論点 | 調査で判明した事実 | 出典 |
|---|---|---|
| 管理権限 | group_members にロール列なし → メンバー全員が管理可 | initial_schema.sql / RLS is_member_of |
| 削除方式 | hard DELETE ポリシー無し → ソフト削除一択 | players RLS（select/insert/update のみ） |
| 入力制約 | name 1〜50字(trim後)、handedness 3択既定unknown | players CHECK 制約 |
| アカウント連動 | players に user_id 列なし → 非連動 | initial_schema.sql / memory |

## 質問と回答

### Q1: チーム内に同名の選手（例:「田中」が2人）の登録を許可するか

**質問日時**: 2026-06-01
**カテゴリ**: 未定義部分詳細化
**背景**: players.name は schema 上 UNIQUE 制約が無く、許可/警告/禁止のいずれも実装可能。
禁止を選ぶ場合のみ追加 migration（UNIQUE 化）が必要になるため、方針確定が必要だった。

**回答**: **許可**（推奨案を採用）

**信頼性への影響**:
- REQ-102（同名登録許可）・EDGE-004 を 🔵 で確定。
- 追加 migration 不要が確定 → prep.md（ユーザー準備タスク）不要。

---

### Q2: 過去の試合に出場している選手を削除しようとしたときの振る舞い

**質問日時**: 2026-06-01
**カテゴリ**: 未定義部分詳細化 / 既存機能への影響
**背景**: soft delete のため履歴は player.id 経由で保持されるが、削除操作時に
「警告するか / 無警告か / そもそも削除不可にするか」は UX 判断で未確定だった。

**回答**: **無警告でソフト削除**（最小構成志向）

**信頼性への影響**:
- REQ-103（無警告ソフト削除）・REQ-104・EDGE-006 を 🔵 で確定。
- 「N 試合に出場」カウント表示は MVP 不要 → UI 簡素化が確定。

---

### Q3: 選手が 0 人のときの一覧画面の表示

**質問日時**: 2026-06-01

**回答**: **空状態の説明文 + 「選手を追加」CTA**

**信頼性への影響**: REQ-201・TC-001-03 を 🟡 → 🔵 に格上げ。

**質問日時**: 2026-06-01
