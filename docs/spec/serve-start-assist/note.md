# serve-start-assist コンテキストノート

**作成日**: 2026-11-01
**関連**: [requirements.md](requirements.md)

## 1. 背景 (なぜやるか)

- 入力時間の最大の要因はライブ記録 (42 分の動画で 40 分) と、ラリーの間の時間 (動画の 80%) まで通しで見ていること (`docs/research/input-automation/analysis.md` §1〜2)。
- 2026-11-01 に戸塚ミックス 1 試合 (3 セット 100 ラリー) の正解をアプリで作り、動画からのサーブ検出とサーバー位置の判定を採点したところ、人の確認を前提にすれば使える精度に届いた (下記 §2)。
- ADR-017 の Stage 3「サーブ / 誰が打ったか → スコア進行の下書き自動化」にあたる。Stage 2 (打点検出) を飛ばして先に出す。打刻の下書き (BL-033) とは独立で、ラリー境界が先に決まると打刻の適合率も 21% → 63% に上がる (HANDOFF §9-10) ので、順序としても先が良い。

## 2. 検出の数字 (2026-11-01、`~/dev/badkichi-ai/`)

採点は 30 秒のクリップ 14 本にかかる 23 サーブ (±1 秒)。生成の流れと採点は HANDOFF §9-10〜9-12。

| 候補の作り方 | 再現 | 余分 (7 分間) |
|---|---|---|
| 追跡の打球候補 + 選手の静止 (serve_detect) | 16/23 | 17 |
| 同上 + 6 秒ルール (終了から 6 秒以内の候補は TrackNet 可視数で選ぶ) | 16/23 | 7 |
| 姿勢の分類器 (4 人の配置 + 手首 + 速度、構え〜サーブを正例) | 18/23 | 8 |
| 上 2 つの和集合 + 6 秒ルール (`serve_combine.py`) | **20/23** | **6** |
| さらに手首種の追跡 (serve_track.py) を和集合 | **21/23** | **14** |
| 全候補 (低しきい値) | 19〜21/23 | 19〜57 |

- 残る見逃し: 奥の選手の座標ノイズで静止が取れない場面 (t150)、クリップの末尾、分類器が 1.4 秒早い場面。
- サーバーのスロット (手前左/右・奥左/右) の 4 択分類器 (`server_slot_clf.py`): セットを 1 つ抜く検証でスロット 91/100、側 (チーム) 97/100、左右 94/100。検出候補の時刻で判定しても 19/20・20/20・19/20。間違いは同じ側の左右。
- 分類器の学習データは戸塚 1 試合 (ダブルス、ベースライン後方 120 cm の三脚、1280×720 30 fps)。別会場・別画角では再学習が要る可能性がある。候補ファイルに信頼度を持たせ、アプリ側はしきい値で出し分けるだけにしておく。
- 処理時間: 姿勢検出が実時間と同程度、TrackNet が実時間の 13 倍 (M2)。候補生成はサーバーの解析ジョブで行う (REQ-402、別単位 video-upload-analysis)。クラウド GPU なら TrackNet も実時間の 1〜2 倍まで縮む見込みで、45 分の試合 1 本あたり 1 時間前後・数十〜数百円の桁 (未検証)。

## 3. 抜けを見つける 3 つの網の根拠 (正解 100 ラリーの集計)

**(a) rule-engine の予測との食い違い**
- 1 本抜けると必ず矛盾が出る: サーブ側が得点していれば同じサーバーが左右を入れ替えるので左右が食い違い、レシーブ側が得点していればサーブ側が食い違う。
- 2 本連続で抜けたとき、サーブ側の 2 連勝なら同じサーバーが同じ箱に戻り矛盾が消える。連続 2 ラリーのうち **17/94 (18%)** がこの組。見逃し率 1 割なら 2 本連続の見逃しは 1 ゲームに 0.3 回程度なので、矛盾が消える 2 本抜けは数ゲームに 1 回。ただし見逃しは条件が揃うと連続する (t150 は 2 本とも静止が取れず落ちた)。

**(b) サーブの間隔**

| 間隔 | 最小 | 10% | 25% | 中央値 | 75% | 90% | 最大 |
|---|---|---|---|---|---|---|---|
| サーブ → 次のサーブ (正常) | 6.7 | 12.7 | 15.1 | 18.8 | 25.2 | 32.0 | 78.7 |
| サーブ → 次の次 (1 本抜け) | 19.3 | 28.9 | 32.9 | 39.7 | 48.2 | 77.3 | 98.4 |
| ラリー終了 → 次のサーブ | 6.7 | 10.9 | 11.9 | 14.2 | 16.8 | 21.7 | 74.4 |

- しきい値 30 秒: 正常な間隔で疑うのが 16/97、1 本抜けを見逃すのが 13/94。35 秒超の正常間隔 8 件は 50〜79 秒がほとんど (インターバル、拾い直し)。
- (a) と独立なので、(a) で消える 2 本抜け (間隔は 40 秒超になりやすい) をここで拾える。
- ミックスダブルス 1 試合の数字。シングルスやテンポの違う相手では中央値がずれるので、しきい値は設定可能にする (REQ-102)。

**(c) 最終得点との本数の差**
- 記録者は最終得点を必ず知っている。21-15 ならラリーは 36 本 + レット。連続抜けで (a)(b) をすり抜けても本数は合わないので、最後の保険になる (REQ-009/111)。

## 4. 「得点者を入力しない」が成り立つ理由と限界

- 競技規則: 得点したチームが次のラリーのサーブ権を持つ (rule-engine REQ-002)。候補 k+1 の画像でサーブ側を確認すれば、ラリー k の得点者が決まる。
- 画像でサーブ側は一目で分かる (シャトルを持って構えている)。検出も側 97% なので、ほとんどは既定値の確認で済む。
- 限界: セットの最後のラリー (次のサーブがない → 最終得点から導く、REQ-110)、抜けがある区間 (埋めるまで得点者が決まらない)、レット (同じ配置が続く、REQ-107)。
- 保険として、候補ファイルにラリー終了の参考時刻 (打球候補の塊の末尾、±2 秒 8/13) を入れ、「ラリーの終わりを見る」で得点者を直接確かめられるようにする (REQ-301)。

## 5. 候補ファイルの形式 (案、kairo-design で確定)

```json
{
  "version": 1,
  "source": { "video_sha256": "...", "fps": 30, "duration_ms": 2658633, "generated_at": "2026-11-01T..." },
  "camera_near_team": "A",
  "candidates": [
    { "t_ms": 155770, "tier": "normal", "score": 0.93, "src": "hit+clf",
      "server_slot": "nearR", "slot_probs": { "nearL": 0.02, "nearR": 0.95, "farL": 0.01, "farR": 0.02 },
      "box": [725, 327, 811, 577], "rally_end_hint_ms": 164250 },
    { "t_ms": 170100, "tier": "low", "score": 0.41, "src": "clf", "server_slot": "farL", "slot_probs": { "...": 0 } }
  ]
}
```

- `tier`: `normal` = 普段提示する候補 (20〜21/23・余分 6〜14 の設定)、`low` = 疑い区間でだけ出す候補。
- `server_slot` は画面の左右で書く (手前右 = 画面右、奥右 = 画面左)。チームへの変換はアプリ側が `camera_near_team` (セット設定、コートチェンジで反転) で行う。
- 選手名・ID は含めない (REQ-406)。
- 生成側: `serve_combine.py` (時刻) + `server_slot_clf.py` (スロット) + `rally_clusters.py` (終了の参考値) の出力をまとめる書き出しスクリプトを badkichi-ai 側に足す (未作成)。解析ワーカーへの移植時はこのスクリプトを入口にする。
- `source.duration_ms` (ファイルの長さ) を入れ、アプリが YouTube の長さと比べてずれ 0 とみなすかを判断する (REQ-113)。

## 7. 要件定義で決めた論点と、設計に残す論点

決めたこと (2026-11-01 ユーザー確認):
- 動画は利用者がアプリにアップロードし、サーバーの解析ジョブが候補を作る (別単位 video-upload-analysis)。運営者の手元で作る経路は検証・障害時用に残す。
- 再生は YouTube。ずれは長さの比較で 0 とみなし、合わなければ最初の候補で 1 回だけ手で合わせる。自動推定はしない (できない)。
- サーブは shots の 1 打目だけ作る。本モードがサーブ・ポジション・得点を入れる主たる流れで、ライブ記録の代替ではなく後継。ラリー終了は別途。
- 得点者は入力せず、次のサーブ側の確認から導く (§4)。
- 抜けの検知は 3 つの網を全部使い、疑い区間でだけ低しきい値の候補を出す (§3)。
- 候補生成は本単位に含めない。ファイルの契約だけ定める (§5)。
- 既存のライブ記録は変えず、別モードにする。

設計に残すこと:
- 候補ファイルの保存先と RLS (REQ-404)。
- 再取り込み時の判断の引き継ぎの突き合わせ幅 (REQ-112 🟡)。
- 疑い区間の見せ方 (タイムライン上の印、区間の再生の既定速度)。
- コートチェンジの指定方法 (既存の仕組みがあるか、EDGE-106)。
- 最初の候補で修正量を合わせる UI と、長さの比較の閾値 0.5 秒 (REQ-113)。
- Storage からの直接再生を出すか (REQ-304 🟡)。
- video-upload-analysis 側: アップロードの上限と再開、ジョブの進捗、原本の削除時期、解析費用の扱い。別途 `/kairo-requirements video-upload-analysis` で起こす。
