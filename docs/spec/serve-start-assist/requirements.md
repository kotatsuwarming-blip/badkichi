# serve-start-assist 要件定義書 — ラリー確認

**作成日**: 2026-11-01 / **改訂**: 2026-11-23 (ADR-020 との整合。改訂箇所は「改訂 2026-11-23」と記す)
**名称**: 単位 ID は `serve-start-assist` のまま。利用者に見せる工程の名前は **「ラリー確認」** (仮称、ADR-020 §1)。
旧「ライブ記録」(動画を見ながら最初の打刻をタップし、ポジションと得点者を入力する工程) を置き換える。
人が見るのは 4 つ: ラリーの開始 (サーブの瞬間)、サーブ打者、ポジション (左右)、結果 (次のサーバーから「どちらが得点したか」
「レットだったか」を判定。得点者は入力しない)。
**作業規模**: match-recording への新しい記録モードの追加 (rule-engine は無変更)、候補ファイルの受け取り、video-playback (YouTube) の再生制御の流用
**依存単位**: match-recording (記録画面・composable)、rule-engine (サーバー/レシーバー推論)、video-playback (再生・シーク)、data-foundation (`rallies` / `shots` / `position_overrides`)、**video-upload / video-analysis-job (別単位: 動画のアップロードと保管、サーバーでの解析ジョブ。候補ファイルを生成して本単位に渡す。親は video-upload-analysis)**、**ai-draft-loop (別単位: 候補と人の判断を保存する二層スキーマ `ai_predictions` / `human_resolutions`、`lead_time_ms`、学習・評価用の書き出し。改訂 2026-11-23)**
**候補の生成ロジック**: `~/dev/badkichi-ai/` の検証コード (HANDOFF §9-10〜9-12) を解析ワーカーに移植する。本単位は候補ファイルの契約 (note.md §5) だけを持つ

## 概要

動画から自動検出した **サーブ候補 (時刻 + サーバーのスロット)** を順に提示し、人が「サーブの瞬間」と「どちらのチームがサーブしているか」を確認するだけで、ラリー境界・得点・サーブ側・左右を含む試合記録を作る記録モード。

いまのライブ記録は、動画を 1 倍速で通しながらショットごとに「打った」を押し、ラリーごとに得点者を入れる (42 分の試合で 40 分、`docs/research/input-automation/analysis.md` §1)。本機能は人の作業を「候補の画像を見て確認する」の 1 種類に揃え、ラリーの間の時間 (動画の 80%) を見なくて済むようにする。

**設計の中心は 3 点**:

1. **得点者は入力しない。** 次のサーブ候補の画像で「どちらのチームがサーブしているか」を確認すれば、競技規則 (得点したチームが次にサーブする) により直前のラリーの得点者が決まる。サーブ側・左右・サーバー・レシーバーは既存の rule-engine が導出する。
2. **検出の取りこぼしは 3 つの網で見つける。** (a) rule-engine の予測 (次は A の右から) と候補のサーバー位置の食い違い、(b) 前の確定サーブからの間隔が長い、(c) セット終了時の最終得点から求めたラリー数と確定数の差。網にかかった区間だけ、普段は出さない低いしきい値の候補を追加で提示し、人に探してもらう。
3. **候補の生成はサーバーの解析ジョブ。** 利用者が動画ファイルをアップロードし、サーバーの解析ワーカーが候補ファイルを作る (別単位 video-analysis-job。アップロードと保管は video-upload)。再生は従来どおり YouTube に任せ、利用者の手元に動画ファイルを置かせない。本単位は候補の提示・確認・保存だけを担う (ADR-013 §6「AI 下書き → 人が確認・訂正」)。
4. **候補と判断は二層で残す** (改訂 2026-11-23)。候補 (AI の予測) と人の判断 (確認・訂正・却下、所要時間) を ai-draft-loop の `ai_predictions` / `human_resolutions` に追記で保存し、人が見たものだけを学習と評価に流す (ADR-020 §2)。本単位は ADR-020 §1 の「記録層」であり、ショット層 (打刻・打者・球種・打点) の下書きは本単位で確定したラリーに対してだけ出る。

背景となる数字 (戸塚ミックス 1 試合、3 セット 100 ラリー、`totsuka/rallies.json` が正解):

| 項目 | 値 | 出典 |
|---|---|---|
| サーブ候補の再現 (±1 秒、23 サーブ) | 20/23 (追跡 + 分類器の和集合)、21/23 (手首種追跡も加えた和集合) | HANDOFF §9-11 / §9-12 |
| 余分な候補 | 7 分間で 6 (20/23 のとき)、14 (21/23 のとき) | 同上 |
| サーバーのスロット (手前左/右・奥左/右) | 91/100 (セット抜き検証)、検出候補の時刻で 19/20。側 97/100、左右 94/100 | HANDOFF §9-11 |
| サーブ → 次のサーブの間隔 | 中央値 18.8 秒、90% が 32 秒以内。1 本抜けると 10% 点で 28.9 秒、中央値 39.7 秒 | 本書 note.md |
| 2 本連続で抜けても矛盾が出ない組 (サーブ側の 2 連勝) | 17/94 (18%) | 同上 |

## スコープ

### 含む
- 解析ジョブが生成したサーブ候補ファイルの受け取り (試合単位、ジョブの再実行で置き換え)
- 候補を順に提示する記録モード (静止画 + 前後の短い再生、rule-engine の予測とサーバー検出の並記、確定 / 違う / レット / 時刻の微調整)
- 候補の確定からの rule-engine 連携 (確定したサーブ側 = 直前ラリーの得点者) と `rallies` / `shots` / `position_overrides` への保存
- 候補と人の判断の `ai_predictions` / `human_resolutions` への保存、候補ごとの `lead_time_ms` の計測 (改訂 2026-11-23)
- 抜けの疑い (予測との食い違い・間隔・本数) の検知と、疑い区間での低しきい値候補の提示・手動追加
- セット終了時の最終得点の入力と本数の突き合わせ
- 既存のライブ記録 UI・注釈・統計のコードを変えないこと (ライブ記録は主経路ではなくなる。REQ-205)

### 動画ファイルと再生の扱い (ユーザー決定 2026-11-01、2026-11-23 に再確認)
- 候補の生成に使う動画ファイルは、利用者がアプリにアップロードする (別単位 video-upload)。運営者だけでなく利用者自身が使えるようにするため。
- 再生は YouTube に任せる (既存の記録・注釈と同じ)。利用者のローカルにファイルを置く必要をなくす。
- 候補の時刻は「アップロードしたファイルの先頭からの秒数」。同じファイルを YouTube に上げていれば YouTube の時刻とのずれはほぼ 0 (南区の実測で 0.06 秒 = 2 フレーム)。ずれの自動推定はできない (YouTube の埋め込みプレーヤーから映像・音声を読めず、サーバーから YouTube を取得して比べるのは利用規約に反する) ので、長さの比較と最初の候補での 1 回の手合わせで扱う (REQ-113)。
- アップロードしたファイルを Storage から直接再生する選択肢は**採らない** (作者決定 2026-11-23: 再生は YouTube だけ、動画は解析用のアップロードのみ。原本は解析後に削除が既定、ADR-020 §6)。旧 REQ-304 は不採用。

### 含まない
- 動画のアップロード、解析ジョブの実行・進捗・費用、原本の保管と削除 (別単位 video-upload / video-analysis-job。候補ファイルの契約だけを本単位で定める)
- ショット (サーブ以外の打刻) の下書き。ショット層の下書きと確認は ai-draft-loop で、本単位で確定したラリーに対して行う
- ラリー終了時刻の確定 (候補の塊の末尾は参考値として持つが、確定はしない。`rallies` に終了時刻の列は無い)
- YouTube 動画とのずれの自動推定 (不可能。REQ-113 の手合わせで扱う)
- 得点板の読み取り (ユーザー判断 2026-10-17: 無い会場が多い)
- シングルス (ルール上は同じ流れで動くはずだが、検出の学習データがダブルスのみ。EDGE-105)

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: 既存の設計文書・rule-engine・競技規則・検証の実測 (HANDOFF) に基づく確実な要件
- 🟡 **黄信号**: 既存実装・検証結果から妥当な推測による要件 (kairo-design で確定)
- 🔴 **赤信号**: 出典のない推測による要件

### 通常要件

- REQ-001: システムは、試合 (`matches`) に紐づく解析ジョブ (video-analysis-job) が生成したサーブ候補ファイルを受け取り、候補の列 (動画時刻 ms、信頼度、サーバーのスロット = 手前左/手前右/奥左/奥右とその確率、生成元の種別) を **`ai_predictions` に追記**しなければならない (target_type = `rally_candidate`、target_id = 候補 ID、field = `start_ms` / `server_slot`、ai_model_version = 候補ファイルの生成モデル版、batch_id = 解析ジョブ ID。ai-draft-loop REQ-001 / REQ-006 の経路。改訂 2026-11-23)。運営者が手元で作った候補ファイルを手動で取り込む経路も残す (検証・障害時用) 🔵 *HANDOFF §9-11 の `serve_combine.py` / `server_slot_clf.py` の出力項目 + ユーザー決定 2026-11-01 (サーバー解析)*
- REQ-002: システムは、候補を動画時刻順に 1 つずつ提示し、各候補について「候補時刻の静止画」と「候補の前後 (−1.5 秒〜+1.5 秒) の繰り返し再生」を提供しなければならない 🔵 *候補の時刻誤差は ±1 秒以内 (再現の定義) + 既存の注釈ループ再生の流用*
- REQ-003: システムは、各候補に rule-engine の予測 (次のサーブ側チーム、サーバーの左右、サーバーとレシーバーの選手名) と、検出のサーバー位置 (スロットを `camera_near_team` でチームに変換したもの) を並べて表示し、両者が食い違う場合は強調表示しなければならない 🔵 *rule-engine REQ-002/003 + サーバー位置の検出 側 97%・左右 94%*
- REQ-004: システムは、候補に対する操作として「サーブとして確定」「サーブではない (捨てる)」「レット (前のラリーのやり直し)」「時刻の微調整 (フレーム単位の前後移動)」を提供しなければならない 🔵 *match-recording REQ-006 の入力種別 (得点・レット) の読み替え + video-playback のフレーム送り*
- REQ-005: システムは、候補の確定時にサーブ側チームを確定させなければならない。既定値は rule-engine の予測とし、人が検出側または手動で上書きできること 🔵 *競技規則 + 本書「得点者は入力しない」方針*
- REQ-011 (改訂 2026-11-23): システムは、候補への人の判断を **`human_resolutions` に追記**しなければならない。確定 (時刻そのまま・サーバー検出どおり) = `confirmed`、時刻を動かした / サーブ側または左右を変えた = `corrected` (field ごとに 1 行)、「サーブではない」= `rejected`、手動追加 = prediction_id が null の `corrected`。各行に候補が提示されてから判断までの `lead_time_ms` を記録する (ai-draft-loop REQ-002 / REQ-016)。確定で作られたラリーに対しては、`rally_candidate` の予測を新しい rally の target に写した予測行も追記し、resolution はそれを参照する 🔵 *ADR-020 §2 (確認も訂正も学習データ)。旧 REQ-302 (任意の訂正履歴) を必須に格上げして置き換え*
- REQ-006: システムは、候補 k+1 の確定で確定したサーブ側チームを、直前に確定したラリー k の得点者 (`point_winner`) として rule-engine (`applyRally`) に渡し、算出されたサーブ側・サーバー位置・サーバー・レシーバーをラリー k+1 に denormalize 保存しなければならない 🔵 *rule-engine REQ-002 (得点チームが次のサーブ権) + match-recording REQ-007*
- REQ-007: システムは、確定したサーブ時刻をラリーの `video_start_timestamp_ms` に保存し、ラリーの 1 打目 (`shots.shot_number = 1`、サーブ) だけを同じ時刻で作成しなければならない。2 打目以降は作らない。1 打目の `input_source` は候補の時刻をそのまま使った場合 `'ai'`、人が時刻を動かした場合または手動追加の場合 `'manual'` とする 🔵 *ユーザー決定 2026-11-01「1 打目だけ入れてよい」+ shots.input_source CHECK ('manual','ai')*
- REQ-008: システムは、現在のスコア・サーブ権・サーバー・レシーバー、確定済みラリーの一覧、残りの候補数を表示しなければならない 🔵 *match-recording REQ-008/009 の流用*
- REQ-009: システムは、セット終了時に最終得点 (チーム A・B の点数) の入力を求め、「得点の合計 + レット数」と確定済みラリー数を突き合わせて差を表示しなければならない 🔵 *競技規則 (1 ラリー = 1 点、レットは加点なし) + 本書「3 つの網」(c)*
- REQ-010: システムは、直前に確定したラリーの取り消し (確定の解除、ラリー行とショット行の物理削除、rule-engine 状態の復元) を提供しなければならない 🔵 *match-recording REQ-110 (統一「取り消し」) の流用*

### 条件付き要件

- REQ-101: 候補のサーバー位置 (チーム・左右) が rule-engine の予測と食い違う場合、システムは候補を「抜けの疑い」として印を付け、人に (a) 予測が正しい (検出の誤り)、(b) 検出が正しい (前にラリーが抜けている、または左右入替)、のどちらかを選ばせなければならない 🔵 *検出の側 97%・左右 94% なので食い違いの多くは抜けか入替*
- REQ-102: 前に確定したサーブからの間隔がしきい値 (既定 30 秒、設定可能) を超える候補を提示する場合、システムは「この間にラリーが抜けている可能性」を表示し、疑い区間 (前の確定サーブ + 5 秒 〜 現在の候補 − 5 秒) を示さなければならない 🔵 *正常な間隔は 90% が 32 秒以内、1 本抜けの間隔は 90% が 28.9 秒以上 (note.md §2)*
- REQ-103: 疑い区間が示された場合、システムは当該区間に限って低しきい値の候補 (候補ファイルの `tier = 'low'`) を追加で提示し、人が確認できるようにしなければならない 🔵 *HANDOFF §9-10「全候補なら再現 19/23 余分 57」、§9-11 分類器 min-run 5 で 19/23 余分 19。普段出すと余分が多すぎるが、区間を絞れば使える*
- REQ-104: 疑い区間に候補が無い場合、または人がどの候補も採らない場合、システムは区間内の任意の時刻を手動でサーブとして追加できなければならない (video-playback のシーク + フレーム送り + 「ここをサーブにする」) 🔵 *再現 87〜91% なので手動の補完は必須*
- REQ-105: 人が「サーブではない」を選んだ候補は、システムはラリーを作らず、候補を却下済みとして記録し、同じセッション内で再提示してはならない 🔵 *余分な候補 (7 分で 6〜14) を 1 回の判断で済ませるため*
- REQ-106: 候補が「レット」として確定された場合、システムは当該ラリーを `is_let = true`・`point_winner = NULL` で保存し、スコアとサーブ権を変えずに次の候補へ進まなければならない 🔵 *rule-engine REQ-006 + match-recording REQ-102*
- REQ-107: 直前の確定ラリーと同じサーバー・同じ左右の構えが続けて確定された場合 (レットまたはサーブ側の 2 連勝で 2 本抜けたとき)、システムは「レット」と「2 本抜けの疑い」の両方を提示し、間隔が REQ-102 のしきい値を超えていれば抜けの疑いを既定にしなければならない 🟡 *2 連勝で配置が戻る組は 18% (note.md §3)。既定の選び方は推測*
- REQ-108: 候補の確定で左右が予測と食い違い、かつ人が「検出が正しい (入替)」を選んだ場合、システムは当該チームの `position_overrides` を記録し rule-engine (`applyOverride`) を適用しなければならない 🔵 *match-recording REQ-105 + rule-engine REQ-104*
- REQ-109: セットの最初の候補を確定する場合、システムはセット設定 (`first_serving_team` / `camera_near_team_at_start`) と初期立ち位置を所与とし、サーブ側の確認を省略してよい 🔵 *match-recording REQ-002/003 + rule-engine REQ-001*
- REQ-110: セットの最後のラリー (最終得点に達した後) の得点者は次のサーブが無いため、システムは最終得点 (REQ-009) から得点者を導出しなければならない。最終得点が未入力の場合は人に得点者を直接入力させる 🔵 *競技規則 + REQ-009*
- REQ-111: 最終得点から求めたラリー数と確定済みラリー数に差がある場合、システムは差の本数を表示し、未解決の疑い区間と、確定サーブ間の間隔が長い順の区間を候補として提示しなければならない 🔵 *本書「3 つの網」(c) + note.md §2*
- REQ-112: 解析ジョブを再実行して新しい候補ファイルが届いた場合、記録を始める前なら黙って置き換え、記録を始めた後なら「そのセットの記録をやり直す」ことを確認してから判断をすべて捨てて置き換えなければならない 🔵 *ユーザー確認 2026-11-01 (判断の引き継ぎは要らない)*
- REQ-113: 候補の時刻はアップロードしたファイルの先頭からの秒数である。システムは、ファイルの長さと YouTube 動画の長さを比べ、差が 0.5 秒以内ならずれ 0 として候補の時刻をそのまま使わなければならない。差が 0.5 秒を超える場合 (冒頭を切って上げた動画など)、システムは最初の候補で人がフレームを合わせた修正量を記憶し、以降の全候補に同じ修正量を適用しなければならない。修正量は後からやり直せること 🔵 *ユーザー決定 2026-11-01 (再生は YouTube、ずれの自動推定は不可) + 南区の実測 (ずれ 0.06 秒)*

### 状態要件

- REQ-201: 候補ファイルがまだ無い試合 (解析ジョブ未実行・実行中・失敗) では、システムは本モードを開始させず、ジョブの状態とアップロードへの導線を表示しなければならない 🔵 *REQ-001*
- REQ-202: 動画がロード未完了・バッファ中の状態では、システムは候補の確定操作を無効化しなければならない 🔵 *match-recording REQ-202*
- REQ-203: セットが決着済み (最終得点入力済みで本数が一致) の状態では、システムは当該セットへの候補確定を不可とし、次セットの候補へ進む導線を出さなければならない 🔵 *match-recording REQ-203*
- REQ-204: 疑い区間が未解決のまま次の候補へ進もうとした場合、システムは進めてよいが、未解決の疑いを一覧に残し、セット終了時 (REQ-111) に再提示しなければならない 🟡 *人の作業を止めないため。残し方は kairo-design*
- REQ-205 (改訂 2026-11-23): ラリー確認は、ラリーの開始・サーブ打者・ポジション (左右)・結果 (得点かレットか) を入れる**唯一の主経路**であり、旧ライブ記録を置き換える。既存のライブ記録 UI はコードを変えずに残すが、動画 (解析ジョブ) の無い試合の最終手段としてだけ提供し、動画のある試合では既定でラリー確認に導く。ライブ記録で記録済みのセットはラリー確認で開かず (二重記録の防止)、未記録のセットはラリー確認で記録する 🔵 *ADR-020 §1 (作者決定 2026-11-23「ライブ記録は AI に置き換える」) + ADR-017 §3 (UI のコードは変えない)*

### オプション要件

- REQ-301: システムは、候補ファイルにラリー終了の参考時刻 (打球候補の塊の末尾) が含まれる場合、「ラリーの終わりを見る」操作でその付近 (−3 秒〜+1 秒) を再生してよい 🔵 *HANDOFF §9-10 塊の末尾 ±2 秒 8/13。得点者を画像で確かめたいときの保険*
- ~~REQ-302: 訂正履歴の保存 (任意)~~ → REQ-011 に格上げ (必須、二層スキーマ)。改訂 2026-11-23
- REQ-303: システムは、候補の信頼度が高い順ではなく動画時刻順に提示することを既定とし、設定で「疑いのある候補だけ提示」に切り替えられてよい 🔴 *熟練者向けの短縮。需要は未確認*
- ~~REQ-304: Storage からの直接再生 (任意)~~ → **不採用**。再生は YouTube だけ、原本は解析後に削除が既定 (作者決定 2026-11-23、ADR-020 §6)

### 制約要件

- REQ-401: システムは rule-engine (`app/utils/rule-engine/`) を無変更で利用しなければならない。得点者の導出 (REQ-006) と抜けの検知 (REQ-101) は match-recording 側の composable で行う 🔵 *ADR-002 + rule-engine REQ-401*
- REQ-402: システムは候補の生成 (動画解析) を記録画面やブラウザで行ってはならない。解析はサーバーの解析ジョブ (video-analysis-job) が担い、本単位は候補ファイルの形式 (JSON、note.md §5) だけを契約として定める 🔵 *ユーザー決定 2026-11-01 + 解析は Python + GPU で実時間の数倍 (STATUS §D)*
- REQ-403: システムは既存のライブ記録 UI (match-recording REQ-005〜007) の画面・composable・保存形式のコードを変えてはならない。ラリー確認は同じ録画系テーブルに同じ列構成で書き、加えて `ai_predictions` / `human_resolutions` に追記する 🔵 *stats-dashboard / shot-annotation が rallies / shots を直接読む (match-recording REQ-410)*
- REQ-404: システムは候補ファイルを試合に紐づく添付としてサーバーに保存する場合、Group の RLS (`is_member_of(matches.group_id)`) に従わなければならない 🔵 *data-foundation RLS 方針*
- REQ-405: システムは画面の全文言を i18n locales (ja/en) 経由で表示しなければならない 🔵 *match-recording REQ-405*
- REQ-406: システムは候補ファイルに選手名・個人を特定する情報を含めてはならない (スロットとチームのみ)。選手への対応付けは rule-engine の初期立ち位置から行う 🔵 *候補生成は公開リポジトリ外で行い、選手名を書かない運用 (HANDOFF §7)*

## 非機能要件

### パフォーマンス

- NFR-001: 「次の候補へ」を押してから、その候補の静止画と前後の再生が画面に出るまでの待ち時間は 0.3 秒以内でなければならない (候補ごとに待たされると、1 ゲーム 50 回の判断で数分のロスになる) 🟡 *数値は目安。video-playback のシークの実測で決める*
- NFR-002: 1 ゲーム (動画 15 分、39 ラリー) の記録にかかる人の作業時間は 8 分以内でなければならない (現在のライブ記録は動画と同じ 15 分)。内訳の見込み: 候補 39 本 + 余分 15 本の判断 × 5 秒 = 4.5 分、抜け 3〜4 本を区間から探す × 30 秒 = 2 分 🟡 *目標値。戸塚第 1 ゲームの候補で実測して見直す*
- NFR-003: 候補の確定から次の予測表示までの遅延は 100 ms 以内でなければならない 🔵 *match-recording NFR-002*
- NFR-004: YouTube の埋め込みプレーヤーのシーク精度 (0.1 秒程度) の範囲で候補の静止画を出せればよく、フレーム単位の正確さは要求しない。フレーム送りは video-playback の既存の実装 (短い秒数のシーク) を使う 🟡 *YouTube IFrame API にはフレーム送りが無い。既存の注釈ループと同じ制約*

### セキュリティ

- NFR-101: 候補ファイルと記録は他 Group から取得・更新できてはならない 🔵 *data-foundation RLS*

### ユーザビリティ

- NFR-201: 候補への操作 (確定 / 却下 / レット / 前後フレーム / サーブ側の切替) はキーボードだけで行えなければならない 🔵 *match-recording NFR-201 + 注釈パスのキー操作の慣習*
- NFR-202: 抜けの疑いは「なぜ疑っているか」(予測との食い違い / 間隔 N 秒 / 本数の差 N 本) を文言で示さなければならない 🟡 *人が判断する前提のため*
- NFR-203: 候補の静止画には検出したサーバーの枠 (または位置) と予測のサーバー名を重ねて表示し、画像を見るだけで「誰がどこからサーブか」を照合できなければならない 🟡 *候補ファイルに枠の座標を含める前提 (serve_detect の `box`)*

### 保守性

- NFR-301: 候補ファイルの形式はバージョン番号を持ち、未知のバージョンは取り込みを拒否しなければならない 🟡 *候補生成側の改良で項目が増える見込み*
- NFR-302: 本モードの composable は候補の読み込み / 提示 / 判断の保存 / 抜けの検知に分割し、Vitest で「得点者の導出」「抜けの検知の 3 条件」「本数の突き合わせ」を単体テストしなければならない 🔵 *ADR-012 + match-recording NFR-302/303*

## Edgeケース

### 入力検証

- EDGE-001: 候補ファイルの時刻が動画の長さを超える、または負の場合 → 当該候補を無視し、件数を取り込み結果に表示する 🔵
- EDGE-002: 同じ時刻 (±1 秒) に複数の候補がある場合 → 信頼度の高い 1 つに畳み、他は低しきい値の候補として扱う 🔵 *serve_combine.py の重なり処理と同じ*
- EDGE-003: 候補の時刻を人が 1 秒を超えて動かした場合 → 動かした時刻で確定し、`input_source = 'manual'`、`human_resolutions` に `corrected` として元の予測への参照と新しい時刻を残す (REQ-007 / REQ-011) 🟡

### データ整合・状態遷移

- EDGE-101: 2 本連続で抜け、かつサーブ側の 2 連勝で配置が戻っている場合 → 予測との食い違いは出ない。間隔 (REQ-102) または本数 (REQ-111) で見つける。どちらにもかからない場合は検出できないことを受け入れ、最終得点の差として必ず表面化させる 🔵 *note.md §3*
- EDGE-102: 間隔のしきい値をインターバル (11 点、セット間) や拾い直しが超える場合 → 疑いは出るが、人が「抜けなし」として閉じられる。正常な間隔で 30 秒を超えるのは 16/97 🔵 *note.md §2*
- EDGE-103: 候補が「サーブ前のシャトル渡し」である場合 (余分の典型) → 静止画でシャトルを手に持ち替えている・ラケットを構えていないのが見えるので人が却下する。却下後の次の候補は同じ構えのはずなので、REQ-107 の重複判定は却下済み候補を対象外とする 🔵 *HANDOFF §9-10 の発見*
- EDGE-104: ファイルと YouTube の長さの差が 0.5 秒を超え、かつ途中をカットした動画でずれが一定でない場合 → 最初の候補で合わせた修正量では後半が合わない。人が候補ごとにフレームを合わせることになる (±1 秒の前後再生で見つかる範囲なら作業は続けられる)。注意書きを出す 🟡
- EDGE-105: シングルスの試合 → rule-engine はシングルスを同一選手の左右スロットとして扱うため流れは同じだが、サーバー位置の検出はダブルスで学習したもので精度は未確認。取り込みは許可し、画面に注意書きを出す 🟡 *singles-support note.md §1*
- EDGE-106: セット途中でコートチェンジ (手前と奥が入れ替わる) がある場合 → `camera_near_team` が変わるので、検出スロット → チームの変換を当該ラリー以降で反転する。コートチェンジの時点は人が指定する (既存のセット設定の仕組みに従う) 🟡 *戸塚セット 3 で発生 (HANDOFF §9-10)*
- EDGE-107: 最終得点の入力が誤っていた場合 → 本数の差が出るので人が気づける。最終得点は後から修正でき、修正で差を再計算する 🔵
- EDGE-108: 候補ファイルの `camera_near_team` 前提 (手前 = どちらのチーム) がセット設定と逆の場合 → 検出の側がすべて食い違うので、最初の 2〜3 候補で全部食い違ったら「カメラの手前チームの設定を確認」を促す 🟡

### 境界値

- EDGE-201: 動画の先頭 1.5 秒以内・末尾 1.5 秒以内の候補 → 前後再生の範囲を動画内に切り詰める 🔵
- EDGE-202: 候補が 0 件の試合 → 本モードは開始できるが全ラリーを手動追加 (REQ-104) することになる。開始時に件数 0 を警告する 🔵
- EDGE-203: 直前の確定サーブから 6 秒未満の候補 → 競技上あり得ない (正解の最小 6.7 秒) ので低しきい値の候補扱いにし、通常の提示から外す 🔵 *HANDOFF §9-10/9-11 の 6 秒ルール*
