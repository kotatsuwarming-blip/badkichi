# data-foundation ヒアリング記録

**作成日**: 2026-04-17
**ヒアリング実施期間**: 2026-04-16 〜 2026-04-17

## ヒアリング目的

PRD（`.dcs/20260328153038_badminton_analytics/prd.md`）および ADR-002（単位分割）から
data-foundation の責務は明確だが、Supabase 環境構築・認証方式・Group 参加 UX・削除ポリシー・
型定義方針などの具体策が未確定だったため、開発者へのヒアリングで確定させた。

開発者はデータエンジニアで Web 開発初学者のため、概念説明（マイグレーション、Group、
シードデータ、フォーム入力、バリデーション、型生成の選択肢）を適宜挟みながら進めた。

## 質問と回答

### Q1: Supabase の開発環境はどう用意するか

**質問日時**: 2026-04-16
**カテゴリ**: 既存設計確認
**背景**: PRD §5.1 で「Supabase（PostgreSQL）」とあるが、dev/prod の分離、ローカル vs クラウドが未定

**回答**: **クラウドのみ（dev/prod プロジェクト分離）**

**信頼性への影響**: REQ-001 を 🔵 として確定。ローカル Supabase（Docker）は不要と判断、
REQ-403 に制約として明記。

---

### Q2: 認証方式は何を MVP で使うか

**質問日時**: 2026-04-16
**カテゴリ**: 既存設計確認
**背景**: PRD §4 で「Supabase Auth による認証」とあるが、プロバイダ選定が未定

**回答**: **Google OAuth**
**理由**: Google アカウントであれば YouTube 動画へのアクセスも同じアカウントで完結するため
（PRD §3.1 F-02 の YouTube 動画連携と整合）

**信頼性への影響**: REQ-002 を 🔵 として確定。Email/Password、Magic Link は MVP 対象外。

---

### Q3: Group への参加フロー

**質問日時**: 2026-04-16
**カテゴリ**: 未定義部分詳細化
**背景**: PRD §1 マルチテナント設計で「Group 単位でのデータ共有」とあるが、新規ユーザーが
どうやって Group に紐付くかが未定

**初回回答**: 「グループという概念がわからない。もう少し説明して」
→ アシスタントから Group = 組織としての所属単位（例: ○○バドミントンクラブ）であり、
複数メンバーがデータを共有する単位であることを具体例で説明。

**再質問**（推奨フロー詳細説明後）:
**回答**: **招待コード方式**
- 最初のユーザーが Group を作成
- 管理者が招待コード（例: BDK-4X7P）を発行、LINE 等で共有
- 新規ユーザーは Google ログイン後、コードを入力して join

**信頼性への影響**: REQ-102, REQ-103 を 🔵 として確定。`group_invitations` テーブルが
必要と判明、スキーマに追加。

---

### Q4: DB マイグレーションの運用

**質問日時**: 2026-04-16
**カテゴリ**: 未定義部分詳細化
**背景**: スキーマ管理方法が未定

**初回回答**: 「マイグレーションも何のことかわかりません」
→ アシスタントから「DDL スクリプトをバージョン管理して順番に適用する仕組み」として説明
（dbt / Alembic / Flyway のアナロジー）。

**再質問**:
**回答**: **Supabase CLI のマイグレーション**（`supabase/migrations/` 配下の連番 SQL）

**信頼性への影響**: REQ-004 を 🔵 として確定。NFR-302（追記のみ運用）も標準原則として追加。

---

### Q5: 削除ポリシー

**質問日時**: 2026-04-16
**カテゴリ**: 未定義部分詳細化
**背景**: 選手を削除した時、その選手を含む過去の試合データをどう扱うかが未定

**回答**: **最終的には論理削除でよいが、MVP は削除機能なし**

**信頼性への影響**: REQ-402 を 🔵 として確定（MVP 削除機能なし）。REQ-301 を 🟡 として
将来移行に備える記述を追加（deleted_at カラムを入れるかはテーブル設計時に判断）。

---

### Q6: TypeScript の DB 型定義

**質問日時**: 2026-04-16
**カテゴリ**: 未定義部分詳細化
**背景**: DB スキーマに対応する TypeScript 型をどう用意するか未定

**初回回答**: 「選択肢が分からないので説明して」
→ アシスタントから 3 オプション（Supabase CLI 自動生成 / 手書き interface / Zod）を比較説明。

**再質問**:
**回答**: 当初「Supabase CLI 自動生成 (Recommended)」を提案したが、開発者から
「フォーム入力とバリデーションの意味がわからない」との質問があり概念説明へ。

**概念説明後の再質問**:
**回答**: バリデーションライブラリ候補の比較を求められ、Zod/Valibot/Yup/Joi を公平に比較。
**最終回答**: **Supabase CLI 自動生成 + Zod 併用**
- DB 型: `supabase gen types typescript` で自動生成
- バリデーション: Zod（Pydantic 類似、ドキュメント最多、Nuxt UI 公式サポート）

**信頼性への影響**: REQ-006, REQ-007 を 🔵 として確定。

---

### Q7: 招待コードの運用

**質問日時**: 2026-04-16
**カテゴリ**: 詳細化
**背景**: 招待コードの有効期限・使用回数制限の方針が未定

**回答**: **有効期限あり（7 日）+ 使用回数制限なし**

**信頼性への影響**: REQ-102, EDGE-101 を 🔵 として確定。

### Q8: 認証 UI の単位配置

**質問日時**: 2026-04-17
**カテゴリ**: スコープ調整
**背景**: ADR-002 で data-foundation に「認証」が含まれるが、UI まで含めるか未定

**初回回答**: 「なぜ含めることを推奨するのですか？？認証だけでなく、色んなラリーデータも扱いますよね？」
→ 開発者の指摘の通り data-foundation はデータ基盤の単位であるべきで、UI は別単位が適切と
アシスタントが判断を修正。

**再質問**（3 オプション提示）:
**回答**: **新規単位 auth-onboarding を追加**（ADR-002 を 7 → 8 単位に改訂）

**信頼性への影響**:
- data-foundation のスコープが「基盤のみ」に確定
- ADR-004（auth-onboarding 単位追加）を新規作成
- data-foundation の要件から UI 系要件を除外

---

### Q9: シードデータ

**質問日時**: 2026-04-17
**カテゴリ**: 未定義部分詳細化
**背景**: dev 環境の初期データ投入方針が未定

**初回回答**: 「シードデータというのがよくわかりません。また、他の UI のコンポーネントなども
検証環境で確認できるようにするとしたら、そこと関連するのではないかと思って難しいと言っています」
→ 開発者の観点が正鵠を射ていた。seed.sql の目的はまさに「UI 検証のための初期データ」であり、
各 UI 単位の検証ニーズとリンクすることをアシスタントが説明。

**再質問**（3 オプション提示）:
**回答**: **枠組みだけ data-foundation で用意、中身は各単位で追加**

**信頼性への影響**: REQ-008, NFR-201 を 🔵 として確定。data-foundation では
`supabase/seed.sql` ファイルと `pnpm db:reset` 相当のコマンドまでを整備し、
サンプル Group / Player / Match 等の具体データは各単位のタスク内で追記する方針に。

---

### Q10: 黄信号項目の確定（4 件一括）

**質問日時**: 2026-04-17
**カテゴリ**: 詳細化（黄 → 青への確定）
**背景**: 要件定義書の 🟡 黄信号 5 件のうち、ユーザー判断が必要な 4 件を確認

**回答**:
1. **deleted_at カラム**: 最初から全テーブルに入れる（MVP では常に NULL を維持）
2. **Email/Password 認証**: 明示的に無効化する（Supabase Dashboard で disabled に設定）
3. **prod 誤操作ガード**: `pnpm db:reset` にリンク先チェックを実装し、prod なら exit 1
4. **招待コード文字数**: 8 文字（英数字）で開始。将来拡張可能な設計（DB は text 型）

**信頼性への影響**:
- REQ-301（オプション → REQ-405 制約に昇格）🟡 → 🔵
- NFR-103（コード文字数確定）🟡 → 🔵
- TC-002-E01（Email disabled 確認）🟡 → 🔵
- TC-008-E01（db:reset ガード）🟡 → 🔵
- TC-INV-E03 / TC-EDGE-002-01（ユニーク制約確認）🟡 → 🔵

## ヒアリング結果サマリー

### 確認できた事項

- Supabase 環境戦略: クラウドのみ（dev/prod 分離）
- 認証方式: Google OAuth（YouTube 連携と統一）
- Group 参加フロー: 招待コード方式（7 日有効、回数制限なし）
- マイグレーション運用: Supabase CLI
- 削除ポリシー: MVP では削除機能なし、将来論理削除
- 型定義: Supabase CLI 自動生成
- バリデーション: Zod
- シードデータ: 枠組みだけ用意

### 追加/変更要件

- **新規単位 auth-onboarding を追加**（ADR-004）により、data-foundation から UI スコープを除外
- `group_invitations` テーブルをスキーマに追加
- TypeScript 型自動生成フロー（`supabase gen types`）を必須化
- `pnpm db:reset` スクリプト整備を必須化

### 残課題

- 招待コードの具体的な生成方式（DB 関数 / クライアント生成 / Edge Function）は kairo-design
  フェーズで決定
- `deleted_at` カラムを全テーブルに入れるか、論理削除に移行するタイミングで追加するかは
  テーブル設計時に判断
- Supabase Edge Functions を利用するかはまだ未決定（招待コード検証・オンボーディングで使う
  可能性はあるが MVP では Nuxt サーバールートで代替可能）
