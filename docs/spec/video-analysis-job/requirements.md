# video-analysis-job 要件定義書

**作成日**: 2026-11-24 (親: [video-upload-analysis](../video-upload-analysis/requirements.md) から分割。分割前の改訂履歴は親の note.md)
**作業規模**: 中〜大。解析ジョブの台帳 (`analysis_jobs`)、サーバー側の解析ワーカー (本体リポジトリ外の Python をジョブとして実行) の起動契約、出力 (サーブ候補ファイル・ショット層の下書き JSON) の保存と受け渡し、動画分析数の計測
**依存単位**: **video-upload (入力側: 「解析に使える状態」の動画と署名 URL、校正、区間、メタデータ)**、data-foundation (`matches`、新規テーブル `analysis_jobs`)、serve-start-assist (候補ファイルの消費側)、ai-draft-loop (下書き JSON の消費側、Issue #102)、billing (動画分析数。課金は保留中)
**上位の決定**: ADR-020 §6 / §7 (推論は運営のバッチから解析ジョブへ)。ユーザーストーリーは親文書 [user-stories.md](../video-upload-analysis/user-stories.md) にあり、本書は対応する要件を持つ ([user-stories.md](user-stories.md) は対応表)

## 概要

video-upload が `ready` にした動画 1 本に対して解析ジョブを 1 件起こし、GPU を使う解析ワーカーに「動画の取得先・コート 4 隅・試合区間・fps と向き・要求する出力」を渡し、**サーブ候補ファイル** (ラリー確認が読む) と、ワーカーの版が対応していれば **ショット層の下書き JSON** (ai-draft-loop が取り込む) を受け取って保存する。本体はワーカーの中身を知らず、台帳と Storage を介してだけ連携する。原本の保管と削除は本単位の外 (video-upload) で、本単位は原本を消さない。

**設計の中心は 4 点**:

1. **解析はジョブ。** 台帳 (`analysis_jobs`) に状態・進捗・結果を持ち、画面はそれを表示するだけ。ワーカーは本体とは別のプロセス (GPU を使う Python)。
2. **出力は小さなファイルだけ。** 動画はワーカーの外に出さず、選手名も含めない (スロットとチームのみ)。
3. **出力の契約はバージョンつきで、サーブ候補と下書き JSON の両方を返せる。** 同じ動画・同じ校正から、ラリー確認用の候補と注釈確認用の下書きを同じジョブで返せる。ワーカーの中身 (`~/dev/badkichi-ai`) が育っても本体の契約は変えない。
4. **再実行は原本があれば何度でも。** 人がラリー区間を直したあとの再推論や、モデルの版が上がったあとの再解析は、新しいジョブとして起こす。原本が消えていれば再アップロードが要る (video-upload REQ-203)。学習に提供された試合 (既定オン) は DVC に登録され物理削除されないので、同じバケットの原本でいつでも再実行でき、モデル改善後の再現チェック (ADR-020 §3) も badkichi-ai 側がそれを使う。

背景の数字 (検証の実測、`~/dev/badkichi-ai/STATUS.md` §D / HANDOFF §9-11):

| 項目 | 値 |
|---|---|
| 検出の処理速度 (Apple M2) | 姿勢検出 ≈ 実時間と同程度、TrackNet ≈ 実時間の 13 倍 |
| 候補ファイルの大きさ | 数十 KB (JSON)。下書き JSON は数 MB まで |
| 精度 (戸塚 1 試合で学習・検証) | サーブ開始 20/23、サーバーのスロット 91/100。別会場・別画角は未検証 |

## スコープ

### 含む
- 解析ジョブの台帳 (`analysis_jobs`) と状態遷移 (待機 → 実行中 → 完了 / 失敗)、進捗と推定残り時間の表示
- 解析ワーカーの起動契約 (入力: 署名 URL、コート 4 隅、試合区間、fps と向き、要求する出力の種類。出力: 候補ファイル、下書き JSON、ログ、処理時間) と結果の保存
- 候補ファイルの保存と serve-start-assist への受け渡し。下書き JSON の保存と ai-draft-loop の取り込み経路への受け渡し
- 失敗の分類と再実行、時間切れ、二重実行の防止
- 動画分析数の計測 (課金は保留中 (ADR-020 §8) なので計測だけ)
- 運営者向けのジョブ一覧と費用の記録

### 含まない
- 動画のアップロード、同意、校正の取得、原本の保管と削除 (**video-upload**)
- 解析アルゴリズムそのもの (`~/dev/badkichi-ai/`。ワーカーへの移植は本単位の実装タスクだが、精度の改良は L1 ループ)
- ショット層の下書きの**中身** (出す・出さないはワーカー側の版で決まる)
- 候補・下書きの確認と訂正 (serve-start-assist / ai-draft-loop)
- 訂正を使った再学習 (ADR-020 §4 L1、`~/dev/badkichi-ai` 側)
- メール等の外部通知 (アプリ内の表示のみ)

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: 既存の設計文書・ADR・検証の実測に基づく確実な要件
- 🟡 **黄信号**: 既存実装・検証結果・一般的な運用から妥当な推測による要件 (kairo-design で確定)
- 🔴 **赤信号**: 出典のない推測による要件

### 通常要件

- REQ-001: システムは、video-upload が動画を `ready` にしたとき、解析ジョブを 1 件作成し、台帳 (`analysis_jobs`: 試合、動画、状態、進捗、開始/終了時刻、エラー、処理時間、要求した出力、出力の参照、ワーカーと契約の版) に記録しなければならない 🔵 *ジョブ方式の採用 (本書「設計の中心」1) + video-upload REQ-007*
- REQ-002: システムは、ジョブの状態 (待機 / 実行中 / 完了 / 失敗) と進捗 (処理済みの動画時間 / 全体) を試合画面で表示し、完了時にラリー確認 (serve-start-assist) へ進む導線を出さなければならない 🔵 *serve-start-assist REQ-201*
- REQ-003: システムは、解析ワーカーに対して「動画の取得先 (video-upload が発行する期限付き署名 URL)、コート 4 隅の画像座標、試合区間 (任意)、動画の fps と向き、要求する出力の種類」を入力として渡さなければならない 🔵 *HANDOFF §9-3 ホモグラフィ、§9-10 クリップ*
- REQ-004: システムは、ワーカーから「サーブ候補ファイル (JSON、serve-start-assist note.md §5 の形式)」と、ワーカーの版が対応していれば「ショット層の下書き JSON (ai-draft-loop REQ-304 の契約。batch_id、ai_model_version、predictions[])」、および処理時間・ログを受け取らなければならない。あわせて、ワーカーが途中で得た**数値特徴量** (フレームごとの選手の骨格キーポイント、シャトル座標、コート射影の行列、音の立ち上がり時刻の列) を抽出モデルの版つきで受け取り、原本が削除された後も人の確認・訂正と組にして学習に使えるように保存しなければならない。特徴量は後から足せないので、使う予定の無いものも含めて広く保存する。出力の種類ごとに契約のバージョンを持つ 🔵 *ADR-020 §4 L1 (推論は 1 コマンド、出力は下書き JSON) + ADR-013 §6-4 (特徴量はケチらず広く・版つきで保存。訂正 = 教師ラベル)。特徴量の保存は 2026-11-25 に追記 (作者: 利用者の訂正を教師データにしたい。映像の学習利用は別の同意なので、特徴量が無いと訂正が使えなくなる)*
- REQ-005: システムは、サーブ候補ファイルを試合に紐づけて保存し serve-start-assist が読める形で提供し、下書き JSON が出力に含まれる場合は ai-draft-loop の取り込み経路 (REQ-006〜008、Issue #102) に渡さなければならない。下書き JSON の取り込みは、ラリー確認で確定したラリーに対してだけ現在の値に反映される (反映の規則は ai-draft-loop 側) 🔵 *serve-start-assist REQ-001 + ai-draft-loop REQ-006〜008*
- REQ-006: システムは、解析ジョブの完了を「動画分析数」として 1 本記録しなければならない (失敗は記録しない)。billing への加算と上限の強制は billing の実装後 🔵 *billing 要件 + ADR-020 §8 (課金は保留)*
- REQ-007: システムは、解析ワーカーが動画を処理する際に 1280 幅・30 fps 相当に正規化し (大きい動画は縮小、60 fps は間引き)、縦向きの動画は向きの情報に従って回転してから処理しなければならない。候補の時刻は元の動画の秒数で返す 🔵 *検証は 1280×720 30 fps (STATUS)。南区は縦向き (HANDOFF §3)*
- REQ-008: システムは、ジョブの成否にかかわらず原本を削除してはならない。原本の保管と削除は video-upload の保持の理由 (REQ-008 / REQ-103) が司る 🔵 *分割 2026-11-24*

### 条件付き要件

- REQ-101: 解析ジョブが失敗した場合、システムは失敗の種類 (動画が読めない / 校正が無い / 処理の内部エラー / 時間切れ / 契約の不一致) を表示し、原本が残っていれば同じ動画で再実行できなければならない。再実行は新しいジョブとして記録する 🔵
- REQ-102: 同じ動画に対して解析ジョブが待機中または実行中の場合、システムは新しいジョブの作成を受け付けてはならない 🔵 *二重実行の防止*
- REQ-103: 候補ファイルが既にある試合で解析を再実行した場合、システムは serve-start-assist の規則 (記録前なら置き換え、記録後は確認のうえ判断を捨てて置き換え) に従わなければならない。下書き JSON の再取り込みは ai-draft-loop の規則 (確定済みは上書きしない) に従う 🔵 *serve-start-assist REQ-112 + ADR-020 §1*
- REQ-104: 試合区間 (video-upload REQ-006) が指定されている場合、ワーカーはその区間だけを解析し、候補の時刻は動画の先頭からの秒数のまま出さなければならない 🔵 *ADR-013 §6-5 + serve-start-assist REQ-113*
- REQ-105: 解析ワーカーが候補を 1 件も出せなかった場合 (コート内に選手を検出できない等)、システムはジョブを「完了 (候補 0 件)」として記録し、撮影条件 (カメラの位置・高さ) の確認を促さなければならない 🔵 *検出はコート後方 120 cm の三脚で検証 (STATUS §D、BL-008)*
- REQ-106: ジョブの実行時間が上限 (既定: 動画の長さの 5 倍、最大 6 時間) を超えた場合、システムはジョブを失敗 (時間切れ) として終了し、ワーカーを停止しなければならない 🟡 *GPU での処理速度は未実測*
- REQ-107: 人がラリー区間を訂正したあとの再推論 (区間を指定した部分的な再実行) を要求された場合、システムは対象の区間だけを入力にした新しいジョブを起こし、出力は該当ラリーの下書きだけを差し替えなければならない 🟡 *作者指摘 2026-11-24 (入力完了まで原本が要る理由)。要求する側は ai-draft-loop*

### 状態要件

- REQ-201: billing が導入された後、動画分析数が契約の上限に達している Group では、システムはジョブの作成を受け付けず、上限とプランの案内を表示しなければならない。billing 導入前は上限を設けない 🔵 *billing (累計 N 本) + ADR-020 §8*
- REQ-202: ジョブが実行中の状態では、システムは進捗を定期的に更新して表示し、画面を離れても再表示で状態が分かるようにしなければならない 🔵 *REQ-002*
- REQ-203: 製品側の原本が削除済みの状態では、システムは再実行を受け付けず、再アップロードの案内 (video-upload REQ-203) に誘導しなければならない。DVC 登録済みの原本は削除されないので、ここに来るのは学習提供を外した試合と置き換え後だけ 🔵

### オプション要件

- REQ-301: システムは、解析ジョブの完了をアプリ内の通知として表示してよい (メール等は対象外) 🟡
- REQ-302: システムは、運営者が手元で作った候補ファイルを手動で登録する経路 (ジョブを経由しない) を提供してよい (検証・障害時用) 🔵 *serve-start-assist REQ-001*
- REQ-303: システムは、ジョブごとの処理時間・GPU 時間・推定費用を運営者向けに記録してよい (利用者には表示しない) 🟡 *費用の見積 (note.md §2)*
- REQ-304: システムは、ワーカーが解析のついでに縮小したプロキシ動画を返す契約を持ってよい (video-upload REQ-301 の採否に従う) 🟡

### 制約要件

- REQ-401: システムは、解析ワーカーが動画・候補以外のデータ (選手名、他の試合、他の Group) にアクセスできないようにし、ワーカーの出力に選手名・個人を特定する情報を含めてはならない 🔵 *serve-start-assist REQ-406 + 最小権限*
- REQ-402: システムは、解析ワーカーを本体 (Nuxt / Vercel) とは別の実行環境 (GPU を使えるジョブ実行基盤) で動かし、本体は台帳と Storage を介してのみワーカーと連携しなければならない 🔵 *Vercel の関数は長時間・GPU に向かない (ADR-014) + 検出は Python*
- REQ-403: システムは、解析に使うモデルと重みのライセンスを商用利用可能なものに限らなければならない (TrackNetV3: MIT、YOLO11: AGPL-3.0 のため商用はライセンス購入か代替モデルの検討が要る) 🔵 *BL-030*
- REQ-404: システムは、画面の全文言を i18n locales (ja/en) 経由で表示しなければならない 🔵

## 非機能要件

### パフォーマンス

- NFR-001: 解析ジョブは、45 分の試合 1 本を 2 時間以内に完了しなければならない (待機時間を除く) 🟡 *GPU で実時間の 1〜2 倍を見込むが未実測*
- NFR-002: 進捗の表示は 30 秒以内の遅れで更新されなければならない 🟡

### セキュリティ

- NFR-101: 候補ファイル・下書き JSON・ジョブの台帳は、他 Group から取得・作成・更新・削除のいずれもできてはならない 🔵 *RLS*
- NFR-102: ワーカーの認証情報 (service role 等) をクライアントに含めてはならず、ワーカーの起動はサーバー側からのみ行わなければならない 🔵

### ユーザビリティ

- NFR-201: 失敗の表示は「何が起きたか」と「利用者ができること」(撮り直し、校正のやり直し、再実行、運営への連絡) を文言で示さなければならない 🟡
- NFR-202: ジョブの作成時に推定の解析時間を表示しなければならない 🟡

### 運用・保守性

- NFR-301: ワーカーの入出力の契約 (REQ-003 / REQ-004) はバージョン番号を持ち、本体とワーカーを独立して更新できなければならない。不一致は失敗 (契約の不一致) として記録する 🟡
- NFR-302: ジョブの台帳は、運営者が全 Group のジョブの状態・失敗率・処理時間を一覧でき、「実行中」のまま残ったジョブを手で失敗にできなければならない 🟡

## Edgeケース

### 解析の条件

- EDGE-101: カメラが横から・床置きの動画 (南区) → 校正はできても検出が成立しない。候補 0 件またはごく少数。REQ-105 の案内で撮影ガイド (BL-008) に誘導する 🔵 *STATUS §D*
- EDGE-102: 途中でカメラが動いた動画 (戸塚 2395 秒付近) → 校正がずれ、以降の候補の精度が落ちる。serve-start-assist 側の抜け検知で表面化させる 🔵 *HANDOFF §9*
- EDGE-103: 別会場・別画角の動画 → スロット分類器は戸塚 1 試合で学習。精度は未検証。初回は運営者が結果を確認する運用にする 🟡
- EDGE-104: 60 fps・1080p 以上の動画 → 30 fps・1280 幅に正規化して処理 (REQ-007)。候補の時刻は元の動画の秒数で返す 🔵
- EDGE-105: 区間の指定なしで 1 本に複数の試合 → 全体を解析し、候補は全部出す。記録側でセットごとに扱う 🔵
- EDGE-106: 動画の音声が無い・壊れている → 検出は映像のみを使うので影響しない 🔵 *音は不採用 (STATUS 行 6)*

### 状態・運用

- EDGE-201: ワーカーが異常終了して台帳が「実行中」のまま残る → REQ-106 の時間切れで失敗に落とす。運営者が手で失敗にできる (NFR-302) 🟡
- EDGE-202: 動画分析数の上限にちょうど達するジョブが失敗した → 加算しない (REQ-006) ので再実行できる 🔵
- EDGE-203: ジョブ実行中に video-upload 側で原本が削除された (利用者の要求) → ワーカーは署名 URL で取得済みなら完了まで進めてよい。完了後の出力は保存する 🟡
- EDGE-204: 契約のバージョンが本体とワーカーで食い違う → 失敗 (契約の不一致) として記録し、運営者に知らせる 🟡 *NFR-301*

## 受け入れ基準

### 機能テスト

- [ ] `ready` でジョブが作られ、状態と進捗が試合画面に出る (REQ-001 / REQ-002)
- [ ] ワーカーが候補ファイルを返し、serve-start-assist で読める (REQ-003 / REQ-004 / REQ-005)
- [ ] 下書き JSON を返した場合、ai-draft-loop の取り込み経路に渡る (REQ-004 / REQ-005)
- [ ] 失敗の種類が表示され、原本があれば再実行できる。原本が無ければ再アップロードに誘導 (REQ-101 / REQ-203)
- [ ] ジョブは原本を消さない (REQ-008)
- [ ] 完了で分析数が 1 加算、失敗は加算しない (REQ-006)
- [ ] 他 Group から候補・下書き・台帳にアクセスできない (NFR-101)

### 非機能テスト

- [ ] 45 分の試合の解析が 2 時間以内に終わる (NFR-001)
- [ ] 時間切れでジョブが失敗に落ち、ワーカーが止まる (REQ-106)

詳細は [acceptance-criteria.md](acceptance-criteria.md)。
