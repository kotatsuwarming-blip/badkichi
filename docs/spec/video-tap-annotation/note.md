## 1. 背景（なぜやるか）

- 打点パスは「動画を見る → 頭でカメラ視点→真上視点に変換 → コート図へカーソル移動 →
  クリック → 視線を動画へ戻す」の**往復が毎打発生**し、長ラリーで負荷が激しい
  （ドッグフーディング所感 2026-08-28。実測 約20分/試合の主因）。
- 案A = **タップ対象を動画そのものにする**。見えている打点（選手の足元）を直接タップし、
  映像座標→コート座標はシステムが射影変換で自動計算。視線・カーソルの往復が 0 になり、
  タブレットなら指タップになる。
- 比較検討済みの代替案（見送り）: テンキー9ゾーン高速入力（座標が粗くなる）/
  タブレット対応のみ（往復が残る）。

## 2. 確定済みの設計要点

1. **校正**: セット開始時に1回、動画上でコートの**外周4隅**（ダブルスライン×バック
   バウンダリーの交点）をタップ → 4点対応から射影変換（ホモグラフィ、DLT で可解）を計算。
   カメラ固定（三脚）前提。**再校正ボタン**をいつでも押せるようにする（カメラズレ対応）。
2. **タップ規則**: 「打った選手の**足元**（コート平面上の点）」をタップする。シャトルの
   空中位置ではない（ホモグラフィはコート平面にのみ正しい）。ガイド文言で明示する。
3. **変換先の座標系**: 既存の**カメラ基準正規化座標**に合わせる（重要）。
   実データの向きは ADR-017 の「y=0=チームA側」ではなく**カメラ基準**
   （注釈者が見たままタップ / カメラ手前チームの半面 = y ∈ [0.5, 1]。
   `docs/spec/shot-stats/note.md` §「座標の向きはカメラ基準と判明（2026-08-08）」参照）。
   ホモグラフィの変換先 unit rect も「手前 = y=1 側」にすれば既存データと完全互換。
4. **ライン外**: REQ-014 はライン外を範囲外値（<0 / >1）として許容。ホモグラフィは平面全体で
   有効なので外挿でそのまま範囲外座標が得られる（クランプしない）。
5. **適用範囲**: 打点タップ（hit_x/hit_y）に加え、**決着の落下点（land_x/land_y）も同じ
   変換を再利用できる**（クイックパスの落下点入力も動画直接タップ化の候補）。
6. **校正の保存**: セット単位。additive migration（例: `annotation_calibrations` テーブル
   （set_id, 4隅の映像座標, created_at）or sets への jsonb 列。設計時に決定）。
   保存済み座標データは変換後の値なので、校正のやり直しは**以降のタップにのみ**影響する。
7. **既存コート図の扱い**: タップ結果の点を表示する**確認用ミニマップ**として残す
   （タップ→ミニマップに点が打たれる = フィードバック）。従来のコート図タップも
   フォールバックとして残すか（YouTube でコート4隅が映らないケース等）は要件定義で決める。
8. **YouTube / ローカル両対応**: 打点パスの既存構造（ローカル=静止フレーム+サムネ帯 /
   YouTube=スローループ窓）はそのまま。タップ面が動画オーバーレイに変わるだけ。
   フレーム上のオーバーレイは video 要素 / YouTube iframe の上に透明 div を重ねる
   （iframe 操作は透過しないよう、タップ受付レイヤの下にプレーヤー操作 UI を別途用意）。

## 5. 要件定義で決める論点（ヒアリング項目）

1. 従来のコート図タップをフォールバックとして残すか（校正不能な動画への対応）
2. 校正 UI の導線（打点パス開始時に強制 / 任意 / 前セットの校正を引き継ぐか）
3. 落下点（クイックパス）も動画直接タップ化するか（同じ変換の再利用）
4. タブレット利用を正式サポートに含めるか（タッチ操作・レイアウト検証の範囲）
5. 校正精度の検証方法（既知のライン交点をタップして誤差表示する等のセルフチェック）
