# video-tap-annotation 要件定義書

**作成日**: 2026-08-28
**作業規模**: フル機能開発（5 点セット）
**位置づけ**: アノテーションスタジオ打点パスの UX 全面改善。ヒアリング2026-08-28 の**案A（動画フレーム直接タップ + コート 4 隅校正 = ホモグラフィ）**を実装する。shot-annotation の後続改善であり、保存データ（`shots.hit_x/hit_y` / `rallies.land_x/land_y`）の意味・スキーマは変えない。
**依存単位**: shot-annotation（打点パス・クイックパスの現行実装、座標定義 REQ-014）, video-playback（`VideoPlayer` のオーバーレイスロット・`useVideoPlayer`）, shot-stats（保存座標をカメラ基準として消費する側。互換維持の相手）

## 概要

現行の打点パスは「動画を見る → 頭でカメラ視点を真上視点に変換 → 横のコート図へカーソル移動 → クリック → 視線を動画へ戻す」の往復が**毎打**発生し、長ラリーで負荷が激しい（ドッグフーディング 2026-08-28。約 20 分/試合の主因）。

本単位では**タップ対象を動画そのもの**にする。セット開始時に動画上でコートの外周 4 隅をタップして射影変換（ホモグラフィ）を求め、以降は打った選手の**足元**を動画フレーム上で直接タップすると、システムが映像座標 → コート正規化座標へ自動変換して保存する。視線・カーソルの往復は 0 になり、タブレットなら指タップで済む。

変換先は既存データと同じ**カメラ基準正規化座標**（カメラ手前 = y=1 側、注釈者から見て左 = x=0）とし、既存の保存データ・集計（shot-stats REQ-105）と完全互換にする。

## スコープ

### 含む

- **コート 4 隅校正**: セット単位で動画上の外周 4 隅をタップ → ホモグラフィ算出・保存。再校正ボタン常設。前セットの校正の引き継ぎ
- **打点の動画直接タップ**: 打点パスで動画フレーム上のタップを `hit_x/hit_y` に変換して保存・自動前進（既存のプレフィル・YouTube 概算打刻・種別同時入力・undo・skip はそのまま）
- **落下点の動画直接タップ**: クイックパスの落下点ステップでも同じ変換を再利用 🟡
- **確認用ミニマップ**: 既存コート図をタップ結果の表示先として残す。ミニマップ自体もタップ可能（= 従来入力のフォールバック）
- **校正の目視セルフチェック**: 校正から逆算したコートライン（外周・ネット・センター・ショートサービスライン）を動画上に投影描画するガイド線
- **純関数のホモグラフィ実装**（4 点 DLT、外部ライブラリなし）+ 単体テスト
- **校正の永続化**（additive migration。テーブル or jsonb 列は kairo-design で決定）
- **座標系文書の改訂**: shot-annotation REQ-014 / `court-coords.ts` / `CourtDiagramInput.vue` の「y=0 = チーム A 側」記述を、実態（カメラ基準）に合わせて改訂 🟡

### 含まない

- 打点パスの巡回・状態機械の変更（打者二択廃止は 2026-08-28 に済み。1/2 打目の自動確定はそのまま）
- `shots` / `rallies` の座標列のスキーマ・意味変更（互換維持が本単位の前提）
- AI による自動打点推定（ADR-017 Stage 2 以降）。本単位は人間の入力効率化のみ
- タブレット専用のレイアウト最適化・タッチ専用 UI（拡大鏡等）。タッチイベントの受付自体は含む（NFR-202）🟡
- カメラが動く（パン・ズーム・手持ち）動画への追従。カメラ固定（三脚）前提。ズレたら再校正で対処
- 校正精度の数値評価 UI（既知点タップで誤差表示）→ オプション REQ-304 🟡
- 統計側（shot-stats）の変更。保存座標の意味が変わらないため不要

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: ADR・確定スキーマ・既存実装・ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: 上記から妥当な推測による要件（note.md §5 の未回答論点に対する提案値を含む。interview-record.md「確認待ち」参照）
- 🔴 **赤信号**: 出典のない推測による要件

### 通常要件

**校正（コート 4 隅）**

- REQ-001: システムは、セットごとに、動画フレーム上でコートの**外周 4 隅**（ダブルスサイドライン × バックバウンダリーラインの交点）を順にタップさせ、4 点対応から映像座標 → コート正規化座標の射影変換（ホモグラフィ）を算出しなければならない。4 隅は 1 点ずつ「次にタップする隅」をガイド表示し、直前の 1 点を取り消せること 🔵 *ヒアリング2026-08-28（案A・note.md §2-1）*
- REQ-002: 4 隅の対応先は、既存データと同じ**カメラ基準**の単位矩形としなければならない: 注釈者から見て**手前左 → (0, 1)、手前右 → (1, 1)、奥右 → (1, 0)、奥左 → (0, 0)**（カメラ手前チームの半面 = y ∈ [0.5, 1]、画面左 = x=0）。これにより従来のコート図タップ（見たままタップ）で保存された座標と完全互換になる 🔵 *note.md §2-3 + shot-stats note §「座標の向きはカメラ基準と判明」+ shot-stats REQ-105*
- REQ-003: システムは、校正結果を**セット単位**で永続化し、同じセットを再度開いたときに校正を復元しなければならない。再校正は上書き（履歴保持は不要）とする。保存内容は少なくとも set_id・4 隅の映像座標（再生面の正規化座標、REQ-406）・作成/更新日時とし、テーブル追加か `sets` への jsonb 列かは kairo-design で決定する 🔵 *note.md §2-6*
- REQ-004: システムは、打点パスおよびクイックパス中に**再校正ボタン**を常時表示し、いつでも校正をやり直せなければならない（カメラのズレ対応） 🔵 *note.md §2-1*
- REQ-005: システムは、校正完了直後に、校正から逆算した**コートライン（外周・ネット・センターライン・ショートサービスライン）を動画上に投影描画**し、実際のラインと重なっているかを目視確認できなければならない。ガイド線は打点入力中も表示/非表示を切り替えられること 🟡 *note.md §5-5（校正精度の検証方法）への提案値: 数値誤差表示より軽く、ズレが一目で分かる*
- REQ-006: システムは、打点パスを開始したセットに校正が保存されていない場合、校正ステップを提示しなければならない。校正はスキップ可能とし、スキップ時はミニマップ（従来のコート図）での入力にフォールバックする（REQ-101） 🟡 *note.md §5-2（校正 UI の導線）への提案値: 強制ではなく提示 + スキップ可*
- REQ-007: システムは、同じ試合の**前セットに校正がある場合**、それを引き継ぐ選択肢（「前セットと同じ」）をワンタップで提示しなければならない。引き継いだ校正も当該セットの校正として保存する（セット単位の原則は維持） 🟡 *note.md §5-2 + §2-1（カメラ固定前提なら同一の可能性が高い）*
- REQ-008: システムは、セットの校正状態（校正済み / 未校正 / 前セットから引き継ぎ）をパネル上にバッジ等で表示しなければならない 🟡 *REQ-006/007 の導線を成立させるための UI 要件*

**打点の動画直接タップ**

- REQ-009: 校正済みセットの打点パスでは、システムは動画フレーム上のタップ/クリック位置を REQ-001 のホモグラフィでコート正規化座標へ変換し、`shots.hit_x/hit_y` として保存して次のショットへ自動前進しなければならない。既存 `setPosition` の規則（1/2 打目のサーバー/レシーバー自動確定、YouTube でのタップ時プレーヤー時刻 `approx` 保存）はそのまま適用する 🔵 *ヒアリング2026-08-28（案A）+ usePositionPass.setPosition 現行実装（2026-08-28 二択廃止後）*
- REQ-010: システムは、タップ対象が「打った選手の**足元**（コート平面上の点）」であり、シャトルの空中位置ではないことをガイド文言で明示しなければならない（ホモグラフィはコート平面上でのみ正しい） 🔵 *note.md §2-2*
- REQ-011: システムは、動画タップの結果を**確認用ミニマップ**（既存コート図）に点として即時表示しなければならない。ミニマップ自体もタップ可能とし、校正済みでも従来どおりコート図で入力・訂正できること（動画タップとミニマップタップは同じ保存経路） 🟡 *note.md §2-7 + §5-1（フォールバックを残すか）への提案値: 残す。表示専用に落とさず入力も兼ねる*
- REQ-012: システムは、タップ位置のマーカーを動画上にも描画し（直近のタップ点）、undo・ショット再訪時には保存済み座標を逆変換して動画上に再表示しなければならない 🟡 *フィードバックの一貫性（ミニマップと動画の両方で確認できる）*
- REQ-013: システムは、動画タップ受付中も既存のキーボード操作（種別キーの同時入力・Shift = バックハンド・Backspace = undo・skip・ショット挿入/削除・ショットチップのジャンプ）をそのまま使えなければならない 🔵 *shot-annotation REQ-007/108 + annotate.vue 現行実装*
- REQ-014: 動画タップの受付レイヤは、`VideoPlayer` の再生面クリック（再生/停止トグル・iframe フォーカス対策の click-catch 層）と**分離**しなければならない。タップ受付中は再生面クリックによる再生/停止を無効化し、再生・停止・シーク・速度はプレーヤーのコントロールバー / 既存キー操作で行う。YouTube iframe へタップが透過してはならない 🔵 *note.md §2-8 + VideoPlayer.client.vue（overlay スロット z-index 2 / click-catch z-index 3）*

**落下点の動画直接タップ**

- REQ-015: 校正済みセットのクイックパス落下点ステップでは、システムは動画フレーム上のタップを同じホモグラフィで変換して `rallies.land_x/land_y` に保存しなければならない。ライン外はそのまま範囲外値で保存され、out 細分は既存規則（`deriveOutDirection`）で導出される。ミニマップでの入力・スキップも従来どおり可能とする 🟡 *note.md §2-5 + §5-3（落下点も動画タップ化するか）への提案値: 採用（同じ変換の再利用でコストが小さい）*

**座標系の文書整合**

- REQ-016: システムの座標系ドキュメント（shot-annotation REQ-014 の「y=0 = チーム A 側」、`court-coords.ts` / `CourtDiagramInput.vue` / `types/shot-annotation.ts` のコメント）を、実態である**カメラ基準**（y=1 = カメラ手前、x=0 = 画面左）の定義に改訂しなければならない。集計側の選手視点変換（shot-stats REQ-105）は変更しない 🟡 *shot-stats note §「座標の向きはカメラ基準と判明」の「将来この実態に合わせて改訂すべき」+ 本単位で座標系を正式にカメラ基準として扱うため*

### 条件付き要件

- REQ-101: セットが未校正の場合、システムは動画タップを受け付けず、ミニマップ（従来のコート図）でのタップ入力を提供し、校正を促す導線（REQ-006）を表示しなければならない 🟡 *note.md §5-1 への提案値（YouTube でコート 4 隅が映らない等、校正不能な動画への対応）*
- REQ-102: 校正をやり直した場合、システムは**以降のタップにのみ**新しい変換を適用し、保存済みの座標（変換後の値）を再変換してはならない 🔵 *note.md §2-6*
- REQ-103: 4 隅の入力が退化している場合（3 点以上が共線 / 四角形が凸でない・自己交差 / 2 点が極端に近い / DLT の係数行列が特異）、システムは校正を保存せず、理由を示して再入力を求めなければならない 🔵 *ホモグラフィの数学的前提（4 点が一般位置）*
- REQ-104: タップの変換結果が妥当範囲外の場合（射影の同次座標 w ≤ 0 = 消失線の向こう側/背後、または |x| や |y| が極端に大きい（閾値は kairo-design で確定。目安 [-1, 2] 外））、システムは座標を保存せず「足元をタップしてください」の警告を出し、同じショットに留まらなければならない 🟡 *ホモグラフィを空中・地平線付近に適用したときの発散を防ぐ*
- REQ-105: 動画が未ロード（ローカル動画の再選択前・YouTube 読込失敗）の場合、システムは校正および動画タップを無効化し、ミニマップ入力のみを提供しなければならない 🔵 *shot-annotation REQ-107（ローカルは方式 A ファイル再選択）+ video-playback EDGE-001*
- REQ-106: YouTube 動画の場合、システムは動画タップ時点のプレーヤー時刻を `annotated_timestamp_ms`（精度 `approx`）として保存する既存規則を維持し、ローカル動画では打刻を書かない（フレーム確定 `confirmFrame` が担う）現行の分担を変えてはならない 🔵 *shot-annotation REQ-010/101 + usePositionPass 現行実装*
- REQ-107: コートチェンジ（`rallies.camera_near_team` の反転）が起きても、システムは校正の再実施を要求してはならない。変換先はカメラ基準であり、カメラが動かない限り校正は有効なままである（チームと座標の対応付けは集計側の責務） 🔵 *note.md §2-3（カメラ基準）+ 2026-08-28 コートチェンジ手動トグル（31c8b9a）+ shot-stats REQ-105*
- REQ-108: 校正の保存に失敗した場合、システムは校正をクライアント側で保持したまま利用を続行させ、失敗を通知しなければならない（既存 EDGE-007「local は保持、通知のみ」と同型） 🔵 *shot-annotation EDGE-007*
- REQ-109: 打点パス・クイックパスのカーソルが別セットのラリーに移動した場合、システムはそのセットの校正へ切り替え（未校正なら REQ-006 の導線）、ガイド線・変換を更新しなければならない 🔵 *セット単位校正（REQ-003）の帰結*

### 状態要件

- REQ-201: 校正中（4 隅入力の途中）は、システムは動画タップを打点入力として扱ってはならず、4 隅の入力としてのみ受け付けなければならない。校正中は打点パスの巡回位置を変えない 🔵 *REQ-001 の帰結*
- REQ-202: 校正済み状態では、動画タップとミニマップタップの両方が有効でなければならない（どちらで入力しても保存先・前進の挙動は同一） 🟡 *REQ-011*
- REQ-203: 打点パスの校正中（shot-annotation REQ-010 の**フレームオフセット校正**）と本単位の**コート 4 隅校正**は独立に進行でき、UI 上で区別できなければならない（用語衝突を避け、本単位は「コート校正」と呼ぶ） 🔵 *usePositionPass.isCalibrating（既存）との同居*

### オプション要件

- REQ-301: システムは、座標の入力方法（動画タップ / コート図タップ）を記録してもよい（将来の精度評価・Stage 2 教師データの品質区分に使える。列追加が必要なため kairo-design で採否を決める） 🟡 *ADR-017 §5「押下時刻 → 真の打球時刻のペアが教師データ」の類推*
- REQ-302: 外周 4 隅が映像内に収まらない動画のために、システムは代替の既知点（例: ショートサービスライン × サイドラインの交点）による校正を提供してもよい 🟡 *EDGE-004 の緩和策*
- REQ-303: システムは、タッチ操作向けにタップ位置の拡大鏡・確定前プレビューを提供してもよい 🟡 *note.md §5-4（タブレット）。v1 対象外*
- REQ-304: システムは、既知のライン交点をタップして変換誤差を数値表示するセルフチェックを提供してもよい 🟡 *note.md §5-5。v1 はガイド線（REQ-005）で代替*

### 制約要件

- REQ-401: ホモグラフィ（4 点 DLT による 8 変数の連立一次方程式の求解・順変換・逆変換・退化判定）は**外部ライブラリを使わない純関数**として `app/utils/annotation/` に実装し、単体テストで検証しなければならない 🔵 *note.md §4 + ADR-012*
- REQ-402: 校正の永続化は additive migration（テーブル追加または列追加）で行い、既存テーブルの列の意味を変えてはならない。RLS は Group メンバー限定（`is_member_of()`）とし、適用は CI 経由 `db:push` とする 🔵 *note.md §2-6 + shot-stats REQ-402 踏襲*
- REQ-403: `shots.hit_x/hit_y` / `rallies.land_x/land_y` の型・値域・意味（カメラ基準正規化座標、ライン外は範囲外値、クランプしない）を変えてはならない 🔵 *note.md §2-3/2-4 + shot-annotation REQ-014*
- REQ-404: 本単位は CSR 限定で動作し、record 画面（match-recording）には一切触れてはならない 🔵 *ADR-010 + shot-annotation REQ-407*
- REQ-405: UI 文言は i18n（locale ファイル）で解決し、生文字列を埋め込んではならない 🔵 *error-handling 原則 5 + 既存コンポーネントの作法*
- REQ-406: 校正の映像座標は、`VideoPlayer` の再生面（`.video-player__surface`）に対する正規化座標（0〜1）で保存しなければならない。再生面は CSS で 16:9 固定のため、ウィンドウ幅・デバイスが変わっても同じ校正が再利用できる。レターボックスの有無は校正とタップの双方に同じ写像が掛かるため変換結果に影響しない 🔵 *VideoPlayer.client.vue（`aspect-ratio: 16 / 9` 固定）*
- REQ-407: 校正の状態機械（4 隅の入力順・取り消し・退化判定・引き継ぎ）は composable として分離し単体テスト可能にしなければならない。校正テーブル/列の RLS は integration テスト（CI 専用）で検証する 🔵 *ADR-012 + shot-stats REQ-407 踏襲*
- REQ-408: 動画タップの受付は Pointer Events で実装し、マウス・タッチ・ペンを同一経路で扱わなければならない 🟡 *note.md §5-4 への提案値: タッチ受付は含み、タブレット最適化は含まない*

## 非機能要件

### パフォーマンス

- NFR-001: 動画タップから変換・保存要求・次ショットへの前進までは同期的に完了し、体感即時（変換自体は 1ms 未満。ショット間遷移は shot-annotation NFR-001 の 300ms 以内を維持）でなければならない 🔵 *shot-annotation NFR-001*
- NFR-002: コート校正 1 回は、4 タップ + 確認で 30 秒以内に完了できる導線でなければならない（セットごとに繰り返すため） 🟡 *note.md §1（約 20 分/試合の短縮が目的。校正が新たなボトルネックにならないこと）*
- NFR-003: 案A 導入後の打点パス所要時間は、現行（約 20 分/試合）から有意に短縮されることをドッグフーディングで確認する（目標値は設けず、実測を note.md に記録） 🟡 *note.md §1*

### セキュリティ

- NFR-101: 校正データは RLS により他 Group から読み書きできてはならない 🔵 *shot-stats NFR-101 踏襲*

### ユーザビリティ

- NFR-201: 打点入力に必要な操作（タップ・種別キー・skip・undo）が**動画面から視線を外さず**に完結しなければならない（本単位の目的そのもの） 🔵 *note.md §1*
- NFR-202: 主対象は PC（マウス/トラックパッド）とし、タッチ操作は Pointer Events により受け付ける。タブレットのレイアウト検証・最適化は本単位の対象外とする 🟡 *note.md §5-4 への提案値*
- NFR-203: 座標精度は既存と同じ ±50cm トーンとし、校正のズレはガイド線（REQ-005）で目視検知できればよい 🔵 *shot-annotation NFR-202（CourtDiagramInput の精度トーン）*
- NFR-204: ガイド文言・校正手順は、初見の注釈者が説明なしに 4 隅の順序・足元タップの規則を理解できる表現でなければならない 🟡 *REQ-001/010*

## Edgeケース

### エラー処理

- EDGE-001: DLT の係数行列が特異（4 点のうち 3 点が共線など）→ 校正を拒否し再入力（REQ-103） 🔵
- EDGE-002: タップ点が消失線の向こう側（w ≤ 0）や極端な外挿値 → 保存せず警告、同じショットに留まる（REQ-104） 🟡
- EDGE-003: 校正の保存失敗 → クライアント側で校正を保持し続行、toast 通知（REQ-108） 🔵
- EDGE-004: コート 4 隅の一部が映像外（カメラが寄りすぎ/画角不足）→ 校正不能。スキップしてミニマップ入力（REQ-101）。代替既知点は REQ-302 🟡
- EDGE-005: タップ受付レイヤが表示されている間に動画がエラー/再選択状態になった → レイヤを無効化しミニマップのみ（REQ-105） 🔵

### 境界値

- EDGE-101: ライン上・ライン外ぎりぎりの足元 → 範囲外値（<0 / >1）をそのまま保存。打点・落下点ともクランプしない（REQ-403）。既存の `CourtDiagramInput` 既定（`allowOutZone=true`）と同じ挙動 🔵
- EDGE-102: ウィンドウのリサイズ・別デバイスで再開 → 正規化座標（REQ-406）のため校正はそのまま有効 🔵
- EDGE-103: セット途中でカメラ（三脚）がズレた → ガイド線のズレで気付き、再校正（REQ-004）。ズレ前に保存した座標はそのまま（REQ-102） 🔵
- EDGE-104: ローカル動画で別ファイル（別アスペクト比）を再選択 → 同一試合の同一動画が前提。ズレはガイド線で検知し再校正 🟡
- EDGE-105: 第 3 セットのコートチェンジ（11 点でチェンジエンズ）→ 校正はそのまま。UI は何も促さない（REQ-107） 🔵
- EDGE-106: 同一セット内でラリー一覧から別セットのラリーへジャンプ → 校正を切り替え（REQ-109） 🔵
- EDGE-107: 校正の 4 隅を誤った順序でタップ（例: 手前左→奥左）→ 四角形が非凸/ねじれとなれば REQ-103 で拒否。凸だが回転している（順序が 1 つずれた）場合は検出できないため、ガイド線（REQ-005）で気付く前提とし、UI の順序ガイドで予防する 🟡
