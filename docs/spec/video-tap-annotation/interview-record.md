### Q2: 前セッションで確定済みの設計要点（2026-08-28・note.md §2 転記）

**カテゴリ**: 既存設計確認
**背景**: ヒアリング2026-08-28（前セッション）で案A を採用し、以下が確定している。

**回答（確定済み・🔵）**:
1. 校正はセット開始時に外周 4 隅をタップ → ホモグラフィ（DLT）。カメラ固定前提。再校正ボタン常設 → REQ-001/004
2. タップ規則は「打った選手の足元」。ガイド文言で明示 → REQ-010
3. 変換先は既存のカメラ基準正規化座標（手前 = y=1 側） → REQ-002
4. ライン外は範囲外値のまま（クランプしない） → REQ-403 / EDGE-101
5. 落下点（land_x/y）も同じ変換を再利用できる → REQ-015（採否は Q5）
6. 校正の保存はセット単位・additive migration。やり直しは以降のタップのみに影響 → REQ-003/102/402
7. 既存コート図は確認用ミニマップとして残す → REQ-011
8. YouTube / ローカル両対応。タップ面は動画オーバーレイ。iframe へ透過させない → REQ-014

**信頼性への影響**: 上記に対応する REQ は 🔵。

### Q3: 従来のコート図タップをフォールバックとして残すか（note.md §5-1）

**カテゴリ**: 未定義部分詳細化
**背景**: YouTube でコート 4 隅が映らない、カメラが寄りすぎている等、校正不能な動画がありうる。

**提案（仮置き）**: **残す**。しかも「表示専用ミニマップ」ではなく**ミニマップ自体をタップ可能**にし、校正済みでも従来入力・訂正ができる（REQ-011/101/202）。
- 理由: 表示専用に落とすと校正不能動画で打点パスが使えなくなる。同じ `CourtDiagramInput` を残すだけで実装コストはほぼゼロ。動画タップとミニマップは同じ保存経路（`setPosition`）に合流させる。

**確認待ち**: ミニマップは表示専用にして欲しい場合は REQ-011/202 を改訂。

### Q4: 校正 UI の導線（note.md §5-2）

**カテゴリ**: 未定義部分詳細化
**背景**: 打点パス開始時に強制するか、任意にするか、前セットの校正を引き継ぐか。

**提案（仮置き）**:
- 打点パス開始時、そのセットに校正がなければ**校正ステップを提示。スキップ可**（スキップ時はミニマップ入力）→ REQ-006
- 前セットに校正があれば「**前セットと同じ**」をワンタップで採用可。採用した校正も当該セットに保存 → REQ-007
- 校正状態はバッジで常時表示 → REQ-008
- 理由: カメラ固定（三脚）なら全セット同一のことが多く、毎セット 4 タップは冗長。一方で三脚の移動もありうるため「自動で引き継ぐ」ではなく「提案して 1 タップ」にする。

**確認待ち**: 「校正を必須（スキップ不可）にしたい」「自動引き継ぎで良い」なら REQ-006/007 を改訂。

### Q5: 落下点（クイックパス）も動画直接タップ化するか（note.md §5-3）

**カテゴリ**: 追加要件
**背景**: 同じホモグラフィを再利用できる。クイックパスは決着窓を通し再生して停止した状態で落下点を入力するため、停止フレームにおおむね落下地点が映っている。

**提案（仮置き）**: **採用**（REQ-015）。優先度は打点より一段下（Should Have）。校正済みセットのみ。ミニマップ入力・スキップは従来どおり。

**確認待ち**: v1 スコープから外すなら REQ-015 を「含まない」へ移動。

---

### Q6: タブレット利用を正式サポートに含めるか（note.md §5-4）

**カテゴリ**: スコープ
**背景**: note.md §1「タブレットなら指タップになる」。ただしレイアウト検証・タッチ専用 UI（拡大鏡等）まで含めると範囲が広がる。

**提案（仮置き）**: **正式サポートには含めない**が、タップ受付は Pointer Events で実装し**タッチも同じ経路で受け付ける**（REQ-408 / NFR-202）。拡大鏡・確定前プレビューはオプション REQ-303。
- 理由: 主なドッグフーディング環境が PC。Pointer Events にしておけばタブレットで「動く」状態にはなり、必要になった時点で最適化を別単位にできる。

**確認待ち**: タブレットを正式対象にするなら NFR-202 を改訂し、REQ-303 を通常要件へ格上げ。

---

### Q7: 校正精度の検証方法（note.md §5-5）

**カテゴリ**: 未定義部分詳細化
**背景**: 既知のライン交点をタップして誤差を数値表示するセルフチェック案があった。

**提案（仮置き）**: **ガイド線の投影描画**を採用（REQ-005）。校正から逆算したコートライン（外周・ネット・センター・ショートサービスライン）を動画上に重ね描きし、実ラインと重なるかを目視確認する。打点入力中も表示/非表示を切替可。数値誤差表示はオプション REQ-304。
- 理由: 追加タップなしでズレが一目で分かり、三脚ズレ（EDGE-103）の検知にも常時使える。ホモグラフィの逆変換は REQ-401 の純関数に含まれるため実装コストが小さい。

**確認待ち**: 数値セルフチェックも v1 に欲しければ REQ-304 を通常要件へ格上げ。

### Q8: コートチェンジとの関係（2026-08-28・実装調査）

**カテゴリ**: 既存設計確認
**背景**: 2026-08-28 にコートチェンジ（チェンジエンズ）手動トグル（31c8b9a）が追加され、`rallies.camera_near_team` がセット途中で反転しうる。校正の再実施が必要か。

**回答（実装調査による確定・🔵）**: **不要**。変換先はカメラ基準座標であり、カメラが動かなければ校正は有効なまま。チームと座標の対応付けは集計側（shot-stats REQ-105 が `camera_near_team` で選手視点へ変換）の責務 → REQ-107 / EDGE-105。

### Q9: 座標系ドキュメントの改訂を含めるか（2026-08-28・実装調査）

**カテゴリ**: 追加要件
**背景**: shot-stats note §「座標の向きはカメラ基準と判明」に「shot-annotation 側の文書（REQ-014 / ADR-017 の絶対座標定義）も将来この実態に合わせて改訂すべき」とある。本単位はホモグラフィの変換先をカメラ基準として明文化するため、放置すると文書とコードの矛盾が固定化する。

**提案（仮置き）**: **含める**（REQ-016。文書 + コードコメントのみ、ロジック変更なし）。

**確認待ち**: 別 PR（docs/xxx）に分けたい場合は「含まない」へ。

---

### Q10: 校正座標の保存基準（2026-08-28・実装調査）

**カテゴリ**: 既存設計確認
**背景**: `VideoPlayer` の再生面は CSS で `aspect-ratio: 16 / 9` 固定。ローカル動画のレターボックスや YouTube iframe 内の描画は再生面の中で行われる。

**回答（実装調査による確定・🔵）**: 校正の映像座標は**再生面に対する正規化座標（0〜1）**で保存する（REQ-406）。校正とタップの双方に同じレターボックス写像が掛かるため変換結果に影響せず、ウィンドウ幅やデバイスが変わっても校正を再利用できる（EDGE-102）。
