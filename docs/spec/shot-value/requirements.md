**作成日**: 2026-09-16
**作業規模**: 中規模（1画面 + タブ改組 + RPC 1本）
**位置づけ**: 川島氏の「強みと課題をショット単位で見たい」（usability-test-01 / 2026-06-16）への直接回答。
shot-stats 探針群の発展形で、現在プレースホルダの「強み分析」タブを実体化し、「弱点分析」タブと統合する。
**依存単位**: shot-stats（注釈集計の前例・タブ画面・ミラー規則。**feat/shot-stats は main 未マージ**）,
singles-support（feature/singles PR #60 進行中。タブ改組は同 PR のマージ後に実装すること）,
shot-annotation（データ供給源）, stats-dashboard（グローバルフィルタ・母数併記 NFR-201）

## 概要

ショット1本ごとに「ポイントへの貢献」を採点し、球種 × 打点ゾーン（自陣 3×3）で集計した
**ポイント収支統計（SV: Shot Value）** を追加する。テニスの実務指標
FHP/BHP（Tennis Abstract, Match Charting Project）の採点構造をバドミントンの注釈データモデル
（ADR-017 / shot-annotation）へ翻案したもの。バドミントンには同種の普及指標が存在しない
（研究側の shot influence は学習ベースで将来枠 = スコープ外）。

集計は既存注釈データ（shots / rallies）の読み取りのみで成立し、追加の注釈入力を一切要求しない。

あわせて既存の「強み分析」「弱点分析」の 2 タブを **「強み・課題」1 タブに統合**し、
弱点分析タブの「ミスした打点」「決められた落下点」チャートを同タブへ移設する。

## スコープ

### 含む

1. **SV 採点規則**（REQ-001〜003）とその集計 RPC（additive migration・読み取り専用）
2. **SV 画面**: 自陣 3×3 ゾーンセレクタ（複数選択）+ 合計タイル（稼いだ − 失った = 収支）+ 球種別ポイント内訳（5 役割の積み上げ棒 + 信頼区間ヒゲ）
3. **タブ改組**: 「強み分析」+「弱点分析」→「強み・課題」。既存 `StatsWeaknessMaps`（ミスした打点 / 決められた落下点）を同タブ下部へ移設

## 機能要件（EARS記法）

### SV 採点規則

- REQ-001: システムは、対象ラリー（`is_let = false` かつ `is_point_confirmed = true` かつ `point_winner` 非 null かつ `end_reason` が floor/body/net/not_over/service_fault のいずれか）の各ショットに、以下の**排他的な役割**を割り当て採点しなければならない。決定打の位置・ミスの判定は `decisiveShotIndex` / `deriveInOut` と同一規則とする 🔵 *ヒアリング2026-08-16（FHP/BHP 翻案）+ 08-28（遡り配点の採用）*
  - **決め（+1）**: エース決着（body / floor×最終打者=勝者）の決定打
  - **ミス誘発（+w）**: ミス決着（net / not_over / floor×最終打者=敗者）の決定打（= 相手ミスの 1 本前の勝者側ショット）
  - **布石（+b1 / +b2）**: 決定打から**同チーム内で** 1 本前（ラリー全体では 2 本前）に +b1、2 本前（全体で 4 本前）に +b2
  - **自ミス（−1）**: ミス決着の最終ショット。service_fault はサーブ（1 打目）に −1
  - **相手の決めを許した（−b1 / −b2）**: 敗者側の遡り。ミス決着では自ミスから同チーム内 1 本前に −b1・2 本前に −b2。エース決着では決められる直前の返球（エースの 1 本前）に −b1・その同チーム 1 本前に −b2
  - 上記以外のショットは 0 点。該当打順が存在しない場合（短いラリー）は単にスキップする
- REQ-002: 採点の定数は **w = 1.0（ミス誘発の重み）、b1 = 0.7、b2 = 0.5（遡り配点）** を初期値とし、クライアントコード内の**1 箇所の調整可能定数**として実装しなければならない。遡りは同チーム 2 本前まで（それ以前は 0）とする 🟡 *ヒアリング2026-09-16（値は実データ較正前提の暫定と明示的に合意。RPC は役割別カウントを返し、重み変更にマイグレーション不要な構造とすること）*
- REQ-003: システムは、SV を **100 本あたりのポイント収支**（SV100 = 100 × Σscore ÷ n）として表示し、合計値は「**稼いだ（+成分計） − 失った（−成分計） = 収支**」の等式形式と、平易文（例:「ここから100本打つと、だいたい 7 点ぶん損している計算です」）を併記しなければならない 🔵 *ヒアリング2026-09-16（等式表示の要望）*

### SV 画面

- REQ-004: システムは、打点（`hit_x`/`hit_y`）に基づく**自陣 3×3 ゾーンセレクタ**（コート図）を表示しなければならない。セルは**複数同時選択**（和集合）でき、行ラベルで一列一括選択でき、**未選択時はコート全体**の集計を表示する。各セルにはそのゾーンの収支/100本と n を表示する。選手視点ミラーは shot-stats REQ-105（`camera_near_team` 180° 反転）と同一規則とする 🔵 *ヒアリング2026-09-02（3×3・複数選択）+ 09-16（ゾーン合算の独立チャートは持たず本画面に統合）*
- REQ-005: システムは、選択範囲の**球種別ポイント内訳**を表示しなければならない。各球種の行は中央 0 軸の左右に 5 役割（決め / ミス誘発 / 布石 = 右、自ミス / 相手の決めを許した = 左）を色分け積み上げし、ホバー/タップで役割名と数値を表示、行末に収支/100本 ± 信頼区間を表示、n 降順に並べる 🔵 *ヒアリング2026-09-16（5 色でいったん確定。凡例必須）*
- REQ-006: システムは、収支の **95% 信頼区間**（score の標本分散から 1.96 × sd ÷ √n × 100）を算出し、内訳行と合計にヒゲ（±値）として表示しなければならない。固定の最低本数閾値による非表示は行わない 🔵 *ヒアリング2026-08-19（閾値でなく揺れ幅表示の方針）*
- REQ-007: n < 5 の球種行は薄表示 +「本数不足」注記としなければならない（非表示にはしない）🔵 *同上*

### 条件付き要件

- REQ-101: ゾーン選択中の場合、打点座標が null のショットおよび `camera_near_team` が null のラリーのショットは集計対象外とし、母数表示（n / N）に反映しなければならない。未選択（全体）時は座標の有無・ミラー可否に関わらず全対象ショットを含める
- REQ-102: `end_reason` が null または unknown のラリーは、採点対象にも**分母にも**含めてはならない（加点も減点も発生し得ないショットで収支が薄まるのを防ぐ）🔵 *ヒアリング2026-08-19*
- REQ-103: `shot_type` が null のショットは `unknown` 区分として内訳に表示しなければならない（採点・分母には含まれる）
- REQ-104: `hit_player_id` が null のショットは選手別集計から除外するが、遡り配点の**打順位置としては消費**しなければならない（チーム帰属は打順の偶奇で決まる — derive.ts の全接触記録前提）

### 状態要件

- REQ-201: タブ構成は「サーブ周り /**強み・課題**/ ラリー展開」の 3 タブとし、「強み・課題」タブは上から SV 画面 → ミスした打点 → 決められた落下点の順に表示しなければならない。既存の「強み分析」「弱点分析」タブは廃止する 🔵 *タブ名「強み・課題」は LP コピー「強みと課題を数字で分析」との整合から提案し、ユーザ承認（ヒアリング2026-09-16）。検算例（採点規則）も同日承認*
- REQ-202: フィルタは打者選手・セット・hand を提供し、既存グローバルフィルタと併用できなければならない。球種フィルタは本画面では不要（内訳表示自体が球種分解のため）
- REQ-203: シングルス試合（singles-support）ではチーム = 選手として同一規則で動作しなければならない（StatsWeaknessMaps の注記切替 REQ-302 前例を踏襲）

### オプション要件

- REQ-301: システムは、内訳行から該当役割のラリーへの動画ジャンプを提供してもよい（将来候補）

### 制約要件

- REQ-401: 集計は読み取り専用 RPC（additive migration）で行い、テーブル変更・書き込みを行ってはならない。RPC は**役割別カウント**（grain: 打者 × 球種 × ゾーン × 役割）を返し、重み計算・ゾーン合算・CI 算出はクライアント側で行うこと（REQ-002 の重み変更耐性のため）
- REQ-402: 母数併記（注釈済み n / 全体 N）・注釈率バッジは shot-stats REQ-002/003 を踏襲しなければならない

## 非機能要件

- NFR-001: SV 画面はゾーン選択のたびに RPC を再実行せず、初回取得（役割別カウント）のクライアント集計で応答すること
- NFR-201: 5 色の役割区別を色のみに依存させないこと（凡例 + ホバー数値必須。積み上げの左右分離自体が主判別）

## 採点の検算例（実装テストの基準値）

ラリー: A1 サーブ → B1 レシーブ → A2 クリア → B2 スマッシュ → A1 レシーブがネット（end_reason = net、勝者 B）

| 打順 | ショット | チーム | 役割 | 点 |
|---|---|---|---|---|
| 1 | A1 サーブ | A | 許した(−b2)〔自ミスから同チーム2本前〕 | −0.5 |
| 2 | B1 レシーブ | B | 布石(+b1)〔決定打から同チーム1本前〕 | +0.7 |
| 3 | A2 クリア | A | 許した(−b1) | −0.7 |
| 4 | B2 スマッシュ | B | ミス誘発(+w)〔決定打〕 | +1.0 |
| 5 | A1 レシーブ | A | 自ミス | −1.0 |

エース決着の例: 上記 5 打目が「B2 スマッシュが床に決まる」（end_reason = floor、最終打者 = 勝者）なら、
B2 スマッシュ(5打目) = 決め +1 / A1(4打目) = 許した −b1 / B1(3打目) = 布石 +b1 / A2(2打目) = 許した −b2 / B サーブ(1打目) = 布石 +b2。

service_fault: サーブに −1 のみ。誰も加点されない。

## Edgeケース

- EDGE-001: 3 打未満のラリー（遡り先が存在しない）— 存在する打順のみ採点（REQ-001 末尾）
- EDGE-002: 全セル選択解除 → 全体表示に戻る（REQ-004）
- EDGE-003: 選択ゾーンに該当ショット 0 件 → 空状態表示（収支非表示 + 案内文言）
- EDGE-004: 注釈が部分的（クイックパスのみ = 決着注釈あり・球種なし）→ unknown 区分に収支が出る（REQ-103）。母数併記で状況が読めること
