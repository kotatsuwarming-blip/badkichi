# shot-annotation ヒアリング記録

**作成日**: 2026-07-19
**ヒアリング実施**: ADR-017/018 策定時の設計対話（2026-07-05〜2026-07-19）を要件観点で整理

## ヒアリング目的

川島氏のアドバイス（ショット種別・位置の手動入力 UI）を起点に、注釈の入力タイミング・
操作モデル・分類語彙・決着の表現・動画ソース制約を確定するための対話を、
ADR-017/018 の策定と並行して実施した。本記録はその要件determinant部分の抜粋。

## 質問と回答

### Q1: 注釈はライブ記録中に入れるか、後付けか

**質問日時**: 2026-07-05〜06
**カテゴリ**: スコープ / UX 方針
**背景**: PRD §3.2 は「手動入力は負荷が高すぎる」として除外していた。ライブ中の
「決着時1タップ」案を提示したところ検討が必要になった。

**回答**: **「決着時の1タップがそんなに簡単に判断できるものでもない」** → ライブ記録 UI には
触れず、注釈は**後付けのアノテーションスタジオに一本化**（クイック/種別/打点の3モード）。

**信頼性への影響**: REQ-003 / REQ-407 を 🔵 で確定。ADR-017 選択肢 A（ライブ1タップ）却下。

---

### Q2: 種別と打点を1周で同時入力できるか

**質問日時**: 2026-07-06
**カテゴリ**: 操作モデル
**背景**: 当初案は「1ショットにつき種別キー + 打点クリックを同時に」だった。

**回答**: **「キーボードで種別選択とマウスで打点入力の同時は人間には不可能な処理速度」** →
**2周方式**。種別=連続再生+キーボード（1.5倍速可）、打点=再生に追われない方式。

**信頼性への影響**: REQ-007〜011 の2パス構造を 🔵 で確定。種別は動きが要る/打点は静止画で
足りるという性質差により、2周でも視聴は2倍にならない設計に帰着。

---

### Q3: 記録済みタイムスタンプは静止画を出せる精度か

**質問日時**: 2026-07-06
**カテゴリ**: データ品質
**背景**: 打点パスの当初案は記録時刻の1点静止画だった。

**回答**: **「静止画で出せるほど正確な時間を記録できているか怪しい。速い展開だと0.何秒」** →
押下は反応遅延（0.2〜0.5秒）を系統的に含む前提で、**一律オフセット校正 + サムネイル帯
ナッジ + スローループ fallback** に修正。人間のナッジ訂正は Stage 2（スナッピング）の
教師データになる。

**信頼性への影響**: REQ-010 / REQ-011 を 🔵 で確定。`annotated_timestamp_ms` 列の追加
（元の押下時刻と訂正後時刻のペア保持）を要件化（REQ-002 🟡）。

---

### Q4: ショット種別の分類語彙（taxonomy）

**質問日時**: 2026-07-13〜17
**カテゴリ**: ドメイン語彙
**背景**: 叩き台は8分類 + 「レシーブは文脈から導出できるので独立させない」だった。

**回答**（複数回の往復で確定）:
- 「**細かく分けても、後で学習する際に統合すればいい**」→ 細分保存・統合は集計/学習時
- カット/ドロップは分ける。プッシュ/ドライブも分ける
- 「**スマッシュレシーブはレシーブというもので入れて。プッシュの次もレシーブ**。
  ロングレシーブ/ドライブレシーブ/ショートレシーブのどれか」→ レシーブ3種を独立
- 「**ハーフ**というショットがある（前衛と後衛の間に落とす）」→ 追加
- 「**プッシュとハーフは前方から打つ**。中間からのショットに名前はあまりない。
  この選択肢なら上げるのはロブ、落とすのはドロップ」→ グループ分けは UI 表示のみ。
  球種×打点座標の直交設計により中間からの球も情報が落ちない
- サーブに**ドライブサーブ**を追加 / **リバースカット**を追加 → 計16種
- フォア/バックは「欲しい気もするが入力が増えるのは考え所」→ **修飾キーの任意入力**で合意

**信頼性への影響**: REQ-103 / REQ-104 / REQ-109 と ADR-017 §6（16種）を 🔵 で確定。

---

### Q5: end_reason の再設計と touched フラグの廃止

**質問日時**: 2026-07-17
**カテゴリ**: データモデル
**背景**: 当初案は end_reason（floor/net/out/…）+ touched フラグの2軸だった。

**回答**: 「end_reason は **相手コートの床に落ちる（out, in）/ ネットにかかる / 体に当たる /
ラケットには当たるがネットを超えない（ダブルタッチも）** にして。out には **side / back /
両方** がある。**ラケットに当たった場合に打ったを記録するので、最後に誰が打ったかは分かる。
その情報と end_reason だけあれば十分**」

→ **全ラケット接触をショットとして記録する運用**に変更し、touched フラグを廃止。
最終接触者 + end_reason で勝敗の向きまで導出可能に（整合チェック REQ-102 の根拠）。

**信頼性への影響**: REQ-004 / REQ-005 / REQ-102 / REQ-105 を 🔵 で確定。
ADR-017 §7 / 選択肢 K に反映済み。

---

### Q6: service_fault と、打点/落下点の役割分担

**質問日時**: 2026-07-19
**カテゴリ**: データモデル確認
**背景**: Q5 の再設計で service_fault を一度落としていた。また座標入力の役割の確認があった。

**回答**:
- 「**service_fault は残していい**」→ 復活（物理結果に現れない反則宣告用。サーブの
  ネット/アウトは物理分類を使う排他ルール）
- 「**ラリー中は打点座標を入力する（落下する前に打つので落下点は分からない）。
  落下点入力とは別と考えていた**」→ 認識一致を確認。打点=全ショット、
  落下点=最終ショットのみ（in/out 決着時）を明文化

**信頼性への影響**: REQ-005 / REQ-009 / REQ-014 を 🔵 で確定。

---

### Q7: 動画ソースは何を前提にするか

**質問日時**: 2026-07-19
**カテゴリ**: 制約 / ロードマップ
**背景**: YouTube iframe はフレーム制御・ピクセル取得が不可で、サムネ帯・静止画紙芝居・
ブラウザ内 AI 推論が成立しない。クラウド保存のコスト試算（R2 なら1試合 ¥100/年オーダー）
と代替案（ローカル原本の再選択との両対応）を提示した。

**回答**: 「**まあ、YouTube だけで一回やってみます**」→ 検証フェーズは YouTube のみ、
スローループ方式への劣化を受容。クラウド動画保存は必要になったら別 ADR。

**信頼性への影響**: REQ-101 を 🔵 で確定（Must）。ローカル動画時のサムネ帯（REQ-011）も
実装するが、検証フェーズの主経路は YouTube ループ方式。

### Q8: 要件定義の 🟡（11件）の一括解消

**質問日時**: 2026-07-19
**カテゴリ**: 確定
**背景**: requirements.md 初版の 🟡 11件を個別に確認した。

**回答**:
- `annotated_timestamp_ms` 列: **採用**し、ADR-017 §5 へ追補
- 座標系: **絶対座標**で保存（y=0 = チームA側バックバウンダリー、反転は集計側）。
  具体例（田中/佐藤の対比）による説明の上で確定
- レットラリー: **全モードで除外**（クイックパスのみ除外の推奨案より広い決定）
- undo: **戻って上書き主体 + Backspace 直前1段**（注釈は連鎖効果のない上書きのため
  フルスタック不要、の説明の上で確定）
- 軽微7件（REQ-201 / NFR-001 / NFR-402 6分割 / EDGE-001 last-write-wins /
  EDGE-002 / EDGE-004 / EDGE-005）: 推奨どおり確定

**信頼性への影響**: 要件定義・受け入れ基準の 🟡 は全件 🔵 へ昇格（🔵 100%）。

### Q9: land 系列の配置修正

**質問日時**: 2026-07-19
**カテゴリ**: データモデル修正
**背景**: 初版は `land_x` / `land_y` を `shots` に置いていた（「最終ショットの落下点」という
整理）。

**回答**: 「**land 系は shots に追加するのがおかしい**」→ その通り。落下点は設計上
**1ラリーに高々1点**しか存在しない（ラリー中の球は落下前に打ち返される）ラリー属性であり、
`end_reason` / `out_direction` と同じ **`rallies` へ移動**。shots はショット単位の属性のみに
なり整合。

**信頼性への影響**: REQ-002 / REQ-005 / note.md / ADR-017 §5 を修正。
