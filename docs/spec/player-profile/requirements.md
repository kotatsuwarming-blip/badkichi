# player-profile 要件定義書

**作成日**: 2026-09-26
**作業規模**: 中規模（2 PR に分割: ① メンバー区分 ② プロフィール拡張）
**位置づけ**: 分析軸の拡充。プロフィール属性（性別・身長・年齢・歴 等）を統計のフィルタ軸・
選手間比較の文脈にする土台。川島氏インタビューの「チーム/実業団向け」路線とも整合。
**依存単位**: player-management（players テーブル・選手 UI）, stats-dashboard / shot-stats（消費側）

## 概要

選手（players）に 2 つの拡張を行う:

1. **メンバー区分（PR ①・ブランチ `feat/player-roster-type`）**: 自チームメンバーと対戦相手
   （記録のために登録しただけの選手）を区別する。分析対象は基本的に自チームのため、
   選手一覧・統計の選手選択で自チームを優先表示する。
2. **プロフィール拡張（PR ②・ブランチ `feat/player-profile`）**: 性別・身長・体重・生年月日
   （年齢は導出）・バドミントン開始時期（歴は導出）・練習頻度・プレースタイル（複数キーワード）。
   全項目任意入力。まず入力・表示の土台を作り、統計軸への組み込みは後続とする。

## 機能要件（EARS記法）

### PR ①: メンバー区分

- REQ-001: システムは、選手にメンバー区分 `roster_type`（`member` = 自チーム / `opponent` = 対戦相手）を保持しなければならない。既存選手は `member` に初期化する（誤区分は編集で直せる）🔵 *ヒアリング2026-09-27*
- REQ-002: **選手の新規登録フォームで最初から区分を選択**できなければならない（セグメント。既定 = 自チーム）。編集でも変更可能とする 🔵 *ヒアリング2026-09-27（最初の登録時に選択できるように）*
- REQ-003: 選手一覧は自チーム → 対戦相手の順にグルーピング表示しなければならない
- REQ-004: 統計画面の選手/ペア選択（グローバルフィルタ）は自チームを先頭グループに表示しなければならない。**対戦相手も選択可能なまま残す**（shot-stats REQ-009 で「相手選手も分析対象」が確定済みのため、除外はしない）🔵 *ヒアリング2026-09-26（分けたい・分析は基本自チーム）+ shot-stats 既決との整合*
- REQ-005: 試合作成の選手選択では区分を混在で選べなければならない（対戦相手を登録して組む従来フローを壊さない）

### PR ②: プロフィール拡張

- REQ-101: システムは、選手に以下の任意プロフィールを保持しなければならない 🔵 *ヒアリング2026-09-26*
  - `sex`: `male` / `female` / `unspecified`（既定 unspecified。ミックス分析の軸）
  - `height_cm`: smallint（100〜250 チェック）
  - `weight_kg`: numeric(4,1)（30.0〜150.0 チェック）
  - `birthdate`: date — **年齢は保存せず表示時に導出**
  - `badminton_since`: date（月単位入力・日は 1 日固定）— **歴は保存せず「現在 − since」で導出**。
    「歴 n 年」を直接入力した場合は「今日 − n 年」を since に逆算して保存（自動で歴が上がる、
    かつ編集可能、というヒアリング要望の両立）🔵 *ヒアリング2026-09-26（自動で上がる方がいい？が編集可能 → 開始時期を持てば両立）*
  - `practice_frequency`: `daily` / `several_per_week` / `weekly` / `monthly` / `rarely`（5 段階）🔵 *ヒアリング2026-09-27 確定*
  - `play_styles`: text[] — 定義済みキーワードからの**複数選択** 🔵 *ヒアリング2026-09-26（いくつかのキーワードを選択）*
- REQ-102: プレースタイルのキーワードは定数 1 箇所（クライアント + DB CHECK）で管理し、初期セットは
  `attacker`（攻撃型）/ `defender`（守備型）/ `all_round`（オールラウンド）/ `front_player`（前衛型）/
  `rear_player`（後衛型）/ `rally_oriented`（ラリー型）/ `speed_oriented`（スピード型）/
  `technical`（テクニック型）/ `power`（パワー型）の **9 種**とし、**複数選択可**とする 🔵 *ヒアリング2026-09-27（パワー型追加・複数選択を明示）*
- REQ-103: 選手フォームにプロフィール入力欄（折りたたみ可の「詳細プロフィール」セクション）を追加しなければならない。全項目未入力でも保存できること
- REQ-104: 選手一覧/詳細で入力済みプロフィール（年齢・歴は導出値）を表示しなければならない
- REQ-105: 年齢・歴の導出は誕生日/開始日を跨いだ時点で自動反映されなければならない（表示時計算のため自然に満たす）

### 制約要件

- REQ-401: スキーマ変更は players への **additive な列追加のみ**（NOT NULL 追加時は DEFAULT 必須。
  既存行を壊さない）。RLS は既存の players ポリシーを踏襲
- REQ-402: プロフィールは統計 RPC には**まだ載せない**（統計軸への組み込み = 属性別比較・
  フィルタは後続要件。本件は入力・表示の土台まで）🔵 *ヒアリング2026-09-26（分析に使うのが目的だが、PR は小さく分ける方針）*

## Edgeケース

- EDGE-001: birthdate が未来日 / badminton_since が birthdate より前 → フォームバリデーションで拒否
- EDGE-002: 歴の直接入力が 0 年（今年開始）→ since = 今日で保存し「1 年未満」表示
- EDGE-003: 対戦相手区分の選手が試合・注釈に既に紐づいていても区分変更で壊れないこと（区分は表示・並び順にのみ影響）

- [ ] プロフィール全項目が未入力でも保存でき、入力すると一覧/詳細に出る
- [ ] 年齢・歴が誕生日/開始日から正しく導出される（境界日テスト）
