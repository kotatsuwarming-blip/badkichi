# match-management ヒアリング記録

**作成日**: 2026-06-02
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

ADR-002・data-foundation の確定スキーマ（matches テーブル）・先行単位（player-management /
auth-onboarding）を確認したうえで、match-management のスコープ境界と操作仕様の曖昧点を
明確化するためのヒアリングを実施した。特に ADR-002 の「試合作成（4人選択・初期立ち位置・
動画ソース）、Group 管理」という記述と、確定スキーマ・後続単位（match-recording）の責務との
境界が論点だった。

## 質問と回答

### Q0: 作業規模

**カテゴリ**: 前提確認
**背景**: 要件定義の詳細度を決めるため。

**回答**: フル機能開発（詳細な EARS・包括的ユーザーストーリー・完全な受け入れ基準・非機能/エッジ含む）

---

### Q1: スコープ境界（sets / 初期立ち位置を含むか）

**カテゴリ**: 既存設計確認 / 未定義部分詳細化
**背景**: ADR-002 は match-management に「初期立ち位置」を含めると記述するが、DB スキーマ上
`sets`（セット設定）・`set_player_positions`（左右立ち位置）は matches とは別テーブルで、
録画時の関心事（match-recording 責務）とも解釈できる。単位の大きさが大きく変わる最重要論点。

**回答**: **matches のみ（最小/推奨）**。試合マスタ = 4 選手 + 動画ソースのみを CRUD し、
sets / 立ち位置は録画開始時に match-recording が作成する。

**信頼性への影響**:
- REQ-405（録画系テーブル非書き込み）を 🔵 で確定。スコープ「含まない」セクションを確定。
- 本単位を player-management と同規模の薄い UI 層として確定。

---

### Q2: 動画ソース入力の扱い（video_source_url NOT NULL / local 方式A）

**カテゴリ**: 未定義部分詳細化
**背景**: `video_source_url` は NOT NULL。video-playback はローカル動画を「毎回再選択（方式A）」と
確定済みのため、local の場合に永続パスを保持できず、url に何を保存するかが不明だった。

**回答**: **MVP はローカル動画を使うため local が必須**。ただし youtube や将来的な独自クラウドも
追加できる構成にしておきたい。

**信頼性への影響**:
- REQ-106（local: 識別ラベルを url に保存）/ REQ-107（youtube: URL/ID）を 🔵 で確定。
- REQ-302（video_source_type を将来拡張可能な構成にしてよい）を 🔵 で追加。

---

### Q3: 作成済み試合の編集範囲

**カテゴリ**: 未定義部分詳細化
**背景**: 試合は下流に録画データ（sets/rallies）を持つため、選手構成や動画ソースの後編集が
整合性リスクになりうる。どこまで編集を許すかが論点。

**回答**: **全項目編集可（推奨）**。4 選手構成・動画ソースをいつでも編集可能。

**信頼性への影響**:
- REQ-003（全項目編集）を 🔵 で確定。

---

### Q4: 試合の削除の振る舞い

**カテゴリ**: 未定義部分詳細化
**背景**: player-management は無警告ソフト削除だが、試合は録画データを伴うため、同じ無警告で
よいか確認が必要だった。

**回答**: **確認ダイアログ付きソフト削除（推奨）**。削除前に確認ダイアログを出し、実体は
`deleted_at` ソフト削除。

**信頼性への影響**:
- REQ-004 / REQ-105（確認ダイアログ付きソフト削除）を 🔵 で確定。player-management との差分を明確化。

---

### Q5: 同一カードの重複作成

**カテゴリ**: データ整合 / 未定義部分詳細化
**背景**: 同じ 4 選手・同じ動画の試合を複数登録できるかが不明だった（DB に該当 UNIQUE 無し）。

**回答**: **複数作成を許可（推奨）**。player の同名許可と同様、同カードでも別試合を複数登録可。

**信頼性への影響**:
- REQ-104 / EDGE-005（重複許可）を 🔵 で確定。

---

### Q6: 試合一覧の表示・並び順（→ スキーマ拡張の発覚）

**質問日時**: 2026-06-05
**カテゴリ**: 未定義部分詳細化 / 既存設計の過不足
**背景**: NFR-203（一覧表示・並び順）を 🔵 化するため確認したところ、確定スキーマに無い属性の
要望が出て、スキーマ拡張の要否が論点化した。

**回答**:
- 並びは新しい順。日ではなく**時刻まで**の精度が欲しい。
- 作成日ではなく**その試合の日付（match_date）で管理**したい。表示は日付だけでよい。
- **試合に名前を付けたい**（例: XX練習会、横浜市大会）。

**信頼性への影響**:
- 確定 `matches` に `name` / `match_date` 列が無いことが判明 → 「新規 DB スキーマを作らない」前提を見直し。

---

### Q7: スキーマ拡張の方針（name / match_date / video_source_url）

**質問日時**: 2026-06-05
**カテゴリ**: 既存設計確認 / 追加要件
**背景**: Q6 の要望は matches への列追加と NOT NULL 制約の扱いに関わるため、拡張方針を確認。

**回答**:
- `match_date` と `name` は**追加する**。
- 試合名は**任意入力**。試合日付は**date 型**（表示は日付のみ、新しい順）。
- `video_source_url` は「local はパス / youtube は URL」の想定なら **NOT NULL のままでよい**。
- 「ファイル名ラベル保存とは？」という質問が出たため、ブラウザはローカルパスを永続化できず
  （video-playback 方式A＝毎回再選択）、local の url は再生に使えず**表示用ラベル**にしかならない旨を説明。
- 説明後、**local はファイル名ラベルを保存・NOT NULL 維持**を選択。

**信頼性への影響**:
- REQ-007（試合名 任意）/ REQ-008・REQ-109（試合日付 date・必須運用）/ REQ-108（name 1〜50字）/
  REQ-408（additive migration）/ REQ-106（local ラベル・NOT NULL維持）/ NFR-203（表示・並び）を 🔵 で確定。
- 本単位の性質を「純 UI 層」→「UI ＋ data-foundation への additive migration 1 本」に更新。

**設計上の補足（重要な気づき）**:
- ブラウザのファイル入力は**セッション限りの File オブジェクト**しか得られず、OS パスを保存しても
  後で開けない（セキュリティ制約）。これが video-playback「方式A」の根拠であり、local 動画の
  `video_source_url` は再生用ではなく「前回のファイル名」という人間向けの目印に限定される。

## ヒアリング結果サマリー

### 確認できた事項
- スコープは **matches のみ**。sets / 立ち位置 / 録画系は match-recording 責務（REQ-405）。
- Group 管理は auth-onboarding が担当済のため本単位スコープ外（ADR-002 の記述は実質移管済）。
- 動画ソースは **local 必須**かつ **type は将来拡張可能**な構成。local はファイル名ラベルを保存（NOT NULL 維持）。
- 編集は全項目可、削除は確認ダイアログ付きソフト削除、同カード重複は許可。
- **試合名（任意）と試合日付（date・必須運用）を matches に列追加**（data-foundation への additive migration）。
- 一覧表示は「試合名 or 対戦カード」＋「試合日付（日付のみ）」、試合日付の新しい順（同日は created_at 安定ソート）。

### 追加/変更要件
- REQ-007 / REQ-008 / REQ-108 / REQ-109（試合名・試合日付）を新規追加。
- REQ-408（additive migration の制約）を新規追加。本単位の性質が「純 UI 層」→「UI ＋ migration 1 本」へ。
- REQ-302（video_source_type 拡張可能構成）を新規追加。
- REQ-105（削除前確認ダイアログ）を player-management の無警告削除から差分化。
- NFR-203 を試合名・試合日付ベースの表示/並びに具体化し 🔵 へ昇格。

### 残課題（kairo-design で詳細化）
- 作成／編集 UI の具体形式（UModal か専用ページか）。項目が増えた（名前・日付追加）ためページ案の比重が上がる。
- youtube URL の検証程度（EDGE-004）。
- 選択可能 player が 4 人未満時の UI 導線（REQ-203）。
- 選手選択 UI の重複防止形式（NFR-202）。
- additive migration の配置（data-foundation 既存 schema への追記 or 別 migration ファイル）と適用タスク化。
