# match-recording ヒアリング記録

**作成日**: 2026-06-05
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

PRD（§F-02/§F-03/§5.2/§5.4）・確定済 DB スキーマ・上流仕様（rule-engine / video-playback / match-management）・関連メモリを精読したうえで、MVP のスコープ境界と入力フローが曖昧な点を明確化するためのヒアリングを実施した。

## 質問と回答

### Q1: 「打った」ショット記録（`shots` への1ショットずつの ms 記録）は MVP に含めるか

**質問日時**: 2026-06-05
**カテゴリ**: スコープ確定
**背景**: PRD §F-02 に「打った」ボタン（ms 自動取得）があり、§F-04 副次で「ショット数 × 得点率」分析に使う。一方、連打入力の負担が大きく `shots` への書き込みが発生するため、MVP 範囲を確認する必要があった。

**回答**: **MVP に含める（PRD 通り）**

**信頼性への影響**:
- REQ-005（ショット記録）を 🔵 で確定。`shots` を MVP 書き込みテーブルに含める。
- F-04 のショット数分析の基盤が MVP で揃う。

---

### Q2: `recording_gaps`（動画断絶＝ラリー数すら数えられない区間の記録）は MVP に含めるか

**質問日時**: 2026-06-05
**カテゴリ**: スコープ確定
**背景**: `recording_gaps` テーブルは DB に存在するが、PRD のレイアウト・受入基準には現れない。断絶入力 UX の複雑さに対して MVP 価値が不明だった。

**回答**: **MVP は対象外（推奨を採用）**

**信頼性への影響**:
- REQ-409（recording_gaps 書き込み禁止）を 🔵 で確定。MVP スコープから除外。テーブルは将来利用。
- MVP の複雑度が下がる。

---

### Q3: セット進行（1セット終了→次セット）の進め方

**質問日時**: 2026-06-05
**カテゴリ**: 入力フロー詳細化
**背景**: `sets` は match に複数。rule-engine は勝敗判定を持つ。セット決着→次セット開始（先攻・初期立ち位置再入力・カメラ手前チーム）の繋ぎ方が未定義だった。

**回答**: **勝敗検知し手動で次セット（推奨を採用）**

**信頼性への影響**:
- REQ-010 / REQ-107 を 🔵 で確定。自動遷移せず「次のセットへ」導線を提示、先攻＝前セット勝者を既定。

---

### Q4: 得点者・スコアの修正は UI 上どの範囲を編集可能にするか

**質問日時**: 2026-06-05
**カテゴリ**: 入力フロー詳細化
**背景**: [[project_rally_correction]] は「修正は直前1ラリーの想定」。一方 rule-engine は任意地点からの再計算が可能で、PRD のラリー履歴一覧には各行にジャンプ導線がある。UI の編集範囲でフォーム複雑度が変わる。

**回答**: **直前ラリーのみ（推奨を採用）**

**信頼性への影響**:
- REQ-106 を 🔵 で確定。修正は直前ラリーに限定し UI を単純化（engine は内部的にそれ以降を再計算）。
- 「履歴から任意の過去ラリーを編集」を MVP 範囲外に確定。

---

### Q5: カメラ視点（画面手前のチーム＝コート描画の向き）の MVP での扱い

**質問日時**: 2026-06-05
**カテゴリ**: スコープ確定
**背景**: スキーマは `sets.camera_near_team_at_start`（セット開始時）と `rallies.camera_near_team`（ラリー単位）の両方を持ち、どちらも NULL 許容。左右入れ替わり override の表示にも関わる。

**回答**: **セット開始時に1回設定（推奨を採用）**

**信頼性への影響**:
- REQ-002（camera_near_team_at_start を含む）を 🔵 で確定。ラリー単位の視点変更（`rallies.camera_near_team` の動的更新）を MVP 範囲外に確定。

---

## Claude が主導で決定した事項（お任せ、pros/cons 提示済）

- **position_overrides の swapped/restored vs rule-engine トグルの不整合**: PRD §F-02 が「変わった」→「戻った」の2アクション入力を明記しているため、match-recording がトグル回数の偶奇から `override_type` ラベルを決定して保存し、engine へは `applyOverride(state, team)` を渡す方式で両立（REQ-105 / EDGE-008）。
- **ルート規約**: PRD の `/matches/:id/record` ではなく、実コード規約 `/groups/[id]/...` に合わせ `/groups/[id]/matches/[matchId]/record`（REQ-001）。
- **マイグレーションは DELETE ポリシー追記1本のみ**: 録画系テーブルは確定済を消費。undo の物理削除（REQ-110、後日のUIヒアリングで確定）のため `rallies`/`shots`/`position_overrides` に DELETE RLS ポリシーを additive 追加（REQ-406）。列追加・新規テーブルは不要。
- **スキップ ↔ rule-engine 必須制約**: 未確定ラリーは engine に渡せないため確定まで保留（EDGE-003）。

## ヒアリング結果サマリー

### 確認できた事項
- ショット記録は MVP に含む（PRD 通り）
- recording_gaps は MVP 対象外
- セット進行は勝敗検知後の手動遷移
- 修正は直前ラリーのみ
- カメラ視点はセット開始時に1回設定

### 追加/変更要件
- 上記5点が要件 REQ/EDGE に反映済

### 残課題（kairo-design へ）
- 試合勝者の先取セット数ルール（REQ-011）
- override 入力フローのプロトタイプ検証（NFR-203）
- composable 分割粒度（NFR-302）
- 試合終了後のセット追加抑止挙動（EDGE-011）

**ヒアリング後**: 🔵 51 / 🟡 4 / 🔴 0（全55項目、🔵 93%）
