## タスク概要

Phase 1〜4 で実装した録画ユニットの **コアフローが結合状態で正しく動く**ことを確認する最終検証タスク。dataflow.md「状態管理フロー」の主要遷移を一気通貫で確認する:

> セット設定 → 立ち位置入力 → 打った（ショット）→ 得点 → 次サーバー / レシーバー表示 → undo（ショット物理削除 / 得点を進行中に戻す）→ override（左右入替トグル）→ スキップ → 後確定 → 直前修正 → セット決着 → 次のセットへ（先攻=前勝者）

検証は次の **2レイヤー**で行う（ADR-012 のテスト戦略 + memory feedback_test_layer_separation に整合）:

1. **composable 結合 integration test**（`*.integration.test.ts`、CI 専用、`fileParallelism: false`）: `useRecordingSession` を中心に、フェイク `getCurrentTimeMs` 時計 + 実 Supabase（テスト DB）で、上記コアフローの状態遷移・denormalize 保存・物理削除（undo）・RLS（他 Group 不可）を結合検証する。rule-engine（純関数）との入出力対応（applyRally → 次サーバー、determineSetWinner → winner）も含む。
2. **手動検証導線**（dev 検証ページ、`app/pages/dev/video-playback.vue` の作法踏襲）: 実プレーヤー（YouTube / local）+ 実 UI でコアフローを目視確認する dev 専用ページ、または record.vue 自体を dev データで叩く導線。実プレーヤーの ms 取得〜痕跡表示〜セット遷移を人が確認する。

検証範囲の最終的な配分（どこまで integration で自動化し、どこを手動に残すか）は実装時に詰める（信頼性 🟡）。原則は「engine 連携・物理削除・RLS・denormalize は integration で自動化、実プレーヤー連動の体感 / レイアウトは手動」とする（architecture.md「テスト容易性」+ ADR-012 = 見た目テスト禁止）。

## 実装詳細

### 1. composable 結合 integration test（コアフロー） 🔵
**信頼性**: 🔵 *dataflow.md 機能1〜6 + architecture.md ラリー行ライフサイクル + memory feedback_vitest_provide_inject / feedback_vitest_file_parallelism*

`useRecordingSession` をエントリにフェイク時計を注入し、実 Supabase（テスト DB、publishable key + RLS）でコアフローを一気通貫で叩く。各ステップ後に GameState（スコア / サーバー / レシーバー）と DB 行（rallies の denormalize 列 / shots / position_overrides の存在・物理削除）をアサートする。テスト DB は provide/inject で共有し（globalSetup と worker 分離対策、memory feedback_vitest_provide_inject）、共有 DB のため `fileParallelism: false`（memory feedback_vitest_file_parallelism）。

**実装ファイル**: `tests/integration/match-recording/recording-flow.integration.test.ts`

```ts
// 疑似コード（コアフローの結合検証骨子）
let now = 0
const clock = { getCurrentTimeMs: () => now } // フェイク時計（実プレーヤー不要）

const session = useRecordingSession(matchId, clock)

// 機能1: セットアップ → 第1ラリー確定
await session.configureSet(config)
await session.setPositions(fourPositions)
expect(session.gameState.value.score).toEqual({ A: 0, B: 0 })

// 機能2: 打った → ラリー遅延生成 + shots
now = 1000; await session.recordShot()
now = 2000; await session.recordShot()
// → rallies 1行（denormalize: serving_team/server/receiver）+ shots 2行を DB で確認

// 機能3: 得点 → applyRally → 次サーバー
await session.recordPoint('A')
expect(session.gameState.value.score).toEqual({ A: 1, B: 0 })
// → rallies.point_winner='A', is_point_confirmed=true を DB で確認

// REQ-110a: undo（ショット物理削除）
now = 3000; await session.recordShot()
await session.undoLast()
// → 最後の shots 行が物理削除されていること（空 rally なら rally も削除）

// REQ-110b: undo（得点を進行中に戻す）
await session.recordPoint('B'); await session.undoLast()
// → rally.point_winner=null/is_point_confirmed=false に UPDATE + GameState 復元

// 機能5: override トグル（EDGE-008）
await session.applyOverride('A'); await session.applyOverride('A')
// → position_overrides 2行（swapped→restored）, GameState.positions は元に戻る

// 機能4: スキップ → 後確定
await session.recordSkip(); await session.confirmSkipped('A')

// 機能6: 直前修正
await session.correctPreviousRally('B') // → 再計算・再保存

// 機能: セット決着 → winner → 次セット
// ...applyRally を勝利点まで進め determineSetWinner≠null → updateSet(winner) → nextSet（先攻=前勝者）
```

## 注意事項
- **信頼性 🟡 の所在**: フロー自体（dataflow.md）は確定だが、検証の自動化 / 手動の配分と手動導線の形態（dev ページ新設 vs record.vue dev 叩き）が未確定。実装の tdd-requirements で詰めて 🔵 化する。
- 見た目テストは書かない（ADR-012 / NFR-303）。実プレーヤー連動・レイアウト・体感は手動検証 + 検証ログに残す。
- integration は CI 専用・`fileParallelism: false`・provide/inject 共有 DB を厳守。ローカルで db:push / db:reset を実行しない（feedback_db_password_ci_only）。
- コアフローで不具合が出た場合は本タスクで握り込まず、原因の該当タスク（composable / コンポーネント / record.vue / DELETE ポリシー TASK-0001）へ戻して修正する（kairo-loop の戻り処理）。
- E2E（Playwright）は MVP 保留（ADR-012）。本タスクでは導入しない。
- 本タスクで DB / API / マイグレーションの変更は行わない（TASK-0001 の DELETE ポリシーは既に適用済の前提）。
