## タスク概要

録画対象の試合を `matchId` で1件読み、`useVideoPlayer` の `VideoSource` 構築材料 + 4選手ロスター（`MatchForRecording`: `id` / `name` / `videoSourceType` / `videoSourceUrl` / `roster[{ playerId, name, team }]`）へ射影する **Read composable** `app/composables/useMatchForRecording.ts` を実装する。

`useMatches.ts` の **Read パターン**（`useAsyncData<T>(固定キー, handler)` + PostgREST 埋め込み + snake_case → camelCase マッピング）を踏襲する。`matches` → `players` は**複合 FK**（`(group_id, *_player_id)`）のため、埋め込みヒントは**制約名**（`matches_group_id_team_a_player1_id_fkey` 等）を使う（useMatches.ts の実地検証済み: 単一列ヒントは PGRST200、制約名ヒントは 200 で解決）。

試合は所属 Group・未削除（`is('deleted_at', null)`）に限定。RLS は FK 経由 `is_member_of(matches.group_id)` で担保され、composable は `group_id` を直接持たない。本 composable は録画画面初期化（CSR、REQ-408）の最初の Read で、結果は page が `VideoSource`（youtube / local）構築 + 立ち位置入力の選択肢（4選手）に使う。

## 実装詳細

### 1. useMatchForRecording composable 🔵
**信頼性**: 🔵 *useMatches.ts（固定キー + 制約名ヒント + camelCase）/ interfaces.ts MatchForRecording / REQ-001 / REQ-004 / matches RLS*

`useAsyncData` の handler 内で `matches` を `id` 指定で1件読み、4選手を制約名ヒントで埋め込む。`roster` は team A の2選手・team B の2選手を `{ playerId, name, team }` に平坦化して4件にする。`video_source_type` は `'youtube' | 'local'`、`video_source_url` はそのまま渡す（youtube=URL/ID、local=ファイル名ラベル）。該当行が無ければ `null` を返す（page は not-found 表示）。

**実装ファイル**: `app/composables/useMatchForRecording.ts`

```typescript
/**
 * 【機能概要】: matches を1件 by id 読み、VideoSource 構築材料 + 4選手ロスターへ射影する Read composable
 * 【実装方針】: useMatches.ts を踏襲。useAsyncData 固定キー（matchId 含む）+ 複合FK 制約名ヒント埋め込み
 *             + snake_case → camelCase マッピング。所属 Group・未削除に限定（RLS は FK 経由）。
 * 🔵 interfaces.ts MatchForRecording / REQ-001 / REQ-004 / matches RLS
 */
import type { Database } from '~/types/supabase'
import type { MatchForRecording } from '~/types/match-recording'

export function useMatchForRecording(matchId: string) {
  const client = useSupabaseClient<Database>()

  return useAsyncData<MatchForRecording | null>(`match-for-recording-${matchId}`, async () => {
    // 【1件 read】: 複合 FK は制約名ヒントで解決（useMatches.ts 実地検証済）。
    //   削除済 player も name を維持するため players 側に deleted_at フィルタはかけない。
    const { data, error } = await client
      .from('matches')
      .select('id, name, video_source_type, video_source_url, ta1:players!matches_group_id_team_a_player1_id_fkey(id, name), ta2:players!matches_group_id_team_a_player2_id_fkey(id, name), tb1:players!matches_group_id_team_b_player1_id_fkey(id, name), tb2:players!matches_group_id_team_b_player2_id_fkey(id, name)')
      .eq('id', matchId)
      .is('deleted_at', null)
      .maybeSingle()

    if (error) throw error
    // 【not-found】: 他 Group（RLS）/ 削除済 / 不存在は null（page が not-found 表示）
    if (!data) return null

    // 【マッピング】: snake_case + 埋め込み → MatchForRecording。roster は 4 選手平坦化
    return {
      id: data.id,
      name: data.name,
      videoSourceType: data.video_source_type as 'youtube' | 'local',
      videoSourceUrl: data.video_source_url,
      roster: [
        { playerId: data.ta1.id, name: data.ta1.name, team: 'A' as const },
        { playerId: data.ta2.id, name: data.ta2.name, team: 'A' as const },
        { playerId: data.tb1.id, name: data.tb1.name, team: 'B' as const },
        { playerId: data.tb2.id, name: data.tb2.name, team: 'B' as const }
      ]
    }
  })
}
```

## 注意事項
- 複合 FK の埋め込みは**必ず制約名ヒント**を使う（単一列ヒントは PGRST200、useMatches.ts と同じ）。
- `players` 側に `deleted_at` フィルタをかけない（削除済選手でも名前を表示するため、EDGE-007 相当）。
- `group_id` を composable に持たせない（FK 経由 RLS で自 Group に限定、REQ-401）。
- `useAsyncData` のキーは `matchId` を含めて衝突を避ける（固定キーだが id ごとに分離）。
- 1件取得は `single()` ではなく `maybeSingle()` を使い、該当なしを `null`（error ではない）で扱う。
- `VideoSource` の具体構築（youtube/local の分岐、`File` 再選択）は page 側（REQ-402、composable は射影のみ）。
