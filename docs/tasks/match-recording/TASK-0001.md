## タスク概要

undo（REQ-110）を**物理削除（hard delete）**で行うため、data-foundation の録画系テーブルに
**DELETE RLS ポリシー追加の additive migration を1本のみ**加える。対象は `rallies` / `shots` /
`position_overrides` の3テーブル。これらは現状 SELECT / INSERT / UPDATE ポリシーのみで DELETE
ポリシーが無く、RLS 有効テーブルではポリシー不在＝全 DELETE 拒否となるため、undo の物理削除が
できない。

新規テーブル・列追加・新規 API/RPC は一切無い。既存 `20260519060000_initial_schema.sql` は
**編集せず**、match-management の `20260605120000_match_management_add_name_match_date.sql` と
同じく新規タイムスタンプ migration を1本追加する additive 方式に揃える。各 DELETE ポリシーは
既存 `*_select`/`*_update` と同一の FK 経由 `is_member_of(matches.group_id)` の EXISTS パターンを
そのまま流用し、他 Group の物理削除を RLS で拒否する（NFR-101）。

適用は CI（db:push、ローカル不可・SUPABASE_DB_PASSWORD ローカル不使用）。DELETE ポリシー追加は
列・型を変えないため `app/types/supabase.ts` の Row 型に影響しないが、gen-types CI が自動再生成
することを確認する。

## 実装詳細

### 1. DELETE RLS ポリシー追記 migration 🔵
**信頼性**: 🔵 *REQ-406 / REQ-110a・110c / initial_schema.sql L406-460 の *_select/update（FK 経由 EXISTS）/ match-management 追記 migration 前例*

既存 `initial_schema.sql` の `rallies_update` / `shots_update` / `po_update`（FK 経由
`is_member_of(matches.group_id)` の EXISTS）と**完全同型**の DELETE ポリシーを各テーブルに追加する。
DELETE は `USING` 句のみ（`WITH CHECK` は不要）。FK の連鎖は次のとおり：
- `rallies` → `sets` → `matches`
- `shots` → `rallies` → `sets` → `matches`
- `position_overrides` → `rallies` → `sets` → `matches`

ポリシー名は既存命名（`rallies_*` / `shots_*` / `po_*`）に揃え、`rallies_delete` / `shots_delete` /
`po_delete` とする。

**実装ファイル**: `supabase/migrations/{timestamp}_match_recording_add_delete_policies.sql`（タイムスタンプは既存命名規約 `YYYYMMDDHHMMSS_*.sql` に従い、最新 `20260605120000` より後の値で採番）

```sql
-- ========================================
-- match-recording additive migration: 録画系 DELETE RLS ポリシー
-- ========================================
--
-- 関連設計: docs/design/match-recording/architecture.md「技術的制約」
-- 関連要件: docs/spec/match-recording/requirements.md REQ-406 / REQ-110a / REQ-110c / NFR-101
--
-- 方針:
-- - 既存 20260519060000_initial_schema.sql は **編集しない**。新規タイムスタンプ migration を追加
--   (match-management の name/match_date 追記と同じ additive パターン)。
-- - undo (REQ-110) を物理削除で行うため、録画系 3 テーブルに DELETE ポリシーを追加する。
--   現状 SELECT/INSERT/UPDATE のみで DELETE が無く、RLS 有効テーブルはポリシー不在=全 DELETE 拒否のため。
-- - 列追加・新規テーブルは無し。各 DELETE は既存 *_update と同一の FK 経由 is_member_of EXISTS を流用。
-- - 適用は CI 経由 (db:push、ローカル不可)。適用後 gen-types CI が supabase.ts を再生成
--   (列不変のため Row 型は不変だが再生成自体は走る)。memory: feedback_db_password_ci_only。
-- - recording_gaps は MVP 対象外 (REQ-409) のため DELETE ポリシーを追加しない。

-- rallies: FK 経由 sets → matches。undo で空になった遅延生成 rally を物理削除 (REQ-110a)
CREATE POLICY "rallies_delete" ON rallies FOR DELETE
  USING (EXISTS (
    SELECT 1 FROM sets JOIN matches ON matches.id = sets.match_id
    WHERE sets.id = rallies.set_id AND is_member_of(matches.group_id)
  ));

-- shots: FK 経由 rallies → sets → matches。undo で進行中ラリーの最後の shot を物理削除 (REQ-110a)
CREATE POLICY "shots_delete" ON shots FOR DELETE
  USING (EXISTS (
    SELECT 1 FROM rallies JOIN sets ON sets.id = rallies.set_id
    JOIN matches ON matches.id = sets.match_id
    WHERE rallies.id = shots.rally_id AND is_member_of(matches.group_id)
  ));

-- position_overrides: FK 経由 rallies → sets → matches。undo で override 行を物理削除 (REQ-110c)
CREATE POLICY "po_delete" ON position_overrides FOR DELETE
  USING (EXISTS (
    SELECT 1 FROM rallies JOIN sets ON sets.id = rallies.set_id
    JOIN matches ON matches.id = sets.match_id
    WHERE rallies.id = position_overrides.rally_id AND is_member_of(matches.group_id)
  ));
```

## 統合テスト要件

### 統合テスト1: 自 Group の録画行は物理削除できる 🔵
**信頼性**: 🔵 *REQ-110a / REQ-110c / rallies_delete・shots_delete・po_delete*
**テスト内容**: 自 Group に属する match → set → rally に紐づく `shots` / `position_overrides` 行、および空にした `rallies` 行を、所属メンバーのクライアント（publishable key + RLS）で DELETE できることを検証する。
**期待結果**: 3テーブルそれぞれで DELETE が成功し、対象行が消える。
**テストファイル**: `tests/integration/match-recording/delete-policies.integration.test.ts`（CI 専用、命名 `*.integration.test.ts`、`fileParallelism: false`）

### 統合テスト2: 他 Group の録画行は物理削除できない（RLS 拒否） 🔵
**信頼性**: 🔵 *NFR-101 / REQ-401 / FK 経由 is_member_of*
**テスト内容**: 別 Group の match に紐づく `rallies` / `shots` / `position_overrides` 行に対し DELETE を試行する。
**期待結果**: RLS により対象行が削除されない（影響行 0 / エラーまたは no-op）。SELECT でも見えない。

> 注: 統合テストは provide/inject パターンでテスト DB を共有し、`fileParallelism: false` を厳守する（memory: feedback_vitest_provide_inject / feedback_vitest_file_parallelism）。実 DB 接続のため CI 専用とし、ローカルでは実行しない。

## 注意事項
- **既存 `20260519060000_initial_schema.sql` を編集しない**こと。必ず新規タイムスタンプ migration を1本追加する（match-management 前例と同じ additive 方式）。
- DELETE ポリシーは `USING` のみ。`WITH CHECK` は INSERT/UPDATE 用で DELETE には不要。
- `recording_gaps` には DELETE ポリシーを **追加しない**（MVP 対象外、REQ-409）。`sets` / `set_player_positions` も undo の物理削除対象外（セット作成は同期・境界操作で undo スタックに積まない）のため本 migration では触らない。
- ローカルで `db:push` / `db:reset` を実行しないこと（SUPABASE_DB_PASSWORD ローカル不使用、CI 一本化。memory: feedback_db_password_ci_only）。
- 列・型は変えないため `supabase.ts` の Row 型は不変だが、gen-types CI の再生成自体は走るため typecheck まで CI で確認する。
- ポリシー名 `rallies_delete` / `shots_delete` / `po_delete` は既存命名規約（`po_*` は position_overrides の略）に揃える。
