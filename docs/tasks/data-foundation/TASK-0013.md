## タスク概要

統合テスト (TASK-0014: RLS、TASK-0015: RPC) で必要となる「複数の認証済みテストユーザ」を、Supabase Admin API (`service_role` 経由) でテスト実行前に自動作成し、テスト終了時に削除する共通セットアップを整備する。

具体的には以下を作成する:

- `tests/setup/create-test-users.ts`: Admin API でテストユーザ A・B を作成 / 削除するヘルパ
- `vitest.integration.config.ts`: 統合テスト専用 vitest 設定（`globalSetup` で上記を実行）
- `package.json` に `test:integration` スクリプトを追加
- `.env.test` テンプレート（実体は gitignore、CI では Secrets から注入）

このタスクは TASK-0014 / TASK-0015 の前提となる共通インフラを整える役割を持つ。

### 🔵 テストユーザ作成方針 (B3 確定方針, 2026-05-13)

- **vitest の `globalSetup` で User A / User B を 1 度だけ作成** する。各 `it` ブロックごとの再作成は **採用しない**
- 全テスト終了後の `globalTeardown` で `auth.users` から削除 (cleanup)
- 各 `it` ブロックの `afterEach` で **「User A / User B が作成した Group / 関連データ」を `service_role` で削除** し、副作用リーク（テスト間データ汚染）を防ぐ
- pytest の session-scoped fixture と類似の構造 (Python 経験者向けの理解補助、注意事項参照)
- 採用理由: テストユーザの作成は Admin API 呼び出しで重い (1 user あたり数百 ms)。テストごとに再作成するとテストスイートの実行時間が大幅に延びるため、user は再利用しデータのみ毎回 cleanup する

**配置先**:

- `tests/setup/create-test-users.ts`
- `tests/setup/create-test-users.test.ts`（または `tests/setup/__tests__/create-test-users.test.ts`）
- `vitest.integration.config.ts`
- `.env.test.example`（テンプレートのみコミット）

## 実装詳細

### 1. `tests/setup/create-test-users.ts` 🔵

**信頼性**: 🔵 *スキーマレビュー ⑭ C-16 案γ、architecture.md "CI / 開発者ツール"*

```typescript
// tests/setup/create-test-users.ts
import { createClient, type SupabaseClient } from '@supabase/supabase-js'

interface TestUser {
  id: string
  email: string
  password: string
}

let adminClient: SupabaseClient | null = null
let createdUserIds: string[] = []

function getAdminClient(): SupabaseClient {
  if (adminClient) return adminClient
  const url = process.env.SUPABASE_URL
  const serviceRoleKey = process.env.SUPABASE_SERVICE_ROLE_KEY
  if (!url || !serviceRoleKey) {
    throw new Error('SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY が未設定です (.env.test 参照)')
  }
  adminClient = createClient(url, serviceRoleKey, {
    auth: { autoRefreshToken: false, persistSession: false }
  })
  return adminClient
}

export async function setupTestUsers(): Promise<{ userA: TestUser; userB: TestUser }> {
  const client = getAdminClient()
  const userA = await createOne(client, process.env.TEST_USER_A_EMAIL ?? 'test-a@example.com')
  const userB = await createOne(client, process.env.TEST_USER_B_EMAIL ?? 'test-b@example.com')
  return { userA, userB }
}

export async function teardownTestUsers(): Promise<void> {
  const client = getAdminClient()
  for (const id of createdUserIds) {
    await client.auth.admin.deleteUser(id)
  }
  createdUserIds = []
}

/**
 * afterEach で呼び出す cleanup ヘルパ (B3 確定方針, 2026-05-13)
 *
 * テストユーザは globalSetup で 1 度作成し再利用するため、各テスト間で
 * 「テストが作った group / group_members / group_invitations」を削除して
 * 副作用リークを防ぐ。auth.users は削除しない。
 */
export async function cleanupTestUserData(): Promise<void> {
  const client = getAdminClient()
  if (createdUserIds.length === 0) return
  // groups は ON DELETE CASCADE で group_members / group_invitations / players ... を
  // 連鎖削除する想定 (database-schema.sql の FK 定義に従う)
  await client
    .from('groups')
    .delete()
    .in('owner_user_id', createdUserIds)
  // group_members に owner 以外として参加した分も削除
  await client
    .from('group_members')
    .delete()
    .in('user_id', createdUserIds)
}

async function createOne(client: SupabaseClient, email: string): Promise<TestUser> {
  const password = `test-${crypto.randomUUID()}`
  const { data, error } = await client.auth.admin.createUser({
    email,
    password,
    email_confirm: true
  })
  if (error || !data.user) throw new Error(`createUser failed: ${error?.message}`)
  createdUserIds.push(data.user.id)
  return { id: data.user.id, email, password }
}

// vitest globalSetup 用 default export
export default async function globalSetup() {
  await setupTestUsers()
  return async () => {
    await teardownTestUsers()
  }
}
```

> **注意**: 上記コードは「設計の意図」を示すサンプルであり、実際の関数構造は TDD のテストケースに沿って組み立てる。型 (`TestUser`) は実装段階で別ファイルに切り出しても良い。

## 単体テスト要件（boundary + branch のみ）

> **方針**: redundant ケースは作らず、boundary（正常 1 + 主要分岐ごと）と branch（各例外パス）のみ。

| テストID | 種別 | テスト名 | 期待結果 | 信頼性 |
|----------|------|---------|---------|--------|
| TC-13-01 | boundary | 正常パス: 2 ユーザ作成成功 | `setupTestUsers()` の戻り値が `userA.id` / `userB.id` を持つ（UUID 形式） | 🔵 |
| TC-13-02 | branch | エラーパス: `SUPABASE_SERVICE_ROLE_KEY` 未設定 | `setupTestUsers()` が `Error('...未設定...')` をスロー | 🔵 |
| TC-13-03 | branch | エラーパス: Admin API が 401 を返す（不正キー） | `createUser` の `error` が非 null → 例外スロー | 🔵 |
| TC-13-04 | boundary | cleanup: 作成した user が削除されている | `teardownTestUsers()` 実行後、`auth.admin.listUsers()` で対象 uid が存在しない | 🔵 |
| TC-13-05 | boundary | afterEach cleanup: 作成した group が削除されている (B3 確定方針) | `cleanupTestUserData()` 実行後、User A が作成した `groups` 行が 0 件 | 🔵 |

**省略するケース**（redundant のため）:

- 「3 ユーザ・4 ユーザ作成」: 2 ユーザ作成が通れば N>2 は同じパスのため不要
- 「email 形式バリデーション」: Supabase Admin API 側の責務、本タスクの対象外
- 「password 強度」: 同上
- 「テスト毎再作成」: B3 確定方針により採用しない (globalSetup で 1 度作成)。再作成の検証ケースは不要

**テストの実装方針**:

- TC-13-02 は環境変数を vitest の `vi.stubEnv` で削除して検証
- TC-13-03 は `createClient` を mock するか、不正な service_role を渡して実 API 呼び出しで検証（CI では後者）
- TC-13-04 は実 dev プロジェクトに対する統合テスト扱い（dev 環境必須）
- TC-13-05 は実 dev プロジェクトに対し、事前に User A で `create_group_with_owner` 等で group を作成 → `cleanupTestUserData()` → `groups` 行数 0 を確認

テストファイル: `tests/setup/__tests__/create-test-users.test.ts`

## 注意事項

- **SERVICE_ROLE_KEY の取り扱い**: NFR-101 に従い、`tests/` ディレクトリ以外（Nuxt のビルド対象である `app/` 等）に絶対に持ち出さない。CI では GitHub Actions Secrets として渡し、ログにマスクされていることを必ず確認する 🔵
- **dev プロジェクト依存**: 本タスクは実 Supabase dev プロジェクトに対して書き込みを行う。`pnpm test:integration` は CI または開発者ローカルでのみ実行し、prd プロジェクトには接続しないこと（REQ-009 の精神を流用） 🔵
- **テストユーザの作成戦略 (B3 確定方針, 2026-05-13)**: 🔵
  - **`globalSetup` で User A / User B を 1 度だけ作成し、`globalTeardown` で削除する**
  - **テストごとの再作成は採用しない**（Admin API は重く、テスト時間が伸びるため）
  - 副作用リーク防止のため、各 `it` ブロックの `afterEach` で `cleanupTestUserData()` を呼び、User A / B が作成した `groups` / `group_members` などのデータを `service_role` で削除する
  - pytest の session-scoped fixture と類似 (Python 経験者向けの理解補助)
  - テスト失敗で `globalTeardown` が走らなかった場合に備え、CI ジョブ末尾の `finally` で cleanup 用 npm script を呼ぶ運用も検討する 🟡
- **email_confirm: true 必須**: Supabase Auth は通常 email 確認を要求するが、Admin API では `email_confirm: true` を渡せば即時確認済み user を作れる。これにより `signInWithPassword` がテスト内で即座に成功する 🔵
- **後続タスクへの引き継ぎ**: TASK-0014 / TASK-0015 は `setupTestUsers()` の戻り値（`{ userA, userB }`）を `globalThis` または `getCurrentTestUsers()` 経由で取得する。export 方式は実装者が決めて良いが、戻り値の `id` / `email` / `password` プロパティ名は固定する。また `cleanupTestUserData()` を各 `afterEach` で呼び出す 🔵
- **MVP スコープ**: 「テストユーザの role 分け」「Group 事前作成」までは本タスクでは行わない。各統合テスト内で必要に応じて RPC / service_role で作成する 🟡
