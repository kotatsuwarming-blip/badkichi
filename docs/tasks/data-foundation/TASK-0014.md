## タスク概要

全 11 テーブル（groups, group_members, players, matches, sets, set_player_positions, rallies, shots, position_overrides, recording_gaps, group_invitations）に対し、Supabase RLS ポリシーが「自 Group のデータのみ参照・変更を許可、他 Group のデータには空集合 / 拒否を返す」ことを統合テストで保証する。

TASK-0013 で整備したテストユーザ A・B を用いて、

- User B の Group に属するデータを `service_role` で先に投入
- User A としてログインしたクライアントから SELECT / INSERT / UPDATE を試行
- 期待通りに空集合または拒否されること

を各テーブル × 各操作の境界ケースで検証する。

**配置先**:

- `tests/integration/rls.test.ts`

## 実装詳細

### 1. テストの全体構造 🔵

**信頼性**: 🔵 *REQ-101, REQ-201, NFR-104, EDGE-003*

```typescript
// tests/integration/rls.test.ts
import { describe, it, expect, beforeAll, afterAll } from 'vitest'
import { createClient, type SupabaseClient } from '@supabase/supabase-js'
import { setupTestUsers, teardownTestUsers } from '../setup/create-test-users'

let serviceClient: SupabaseClient
let userAClient: SupabaseClient
let userBGroupId: string
let userBPlayerId: string
// ... 他 User B のエンティティ ID

beforeAll(async () => {
  const { userA, userB } = await setupTestUsers()
  serviceClient = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_SERVICE_ROLE_KEY!)

  // User B のデータを service_role で投入
  userBGroupId = await createGroupForUserB(serviceClient, userB.id)
  userBPlayerId = await createPlayer(serviceClient, userBGroupId)
  // ... match / set / rally / shot / position_override / recording_gap / invitation も投入

  // User A としてログイン
  userAClient = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!)
  await userAClient.auth.signInWithPassword({ email: userA.email, password: userA.password })
})

afterAll(async () => {
  // service_role で User B 側データを削除
  await cleanupUserBData(serviceClient, userBGroupId)
})
```

> User A の Group は作らないか、別 Group ID を持つことで「異なる Group 同士」の境界を作る。

### 2. SELECT 境界テスト（11 テーブル分） 🔵

各テーブルで以下と同型のテストを 1 ケースずつ書く:

```typescript
describe('RLS SELECT: User A は User B Group のデータを取得できない', () => {
  it('groups: 空集合', async () => {
    const { data } = await userAClient.from('groups').select('*').eq('id', userBGroupId)
    expect(data).toEqual([])
  })
  it('players: 空集合', async () => {
    const { data } = await userAClient.from('players').select('*').eq('id', userBPlayerId)
    expect(data).toEqual([])
  })
  // matches, sets, set_player_positions, rallies, shots,
  // position_overrides, recording_gaps, group_invitations, group_members も同型
})
```

### 3. INSERT 境界テスト 🔵

```typescript
describe('RLS INSERT: User A は User B Group に書き込めない', () => {
  it('players: 拒否', async () => {
    const { error } = await userAClient.from('players').insert({
      group_id: userBGroupId,
      name: 'spoof'
    })
    expect(error).not.toBeNull()
  })
  // matches, sets, rallies, shots, position_overrides, recording_gaps も同型
})
```

`groups` の INSERT は RLS 上禁止（RPC 経由のみ）のため、直接 INSERT が `null` 影響または `error` で拒否されることを 1 ケース確認する。
`group_members` / `group_invitations` も RPC 経由のみで、直接 INSERT 拒否を 1 ケースずつ確認する。

### 4. UPDATE 境界テスト 🔵

```typescript
describe('RLS UPDATE: User A は User B Group の行を更新できない', () => {
  it('players: 影響行数 0', async () => {
    const { data } = await userAClient.from('players').update({ name: 'hacked' }).eq('id', userBPlayerId).select()
    expect(data ?? []).toEqual([])
  })
  // matches, sets, rallies, shots, position_overrides, recording_gaps も同型
})
```

> Supabase の RLS では UPDATE が空集合に走るため、`error` ではなく `data` 空が返るのが正しい挙動 (EDGE-003 の派生)。テストではこのパターンを採用する。

### 5. 未認証アクセス（REQ-201）🔵

```typescript
describe('RLS: 未認証ユーザは全テーブルにアクセスできない', () => {
  it('groups SELECT 拒否', async () => {
    const anonClient = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!)
    const { data, error } = await anonClient.from('groups').select('*')
    // anon ロールに RLS でアクセス権を与えていないため空集合または error
    expect(data ?? []).toEqual([])
  })
})
```

1 テーブル分のみ確認（11 テーブル全部は redundant）。

## 注意事項

- **テストデータの cleanup**: User B 側のデータは User B が削除されたタイミング（TASK-0013 の teardown）で CASCADE で消えるはずだが、念のため `afterAll` で `service_role` 明示削除を行う 🔵
- **テスト並列実行注意**: `vitest` のデフォルトはファイル並列だが、本テストは User B の Group ID をグローバルに持つため、`describe` 内では sequential であれば良い。複数の RLS テストファイルを並列実行する場合はテストユーザを分けるかロックする 🟡
- **EDGE-003 の挙動再確認**: Supabase RLS では他 Group の行に対する SELECT は空集合、INSERT は `42501 new row violates row-level security policy` エラー、UPDATE は影響行数 0 となる。テストの assertion はこれに合わせる 🔵
- **groups テーブルの INSERT 直接拒否**: スキーマレビュー ⑦ A-1 + A-2 で「`create_group_with_owner` RPC 経由のみ」と決定されているため、anon・authenticated 共に直接 INSERT は RLS で拒否される。テストはこれを確認する 🔵
- **後続タスク (TASK-0017) への引き継ぎ**: 本テストが dev で全通過しないと、prd 適用後の RLS 問題発見が遅れる。**TASK-0017 (prd 適用) の前に必ず通すこと** 🔵
- **MVP スコープ**: SELECT 性能の負荷テストはここでは行わない（NFR-001 関連は TASK-0017 で別途実測） 🟡
