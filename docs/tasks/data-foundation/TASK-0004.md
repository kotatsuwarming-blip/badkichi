## タスク概要

Supabase CLI を使ってリポジトリに `supabase/` ディレクトリを生成し（`supabase init`）、dev プロジェクトに対する link 手順を確立する。`supabase/config.toml` の `project_id` 設定および `supabase status` / `supabase migration list` がクラウド dev プロジェクトを向いて動作することを確認する。

prd プロジェクトへの link 手順は **誤実行防止のため日常作業では行わない方針** とする。本タスクでは prd link が必要になるシチュエーション（手動マイグレーション確認時など）の手順だけドキュメント化し、平時は dev に link した状態を維持する。

ローカル Supabase（Docker）は **使わない**（REQ-403）。dev 検証はクラウド dev プロジェクトに対して直接行う。

## 実装詳細

### 1. Supabase CLI の動作確認（前提）🔵

**信頼性**: 🔵 *prep.md §5*

```bash
supabase --version
# v1.x.x （またはそれ以降）

supabase login
# ブラウザでアカウント認可（既に完了している想定）

supabase projects list
# badkichi-dev / badkichi-prd が表示されることを確認
# 各 Project Ref を控える
```

> Project Ref は URL `https://{ref}.supabase.co` の `{ref}` 部分。Dashboard → Settings → General → Reference ID でも確認可能。🔵

### 2. `supabase init` 実行 🔵

**信頼性**: 🔵 *REQ-004, architecture.md "ディレクトリ構造"*

リポジトリルートで実行:

```bash
pnpm dlx supabase init
# または
supabase init
```

生成されるファイル:

```
supabase/
├── .gitignore        # .temp/, .branches/ などを ignore
├── config.toml       # ローカル Supabase 用設定（本プロジェクトでは未使用部分が多い）
└── seed.sql          # 空ファイル（後で枠ファイルとしてコミット）
```

> `supabase init` は対話的に「VS Code 用設定を生成するか」「IntelliJ 用を生成するか」を聞いてくることがある。本プロジェクトはどちらも不要なので `n` で OK。🟡

### 3. `supabase/config.toml` の編集 🔵

**信頼性**: 🔵 *Supabase CLI 標準仕様 + REQ-403*

**変更ファイル**: `supabase/config.toml`

主な設定:

```toml
# プロジェクト識別子（CLI が状態管理に使用）
project_id = "badkichi-dev"

# ローカル Supabase は使用しない（REQ-403）が、CLI が要求するため最小設定は残す
[api]
enabled = false  # ローカル API は起動しない

[db]
# port は default のままで OK（ローカル db を起動しない方針）

[studio]
enabled = false  # ローカル Studio は起動しない

[auth]
enabled = false  # ローカル Auth は起動しない
```

> `enabled = false` を明示することで `supabase start` で全ローカルサービスが起動するのを防ぐ。これは REQ-403 の意図（クラウド dev を直接使う）と整合する。🟡
>
> もし `supabase init` のデフォルト config.toml が長大な場合、`enabled = false` を必要箇所に追記するだけで OK。全項目を編集する必要はない。🟡

### 4. dev プロジェクトへの link 🔵

**信頼性**: 🔵 *REQ-004, architecture.md "マイグレーション運用"*

```bash
supabase link --project-ref {DEV_REF}
# プロンプトで Database password を求められたら、TASK-0001 で設定したパスワードを入力
# 入力しない選択肢もある（後続の supabase db push 時に再度聞かれる）
```

完了すると以下が更新される:

- `supabase/.temp/project-ref` — リンク先 ref が保存される（git ignore）
- `supabase/config.toml` — `project_id` 等が更新される場合あり

### 5. 動作確認（dev に link した状態）🔵

**信頼性**: 🔵 *REQ-004*

```bash
supabase status
# 出力例:
# API URL: https://{DEV_REF}.supabase.co
# DB URL: postgresql://postgres.{...}:[YOUR-PASSWORD]@aws-0-{region}.pooler.supabase.com:6543/postgres
# ...

supabase migration list
# 出力例:
# Local | Remote | Time (UTC)
# (空、または既存のマイグレーションがあれば表示)
```

> `supabase status` がローカル Docker を見に行ってエラーになる場合は `supabase status --linked` で remote 状態を確認する。🟡

### 6. prd link 手順のドキュメント化 🔵

**信頼性**: 🔵 *REQ-009 の精神（prd 誤操作ガード）, architecture.md*

prd 接続が必要になるのは以下のような限定的シーン:

- 初回 prd スキーマ適用（GitHub Actions が動かない / 緊急時）
- prd の DB 状態を `supabase migration list` で確認したい
- prd の型を `supabase gen types` で取りたい（通常は dev で生成して問題ない）

これらのため、`README.md` または `docs/operations/supabase-cli.md`（新規）に以下を記載する:

````markdown
## Supabase CLI link 切り替え手順

平時は dev プロジェクトに link した状態を維持してください。
prd に link するのは下記の場合のみです:

- 緊急 prd 確認時
- 初回 prd スキーマ適用時

### dev → prd に切り替え

```bash
supabase link --project-ref {PROD_REF}
supabase migration list  # 何が適用済みかを必ず確認
```

### prd での作業終了後、必ず dev に戻す

```bash
supabase link --project-ref {DEV_REF}
```

⚠️ `pnpm db:reset` は prd に link した状態で **絶対に実行しないこと** （REQ-009 のガードでも止まるが、念のため）。
````

> 配置先は `README.md` の章でも、`docs/operations/supabase-cli.md` の新規ファイルでも可。チーム規模を考慮し、本タスクでは `README.md` の追記を推奨。🟡

### 7. `seed.sql` の空ファイル維持 🔵

**信頼性**: 🔵 *architecture.md "seed.sql 方針 (⑭ C-16)"*

`supabase init` が生成した `supabase/seed.sql` は中身が空または最小コメントだけの状態でコミットする。本プロジェクトでは architecture.md にあるように、`auth.uid()` 紐付けが必要な `group_members` を含む seed は意味をなさないため、空ファイルを維持する方針。

```sql
-- supabase/seed.sql
-- 本プロジェクトでは seed は使用しない。
-- 詳細は docs/design/data-foundation/architecture.md "seed.sql 方針" を参照。
-- テスト用ユーザは tests/setup/create-test-users.ts で動的生成する。
```

### Step 1: `tsumiki:direct-setup` フェーズ

## 注意事項

- **Docker 不使用の徹底**: `supabase start` を **実行しないこと**（REQ-403）。誤って実行した場合は `supabase stop` でローカルサービスを停止し、Docker 容量を解放する。🔵
- **`supabase link` の状態管理**: link 状態は `supabase/.temp/project-ref` に保存され、これは `.gitignore` 対象。つまり「現在どちらにリンクしているか」はローカル環境固有の状態。複数開発者で運用する場合は各自が dev に link する必要がある。🔵
- **prd link 切替の認知負荷**: 同じ CLI ツールで dev/prd を扱う設計の弱点として「うっかり prd のまま db:reset」のリスクがある。これは REQ-009 のガードスクリプト（次タスク以降）で技術的に防御する。本タスクは link 切替の手順整備のみ。🔵
- **`supabase/config.toml` の冗長設定**: `supabase init` が生成するデフォルト config.toml は項目が多い。全部読む必要はなく、`enabled = false` を必要箇所に書くだけで OK。後続で `supabase start` を使う方針に転じた場合に再調整する。🟡
- **CLI バージョン互換性**: Supabase CLI は破壊的変更がたまに入る。`supabase --version` を `package.json` の `engines` フィールドや README に明示しておくと、新規開発者参加時に混乱を減らせる（推奨）。🟡
- **後続タスクへの引き継ぎ事項**:
  - dev に link した状態が前提となるため、TASK-0005 着手前に `supabase status --linked` で確認すること 🔵
  - `package.json` への `db:push` / `db:reset` / `db:types` / `test:integration` スクリプト追加は別タスク（Phase 1 後半）の責務 🔵
- **MVP スコープ**: ローカル Docker Supabase の運用に切り替える判断は MVP 完了後の課題。Free プラン枠超過 / ネットワーク不安定環境での開発などで必要になれば再検討する。🟡
