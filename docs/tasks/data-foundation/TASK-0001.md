## タスク概要

Supabase Cloud 上に開発用 (`badkichi-dev`) と本番用 (`badkichi-prd`) の 2 プロジェクトを作成し、両方で Supabase Auth の Google OAuth プロバイダを有効化、Email/Password プロバイダを明示的に無効化する。Google Cloud Console での OAuth クライアント ID 発行 + redirect URI 設定もこのタスクの範囲とする。

このタスクは Supabase Dashboard / Google Cloud Console / Supabase CLI 等の管理コンソール作業が中心の DIRECT タスクであり、コード変更は発生しない。後続のローカル開発接続 (TASK-0002, TASK-0003) と CLI リンク (TASK-0004) の前提となる。

## 実装詳細

### 1. Supabase プロジェクト作成 🔵

**信頼性**: 🔵 *REQ-001, prep.md §2, architecture.md "コンポーネント構成 → Supabase プロジェクト"*

**操作画面**: Supabase Dashboard (`https://supabase.com/dashboard`)

操作手順:

1. 既存の Organization を開く（prep.md §1 で作成済み）
2. `New project` → 以下を入力:
   - Project name: `badkichi-dev`
   - Database password: 任意の強パスワード（パスワードマネージャに保管）
   - Region: `Northeast Asia (Tokyo)` を推奨（dev/prd で揃える）
   - Pricing plan: `Free`（NFR-101 / アーキテクチャ "技術的制約" Free プラン枠）
3. 作成完了まで数分待機（PostgreSQL 起動）
4. 同じ手順で `badkichi-prd` を作成

完了後、各プロジェクトの **Project Settings → API** から以下を控える:

- `Project URL` (例: `https://xxxxxxx.supabase.co`)
- `anon public` key
- `service_role` key（漏洩厳禁）

> **注意**: service_role key は **絶対にクライアント側コード / リポジトリ / Slack 等に貼らない**（NFR-101）。

### 2. Google Cloud Console で OAuth Client ID を作成 🔵

**信頼性**: 🔵 *REQ-002, prep.md §3*

**操作画面**: `https://console.cloud.google.com`

操作手順:

1. Google Cloud プロジェクト（例: `badkichi`）を選択
2. **APIs & Services → OAuth consent screen** を設定:
   - User Type: `External`
   - スコープ: `email`, `profile`, `openid`
   - テストユーザーに自分の Google アカウントを追加
3. **APIs & Services → Credentials → Create credentials → OAuth client ID**:
   - Application type: `Web application`
   - Name: `badkichi-web`
   - **Authorized redirect URIs** に以下を追加:
     - `https://{supabase-dev-project-ref}.supabase.co/auth/v1/callback`
     - `https://{supabase-prd-project-ref}.supabase.co/auth/v1/callback`
4. 作成された `Client ID` / `Client secret` を控える（次のステップで Supabase に登録）

> dev / prd で **別の OAuth client を作る** か **同一 client に両 redirect URI を登録する** かは任意。今回は単一 client で両方を扱う方針とする（運用負荷を下げるため）。🟡

### 3. Supabase Dashboard で Google プロバイダを有効化 🔵

**信頼性**: 🔵 *REQ-002, prep.md §4, architecture.md "Auth フロー"*

dev / prd 両プロジェクトで以下を実施する:

1. Supabase Dashboard → **Authentication → Providers** を開く
2. `Google` を有効化（Enabled ON）
3. ステップ 2 で取得した `Client ID` / `Client Secret` を入力して保存
4. **Authentication → URL Configuration**:
   - Site URL: dev は `http://localhost:3000`、prd は本番ドメイン（prep.md §7 で確定後に追記。未定なら一旦 localhost）
   - Redirect URLs に以下を追加:
     - dev: `http://localhost:3000`, `http://localhost:3000/confirm`
     - prd: 本番ドメイン + `/confirm`（確定後）

### 4. Supabase Dashboard で Email/Password プロバイダを無効化 🔵

**信頼性**: 🔵 *REQ-010, ヒアリング 2026-04-17*

dev / prd 両プロジェクトで以下を実施する:

1. Supabase Dashboard → **Authentication → Providers** → `Email`
2. `Enabled` を **OFF** にして保存
3. Email confirmations や Sign up に関する設定値は OFF のままで構わない（無効化済み）

> **理由**: badkichi は Google OAuth 単一方式とする（REQ-010）。Email/Password を有効のまま放置すると意図しないサインアップ経路が残るため、明示的に無効化する。

## 注意事項

- **prep.md との並走**: [prep.md](../../spec/data-foundation/prep.md) §1〜§4 はユーザ手動の準備タスクで、このタスクの実装詳細 1〜3 と内容が重複する。両者を別管理にする理由は、prep.md が「実装開始前」のチェックリスト、本タスクが「Phase 1 の最初の DIRECT 作業」という時系列上の位置付けが異なるため。実際の作業は 1 回で済む。🔵
- **prd ドメイン未確定の暫定対応**: prep.md §7（本番ドメイン取得）は data-foundation 完了までは後回し可。本タスクでは prd の Redirect URLs に localhost を入れておき、ドメイン確定後に追記する運用とする。🟡
- **Free プラン枠の確認**: dev/prd を Free プランで運用する場合、1 Organization あたり 2 プロジェクトが上限のことがある（要確認）。超過する場合は dev を別 Organization に分離するか、有料プランへの移行を検討する。🟡
- **service_role キーの取り扱い**: NFR-101 により、クライアントバンドルに service_role キーが混入してはならない。本タスク時点では `.env.*` への記載すら行わず、パスワードマネージャ保管のみとする。🔵
- **後続タスクへの引き継ぎ事項**:
  - dev / prd の **Project URL** と **anon key** → TASK-0003（環境変数管理）で `.env.*` に転記
  - dev の **Project Ref** (`{ref}.supabase.co` の `{ref}` 部分) → TASK-0004（Supabase CLI link）で使用
- **MVP スコープ**: Supabase の有料プラン移行判断（prep.md §10）は MVP スコープ外。Free プラン枠超過が見えてきた時点で別タスクで対応する。🟡
