## タスク概要

3 つの SECURITY DEFINER RPC（`create_group_with_owner`, `generate_invitation_code`, `join_group_with_code`）の振る舞いを統合テストで保証する。

- 正常パス: 期待される戻り値・DB 副作用が発生する
- 異常パス: 各エラーコード（`not_authenticated`, `invalid_group_name`, `not_a_member`, `invitation_not_found`, `invitation_expired`, PG `23505` (既メンバー), `invitation_code_collision_after_retry`）が発生する
- 境界値: 名前長 1 / 50 / 51 文字、期限 7 日ぴったり（EDGE-101）
- 招待コード衝突リトライ: **「5 回連続衝突 → リトライ全敗」のみテストする** (B4 確定方針, 2026-05-13)

TASK-0013 のテストユーザを利用し、認証コンテキスト切り替え（A・B）と `service_role` での直接 DB 操作を組み合わせる。

### 🔵 招待コード衝突リトライテスト方針 (B4 確定方針, 2026-05-13)

- **テストするもの**: 5 回連続衝突 → `invitation_code_collision_after_retry` 例外
  - 再現方法: `service_role` で `group_invitations` に同じコードを事前 INSERT し、`generate_invitation_code` 呼び出し時に必ず UNIQUE 違反させる (5 件分の事前 INSERT で 5 回失敗を確定)
  - 技術的な留意点: `gen_random_uuid()` がランダム値を返すため、正確には「事前に挿入されたコードと一致するまで試行 → 必ずしも 5 回で全敗しない」可能性がある。確実に再現するには、テスト用 RPC または同じ `public.gen_random_uuid` を mock するヘルパーを別途用意する必要がある (詳細は実装時に詳細化、保留メモとして残す) 🟡
- **テストしないもの (省略)**: 「4 回衝突 → 5 回目成功」シナリオ
  - 理由: CSPRNG (`gen_random_uuid()`) 出力を制御不可、テスト構築コストが見合わない
- 正常パス (初回成功、リトライなし) は別途「句読点テストケース」(RPC が呼べる、8 文字コードが返る) として含める

import { describe, it, expect, beforeAll, afterAll, beforeEach } from 'vitest'
import { createClient, type SupabaseClient } from '@supabase/supabase-js'
import { setupTestUsers } from '../setup/create-test-users'

### 2. create_group_with_owner テスト群 🔵

```typescript
describe('create_group_with_owner', () => {
  it('正常: User A が新規 Group を作成 → uuid 返却、groups + group_members に行', async () => {
    const { data, error } = await userAClient.rpc('create_group_with_owner', { group_name: 'テストG' })
    expect(error).toBeNull()
    expect(data).toMatch(/^[0-9a-f-]{36}$/) // uuid 形式

    const { data: groupRow } = await serviceClient.from('groups').select('*').eq('id', data).single()
    expect(groupRow?.owner_user_id).toBe(userAId)

    const { data: memberRow } = await serviceClient
      .from('group_members')
      .select('*')
      .eq('group_id', data)
      .eq('user_id', userAId)
      .single()
    expect(memberRow?.role).toBe('owner')
  })

  it('異常: 未認証 → not_authenticated', async () => {
    const anonClient = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!)
    const { error } = await anonClient.rpc('create_group_with_owner', { group_name: 'x' })
    expect(error?.message).toContain('not_authenticated')
  })

  it('境界: 空文字列 → invalid_group_name', async () => {
    const { error } = await userAClient.rpc('create_group_with_owner', { group_name: '' })
    expect(error?.message).toContain('invalid_group_name')
  })

  it('境界: 51 文字 → invalid_group_name', async () => {
    const { error } = await userAClient.rpc('create_group_with_owner', { group_name: 'a'.repeat(51) })
    expect(error?.message).toContain('invalid_group_name')
  })
})
```

> **boundary**: 名前長 1 文字（正常）は 1 つ目のテストで実質的にカバー（`'テストG'` の代わりに `'a'`）。redundant のため 50 文字ぴったりの「上限ぎりぎり正常」テストは省略（境界の片側 51 文字で十分）。

### 4. join_group_with_code テスト群 🔵

```typescript
describe('join_group_with_code', () => {
  let groupAId: string
  let validCode: string

  beforeAll(async () => {
    const { data } = await userAClient.rpc('create_group_with_owner', { group_name: 'join 用 G' })
    groupAId = data!
    const { data: code } = await userAClient.rpc('generate_invitation_code', { target_group_id: groupAId })
    validCode = code!
  })

  it('正常: User B が有効コードで参加 → group_members に行追加', async () => {
    const { error } = await userBClient.rpc('join_group_with_code', { invite_code: validCode })
    expect(error).toBeNull()
    const { data: memberRow } = await serviceClient
      .from('group_members')
      .select('*')
      .eq('group_id', groupAId)
      .eq('user_id', userBId)
      .single()
    expect(memberRow?.role).toBe('member')
  })

  it('異常: 不正コード → invitation_not_found (TASK-0007 確定値)', async () => {
    const { error } = await userBClient.rpc('join_group_with_code', { invite_code: 'INVALID0' })
    expect(error?.message).toContain('invitation_not_found')
  })

  it('異常: 期限切れコード → invitation_expired (EDGE-001, EDGE-101, TASK-0007 確定値)', async () => {
    // service_role で expires_at を過去に設定したコードを作成
    const expiredCode = 'EXPIRED1'
    await serviceClient.from('group_invitations').insert({
      group_id: groupAId,
      code: expiredCode,
      expires_at: new Date(Date.now() - 1000).toISOString(),
      created_by: userAId
    })
    const { error } = await userBClient.rpc('join_group_with_code', { invite_code: expiredCode })
    expect(error?.message).toContain('invitation_expired')
  })

  it('異常: 既メンバーが再度参加 → PG code 23505 (UNIQUE 違反、TASK-0007 確定値)', async () => {
    // User B は上の「正常」テストで既に参加済み
    const { error } = await userBClient.rpc('join_group_with_code', { invite_code: validCode })
    // api-endpoints.md 行 346 に従い PostgrestError code = '23505' で照合
    expect((error as { code?: string })?.code).toBe('23505')
  })
})
```

> **boundary**: EDGE-101（期限 7 日ぴったり）の正側は「正常テスト」で `validCode` が当日発行 → 7 日以内なので暗黙的にカバー。負側として「過去日時」を 1 ケースで確認すれば boundary 網羅。

### 5. 招待コード衝突リトライ全敗テストの再現方法 🔵 (B4 確定方針, 2026-05-13)

**信頼性**: 🔵 *B4 確定方針 (2026-05-13)*

`generate_invitation_code` の UNIQUE 衝突 5 回リトライ → `invitation_code_collision_after_retry` を再現するため、以下のいずれかを採用する。実装時に詳細化する 🟡。

#### 方針候補 A: service_role での事前 INSERT (シンプルだが完全再現は困難)

```typescript
// 事前に全 16^8 ≒ 4.3 億の hex 空間から「次に gen_random_uuid() が
// 生成する prefix」を予測できないため、確実に 5 回失敗させるには
// 直接アプローチでは難しい。
// → 単純な事前 INSERT は採用しない (技術的留意点)
```

#### 方針候補 B: テスト用 RPC を別途用意 (推奨)

`gen_random_uuid()` を mock しやすい SQL wrapper を作成:

```sql
-- supabase/migrations/{後続}_test_helpers.sql (実装時に決定、本タスクスコープ外も可)
CREATE OR REPLACE FUNCTION test_force_collision_invitation_code(target_group_id uuid)
RETURNS text
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  fixed_code text := 'DEADBEEF';   -- 固定値で 5 回試行
BEGIN
  -- (実装は generate_invitation_code をコピーし gen_random_uuid を fixed_code に置換)
END;
$$;
```

事前に同じ `fixed_code` で 1 件 `group_invitations` に INSERT しておき、`test_force_collision_invitation_code` を呼び出すと 5 回連続で UNIQUE 違反 → `invitation_code_collision_after_retry` を確実に再現できる。

#### 方針候補 C: アプリ側 wrapper で seed 制御 (TypeScript 側)

`generate_invitation_code` 自体は変更せず、テスト中だけ pg_catalog の関数を一時 override するアプローチもあるが、Supabase Cloud では `pg_catalog` 改変権限がなく非現実的。

#### 採用: B 案を実装時の第一候補とし、保留メモとして残す 🟡

実装時に上記 B 案を tdd-red フェーズで詳細化する。実装の細部 (テスト用 RPC を本タスクの SQL に含めるか、別マイグレーションで追加するか) は実装時に決定する。

### 6. 固定時刻 mock の検討 🟡

**信頼性**: 🟡 *タスク仕様の注意事項より*

`expires_at` を `new Date(Date.now() - 1000)` のような相対時間で作るのが標準。`vi.useFakeTimers()` で日時固定する方式も可能だが、Supabase 側の `now()` は実時刻なので mock は効かない点に注意（PostgreSQL 側時刻を制御できない）。本タスクでは service_role での直接 INSERT を採用し、PostgreSQL の `now()` ベースの判定を実時刻で検証する。

## 注意事項

- **タイムスタンプ依存テストの実時刻使用**: PostgreSQL の `now()` は実時刻のため、`vi.useFakeTimers()` では制御不能。期限切れ判定は `service_role` で `expires_at` を過去に設定して再現する 🔵
- **テスト順序依存**: `join_group_with_code` の「既メンバー再参加」テストは前のテストで参加済みであることが前提。`describe` 内では順序保証されるが、ファイル分割する場合は順序を明示する 🟡
- **エラー文字列の照合**: `error.message.includes('invitation_not_found')` のような部分一致で照合する。Supabase の error wrapping によりプレフィックスが変わる可能性があるため厳密一致は避ける。ただし PG code `23505` は `error.code` で厳密に照合する 🔵
- **例外名は TASK-0007 / database-schema.sql 確定値に統一**: 旧仕様の `invalid_code` / `expired_code` / `already_member` ではなく、**`invitation_not_found` / `invitation_expired` / PG `23505`** を採用する (api-endpoints.md 行 320〜332 と整合) 🔵
- **service_role での直接 INSERT は限定的に使用**: RPC の振る舞いを検証するテストなので、「期限切れコード作成」のような RPC では作れないシナリオでのみ service_role を使う 🔵
- **後続タスク (TASK-0017) への引き継ぎ**: RPC テストが dev で全通過しないと、prd 適用後の RPC 不具合発見が遅れる。**TASK-0017 (prd 適用) の前に必ず通すこと** 🔵
- **招待コード衝突リトライ全敗テストの方針 (B4 確定方針, 2026-05-13)**: 🔵
  - **「5 回連続衝突 → `invitation_code_collision_after_retry`」のみテストする**
  - 「4 回衝突 → 5 回目成功」は CSPRNG 出力制御不可のため省略
  - 再現方法は実装詳細 5 参照。詳細は実装時 (tdd-red フェーズ) に決定 🟡
