## タスク概要

開発者が `git clone → pnpm install → pnpm db:reset` の 3 ステップだけで dev 用 Supabase スキーマを初期化できる状態を整備する（NFR-201）。具体的には:

1. `supabase/seed.sql` を **空のコメント付き枠ファイル**として作成する（⑭ C-16 で確定。`auth.uid()` 依存により実データ投入は CI 内 setup スクリプトに委譲）。
2. `package.json` の `scripts` に `db:reset` を追加し、`supabase db reset --linked` を呼び出す。
3. **prd 誤操作ガード**として `scripts/db-reset-guard.sh` を作成し、リンク先 Supabase プロジェクトが `badkichi-dev` 以外の場合は exit 1 で拒否する（REQ-009）。

このタスクは Supabase CLI / シェルスクリプト / `package.json` 編集のみで完結する DIRECT タスクであり、コード本体（`app/`）には変更を加えない。後続の TASK-0011（マイグレーション改変検出）/ TASK-0017（prd 初回適用）の前提となる。

## 実装詳細

### 1. `supabase/seed.sql` の作成 🔵

**信頼性**: 🔵 *REQ-008, スキーマレビュー ⑭ C-16, architecture.md "マイグレーション運用 → seed.sql 方針"*

`supabase/seed.sql` を以下のような **空のコメント付き枠ファイル**として作成する。

```sql
-- supabase/seed.sql
--
-- 本ファイルは `pnpm db:reset` で適用される dev 用シードデータ枠ファイルである。
-- 現時点では INSERT 文を含まない（空ファイル）。
--
-- 理由 (⑭ C-16):
--   - Group / group_members は auth.uid() 紐付けが必要であり、
--     メンバーなしの Group を seed しても RLS により誰にも見えない。
--   - 意味のあるテストデータ作成には本物の auth ユーザが必要。
--   - そのため、テストデータは CI 内の setup スクリプト
--     (tests/setup/create-test-users.ts) から Supabase Admin API 経由で生成する。
--
-- 将来 (RLS を介さない dev 用 fixture が必要になった場合) はここに INSERT を追加する。
```

> **配置**: リポジトリルートからの相対パスで `supabase/seed.sql`。Supabase CLI 標準のパスのためファイル名を変更しないこと。

### 2. `scripts/db-reset-guard.sh` の作成 🔵

**信頼性**: 🔵 *REQ-009, architecture.md "CI / 開発者ツール → pnpm db:reset"*

`scripts/db-reset-guard.sh` を以下の方針で作成する。

```bash
#!/usr/bin/env bash
set -euo pipefail

# 現在の Supabase CLI リンク先プロジェクト名を取得する。
# 取得方法は CLI バージョンにより `supabase status` の出力フォーマットが変わるため、
# 安定して取れる箇所を選ぶ。MVP 時点では `supabase projects list` の
# `LINKED` カラムを参照する想定だが、CLI バージョン確定後に微調整可。
LINKED_NAME="$(supabase projects list --output json \
  | jq -r '.[] | select(.linked == true) | .name')"

if [ -z "${LINKED_NAME}" ]; then
  echo "[db-reset-guard] エラー: リンク先プロジェクトが取得できませんでした。" >&2
  echo "  先に \`supabase link --project-ref <dev-ref>\` を実行してください。" >&2
  exit 1
fi

if [ "${LINKED_NAME}" != "badkichi-dev" ]; then
  echo "[db-reset-guard] 拒否: 現在のリンク先は '${LINKED_NAME}' です。" >&2
  echo "  pnpm db:reset は dev (badkichi-dev) でのみ実行可能です（REQ-009）。" >&2
  exit 1
fi

echo "[db-reset-guard] OK: リンク先は badkichi-dev です。db:reset を続行します。"
```

> **注意**: Supabase CLI のサブコマンド / 出力フォーマットはバージョン依存。実装時に `supabase --version` でバージョンを固定し、出力を確認した上で `jq` クエリを調整する。`supabase projects list --output json` が利用できない場合は `supabase status` の TEXT 出力を `grep` するフォールバックでも可。🟡

```bash
# 実行権限を付与
chmod +x scripts/db-reset-guard.sh
```

### 3. `package.json` scripts への登録 🔵

**信頼性**: 🔵 *REQ-008, REQ-009*

`package.json` の `scripts` に以下を追加する。

```json
{
  "scripts": {
    "db:reset": "bash scripts/db-reset-guard.sh && supabase db reset --linked"
  }
}
```

> **補足**: `db:push`（dev へのマイグレーション適用）や `db:types`（型生成）は別タスク（TASK-0009 / TASK-0008 系）でカバーされる想定。本タスクのスコープは `db:reset` のみ。

## 注意事項

- **Supabase CLI バージョン依存**: `supabase projects list --output json` および `supabase status` の出力フォーマットは CLI バージョンに依存する。本タスク実装時の CLI バージョンを README または `prep.md` に記載し、将来 CLI 更新時に再検証する運用とする。🟡
- **seed.sql を空にする理由**: スキーマレビュー ⑭ C-16 で確定。`group_members` が `auth.uid()` 紐付け前提のため、seed で Group を作成しても RLS により誰にも見えない。意味のある dev 用初期データが必要になったタイミングで別タスクとして検討する。🔵
- **ガードのフォールバック**: `jq` 未インストール環境では `supabase status` の TEXT 出力を `grep` する形式に変更可。MVP 段階では開発者ローカルに `jq` がある前提とし、無ければ Homebrew 等で導入してもらう。🟡
- **prd 誤操作ガードのテストにかかるリスク**: 動作確認の再現手順 3〜4 で一時的に prd リンクに切り替えるが、`db:reset` 以外のコマンド（`supabase db push` 等）を **誤って** 叩かないよう注意する。検証直後に必ず `supabase link` で dev に戻す。🟡
- **後続タスクへの引き継ぎ**:
  - 本タスクで整備した `db:reset` を TASK-0011 のドキュメント（CI で `db:reset` を呼ぶ場合の手順）から参照する
  - TASK-0017（prd 初回適用）は `migrate-prd.yml` 経由で行うため、本タスクのガードは prd 適用フローには影響しない（migrate-prd.yml は `db:reset` を呼ばない）🔵
- **MVP スコープ**: 本タスクは MVP の Phase 3 に必須。dev 環境の再構築可能性が確保されない限り、後続のスキーマ変更タスクで開発者が詰む。🔵
