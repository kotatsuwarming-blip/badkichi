## タスク概要

dev / prod の 2 環境に対する `.env.*` ファイル運用を確立する。

具体的には以下を実施する:

1. リポジトリに `.env.example` を作成し、必要な環境変数キー一覧を明示（git 管理する）
2. ローカルに `.env.development` / `.env.production` を作成し、TASK-0001 で取得した実際の Supabase URL / anon key を流し込む（git 管理しない）
3. `.gitignore` で `.env.*` を除外しつつ `.env.example` のみ追跡対象とする
4. `@nuxtjs/supabase` が自動で読む `SUPABASE_URL` / `SUPABASE_KEY` の動作を確認
5. `SUPABASE_SERVICE_ROLE_KEY` はサーバー専用とし、ブラウザバンドルに含めない（NFR-101）

このタスク完了後、`pnpm dev` 起動時に Supabase クライアントが dev プロジェクトに正しく接続できる状態になる。

## 実装詳細

### 1. `.env.example` の作成（git 管理）🔵

**信頼性**: 🔵 *NFR-102, prep.md §6, architecture.md "Nuxt 側の接続設定"*

**変更ファイル**: `.env.example`（新規作成）

**内容**:

```env
# Supabase クライアント設定（ブラウザに露出する、anon キーは RLS で保護）
# 値は Supabase Dashboard → Project Settings → API から取得する
SUPABASE_URL=https://xxxxxxxxxxxxxxxxxxxx.supabase.co
SUPABASE_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6...  # anon public key

# Supabase service_role キー（サーバー側のみで使用、絶対にクライアントに含めないこと）
# 用途: マイグレーション適用、テスト用ユーザ作成 (tests/setup/create-test-users.ts)
# Nuxt server/ ルートからのみ参照する
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6...  # service_role key (DO NOT commit)
```

**ポイント**:

- `SUPABASE_URL` / `SUPABASE_KEY` は `@nuxtjs/supabase` の規定キー名（モジュールが自動的に読む）🔵
- `SUPABASE_SERVICE_ROLE_KEY` はカスタムキー。サーバー側コード（`server/api/`, `tests/setup/`）で `process.env.SUPABASE_SERVICE_ROLE_KEY` として参照する想定 🔵
- 値はダミー値（`eyJ...`）で OK。実値は `.env.development` / `.env.production` に入れる 🔵

### 2. `.env.development` / `.env.production` の作成（git 管理外）🔵

**信頼性**: 🔵 *prep.md §6*

**変更ファイル**: `.env.development`, `.env.production`（新規作成、git ignore 対象）

**`.env.development` の内容例**:

```env
SUPABASE_URL=https://{dev-project-ref}.supabase.co
SUPABASE_KEY={dev-anon-key}
SUPABASE_SERVICE_ROLE_KEY={dev-service-role-key}
```

**`.env.production` の内容例**:

```env
SUPABASE_URL=https://{prod-project-ref}.supabase.co
SUPABASE_KEY={prod-anon-key}
SUPABASE_SERVICE_ROLE_KEY={prod-service-role-key}
```

> **注意**: prod の service_role キーはローカル `.env.production` には **入れないほうが安全**。GitHub Actions / デプロイ環境のシークレット管理に委ねる方針も検討すること。本タスクでは手元保管とローカルファイル管理を許容するが、リポジトリ外秘匿チャンネル（パスワードマネージャ等）への保管を推奨する。🟡

> Nuxt は `.env.development` / `.env.production` を自動で読むわけではない。`NODE_ENV=development` 時は `.env` を読む。本プロジェクトでは `dotenv-cli` 等の併用または `nuxt dev --dotenv .env.development` を採用するか、`.env` を `.env.development` のシンボリックリンクにする運用を選ぶ。本タスクではシンボリックリンク方式を推奨する（後続タスクで CI/CD を整える際に再検討可）。🟡

### 3. `.gitignore` の編集 🔵

**信頼性**: 🔵 *NFR-101, NFR-102, Nuxt 標準 .gitignore*

**変更ファイル**: `.gitignore`

既存 Nuxt 標準の `.gitignore` には `.env` が含まれている想定。以下を追記する:

```gitignore
# Environment variables
.env
.env.*
!.env.example
```

**確認方法**:

```bash
git check-ignore -v .env.development  # → matched by .gitignore
git check-ignore -v .env.example      # → not ignored (空出力)
```

### 4. `runtimeConfig.public` 連携の確認 🔵

**信頼性**: 🔵 *NFR-102, architecture.md*

`@nuxtjs/supabase` モジュールは `SUPABASE_URL` / `SUPABASE_KEY` を自動的に `runtimeConfig.public.supabase` 配下に展開する。追加のコード変更は不要だが、以下を確認する:

```bash
pnpm dev
# ブラウザコンソールで:
# > useRuntimeConfig().public.supabase
# → { url: 'https://...', key: 'eyJ...' } のように出力されれば OK
```

> 確認用に一時的に `app/pages/index.vue` で `<pre>{{ config }}</pre>` を表示することも可能（確認後は削除）。🟡

### 5. service_role キーのサーバー専用扱い 🔵

**信頼性**: 🔵 *NFR-101*

`SUPABASE_SERVICE_ROLE_KEY` は以下のルールで扱う:

- ✅ `process.env.SUPABASE_SERVICE_ROLE_KEY` をサーバー側コード（`server/api/`, `scripts/`, `tests/setup/`）で参照
- ✅ `nuxt.config.ts` の `runtimeConfig` (private 側) に展開してもよい
- ❌ `runtimeConfig.public` に展開しない（ブラウザバンドルに含まれてしまう）
- ❌ Vue SFC / `app/utils/` から直接参照しない

本タスク時点では参照箇所はまだ無いので、運用ルールの確立のみで OK。🔵

## 実装手順（DIRECT）

DIRECT タスクのため `direct-setup` → `direct-verify` の 2 段階で実施する。

### Step 1: `tsumiki:direct-setup` フェーズ

1. `.env.example` を作成（実装詳細 §1）🔵
2. `.env.development` を作成し、TASK-0001 で取得した dev の URL / anon key / service_role key を記載 🔵
3. `.env.production` を作成し、prod の値を記載 🔵
4. `.gitignore` を編集（実装詳細 §3）🔵
5. `.env` → `.env.development` のシンボリックリンクを作成（または `nuxt dev --dotenv .env.development` を `package.json` の `dev` スクリプトに反映）🟡
   ```bash
   ln -s .env.development .env
   ```

### Step 2: `tsumiki:direct-verify` フェーズ

1. `git status` を実行し、`.env.development` / `.env.production` が untracked にも staged にも上がらないことを確認 🔵
2. `git check-ignore -v .env.development .env.production .env.example` を実行し、最初の 2 つだけがマッチすることを確認 🔵
3. `pnpm dev` を実行し、Supabase 関連のエラー / 警告が出ないことを確認 🔵
4. ブラウザを開き、`useRuntimeConfig().public.supabase` で dev の URL / anon key が読めることを確認（一時的に index.vue で表示）🟡
5. `Ctrl+C` で停止、一時表示用コードは元に戻す
6. 動作確認テーブルの全項目をチェック

## 注意事項

- **シンボリックリンク方式の制約**: macOS / Linux では `ln -s .env.development .env` が動くが、Windows 環境ではシンボリックリンクの扱いが異なる。本プロジェクトは現在 macOS 単一開発のため許容するが、CI 環境（GitHub Actions Linux）でも動作確認すること。🟡
- **dotenv-cli の代替**: `package.json` の `scripts.dev` を `"dev": "dotenv -e .env.development -- nuxt dev"` に変えるアプローチもある。シンボリックリンクが嫌な場合はこちらを採用。本タスクではどちらでも OK。🟡
- **prod の service_role キーのローカル保管**: 上述のとおり、誤って commit するリスクや漏洩リスクを下げるため、ローカル `.env.production` には **prod の service_role キーを書かない** という運用も選択肢。本タスクでは「書いても良い、ただし要注意」のスタンスとし、運用判断を開発者に委ねる。🟡
- **CI/CD でのシークレット**: GitHub Actions の `.github/workflows/migrate-prod.yml`（[architecture.md](../../design/data-foundation/architecture.md) §マイグレーション運用）で prod 適用する際は GitHub Secrets を使用する。本タスクでは GitHub Secrets 登録は対象外（Phase 1 後半 / 別タスクで対応）。🔵
- **`SUPABASE_KEY` の名称**: `@nuxtjs/supabase` のデフォルト規約。誤って `SUPABASE_ANON_KEY` と書かないこと（モジュールが拾わない）。🔵
- **NFR-101 違反の早期検知**: 将来的に CI で `service_role` 文字列がブラウザバンドルに含まれていないか grep する仕組みを入れる案あり。本タスクでは手動 DevTools 確認にとどめる。🟡
