### ステップ 4: Dashboard / SQL Editor 検証 🔵

**信頼性**: 🔵 *psql / Supabase Dashboard 標準クエリ*

Supabase Dashboard の SQL Editor で以下を順に実行し、結果を `docs/implements/data-foundation/TASK-0009/direct-verify.md` に貼る:

```sql
-- 1. 11 テーブル存在確認
SELECT tablename
FROM pg_tables
WHERE schemaname='public'
ORDER BY tablename;
-- 期待: 11 件

-- 2. RLS 有効化確認
SELECT relname, relrowsecurity
FROM pg_class
WHERE relname IN (
  'groups','group_members','group_invitations','players','matches',
  'sets','set_player_positions','rallies','shots','position_overrides','recording_gaps'
)
AND relkind = 'r';
-- 期待: 全件 relrowsecurity = t

-- 3. ポリシー数確認
SELECT tablename, COUNT(*) AS policy_count
FROM pg_policies
WHERE schemaname='public'
GROUP BY tablename
ORDER BY tablename;
-- 期待: groups=2, group_members=1, group_invitations=1, players=3, matches=3,
--       sets=3, set_player_positions=3, rallies=3, shots=3,
--       position_overrides=3, recording_gaps=3

-- 4. RPC 3 関数存在確認
SELECT proname, prosecdef
FROM pg_proc
WHERE proname IN ('create_group_with_owner','generate_invitation_code','join_group_with_code');
-- 期待: 3 件、すべて prosecdef = t

-- 5. ヘルパー関数確認
SELECT proname
FROM pg_proc
WHERE proname IN ('is_member_of','update_updated_at');
-- 期待: 2 件

-- 6. 部分インデックス確認
SELECT indexname
FROM pg_indexes
WHERE schemaname='public' AND indexdef LIKE '%deleted_at IS NULL%';
-- 期待: 11 本以上
```

## 注意事項 ⚠

- 🔵 失敗時の対応:
  - マイグレーション SQL に問題がある場合、**既存ファイルの改変は禁止**（NFR-302）
  - **新規マイグレーションファイルを追加** して修正する（例: `{timestamp}_fix_xxx.sql`）
  - 該当する元タスク（TASK-0005 / 0006 / 0007）に戻って再検証する流れを取る
- 🔵 dev DB の状態は本タスク後に変化している（11 テーブルが空状態で存在）。以降のタスク（TASK-0010 以降）の前提となる
- 🟡 NFR-001（30 秒以内）の参考実測: マイグレーション規模（11 テーブル + RLS + RPC）から十分余裕の見込みだが、ネットワーク経路次第で変動する可能性あり。**本格実測は TASK-0017**
- 🔵 prod プロジェクトへの適用は **行わない**。本タスクは dev のみ対象。prod は TASK-0016（main merge 時の GitHub Actions による自動適用、⑮ C-17）
- 🔵 `supabase link` が dev ではなく prod を向いている状態で実行すると prod に適用されてしまう（事故）。事前確認（ステップ 1）を必ず実施する
- 🟡 検証 SQL の発行は Supabase Dashboard / `psql` どちらでも可。CI からの自動検証は TASK-0014 / TASK-0015 で導入予定
