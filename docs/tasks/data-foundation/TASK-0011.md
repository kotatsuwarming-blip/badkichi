## タスク概要

本タスクは 2 つの CI ガードを整備する DIRECT タスク。コード本体（`app/`）には変更を加えない。

### ガード 1: 既存マイグレーション改変検出

`supabase/migrations/` 配下の **既存マイグレーションファイル**が改変された場合に、pre-commit フックと GitHub Actions の両方で検出・拒否する仕組みを整備する（REQ-011 / NFR-302）。マイグレーションは「追記のみ」の運用とし、既存ファイルの変更は dev/prd 間のスキーマ齟齬を生むため絶対に避ける必要がある。

ガードは **pre-commit（早期 fail）+ CI（セーフティネット）** の二重構成とする:

- pre-commit: ローカルでコミット時に検出して開発者にフィードバック
- GitHub Actions: pre-commit を skip された場合のセーフティネット

### ガード 2: `supabase db lint` による静的解析 🔵 (B2 確定方針, 2026-05-13)

**追加スコープ**: `supabase db lint --linked --level error` を GitHub Actions で実行し、SECURITY DEFINER 関数の `search_path` 未固定 (`function_search_path_mutable`) や RLS 無効化 (`rls_disabled_in_public`) などのセキュリティアンチパターンを検出する。

TASK-0006 / TASK-0007 で全 SECURITY DEFINER 関数に `SET search_path = public` を付与する方針 (B2) と組み合わせ、**「実装時に正しく書く + lint で網羅検証する」** の二重防御を実現する。

pre-commit では dev DB リンクに時間がかかるため **GitHub Actions のみで実行する** (MVP は CI のみで十分)。

## 実装詳細

### 1. `scripts/check-migration-integrity.sh` の作成 🔵

**信頼性**: 🔵 *REQ-011, NFR-302, architecture.md "マイグレーション運用 → 変更検出"*

`scripts/check-migration-integrity.sh` を以下の方針で作成する。

```bash
#!/usr/bin/env bash
set -euo pipefail

# HEAD~1 と HEAD の差分から、supabase/migrations/ 配下で
# "変更された (Modified / Deleted / Renamed) 既存ファイル" を検出する。
# 新規追加 (Added) は許可する。
#
# 検出ロジック:
#   git diff --name-status HEAD~1 HEAD -- 'supabase/migrations/*.sql'
#     の出力フォーマット:
#       A<TAB>supabase/migrations/20260501_xxx.sql   (新規追加 — OK)
#       M<TAB>supabase/migrations/20260420_yyy.sql   (変更 — NG)
#       D<TAB>supabase/migrations/20260420_zzz.sql   (削除 — NG)
#       R100<TAB>old.sql<TAB>new.sql                 (リネーム — NG)

if ! git rev-parse --verify HEAD~1 >/dev/null 2>&1; then
  # 初回コミット時は HEAD~1 が無いのでスキップ
  echo "[check-migration-integrity] HEAD~1 が存在しないためスキップ"
  exit 0
fi

CHANGED="$(git diff --name-status HEAD~1 HEAD -- 'supabase/migrations/*.sql' \
  | awk '$1 !~ /^A/ { print }')"

if [ -n "${CHANGED}" ]; then
  echo "[check-migration-integrity] エラー: 既存マイグレーションファイルが変更されています。" >&2
  echo "  マイグレーションは追記のみ運用です（NFR-302 / REQ-011）。" >&2
  echo "  既存ファイルを変更する代わりに、新しいタイムスタンプ付き .sql を追加してください。" >&2
  echo "" >&2
  echo "変更検知の内訳:" >&2
  echo "${CHANGED}" >&2
  exit 1
fi

echo "[check-migration-integrity] OK: 既存マイグレーションファイルは改変されていません。"
```

```bash
# 実行権限付与
chmod +x scripts/check-migration-integrity.sh
```

> **注意**: pre-commit 時には `HEAD~1` と `HEAD` ではなくステージング内容を見るのが本来正しい。MVP では「コミット作成直後（push 前）」ではなく **コミット作成前の検査** とするため、`git diff --cached HEAD --name-status -- 'supabase/migrations/*.sql'` を使う形に分岐させる方が確実。CI（GitHub Actions）側は `HEAD~1..HEAD` 比較で OK。実装時はモード（pre-commit / ci）を引数で切り替える形式とする。🟡

#### モード切り替えの実装例

```bash
MODE="${1:-ci}"   # "pre-commit" or "ci"

if [ "${MODE}" = "pre-commit" ]; then
  DIFF_CMD="git diff --cached --name-status -- 'supabase/migrations/*.sql'"
else
  DIFF_CMD="git diff --name-status HEAD~1 HEAD -- 'supabase/migrations/*.sql'"
fi
```

### 3. GitHub Actions への追加 🔵

**信頼性**: 🔵 *REQ-011, architecture.md "CI / 開発者ツール → GitHub Actions"*

既存の `.github/workflows/ci.yml` を以下のように編集する（既存ジョブを壊さない）。

```yaml
# .github/workflows/ci.yml (抜粋差分)

jobs:
  migration-integrity:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v6
        with:
          fetch-depth: 2   # HEAD~1 比較のため最低 2 必要

      - name: Check migration integrity
        run: bash scripts/check-migration-integrity.sh ci

  ci:
    # 既存ジョブ（lint / typecheck / test）はそのまま温存
    runs-on: ${{ matrix.os }}
    # ...
```

> **並列 / 直列**: `migration-integrity` は独立ジョブとして `ci` と並列実行する（実行時間短縮）。依存 (`needs: migration-integrity`) を入れて直列にする選択肢もあるが、検出系は並列で十分。🟡

> **fetch-depth の注意**: `actions/checkout` のデフォルト `fetch-depth: 1` だと `HEAD~1` が取れない。本ジョブでは `fetch-depth: 2` を明示すること。🔵

### 4. `supabase db lint` ジョブの追加 🔵 (B2 確定方針, 2026-05-13)

**信頼性**: 🔵 *B2 確定方針 + Supabase 公式ドキュメント*

`.github/workflows/ci.yml` に dev プロジェクトをリンクして `supabase db lint` を実行するジョブを追加する。

```yaml
# .github/workflows/ci.yml (抜粋差分、追加分)

jobs:
  supabase-db-lint:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v6

      - name: Setup Supabase CLI
        uses: supabase/setup-cli@v1
        with:
          version: 1.x.x   # 🟡 具体バージョンは pin 推奨 (検出ルールは CLI バージョン依存)

      - name: Link to dev project
        run: supabase link --project-ref ${{ secrets.SUPABASE_DEV_PROJECT_REF }}
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}

      - name: Run db lint (error level)
        run: supabase db lint --linked --level error
```

## 注意事項

- **husky 新規導入の影響**: 既存リポジトリには現時点で `.husky/` が無いため、husky 導入により `package.json` の `prepare` スクリプトが追加される。他開発者が `pnpm install` した時に自動でフックが有効化されることをドキュメント（README）に明記する。🟡
- **`--no-verify` での bypass**: pre-commit は `git commit --no-verify` で skip 可能。GitHub Actions が **セーフティネット** として機能するため、bypass しても最終的に CI で検出される。🔵
- **既存マイグレーションファイルの定義**: 「既存」とは `HEAD~1`（pre-commit 時はステージング前の HEAD）に存在するファイルを指す。リネームは「変更」扱いとして拒否する（マイグレーションの順序が壊れるため）。🔵
- **shallow clone 対策**: GitHub Actions の `actions/checkout` はデフォルトで `fetch-depth: 1`。本ジョブでは `fetch-depth: 2` 必須。PR の場合はマージコミット側が `HEAD` なので親が複数になりうるが、`HEAD~1` で実用上問題ない。🟡
- **pre-commit と CI のロジック差分**: pre-commit は `--cached`（ステージング差分）を見る、CI は `HEAD~1..HEAD` を見る、という非対称性がある。これは pre-commit がコミット **作成前** に走るためで、意図的。両者を統一する場合は CI 側も `HEAD~1..HEAD` で良い（本タスクではそうしている）。🔵
- **後続タスクへの引き継ぎ**:
  - 本タスクで追加した `migration-integrity` ジョブを TASK-0012（prd 自動適用）が前提とする（改変があれば main にマージされないことを保証）🔵
  - 本タスクで追加した `supabase-db-lint` ジョブは TASK-0006 / TASK-0007 の `SET search_path = public` 実装方針 (B2) と組み合わせて、SECURITY DEFINER 関数の search_path 攻撃を二重防御する 🔵
- **`supabase db lint` の検出ルール一覧は Supabase CLI バージョンに依存**。`supabase/setup-cli` action の `version:` 指定でバージョン pin を行い、CLI 更新時はルール差分を確認すること 🟡
- **MVP スコープ**: 本タスクは MVP の Phase 3 に必須。マイグレーション改変を検出できない状態で開発者が増えると、dev/prd 間スキーマ齟齬で詰む。`supabase db lint` の追加で、SECURITY DEFINER 関数のセキュリティ問題も早期検出する 🔵
