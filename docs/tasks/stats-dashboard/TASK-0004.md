## タスク概要

TASK-0003 で作成した同一 migration ファイルへ、**ラリー長集計（`stats_rally_length`）とラリー行取得
（`stats_rallies`）**の 2 関数 + GRANT を追記・検証する。

- `stats_rally_length` は確定ラリーを shot 本数（`shots` の count、`deleted_at IS NULL`）でグルーピングし、
  **shot_count > 0 のみ**（EDGE-102: ショット 0 ラリーは長さ分析から除外）本数分布 `rallies` と
  サーブ側勝数 `serve_won` を返す。勝率（`serve_won / rallies`）はクライアントで算出。
- `stats_rallies` は**全ライブラリー**（レット・未確定含む。テーブルは履歴表示 REQ-006）を返し、
  クロスフィルタ・再生に使う。フィルタ引数で 1 選手（`p_server_player_id` / `p_receiver_player_id`、
  `p_role` 連動）/ ペア（`p_pair_player1_id` / `p_pair_player2_id`、`p_role` 連動）/ ラリー長ビン
  （`p_shot_ranges` jsonb の OR 範囲）を絞り込む。再生用に試合の動画ソース
  （`video_source_type` / `video_source_url`）を同梱（REQ-104）。`p_limit`（既定 200）は上限 1000 で
  暴走防止、`p_offset`（既定 0）。

両関数とも `SECURITY INVOKER` + `STABLE` + `SET search_path = public` + `invalid_scope` ガードで
TASK-0003 と方針統一。RLS を継承して他 Group を返さない（REQ-403 / NFR-101）。チーム A/B はフィルタ軸に
せず serve/receive 判定の内部利用のみ（ヒアリング2026-06-09）。

既存スキーマ不変（additive）。適用は CI（`db:push`、ローカル不可）。検証は integration テスト（CI 専用）。

## 実装詳細

### 1. stats_rally_length（ラリー長別 本数分布 + サーブ側勝数） 🔵
**信頼性**: 🔵 *database-schema.sql 関数 3 / REQ-005 / EDGE-102*

確定ラリー（TASK-0003 と同条件）に各ラリーの shot 本数 `sc`（`shots` の `deleted_at IS NULL` を count）を
付け、`WHERE sc > 0` で**ショット 0 ラリーを除外**（EDGE-102）。`sc` で GROUP BY して `rallies = count(*)`、
`serve_won = count(*) FILTER (WHERE point_winner = serving_team)` を `ORDER BY sc`。勝率はクライアントの
`toRallyLengthBins` / `toRallyLengthSeries` が `serve_won / rallies` で算出（区間 0 件は null）。

```sql
-- 要点（全体は database-schema.sql L172-213 を正とする）
WITH confirmed AS (
  SELECT r.id, r.serving_team, r.point_winner,
         (SELECT count(*) FROM shots sh WHERE sh.rally_id = r.id AND sh.deleted_at IS NULL) AS sc
  FROM rallies r
  JOIN sets s ON s.id = r.set_id AND s.deleted_at IS NULL
  JOIN matches m ON m.id = s.match_id AND m.deleted_at IS NULL
  WHERE r.deleted_at IS NULL AND r.is_let = false
    AND r.is_point_confirmed = true AND r.point_winner IS NOT NULL
    AND (p_match_id IS NULL OR m.id = p_match_id)
    AND (p_group_id IS NULL OR m.group_id = p_group_id)
)
SELECT c.sc AS shot_count, count(*) AS rallies,
       count(*) FILTER (WHERE c.point_winner = c.serving_team) AS serve_won
FROM confirmed c WHERE c.sc > 0 GROUP BY c.sc ORDER BY c.sc;
```

### 2. stats_rallies（ラリー行 / テーブル / クロスフィルタ / 再生） 🔵
**信頼性**: 🔵 *database-schema.sql 関数 4 / REQ-006/007/010/104 / ヒアリング2026-06-09（役割連動・ビン OR）*

**全ライブラリー**（`r.deleted_at IS NULL` のみ。レット・未確定も含む = テーブルの履歴表示 REQ-006）を
返す。各行に `shot_count`（shots count）と試合の動画ソース（`m.video_source_type` /
`m.video_source_url` / `r.video_start_timestamp_ms`）を同梱（再生・Group 横断のソース切替 REQ-104 /
EDGE-103）。フィルタ:
- **1 選手 + role 連動**: `(p_server_player_id IS NULL OR (p_role IS DISTINCT FROM 'receive' AND r.server_player_id = p_server_player_id))` / receiver も対称。
- **ラリー長ビン OR**: `p_shot_ranges` が NULL でなければ `EXISTS (SELECT 1 FROM jsonb_array_elements(p_shot_ranges) e WHERE shot_count BETWEEN (e->>'min')::int AND COALESCE((e->>'max')::int, 2147483647))`。
- **ペア + role 連動**: 試合のチーム構成（`matches.team_*`）から `LEAST`/`GREATEST` の正規化ペアが、`r.serving_team` 側（role='serve'）/ 受け側（role='receive'）/ どちらか（role NULL）に一致する EXISTS。
- **並び**: `ORDER BY m.match_date DESC NULLS LAST, m.created_at DESC, s.set_number, r.rally_number`。
- **ページング**: `LIMIT GREATEST(0, LEAST(COALESCE(p_limit,200), 1000))` / `OFFSET GREATEST(0, COALESCE(p_offset,0))`。

> 完全な本体（フィルタ条件・型・引数順）は database-schema.sql 関数 4（L222-328）を正として一致させる。
> 引数順は GRANT のシグネチャ（`uuid,uuid,uuid,uuid,uuid,uuid,text,jsonb,int,int`）と一致させること。

### TC-005-01: ラリー長別 rallies / serve_won（正常系） 🔵
**信頼性**: 🔵 *REQ-005 / database-schema.sql 関数 3*
**Given**: 確定ラリーを shot 本数 3 のもの 2 件（うち 1 件サーブ側勝ち）、本数 5 のもの 1 件（サーブ側勝ち）で seed
**When**: `stats_rally_length(p_match_id: M)`
**Then**: `{ shot_count: 3, rallies: 2, serve_won: 1 }` と `{ shot_count: 5, rallies: 1, serve_won: 1 }` を `shot_count` 昇順で返す

### TC-102-01: shot_count = 0 のラリー除外（EDGE-102 境界） 🔵
**信頼性**: 🔵 *EDGE-102 / database-schema.sql `WHERE sc > 0`*
**Given**: shots を 1 件も持たない確定ラリーを追加 seed
**When**: `stats_rally_length(p_match_id: M)`
**Then**: shot_count=0 の行は返らない（長さ分析から除外。ただし `stats_rallies` には現れる = TC-rallies-01 で確認）

### TC-rallies-01: stats_rallies は全ライブラリーを返す（REQ-006） 🔵
**信頼性**: 🔵 *REQ-006 / database-schema.sql 関数 4（レット・未確定含む）*
**Given**: 確定ラリー / レットラリー / 未確定ラリー / shot 0 ラリーを混在 seed
**When**: `stats_rallies(p_match_id: M)`（フィルタなし）
**Then**: 全件（レット・未確定・shot 0 含む）が返り、各行に `shot_count` と `video_source_type` / `video_source_url` が同梱される

### TC-rallies-02: 選手フィルタ × role 連動（分岐） 🔵
**信頼性**: 🔵 *REQ-010 / ヒアリング2026-06-09（役割連動）*
**Given**: 選手 P がサーバーのラリーとレシーバーのラリーを seed
**When**: `stats_rallies(p_match_id: M, p_server_player_id: P, p_role: 'serve')`
**Then**: P がサーバーのラリーのみ返る（receiver のラリーは含まれない）。`p_role: 'receive'` + `p_receiver_player_id: P` では receiver のラリーのみ

### TC-rallies-03: ペアフィルタ × role 連動（serve / receive 判定） 🔵
**信頼性**: 🔵 *REQ-012 / ヒアリング2026-06-09（ペアが serving 側 / 受け側）*
**Given**: ペア (X,Y) が team A、相手が team B の試合で、serving_team が A のラリーと B のラリーを seed
**When**: `stats_rallies(p_match_id: M, p_pair_player1_id: X, p_pair_player2_id: Y, p_role: 'serve')`
**Then**: (X,Y) が serving 側（serving_team=A）のラリーのみ返る。`p_role: 'receive'` では (X,Y) が受け側（serving_team=B）のラリーのみ

### TC-rallies-04: ラリー長ビン OR（p_shot_ranges 分岐） 🔵
**信頼性**: 🔵 *ヒアリング2026-06-09（複数ビンの和集合）/ database-schema.sql jsonb_array_elements*
**Given**: shot 本数 2 / 5 / 14 のラリーを seed
**When**: `stats_rallies(p_match_id: M, p_shot_ranges: [{"min":1,"max":3},{"min":13,"max":null}])`
**Then**: 本数 2（1〜3 に該当）と本数 14（13+ に該当）のラリーが返り、本数 5 は返らない（OR の和集合・上限 null の境界）

### TC-rallies-05: limit 上限クランプ（境界値） 🔵
**信頼性**: 🔵 *database-schema.sql `LEAST(COALESCE(p_limit,200), 1000)`*
**When**: `stats_rallies(p_match_id: M, p_limit: 5000)`
**Then**: 返却件数が 1000 を超えない（上限 1000 でクランプ）。`p_limit` 既定（未指定）は 200 件上限

### TC-rallies-06: RLS（他 Group は 0 件） 🔵
**信頼性**: 🔵 *REQ-403 / NFR-101 / SECURITY INVOKER*
**Given**: User B の Group のみにラリーを seed
**When**: User A クライアントで `stats_rally_length(p_group_id: G_userB)` / `stats_rallies(p_group_id: G_userB)`
**Then**: いずれも空（0 件）

## 注意事項
- **同一 migration への追記**: TASK-0003 が作成したファイルへ追記する（新規ファイルを増やさない）。タイムスタンプ・ヘッダコメントは TASK-0003 と共有。
- **引数順と GRANT の一致**: `stats_rallies` は引数が多い（10 個）。`p_role text` / `p_shot_ranges jsonb` の位置、GRANT の型リスト（`uuid,uuid,uuid,uuid,uuid,uuid,text,jsonb,int,int`）を database-schema.sql と完全一致させる（順序ずれは RPC 呼び出し時の型不一致を招く）。
- **shot count のサブクエリ**: `shots` は `deleted_at IS NULL` でカウント（物理削除でない論理削除分を除外）。`stats_rally_length` と `stats_rallies` で count 条件を揃える。
- **全ライブラリー vs 確定ラリー**: `stats_rallies` は**全ライブラリー**（テーブル表示 REQ-006）、`stats_rally_length` は**確定ラリーのみ**（長さ × 勝率分析）。両者の WHERE を取り違えない。
- **チーム A/B はフィルタ軸にしない**: ペア絞り込みは `LEAST`/`GREATEST` 正規化ペアと role で判定し、A/B ラベルを直接の絞り込みキーにしない（ヒアリング2026-06-09）。serve/receive 判定の内部利用に留める。
- **SECURITY INVOKER / STABLE / search_path / 読み取り専用**: TASK-0003 と同方針を厳守（REQ-403 / REQ-408 / NFR-101）。
- **ローカル適用禁止 / CI db:push**: TASK-0003 と同じ（[[feedback_db_password_ci_only]]）。
