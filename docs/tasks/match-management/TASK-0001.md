## タスク概要

`docs/design/match-management/database-schema.sql` の内容で、`matches` テーブルへ
**試合名 (`name`) と試合日付 (`match_date`)** を **additive（列追加のみ）** で加える
**新規タイムスタンプ migration** を作成する。既存 `supabase/migrations/20260519060000_initial_schema.sql`
は **編集しない**（TASK-0018 の ADR-006 追記 migration と同じパターン、REQ-408）。

追加内容は以下の 3 点：
- `ADD COLUMN name text`（任意・NULL 可）+ `matches_name_length_check`
  （`name IS NULL OR char_length(trim(name)) BETWEEN 1 AND 50`、REQ-108 / EDGE-011）
- `ADD COLUMN match_date date NOT NULL DEFAULT CURRENT_DATE`（REQ-008 / REQ-109）
- 部分インデックス `idx_matches_group_id_match_date ON matches (group_id, match_date DESC) WHERE deleted_at IS NULL`
  （並び替え最適化、NFR-203）

migration の適用は **CI 経由（db:push、ローカル不可）**。適用後 `app/types/supabase.ts` を
**Management API 経由で再生成**し、`matches` Row に `name (string | null)` / `match_date (string)`
が現れる状態にする（後続 composable の型がこれに依存）。新規 RPC・新規 RLS ポリシー・
新規エラーコードは作らない（既存 `matches_select/insert/update = is_member_of` をそのまま利用）。

## 実装詳細

### 1. additive migration の新規作成 🔵
**信頼性**: 🔵 *database-schema.sql / requirements.md §スキーマ拡張 / REQ-007・008・108・109*

`database-schema.sql` の本文をそのまま新規 migration ファイルに落とす。配置先は
`supabase/migrations/<timestamp>_match_management_add_name_match_date.sql`。`<timestamp>` は
既存最新（`20260529124258`）より後の値を採番する（Supabase migration の昇順適用規約）。

**実装ファイル**: `supabase/migrations/<timestamp>_match_management_add_name_match_date.sql`

```sql
-- matches: 試合名 (name) — 任意 (NULL 可)。REQ-007 / REQ-108 / EDGE-011
ALTER TABLE matches
  ADD COLUMN name text;

ALTER TABLE matches
  ADD CONSTRAINT matches_name_length_check
  CHECK (name IS NULL OR char_length(trim(name)) BETWEEN 1 AND 50);

-- matches: 試合日付 (match_date) — 必須運用。NOT NULL + DEFAULT CURRENT_DATE。REQ-008 / REQ-109
ALTER TABLE matches
  ADD COLUMN match_date date NOT NULL DEFAULT CURRENT_DATE;

-- 並び替え最適化の部分インデックス。NFR-203
CREATE INDEX IF NOT EXISTS idx_matches_group_id_match_date
  ON matches (group_id, match_date DESC)
  WHERE deleted_at IS NULL;
```

### 2. CI での db:push 適用 🔵
**信頼性**: 🔵 *REQ-408 / memory feedback_db_password_ci_only*

`SUPABASE_DB_PASSWORD` はローカルで一切使わない（memory）。migration の適用は CI の
`db:push` ジョブに一本化する。ローカルでは `supabase db reset` 等を実行しない。

### 3. supabase.ts の型再生成（Management API 経由） 🔵
**信頼性**: 🔵 *REQ-408 / memory feedback_db_password_ci_only（db:types は Management API 経由）*

migration 適用後、`app/types/supabase.ts` を Management API 経由（`db:types`）で再生成する。
再生成後の `Database['public']['Tables']['matches']['Row']` に `name: string | null` /
`match_date: string` が含まれることを確認する。これが揃わないと TASK-0002 以降の
`MatchListItem` / `CreateMatchInput` の型参照が通らない。

**実装ファイル**: `app/types/supabase.ts`（自動生成、手書き編集禁止）

## 注意事項
- **破壊的変更なし（additive）**。既存 `initial_schema.sql` は **絶対に編集しない**（新規 migration を追加）。
- 型再生成（`app/types/supabase.ts`）まで完了しないと、後続 composable（TASK-0003〜0006）の
  `matches` Row 型に `name` / `match_date` が出ず型が通らない。本タスクの「完了」は型再生成まで含む。
- `video_source_url` は NOT NULL のまま変更しない（REQ-106、local=ファイル名ラベル / youtube=URL）。
- RLS は既存 `matches_select / matches_insert / matches_update = is_member_of(group_id)` を利用。
  新規ポリシーは作らない。
- `matches_players_distinct_check` / 複合 FK / 録画系テーブル（sets / rallies 等）は一切触らない（REQ-405）。
- migration 適用・型再生成は **CI / Management API 経由**。`SUPABASE_DB_PASSWORD` をローカルで使わない
  （memory `feedback_db_password_ci_only` / `feedback_strict_secret_policy`）。
