## タスク概要

試合を **ソフト削除（`deleted_at` を now() に update）** する **Write composable**
`app/composables/useDeleteMatch.ts` を実装する。物理削除しない（REQ-402、matches に DELETE
ポリシーは無い）。`useDeletePlayer.ts` のソフト削除パターン（`update({ deleted_at })` + pending
try/finally）を踏襲し、`deleteMatch(id)` で `from('matches').update({ deleted_at: <now> }).eq('id', id)`
を実行する。戻りは `ActionResult<null>`。

**確認ダイアログは page 側（REQ-105）** の責務であり、本 composable は承認後に呼ばれて**即実行**する
（ダイアログ表示は含まない）。RLS / 通信エラーは `ActionResult.error` で返し、表示（toast）は
page 側（ADR-007、EDGE-010）。削除後の一覧除外（`deleted_at IS NULL` フィルタ、EDGE-006）は
page 側の `useMatches().refresh()` による。

## 実装詳細

### 1. useDeleteMatch composable 🔵
**信頼性**: 🔵 *useDeletePlayer.ts ソフト削除 / interfaces.ts UseDeleteMatchReturn / REQ-004 / REQ-402 / matches_update RLS*

`useDeletePlayer.ts` のソフト削除パターンを踏襲。`update({ deleted_at: <now> })` を `eq('id', id)` で
対象行に限定して実行する（DELETE ポリシーは無いため物理削除は不可、REQ-402）。`deleted_at` の値は
`new Date().toISOString()`（DB の timestamptz と整合）。RLS `matches_update = is_member_of(group_id)`
で自 Group のみソフト削除可。

**実装ファイル**: `app/composables/useDeleteMatch.ts`

```typescript
/**
 * 【機能概要】: 試合を deleted_at = now() でソフト削除する Write composable (REQ-004 / REQ-402)
 * 【実装方針】: useDeletePlayer.ts のソフト削除を踏襲。update({deleted_at}).eq('id', id)。
 *             確認ダイアログは page 側 (REQ-105)、本 composable は承認後に即実行する。
 * 🔵 interfaces.ts UseDeleteMatchReturn / REQ-004 / REQ-402 / matches_update RLS
 */
import type { Database } from '~/types/supabase'
import type { MatchListItem } from '~/types/match'

interface ActionResult<T> { data: T | null; error: unknown }

interface UseDeleteMatchReturn {
  deleteMatch: (id: MatchListItem['id']) => Promise<ActionResult<null>>
  pending: Ref<boolean>
}

export function useDeleteMatch(): UseDeleteMatchReturn {
  const pending = ref(false)
  const client = useSupabaseClient<Database>()

  async function deleteMatch(id: MatchListItem['id']): Promise<ActionResult<null>> {
    pending.value = true
    try {
      // 【ソフト削除】: deleted_at を now() に update。物理 DELETE はしない (REQ-402)。
      //   eq('id', id) で対象限定、RLS で自 Group のみ。EDGE-006 の一覧除外は refresh で成立 🔵
      const { error } = await client
        .from('matches')
        .update({ deleted_at: new Date().toISOString() })
        .eq('id', id)

      // 【エラー処理】: RLS 拒否 / 通信は ActionResult.error に詰める (EDGE-010) 🔵
      if (error) return { data: null, error }

      // 【成功戻り値】: ソフト削除成功。data は null (削除に返却データ無し) 🔵
      return { data: null, error: null }
    } finally {
      // 【pending リセット】: 成功・エラーを問わず必ず false に戻す 🔵
      pending.value = false
    }
  }

  return { deleteMatch, pending }
}
```

## 単体テスト要件

> テスト方針: 最小境界 + 分岐網羅のみ。Supabase クライアントをモックし、update に `deleted_at` が
> セットされ `eq('id', id)` が呼ばれること、分岐（成功 / エラー）を検証する。物理 DELETE が
> 呼ばれないことは「`from(...).delete` を呼ばない」で担保。

**テストファイル**: `tests/unit/composables/useDeleteMatch.test.ts`

### テストケース1: 成功で deleted_at がセットされる（ソフト削除） 🔵
**信頼性**: 🔵 *REQ-004 / REQ-402 / matches_update RLS*
**Given**: update が `{ error: null }` を返す / **When**: `deleteMatch('m1')` / **Then**:
`update` の引数に `deleted_at`（非 null の ISO 文字列）が含まれ、`eq('id', 'm1')` が呼ばれ、`error` が null。物理 `delete` は呼ばれない

### テストケース2: RLS / 通信エラーは ActionResult.error で返す 🔵
**信頼性**: 🔵 *EDGE-010 / ActionResult 契約*
**Given**: update が `{ error }` を返す / **When**: `deleteMatch('m1')` / **Then**:
`{ data: null, error }` を返し `pending` が finally で false に戻る

```typescript
import { describe, it, expect, vi, beforeEach } from 'vitest'

const eq = vi.fn()
const update = vi.fn(() => ({ eq }))
const del = vi.fn()
const from = vi.fn(() => ({ update, delete: del }))

vi.stubGlobal('useSupabaseClient', () => ({ from }))
vi.stubGlobal('ref', (v: unknown) => ({ value: v }))

const { useDeleteMatch } = await import('~/composables/useDeleteMatch')

beforeEach(() => {
  update.mockClear(); eq.mockClear(); del.mockClear()
  eq.mockResolvedValue({ error: null })
})

describe('useDeleteMatch', () => {
  it('TC1: 成功で deleted_at セット (物理 DELETE しない)', async () => {
    const { deleteMatch } = useDeleteMatch()
    const r = await deleteMatch('m1')
    const arg = update.mock.calls[0]?.[0] as { deleted_at?: string }
    expect(arg.deleted_at).toBeTruthy()
    expect(eq).toHaveBeenCalledWith('id', 'm1')
    expect(del).not.toHaveBeenCalled()
    expect(r.error).toBeNull()
  })

  it('TC2: RLS/通信エラーは ActionResult.error で返し pending を戻す', async () => {
    const err = { message: 'rls_denied' }
    eq.mockResolvedValue({ error: err })
    const { deleteMatch, pending } = useDeleteMatch()
    const r = await deleteMatch('m1')
    expect(r.data).toBeNull()
    expect(r.error).toBe(err)
    expect(pending.value).toBe(false)
  })
})
```

## 統合テスト要件

### 統合テスト1: 物理 DELETE されず deleted_at のみセットされる 🔵
**信頼性**: 🔵 *REQ-402 / EDGE-006 / matches_update RLS*
**テスト内容**: 実 Supabase に対し、自 Group の試合に `deleteMatch` を実行すると、行が物理削除されず
`deleted_at` のみ設定されること（行は DB に残存）、その後 `useMatches` 相当の SELECT
（`deleted_at IS NULL`）から除外されること（EDGE-006）、他 Group の試合は削除不可（RLS）を検証する。
**テストファイル**: `tests/unit/composables/useDeleteMatch.integration.test.ts`（CI 専用、命名規約
`*.integration.test.ts`、`fileParallelism: false` 前提、memory `feedback_vitest_file_parallelism`）
**期待結果**: 対象行が DB に残存し `deleted_at IS NOT NULL`、未削除一覧から除外、他 Group は削除不可。

## 注意事項
- **物理削除を行わない**（REQ-402、matches に DELETE ポリシー無し）。必ず `update({ deleted_at })` を使う。
- **確認ダイアログは page 側（REQ-105）**。本 composable はダイアログを持たず、承認後に即実行する
  （player の無警告削除と異なり、警告は page で出す）。
- `pending` は **必ず try/finally** で false に戻す（useDeletePlayer.ts 同方針）。
- `deleted_at` は `new Date().toISOString()`（DB timestamptz と整合）。`group_id` は送らない
  （id 指定 + RLS で自 Group 限定）。
- エラーは `ActionResult.error` に詰めて返す。表示チャネル（toast、EDGE-010）の選択は page 側（ADR-007）。
- 削除後の一覧除外（EDGE-006）は page 側の `useMatches().refresh()`（`deleted_at IS NULL` フィルタ）による。
