## タスク概要

試合管理のルートページ `app/pages/groups/[id]/matches.vue` を実装する。`useMatches()`（TASK-0003）で
未削除試合一覧を取得・表示し、各行に「**試合名（未入力時は対戦カード `A1・A2 vs B1・B2`）**」+
「**試合日付（日付のみ）**」を `match_date` 降順（同日は created_at 降順）で並べる（NFR-203）。
0 件時は**空状態の説明文 + 「試合を追加」CTA**（REQ-201）を出す。

選択可能 player（`usePlayers`（TASK-0002）の未削除ロスター）が **4 人未満**のときは「試合を追加」を
**disabled** にし、`/groups/[id]/players` への導線と説明を表示する（REQ-203）。追加 / 編集は
`MatchFormModal`（TASK-0008）を create / edit mode で開き、`saved` 後に `useMatches().refresh()` する。
削除は player（無警告）と異なり**確認ダイアログ（`<UModal>`）→ 承認で `useDeleteMatch`（TASK-0006）**を
実行し refresh する（REQ-105）。

`layout` は無指定（`default` 自動適用、ADR-011 D1）。保護は `auth.global.ts` が担い、本 page 到達時点で
「認証済み・Group 所属済み」が保証される（REQ-202）。supabase 直叩き禁止・composable 経由（REQ-403）。
全文言 i18n。新規 DB スキーマ・API・エラーコードは作らない。

## 実装詳細

### 1. 一覧取得とローディング / 空状態 / 選手不足分岐 🔵
**信頼性**: 🔵 *REQ-001 / REQ-201 / REQ-203 / dataflow.md 機能1 / players.vue ローディング pattern*

`useMatches()` の `data` / `pending` / `refresh`、`usePlayers()` の `data`（人数判定）を使う。
`pending` 中は `USkeleton`、取得後 0 件なら空状態（`t('matches.empty')` + CTA）、1 件以上なら一覧。
選択可能 player が 4 人未満なら「試合を追加」を disabled にし、選手追加導線を出す（REQ-203）。

**実装ファイル**: `app/pages/groups/[id]/matches.vue`

```vue
<script setup lang="ts">
import type { MatchListItem } from '~/types/match'

const route = useRoute()
const { t } = useI18n()

// 一覧取得（composable 経由・supabase 直叩き禁止, REQ-403）
const { data: matches, pending, error, refresh } = useMatches()

// 選手不足判定（REQ-203）。選択肢は未削除ロスター
const { data: players } = usePlayers()
const hasEnoughPlayers = computed(() => (players.value?.length ?? 0) >= 4)
const playersPath = computed(() => `/groups/${route.params.id}/players`)
</script>
```

### 2. 表示ラベル（試合名 or 対戦カード）と日付 🔵
**信頼性**: 🔵 *NFR-203 / interfaces.ts MatchListItem / architecture.md §UI*

埋め込みで解決済み、削除済 player も名前維持 = EDGE-007）。日付は `matchDate`（`YYYY-MM-DD`）を
日付のみ表示する。並びは `useMatches` のクエリ責務（NFR-203）なので page 側で再ソートしない。

<script setup lang="ts">
function cardLabel(m: MatchListItem): string {
  const a = `${m.teamA[0].name}・${m.teamA[1].name}`
  const b = `${m.teamB[0].name}・${m.teamB[1].name}`
  return `${a} ${t('matches.versus')} ${b}`
}
function titleOf(m: MatchListItem): string {
  return m.name && m.name.length > 0 ? m.name : cardLabel(m)   // NFR-203
}

### 3. モーダル開閉（create / edit）と saved 後 refresh 🔵
**信頼性**: 🔵 *architecture.md §UI / dataflow.md 機能2・機能3 / TASK-0008 emits*

`modalOpen` / `modalMode` / `editTarget` で `MatchFormModal` を制御。CTA で create、行の編集ボタンで
edit（対象 match をセット）。`saved` を受けてモーダルを閉じ `refresh()` する。

```vue
<script setup lang="ts">
const modalOpen = ref(false)
const modalMode = ref<'create' | 'edit'>('create')
const editTarget = ref<MatchListItem | undefined>(undefined)

function openCreate() {
  modalMode.value = 'create'
  editTarget.value = undefined
  modalOpen.value = true
}
function openEdit(m: MatchListItem) {
  modalMode.value = 'edit'
  editTarget.value = m
  modalOpen.value = true
}
async function onSaved() {
  modalOpen.value = false        // 親がモーダルを閉じる（TASK-0008 注意事項）
  await refresh()                // 一覧再取得（機能2/3 成功後）
}
</script>
```

### 4. 削除（確認ダイアログ → 承認で削除 → refresh） 🔵
**信頼性**: 🔵 *REQ-105 / REQ-004 / dataflow.md 機能4 / TC-004-01 / TC-004-02 / EDGE-006 / EDGE-010*

player の無警告削除と異なり、試合は録画データを伴うため**確認ダイアログ必須**（REQ-105）。削除ボタンで
確認ダイアログを開き、承認で `useDeleteMatch.deleteMatch(id)` を実行。`error` が無ければ `refresh()` で
一覧から消す（`deleted_at IS NULL` フィルタ、EDGE-006）。`error` なら toast（EDGE-010）。キャンセルでは
削除しない（TC-004-02）。`deletePending` 中はボタン disabled で二重実行防止。

```vue
<script setup lang="ts">
const { deleteMatch, pending: deletePending } = useDeleteMatch()
const { showError } = useToastErrors()

const confirmOpen = ref(false)
const deleteTarget = ref<MatchListItem | null>(null)

function askDelete(m: MatchListItem) {
  deleteTarget.value = m
  confirmOpen.value = true        // 確認ダイアログを開く（REQ-105）
}
async function onDeleteApprove() {
  if (!deleteTarget.value) return
  const { error } = await deleteMatch(deleteTarget.value.id)   // composable 経由（REQ-403）
  if (error) {
    showError(error)              // 通信 / RLS → toast（EDGE-010）
    return
  }
  confirmOpen.value = false
  deleteTarget.value = null
  await refresh()                 // 一覧から除外（EDGE-006）
}
</script>
```

### 5. 取得エラーのハンドリング 🔵
**信頼性**: 🔵 *error-handling §6④/⑦ / dataflow.md エラーフロー*

`useMatches()` の `error`（取得失敗）は error チャネルへ委譲。一覧取得失敗時に `showError(error)` を
一度通知（toast）し、空状態と取得失敗を区別する。想定外は Nuxt `error.vue` に委譲。

```vue
<script setup lang="ts">
watch(error, (e) => {
  if (e) showError(e)             // 取得失敗を toast（§6④）
})
</script>
```

## 注意事項
- **layout は無指定**（`default.vue` 自動継承、ADR-011 D1）。`definePageMeta({ layout })` を書かない。
- 保護は `auth.global.ts` middleware が担保。本 page で認証 / 所属チェックを再実装しない（到達時点で保証、REQ-202）。
- 削除は **確認ダイアログ必須**（REQ-105、player の無警告削除と差分）。承認後のみ `deleteMatch` を呼ぶ。
- 並び順は **`useMatches` クエリの責務**（`match_date` 降順→`created_at` 降順、NFR-203）。page で再ソートしない。

- supabase を直叩きしない（一覧 / 削除いずれも composable 経由、REQ-403）。
- `MatchFormModal` の auto-import 名はディレクトリ規約上 `MatchesMatchFormModal`

- `saved` 後の **モーダルを閉じる責務は本 page**（`modalOpen=false`）+ `refresh()`。TASK-0008 は emit のみ。
- テストは happy-dom + i18n mock。`useMatches` / `usePlayers` / `useDeleteMatch` / `MatchFormModal` を
