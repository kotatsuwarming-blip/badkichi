## タスク概要
`locales/ja.json` (主軸) と `locales/en.json` (ハコ) を error-handling.md §5.4 / §7.3 に従って作成する。App 識別子はフラットキー、PG SQLSTATE はツリー構造で配置する。さらに ja/en のキー構造一致を専用 CLI スクリプトで検証し (NFR-303)、pre-commit と CI の両方に組み込む。文言は ja のみ表示し (REQ-403)、コードに文言を直書きしない (NFR-204) 体制を整える。

## 依存タスク

- **後続タスク**: TASK-0007 (useErrorMessage が locale キーを参照)

## 完了条件
- [ ] `locales/ja.json`: `errors.*` (App 識別子はフラット、PG SQLSTATE はツリー) + 各画面文言を定義している
- [ ] `locales/en.json`: ja と同一のキー構造で、値は空文字 or `[en]` プレースホルダ
- [ ] ja/en キー構造一致チェックスクリプト (専用 CLI。汎用 Python ワンライナーは不可) を実装している

- [ ] キー欠落時に fail することを確認している

## 実装詳細
### 1. locales/ja.json 🔵
**信頼性**: 🔵 *error-handling.md §5.4*
App 識別子 (`generic` / `not_authenticated` / `not_a_member` / `invalid_group_name` / `invitation_not_found_by_link` / `invitation_expired` / `invitation_code_collision_after_retry` / `rls_rejected`) はフラットキー。PG SQLSTATE (`unique_violation` / `fk_violation` / `check_violation`) は context ツリー (`generic` / `join_group` / `create_group`)。TASK-0003 で追加した `ALREADY_IN_GROUP` に対応する `errors.already_in_group` も追記する (architecture.md 注3、REQ-105)。各画面文言 (ログイン / オンボーディング / Group 作成 / 招待リンク着地 / Group 設定) も配置する。
**実装ファイル**: `locales/ja.json`
```jsonc
{
  "errors": {
    "generic": "予期しないエラーが発生しました",
    "not_authenticated": "ログインが必要です",
    "not_a_member": "このグループのメンバーではありません",
    "invalid_group_name": "グループ名は 1〜50 文字で入力してください",
    "invitation_not_found_by_link": "招待リンクが無効です。発行者にご確認ください",
    "invitation_expired": "招待コードの有効期限が切れています",
    "invitation_code_collision_after_retry": "招待コードの生成に失敗しました。再度お試しください",
    "already_in_group": "すでにグループに参加しています",
    "rls_rejected": "操作する権限がありません",
    "unique_violation": {
      "generic": "既に存在します",
      "join_group": "すでに参加済みです",
      "create_group": "同じ名前のグループがすでに存在します"
    },
    "fk_violation": { "generic": "関連するデータが見つかりません" },
    "check_violation": { "generic": "入力値が不正です" }
  }
  // + 各画面文言 (login / onboarding / groups.new / join / groups.settings)
}
```

### 2. locales/en.json (ハコ) 🔵
**信頼性**: 🔵 *error-handling.md §7.3*
`ja.json` のキー構造を完全にコピーし、値は空文字 (`""`) または `[en]` プレースホルダにする (将来翻訳の作業しやすさ優先)。値は空でよいがキー構造は ja と一致させる。
**実装ファイル**: `locales/en.json`

### 3. ja/en キー構造一致チェック 🔵
**信頼性**: 🔵 *NFR-303 + memory `feedback_dedicated_linter_cli`*
ja/en の deep key set を比較し、片方にしかないキーがあれば fail する専用チェックスクリプトを実装する。汎用 Python ワンライナーでの代用は不可 (memory `feedback_dedicated_linter_cli`: 形式チェックは専用 CLI を使う)。スクリプトは TypeScript/Node で実装し `package.json` の script (例: `pnpm i18n:check`) として登録、pre-commit hook と CI の両方に組み込む。本チェックは auth-onboarding 専用ではなく全単位横断 (NFR-303)。
**実装ファイル**: チェックスクリプト本体 (例: `scripts/check-i18n-keys.ts`) + `package.json` script 登録 + pre-commit / CI 設定

## 単体テスト要件
**信頼性**: 🔵 *NFR-303 + ADR-012 D3 (境界値 + 分岐)*
キー構造一致チェックのロジックを境界 + 分岐で検証する (memory `feedback_test_coverage`)。テストファイル: チェックスクリプトの配置に応じて `tests/unit/` 配下 (例: `tests/unit/scripts/check-i18n-keys.test.ts`)。チェックロジックを純関数として切り出し、固定の ja/en オブジェクトを入力にテストする。

- **Given**: ja にのみ存在するキーがある ja/en ペア / **When**: 一致チェックを実行 / **Then**: fail (不一致を検出)
- **Given**: en にのみ存在するキーがある ja/en ペア / **When**: 一致チェックを実行 / **Then**: fail (不一致を検出)
- **Given**: ja/en が完全に同一のキー構造 / **When**: 一致チェックを実行 / **Then**: pass

## 注意事項
- 文言は ja のみ表示し、en は dev の `?locale=en` でのみ切替 (REQ-403)。prd では切替 UI を提供しない。
- コードに文言を直書きしない (NFR-204)。文言は必ず locale JSON から取得する。
- ネストキー (PG SQLSTATE ツリー) も deep に比較すること。トップレベルキーだけの比較では `unique_violation.join_group` 等の欠落を見逃す。
