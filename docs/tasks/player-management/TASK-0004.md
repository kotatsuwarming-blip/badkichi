## タスク概要

既存選手の `name` / `handedness` を update する **Write composable**
`app/composables/useUpdatePlayer.ts` を実装する。`UseUpdatePlayerReturn` 契約
（`{ updatePlayer, pending }`）に従い、`updatePlayer(id, { name, handedness })` で
`from('players').update({ name, handedness }).eq('id', id).select().single()` を実行する。

`useCreateGroup.ts` の **pending を try/finally で制御**するパターンを踏襲（PostgREST update）。
戻りは `ActionResult<Player>`。RLS は `players_update = is_member_of(group_id)` で自 Group のみ更新可。
name の Zod 検証はフォーム側（Phase 2）の責務で、本 composable は update 実行に専念する。

## 実装詳細

### 1. useUpdatePlayer composable 🔵
**信頼性**: 🔵 *interfaces.ts UseUpdatePlayerReturn / useCreateGroup.ts pending・try/finally / REQ-003 / players_update RLS*

`useCreateGroup.ts` の Write パターン（pending → try で実行 → finally でリセット）を踏襲。
`update({ name, handedness })` を `eq('id', id)` で対象行に限定し、`.select().single()` で
更新後の行を取得する。`group_id` の付与は不要（id 指定 + RLS で自 Group に限定される）。
エラー時は `ActionResult.error` に詰めて返し、表示は page 側 toast（ADR-007）。

**実装ファイル**: `app/composables/useUpdatePlayer.ts`

```typescript
/**
 * 【機能概要】: 既存選手の name/handedness を update する Write composable
 * 【実装方針】: useCreateGroup.ts の pending/try-finally を踏襲。
 *             update({name,handedness}).eq('id', id).select().single() を実行する。
 * 🔵 interfaces.ts UseUpdatePlayerReturn / REQ-003 / players_update RLS
 */
import type { Database } from '~/types/supabase'
import type { UpdatePlayerInput, Player } from '~/types/player'

interface ActionResult<T> { data: T | null; error: unknown }

interface UseUpdatePlayerReturn {
  updatePlayer: (id: Player['id'], input: UpdatePlayerInput) => Promise<ActionResult<Player>>
  pending: Ref<boolean>
}

export function useUpdatePlayer(): UseUpdatePlayerReturn {
  // 【pending 初期化】: 二重送信防止のため false で初期化 🔵
  const pending = ref(false)

  // 【型付きクライアント】: Database 型付きで型安全に update する 🔵
  const client = useSupabaseClient<Database>()

  async function updatePlayer(id: Player['id'], input: UpdatePlayerInput): Promise<ActionResult<Player>> {
    // 【pending 開始】: 実行中は pending=true 🔵
    pending.value = true

    try {
      // 【update 実行】: name/handedness を eq('id', id) で対象行に限定して更新。
      //   RLS players_update = is_member_of(group_id) で自 Group のみ更新可 🔵
      const { data, error } = await client
        .from('players')
        .update({ name: input.name, handedness: input.handedness })
        .eq('id', id)
        .select('id, name, handedness')
        .single()

      // 【エラー処理】: RLS 拒否 / PostgREST / 通信エラーは ActionResult.error に詰めて返す 🔵
      if (error) return { data: null, error }

      // 【成功戻り値】: 更新後の行を Player として返す 🔵
      return { data: data as Player, error: null }
    } finally {
      // 【pending リセット】: 成功・エラーを問わず必ず false に戻す 🔵
      pending.value = false
    }
  }

  return { updatePlayer, pending }
}
```

## 単体テスト要件

> テスト方針: 最小境界値 + 分岐網羅のみ。Supabase クライアントをモックし、update 引数と eq('id', id) を検証する。

### テストケース1: TC-003-01 name/handedness 更新が反映（update 引数検証） 🔵
**信頼性**: 🔵 *REQ-003 / players_update RLS*
**Given**: `updatePlayer('p1', { name: '佐藤', handedness: 'left' })`、update が更新後行を返す / **When**: 実行 / **Then**: `update({ name: '佐藤', handedness: 'left' })` と `eq('id', 'p1')` が呼ばれ、`ActionResult.data` が更新後行になる

**テストファイル**: `tests/unit/composables/useUpdatePlayer.test.ts`

```typescript
import { describe, it, expect, vi, beforeEach } from 'vitest'

const single = vi.fn()
const selectAfterEq = vi.fn(() => ({ single }))
const eq = vi.fn(() => ({ select: selectAfterEq }))
const update = vi.fn(() => ({ eq }))
const from = vi.fn(() => ({ update }))
vi.stubGlobal('useSupabaseClient', () => ({ from }))
vi.stubGlobal('ref', (v: unknown) => ({ value: v }))

const { useUpdatePlayer } = await import('~/composables/useUpdatePlayer')

beforeEach(() => {
  single.mockResolvedValue({ data: { id: 'p1', name: '佐藤', handedness: 'left' }, error: null })
})

describe('useUpdatePlayer', () => {
  it('TC-003-01: name/handedness 更新を eq(id) で反映する', async () => {
    const { updatePlayer } = useUpdatePlayer()
    const r = await updatePlayer('p1', { name: '佐藤', handedness: 'left' })
    expect(update).toHaveBeenCalledWith({ name: '佐藤', handedness: 'left' })
    expect(eq).toHaveBeenCalledWith('id', 'p1')
    expect(r.data).toEqual({ id: 'p1', name: '佐藤', handedness: 'left' })
    expect(r.error).toBeNull()
  })
})
```

### テストケース2: TC-003-B01 編集時もエラーは ActionResult.error で返す 🔵
**信頼性**: 🔵 *REQ-101 / REQ-401 / ActionResult 契約*
**Given**: update が `{ data: null, error: <CHECK違反/RLS拒否> }` を返す（name 1〜50字の最終防衛は DB CHECK / inline 検証はフォーム側）。本 composable は update を実行しエラーを素通しする。
**When**: `updatePlayer('p1', { name: '', handedness: 'unknown' })` 等でエラー返却
**Then**: `{ data: null, error }` を返し、`pending` が finally で false に戻る

```typescript
it('TC-003-B01: エラーは ActionResult.error で返し pending を戻す (検証はフォーム側責務)', async () => {
  const err = { message: 'players_name_length_check' }
  single.mockResolvedValue({ data: null, error: err })
  const { updatePlayer, pending } = useUpdatePlayer()
  const r = await updatePlayer('p1', { name: '', handedness: 'unknown' })
  expect(r.data).toBeNull()
  expect(r.error).toBe(err)
  expect(pending.value).toBe(false)
})
```

## 注意事項
- `pending` は **必ず try/finally** で false に戻す（useCreateGroup.ts と同方針）。
- 本 composable は **name の Zod 検証を行わない**。編集フォームでも `playerNameSchema` を再適用するのは **Phase 2 フォーム側**の責務。composable は update 実行に専念し、CHECK 違反等は DB が最終防衛して `ActionResult.error` で返す。
- `group_id` を update 引数に含めない（選手の所属 Group 変更は本単位スコープ外、id 指定 + RLS で自 Group に限定）。
- エラーは `ActionResult.error` に詰めて返す。表示チャネル（toast）の選択は page 側（ADR-007）。
- 成功後の一覧更新は **page 側で `usePlayers().refresh()`**。
